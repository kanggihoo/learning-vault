카프카 클러스터의 두뇌: ZooKeeper에서 KRaft로

목표: Kafka Broker들이 "지금 몇 개의 Topic이 있는지, 어느 Partition이 어느 Broker에 있는지, 누가 Leader인지" 같은 metadata를 어디에 저장하고 관리하는지 이해한다. 이 역할이 예전엔 ZooKeeper였고, 지금은 KRaft로 바뀌었다는 것과 그 이유를 설명할 수 있게 된다.

0. 출발점 — Broker들은 서로 어떻게 알고 지내나

이전 레슨에서 Topic이 여러 Partition으로 쪼개져 여러 Broker에 분산 저장된다고 배웠다. 그런데 누군가는 이런 질문에 답을 갖고 있어야 한다. 

"payments 토픽의 Partition 2는 지금 어느 Broker에 있지?"
"그 Partition의 Leader는 누구지? 방금 죽은 것 같은데, 다음 Leader는 누가 되지?"
"지금 클러스터에 살아있는 Broker는 몇 대지?"
"Consumer Group 'billing-service'는 어느 Partition을 어디까지 읽었지?"

→ 이런 질문에 답하는 정보가 metadata다.
→ 이 metadata를 누가 관리하느냐가 Kafka 클러스터의 "두뇌"를 결정한다.

쿠버네티스를 배웠다면 이미 익숙한 구조다. 쿠버네티스의 etcd + controller-manager가 "무엇이 어디에 떠 있어야 하는가"를 관리하듯, Kafka도 metadata를 관리하는 별도의 두뇌가 필요하다. 다만 Kafka는 최근까지 이 두뇌를 자기 자신이 아니라 외부 시스템(ZooKeeper)에 맡겼었다.

1. 예전 방식 — ZooKeeper mode

Apache ZooKeeper는 분산 시스템을 위한 범용 coordination 서비스다. ZooKeeper mode에서 Kafka는 metadata 관리를 ZooKeeper에 의존했다.

ZooKeeper는 broker 등록, controller 선출(어느 broker가 metadata 관리를 맡을지), ACL, 일부 dynamic configuration 저장을 담당했다. 문제는 Kafka 클러스터 하나를 운영하려면 ZooKeeper 앙상블이라는 별도의 분산 시스템을 통째로 하나 더 운영해야 한다는 점, 그리고 metadata가 많아질수록(Partition 수가 수십만 단위로 커질수록) ZooKeeper 기반 구조가 확장성의 한계에 부딫혔다는 점이다.

2. 새 방식 — KRaft mode

KRaft(Kafka Raft)는 ZooKeeper 의존성을 완전히 제거하고, metadata 관리를 Kafka 내부의 controller quorum이 Raft protocol로 직접 수행하는 방식이다.

핵심 변화 두 가지:
① 역할 분리 — broker는 data 요청만, controller(quorum controller)는 metadata 요청만 처리하도록 명확히 나뉜다.
② 내부화 — controller들끼리의 합의는 ZooKeeper가 아니라 Kafka 자체의 Raft protocol로 이루어진다. 그래서 별도의 외부 시스템이 필요 없다.

자주 나오는 질문 — "브로커 여러 대가 모이면 클러스터가 되는데, 그 클러스터를 관리하는 얘랑 KRaft는 다른 건가?"

다른 게 아니다. KRaft가 바로 그 "클러스터를 관리하는 얘"(Controller)의 최신 구현 방식이다. 이전 레슨에서 "브로커가 여러 대면 누군가는 메타데이터(어느 Partition이 어느 Broker에 있는지, 누가 Leader인지)를 관리해야 한다"고 했고, 그 역할을 Controller가 한다고 했다. KRaft는 정확히 그 Controller 역할을 ZooKeeper라는 별도 시스템 없이 Kafka 브로커 자신이 수행하게 만드는 내부 합의 프로토콜(consensus protocol)이다. 

예전: Broker들 ← (메타데이터 관리를 위임) → ZooKeeper (완전 별도 시스템)
지금: Broker 중 일부가 KRaft 프로토콜로 스스로 Controller 역할을 맡음 (별도 시스템 불필요)

즉 "브로커 클러스터"와 "그걸 관리하는 존재"가 서로 다른 두 개의 시스템이 아니라, KRaft는 그 관리자(Controller) 역할을 Kafka 브로커들 스스로 수행하게 만드는 프로토콜이다.

Raft가 뭔지 아주 간단히: 여러 대의 서버가 "우리 중 누가 대표(Leader)이고, 상태 변경을 어떤 순서로 기록할지"에 합의하는 분산 합의 알고리즘이다. KRaft는 이 Raft를 카프카 메타데이터 관리에 적용한 것이고:

  • Controller 역할을 할 브로커 몇 대(보통 3~5대)가 Controller Quorum을 이룬다
  • 그중 Raft로 선출된 Active Controller 하나가 실제 메타데이터 변경을 처리한다
  • 나머지(Standby)는 그 변경 로그를 복제해 들고 있다가, Active Controller가 죽으면 즉시 새 Controller로 승격한다

이건 이전 레슨에서 본 Partition의 Leader/Follower + Replication과 똑같은 패턴이다 — 다만 복제되는 대상이 "이벤트 데이터"가 아니라 "클러스터 메타데이터"라는 것만 다르다.

3. ZooKeeper mode → KRaft mode, 무엇이 사라지고 왜 사라졌는가

ZooKeeper mode에만 있던 설정과 기능들이 KRaft mode에서는 제거되거나 대체되었다. 원문(Apache Kafka Documentation: KRaft)의 변경 목록을 "왜 사라졌는가" 기준으로 압축하면 다음과 같다.

사라진 것 (ZooKeeper mode)대체/현재 (KRaft mode)왜 이렇게 바뀌었는가
zookeeper.connect 등 ZooKeeper 접속 설정 전체 —(불필요) ZooKeeper 자체가 없으므로 접속 설정도 필요 없다.
password.encoder.* (secret, algorithm, key length 등) Kafka가 sensitive data를 record에 저장 (encrypt는 별도 계층) ZooKeeper에 저장할 password를 암호화하던 장치였는데, 저장 위치가 Kafka 내부 record로 바뀌었다.
control.plane.listener.name controller.listener.names, listeners, listener.security.protocol.map control plane 통신이 ZooKeeper 의존 구조에서 Kafka 내부 controller-broker 통신 구조로 바뀌었다.
reserved.broker.max.id, broker.id.generation.enable node.id ZooKeeper가 broker id를 auto-generate하던 방식에서, KRaft는 broker/controller를 node.id 하나로 통일해 식별한다.
inter.broker.protocol.version metadata.version (+ kafka-features.sh) 클러스터 feature level 제어 방식이 broker 간 protocol 버전에서 metadata 버전 관리로 통합됐다.
ZooKeeper 기반 dynamic config (예: advertised.listeners) 변경 시 broker/controller 재시작 필요 ZooKeeper가 즉시 반영해주던 일부 동적 설정이, KRaft에서는 재시작이 필요한 정적 설정으로 바뀌었다 (버전에 따라 점차 dynamic 지원이 확대됨).
leader.imbalance.per.broker.percentage —(제거) ZooKeeper 구조에서만 의미가 있던 leader 재선출 빈도 제한이었다.
ZooKeeper 관련 metric 전체 (ControlPlaneNetworkProcessorAvgIdlePercent 등) NetworkProcessorAvgIdlePercent 등 동일 목적의 KRaft 버전 metric 모니터링 대상이 "ZooKeeper와의 관계"에서 "Kafka 내부 controller 상태"로 바뀌었다.

표에 적지 않은 세부 설정까지 실제 마이그레이션에서 필요하면, 원문의 전체 설정/metric 목록을 그대로 체크리스트로 쓰면 된다. 여기서는 "왜"에 집중해 압축했다 — 이게 이 레슨의 목적이다.

4. 그 외 동작 차이 (Behavioral Change)

설정 값 크기 제한

KRaft mode는 configuration value를 최대 Short.MAX_VALUE 크기로 제한한다. append로 이어붙여 더 큰 값을 만드는 방식이 막힌다.

Policy Class는 Controller에서 실행

CreateTopicPolicy, AlterConfigPolicy 플러그인이 이제 broker가 아니라 controller에서 실행된다. 마이그레이션 시 JAR 배포 위치를 옮겨야 한다.

Custom Principal Builder

KafkaPrincipalBuilder를 커스텀 구현할 때 KafkaPrincipalSerde도 함께 구현해야 한다. 안 하면 broker가 request를 controller로 forward하지 못한다.

5. 실무에서 알아야 할 결론

신규로 Kafka를 도입한다면 사실상 선택의 여지가 없다. 최신 Kafka는 KRaft mode가 기본이고 권장되는 방식이며, ZooKeeper mode는 legacy로 취급된다. 기존 ZooKeeper 기반 클러스터를 운영 중이라면 ZooKeeper to KRaft Migration 절차를 통해 무중단으로 전환할 수 있다. 지금 도입을 계획하고 있다면, 이 레슨의 KRaft 구조가 곧 당신이 실제로 마주할 구조다.
