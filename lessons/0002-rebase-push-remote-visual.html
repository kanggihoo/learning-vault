rebase와 push가 실제로 바꾸는 것

핵심: rebase는 로컬 브랜치만 바꾼다. 원격 브랜치는 push할 때 바뀐다.

0. 시작 상태

원격 origin/A, 내 로컬 A, 철수 로컬 A가 모두 같은 커밋을 보고 있다.

M1 -- M2 -- A1 -- A2
              ▲
              ├─ origin/A
              ├─ 내 로컬 A
              └─ 철수 로컬 A

1. main에 새 커밋 M3가 생김

origin/main만 앞으로 갔다. origin/A는 아직 그대로다.

M1 -- M2 -- M3
        ▲     ▲
        │     └─ origin/main
        │
        └-- A1 -- A2
                  ▲
                  ├─ origin/A
                  ├─ 내 로컬 A
                  └─ 철수 로컬 A

2. 내가 로컬에서 rebase

git switch A
git fetch origin
git rebase origin/main

여기서는 원격이 안 바뀐다. 내 로컬 A만 M3 뒤로 이동하며 새 커밋 A1', A2'가 된다.

M1 -- M2 -- M3 -- A1' -- A2'
        ▲           ▲       ▲
        │           │       └─ 내 로컬 A
        │           └─ 새로 만들어진 커밋
        │
        └-- A1 -- A2
                  ▲
                  ├─ origin/A  그대로
                  └─ 철수 로컬 A 그대로

3. 내가 force push

git push --force-with-lease origin A

이 순간 origin/A가 바뀐다. rebase 때문이 아니라 push 때문이다.

M1 -- M2 -- M3 -- A1' -- A2'
        ▲                   ▲
        │                   ├─ 내 로컬 A
        │                   └─ origin/A  여기로 바뀜
        │
        └-- A1 -- A2
                  ▲
                  └─ 철수 로컬 A는 아직 여기

4. 왜 공유 브랜치면 문제인가

철수가 옛 A2 위에서 C1을 만들었다고 하자.

원격 origin/A:
M1 -- M2 -- M3 -- A1' -- A2'
                            ▲
                            └─ origin/A

철수 로컬 A:
M1 -- M2 -- A1 -- A2 -- C1
                        ▲
                        └─ 철수 로컬 A

Git 입장에서는 A1/A2와 A1'/A2'가 다른 커밋이다. 그래서 철수의 브랜치와 원격 브랜치가 갈라진다.

5. 개인 브랜치면 왜 괜찮나

철수가 origin/A를 쓰지 않았다면, 깨질 사람이 없다.

M1 -- M2 -- M3 -- A1' -- A2'
                            ▲
                            ├─ 내 로컬 A
                            └─ origin/A

다른 사람이 A1/A2를 기준으로 작업하지 않았음
=> 문제 없음

결론

OK
개인 브랜치 A:
git rebase origin/main
git push --force-with-lease origin A

위험
여러 명이 쓰는 브랜치 A:
git rebase origin/main
git push --force-with-lease origin A
