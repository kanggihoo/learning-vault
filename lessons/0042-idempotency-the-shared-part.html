아키텍처 설계 · 6/N · 레슨 0042 · 0040이 남긴 질문

멱등성 — 분산 설계의 공용 부품

0040 §3의 그림에서 Idempotent Consumer가 세 체인 모두에 나왔다. 재시도 체인에도, 큐 체인에도, Saga 체인에도. 이 레슨은 그 이유를 끝까지 판다 — 그리고 실제로 결정해야 하는 것들을 하나씩 닫는다. 멱등 키를 무엇으로 잡나. 동시 중복은 어떻게 막나. 보상이 실패하면 어떻게 하나.

이 레슨 하나로 얻는 것. ① exactly-once가 왜 불가능하고 무엇이 그 자리를 대신하는지 설명할 수 있다. ② 멱등 키로 써도 되는 것과 절대 쓰면 안 되는 것을 가른다. ③ 체크-후-처리 사이의 실패 창과 동시 경쟁을 각각 다른 방법으로 막는다. ④ 시맨틱 락·보상 실패·오케스트레이터 위치 — Saga의 남은 결정 셋을 닫는다.

§1 · exactly-once는 없다. effectively-once가 있다

분산 시스템 전체에 걸친 exactly-once 전달은 현실적으로 보장할 수 없다. exactly-once를 표방하는 브로커조차 자기가 직접 통제하는 동작만 보장할 뿐, 소비자가 다른 시스템에서 일으키는 외부 부수효과는 보장할 수 없다. (…) 지속 가능한 해법은 중복 전달을 없애는 게 아니라 소비자가 중복을 견디게 만드는 것이다. at-least-once 전달과 중복을 무시하는 소비자를 결합하면 effectively exactly-once 처리가 된다. — Azure Architecture Center, Idempotent Consumer

중복은 세 지점에서 생긴다. 셋 다 "장애"가 아니라 정상 동작이라는 게 핵심이다.

§2 · 먼저 물을 것 — 자연 멱등으로 만들 수 있나?

자연 멱등을 먼저 설계하고, 자연 멱등으로 만들 수 없는 연산에만 중복 제거 기법을 더하라. — Azure Architecture Center, Idempotent Consumer

멱등 키와 중복 제거 저장소는 비용이 있는 장치다. 연산 자체를 멱등하게 만들 수 있으면 그게 먼저다. 기준은 하나 — 상대 변경인가, 절대 상태인가.

절대 상태로 바꾸면 새 문제가 생긴다 — 순서. "42개"와 "40개" 이벤트가 뒤바뀌어 도착하면 틀린 값이 남는다. 그래서 절대 상태 이벤트에는 버전이나 시퀀스를 실어 오래된 것을 거부해야 한다. 중복 제거는 순서를 보장하지 않는다 — 이 둘은 다른 문제다.

상관관계 ID (correlationId)안 된다여러 메시지가 공유한다 — 요청과 응답이 같은 값을 갖는다. 첫 메시지가 나머지를 전부 막는다.
전송 계층 배달 ID안 된다브로커가 재전달할 때 새로 만든다. 중복마다 값이 달라 탐지가 안 된다.
수신 타임스탬프안 된다매번 달라진다. 같은 이유.
이메일 등 개인정보안 된다Stripe가 명시적으로 금지한다. 키는 로그·저장소에 오래 남는다.

가장 자주 놓치는 함정: 구독자가 여러 개일 때. pub/sub에서 소비자 A·B·C가 각자 같은 메시지를 처리하는 게 정상이다. 그런데 셋이 중복 제거 저장소를 공유하면서 메시지 ID만으로 키를 잡으면, A가 처리한 순간 B·C가 중복으로 판정되어 아무 일도 안 한다.
해법: 키를 (소비자 신원 + 메시지 ID) 복합키로 잡는다. "알림이 안 갔어요" 류 버그의 단골 원인이다.

Stripe가 정한 규칙들도 참고할 만하다 — 결과(상태 코드와 본문)를 저장했다가 그대로 돌려준다 (500 에러였어도 500을 돌려준다). 키는 최소 24시간 보관 후 정리한다. 그리고 같은 키로 다른 파라미터가 오면 에러를 낸다 — 실수로 키를 재사용하는 걸 막기 위해서다. GET·DELETE에는 멱등 키를 보내지 않는다. 이미 정의상 멱등이기 때문이다.

§4 · 두 가지 다른 실패 — 창(window)과 경쟁(race)

실패 ① 체크와 처리 사이의 창 → inbox 패턴

"키가 있나 확인 → 처리 → 키 기록" 순으로 짜면 처리와 기록 사이에 죽는 창이 생긴다. 부수효과는 남았는데 키는 없으므로, 재전달되면 다시 처리한다.

실패 ② 동시에 도착한 중복 → 유니크 제약

경쟁 소비자가 같은 메시지의 사본을 동시에 받으면, 둘 다 "키가 없다"를 통과한 뒤 둘 다 처리한다. 트랜잭션으로 묶어도 이건 안 막힌다 — 두 트랜잭션이 각각 정상 커밋되기 때문이다.

애플리케이션 로직이 아니라 데이터 저장소에서 정합성을 강제하라. 중복 제거 키에 유니크 제약을 건다. 두 트랜잭션이 모두 키 삽입을 시도하지만 하나만 성공한다. 다른 하나는 제약 위반으로 실패하고 그 메시지를 중복으로 처리한다. DB가 유일한 심판이 된다. — Azure Architecture Center, Idempotent Consumer

캐시로 중복 제거를 하는 경우 특히 주의. "조회 → 없으면 저장"은 두 개의 연산이라 창이 있다. 반드시 원자적 조건부 쓰기를 쓴다 — Redis라면 SET key value NX, RDB라면 유니크 인덱스에 INSERT. 존재 확인과 선점이 한 번에 일어나야 한다.

외부 호출은 트랜잭션에 못 들어간다 → 2단계 기록

  1. 외부 호출 전에 키를 IN_PROGRESS 상태로 기록한다.
  2. 외부 호출을 수행한다.
  3. 결과와 함께 COMPLETED로 갱신한다.

재전달 시 COMPLETED면 건너뛰고, IN_PROGRESS면 "이전 시도가 부분적으로 성공했을 수 있음"을 뜻한다 — 그때는 외부 시스템에 조회해서 확인하는 경로가 필요하다. 결제 연동에서 "승인 조회 API"가 왜 항상 있는지가 여기서 설명된다.

키를 언제 지우나

브로커가 재전달할 수 있는 기간보다 길게 보관한다. 최대 재시도 횟수 × 락(가시성) 타임아웃 + 메시지 TTL을 계산해서, 그보다 긴 TTL을 준다. 그리고 DLQ에서 운영자가 수동으로 재투입하는 경우를 잊지 않는다 — 정상 재전달 창이 한참 지난 뒤에 올 수 있다.

§5 · Saga의 남은 결정 셋

① 시맨틱 락 — 그리고 세 가지 함정

0040에서 본 격리성 대응책. 진행 중인 자원에 PENDING 같은 표시를 걸어 다른 saga가 손대지 못하게 한다. DB의 락을 애플리케이션에서 흉내내는 것이라, DB가 대신 해 주던 것들이 전부 숙제로 돌아온다.

함정무슨 일대응
락을 푸는 주체가 죽는다영원히 PENDING인 좀비 자원이 남는다. DB 락과 달리 세션이 끊겨도 자동으로 안 풀린다.락에 만료 시각을 준다(리스). Azure도 "타임아웃이 있는 단기 락"을 권한다.
읽는 쪽이 무시한다조회 쿼리가 PENDING을 "없는 것"으로 보면 더티 리드가 그대로 남는다. 락은 쓰는 쪽만이 아니라 읽는 쪽도 지켜야 의미가 있다.읽기 경로마다 PENDING 처리 규칙을 정한다 — 숨길지, 보여줄지, 기다릴지.
비즈니스 상태와 섞인다status 하나에 PENDING·CONFIRMED·CANCELLED가 뒤엉켜 상태 머신이 폭발한다.락 상태를 별도 필드로 분리한다. 비즈니스 상태와 진행 상태는 다른 축이다.

② 보상이 실패하면

보상 트랜잭션은 항상 작동하지는 않는다. 보상 트랜잭션 자체가 실패했을 때 반복할 수 있도록 각 단계를 멱등한 명령으로 정의하라. (…) 때로는 수동 개입만이 유일한 복구 방법이다. 그런 경우 시스템은 실패 이유를 담은 상세한 알림을 발생시켜야 한다. — Azure Architecture Center, Compensating Transaction
오해실제
보상은 원래 상태로 되돌린다아니다. 성공했던 작업을 보상할 뿐이다. 항공권 취소가 전액 환불이 아닌 것처럼, 비즈니스 규칙이 적용된다.
보상은 정확히 역순이다아니다. 일부는 병렬로 가능하고, 불일치에 민감한 저장소를 먼저 되돌리는 게 나을 수 있다.
실패하면 바로 보상한다아니다. 순서는 재시도 → 대체 경로 → 그래도 안 되면 보상이다. 보상은 최후 수단이다.
보상 여부는 시스템이 정한다고영향·모호한 경우는 사람이 결정한다. Azure 예시: 호텔 예약이 실패했다고 항공권을 자동 취소하지 말고, 다른 호텔을 제안하고 취소는 고객이 고르게 한다.

그리고 보상 진행 상황을 기록해야 실패 지점부터 재개할 수 있다. 보상이 끝내 실패하면 DLQ로 보내고 상관관계 ID를 포함한 알림을 띄운다 — 사람이 볼 수 있어야 한다.

§6 · 진단 연습

① "메시지의 correlationId로 중복을 걸러냅니다."

확인

키가 틀렸다. 상관관계 ID는 관련된 여러 메시지를 묶는 값이다 — 요청과 응답, 한 saga의 모든 단계가 같은 값을 갖는다.

결과: saga의 2단계가 1단계의 키에 막혀 실행되지 않는다. 게다가 이 버그는 재전달이 실제로 일어나야 드러나므로, 테스트에서는 멀쩡하다.

고칠 것: 메시지별 고유 ID나 비즈니스 키로 바꾼다. 상관관계 ID는 추적용으로만 쓴다.

② "처리 전에 SELECT로 키가 있는지 확인하고, 없으면 처리한 뒤 INSERT합니다."

확인

두 개의 구멍이 동시에 있다.

ⓐ 창: 처리와 INSERT 사이에 죽으면 키가 없어 재처리된다. → 처리와 키 기록을 같은 트랜잭션으로(inbox).

ⓑ 경쟁: 두 소비자가 동시에 SELECT를 통과하면 둘 다 처리한다. → 키 컬럼에 유니크 제약을 걸고, INSERT 실패를 중복 판정으로 쓴다.

ⓐ만 고치면 ⓑ가 남고, ⓑ만 고치면 ⓐ가 남는다. 둘은 다른 실패라 각각 막아야 한다.

③ "주문 취소 시 결제 취소 API를 호출합니다. 실패하면 로그를 남기고 넘어갑니다."

확인

보상 실패를 삼켰다. 결과: 주문은 취소됐는데 결제는 살아 있는 돈이 어긋난 상태가 조용히 남는다. 로그는 아무도 안 본다.

필요한 것 셋: ⓐ 보상 단계를 멱등하게 만들어 재시도 가능하게, ⓑ 재시도 소진 시 DLQ + 알림(상관관계 ID 포함), ⓒ 불일치를 주기적으로 찾는 정합성 검사.

ⓒ가 0038의 감지 전술이다 — 보상 체계에도 "복구"만 있고 "감지"가 없으면 같은 실패다.
