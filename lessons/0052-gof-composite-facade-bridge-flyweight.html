Composite · Facade · Bridge · Flyweight

구조 패턴의 나머지 네 개다. 묶음 2(Decorator·Proxy·Adapter)는 "감싸는 객체"였고, 이번 넷은 각각 다른 질문에 답한다: 트리로 묶기(Composite), 창구 하나 두기(Facade), 두 갈래로 쪼개기(Bridge), 공유로 아끼기(Flyweight).

§0 · 워밍업 — 지난 묶음 4문제

신호 요약. 구조: 감싼 뒤 인터페이스가 달라지면 Adapter / 같으면 기능 추가는 Decorator, 접근 통제는 Proxy. 행위: 방송은 Observer, 허브는 Mediator, 사슬은 Chain, 요청을 물건으로 만들면 Command.

R1. 요청이 "대리 → 과장 → 부장"으로 넘어가며, 처리할 수 있는 첫 사람이 처리한다.

R2. 채팅방 객체를 두고 모든 참가자가 방을 통해서만 메시지를 주고받는다.

R3. class Cached implements Repo { private Repo r; private Map m; public Item find(id){ return m.computeIfAbsent(id, r::find); } } — 캐시 적중이면 원본을 아예 호출하지 않는다.

R4. 상태 객체가 return new Shipped();처럼 다음 상태를 스스로 정해 반환한다.

§1 · 네 개를 한 장으로

패턴답하는 질문비유
Composite부분과 전체를 똑같이 다루고 싶다폴더 안의 파일과 폴더
Facade복잡한 내부 앞에 단순한 창구를 두고 싶다호텔 컨시어지

Flyweight똑같은 객체가 너무 많아 메모리를 아끼고 싶다숲의 나무 1만 그루가 모델 하나 공유

§2 · Composite (컴포지트) — 부분과 전체를 같게

이론. 객체를 트리로 구성하고, 개별 객체(잎)와 묶음 객체(가지)를 같은 인터페이스로 다룬다. 그래서 "크기 구하기"를 파일에 호출하든 폴더에 호출하든 똑같이 쓰고, 폴더는 안에 든 것들에게 재귀로 위임한다.

비유. 컴퓨터의 폴더. 폴더 안에 파일도 있고 폴더도 있다. "용량 확인"은 파일에도 폴더에도 똑같이 누른다.

interface Node { int size(); }
class FileNode implements Node {                        // 잎
    private final int bytes;
    public int size() { return bytes; }
}
class Folder implements Node {                          // 가지: 같은 인터페이스 + 자식 목록
    private final List<Node> children = new ArrayList<>();
    void add(Node n) { children.add(n); }
    public int size() { int s = 0; for (Node c : children) s += c.size(); return s; }  // 재귀
}

구조 신호: 자기와 같은 타입의 리스트를 필드로 들고 있다. Decorator와 모양이 비슷하지만 Decorator는 자식이 하나이고 기능을 더하며, Composite는 자식 여러 개의 결과를 합친다 (Refactoring.Guru).

§3 · Facade (퍼사드) — 단순한 창구

이론. 서브시스템의 여러 클래스를 일일이 호출하지 않아도 되게 높은 수준의 단순한 인터페이스 하나를 제공한다. 서브시스템 객체를 직접 쓰는 것을 막지는 않는다.

비유. 호텔 컨시어지. 식당 예약, 택시, 공연 티켓을 각각 전화하지 않고 창구 한 곳에 부탁한다.

class HomeTheaterFacade {                        // 창구
    private final Amp amp; private final Projector pj; private final Player player;
    void watchMovie(String m) {                  // 호출 한 번에 여러 서브시스템을 조율
        amp.on(); amp.setVolume(5); pj.on(); player.play(m);
    }
}

구조 신호: 여러 서로 다른 객체를 필드로 들고 순서대로 호출하는 메서드가 있다. Adapter와의 차이: Adapter는 기존 인터페이스를 맞추는 것(보통 객체 1개), Facade는 새 인터페이스를 정의하는 것(서브시스템 전체). Proxy와의 차이: Proxy는 원본과 같은 인터페이스, Facade는 다르다 (Refactoring.Guru).

§4 · Bridge (브리지) — 두 갈래로 쪼갠다

이론. 클래스가 두 방향으로 변할 때(예: 리모컨 종류 × TV 제조사), 상속으로 다 만들면 조합 수만큼 클래스가 폭발한다. 그래서 기능(추상) 계층과 구현 계층을 별개의 계층으로 쪼개고, 기능 쪽이 구현 쪽을 필드로 들고 위임한다. 그 필드가 "다리"다.

비유. 리모컨(기본/고급)과 TV(삼성/LG). 상속만 쓰면 기본-삼성, 기본-LG, 고급-삼성, 고급-LG 4개를 만들어야 한다. 쪼개면 리모컨 2개 + TV 2개 = 4개를 더하기로 만들고 조합은 런타임에 연결한다.

interface Device { void on(); void off(); }               // 구현 계층 (TV 제조사)
class SamsungTv implements Device { ... }
class LgTv implements Device { ... }

class Remote {                                            // 기능 계층
    protected final Device device;                        // 다리
    Remote(Device d) { this.device = d; }
    void power() { device.on(); }
}
class AdvancedRemote extends Remote { void mute() { ... } }
new AdvancedRemote(new LgTv());                           // 조합은 선택

용어 주의. 여기서 추상/구현은 Java의 interface·abstract class가 아니다. Refactoring.Guru: 추상 = 상위 수준 제어 계층(예: GUI), 구현 = 플랫폼(예: OS API). 또 Bridge는 보통 처음부터 설계하고, Adapter는 이미 있는 것을 맞추는 데 쓴다.

구조 신호: 합성 모양은 Strategy와 같다(인터페이스를 필드로 들고 위임). 다른 점은 두 계층이 둘 다 확장된다는 것이다 (Refactoring.Guru — Bridge).

§5 · Flyweight (플라이웨이트) — 공유로 아낀다

이론. 똑같은 데이터를 가진 객체가 수만 개면 메모리가 터진다. 그래서 객체의 상태를 둘로 나눈다. 내재 상태(intrinsic) = 바뀌지 않아서 공유할 수 있는 부분, 외재 상태(extrinsic) = 상황마다 달라서 사용할 때 밖에서 넘겨주는 부분. 내재 상태만 가진 가벼운 객체를 하나씩만 만들어 재사용한다.

비유. 게임 속 숲의 나무 1만 그루. 나무 모델·텍스처(내재)는 하나를 공유하고, 위치·크기(외재)만 그루마다 따로 가진다.

class TreeType {                                    // Flyweight: 공유되는 내재 상태 (불변)
    final String name; final byte[] texture;
}
class TreeFactory {                                 // 이미 있으면 재사용
    private static final Map<String, TreeType> cache = new HashMap<>();
    static TreeType get(String name) { return cache.computeIfAbsent(name, TreeType::new); }
}
class Tree { int x, y; TreeType type; }            // 위치(외재)만 개별, 모델은 공유

Singleton과의 차이: Flyweight는 여러 종류의 인스턴스가 있을 수 있고 불변이다. Singleton은 인스턴스가 하나이고 가변일 수 있다 (Refactoring.Guru — Flyweight).

§6 · 헷갈리는 쌍

쌍구분 질문
Composite vs Decorator자식이 여럿이고 결과를 합치면 Composite, 자식이 하나이고 기능을 더하면 Decorator
Facade vs Adapter서브시스템 전체에 새 창구를 만들면 Facade, 기존 모양을 기대하는 모양으로 바꾸면 Adapter
Facade vs MediatorFacade는 서브시스템끼리는 직접 소통하게 둔다(밖에서 쓰기 편하게 할 뿐). Mediator는 소통을 전부 허브로 모은다
Bridge vs Strategy인터페이스를 필드로 들고 위임하는 모양은 같다. 기능 계층이 따로 확장되면 Bridge, 알고리즘 교체만이면 Strategy

§8 · 한 문장으로 회수

트리로 같게 다루면 Composite, 단순 창구면 Facade, 두 계층을 쪼개면 Bridge, 공유로 아끼면 Flyweight.
