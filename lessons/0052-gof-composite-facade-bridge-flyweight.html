Composite · Facade · Bridge · Flyweight

구조 패턴의 나머지 네 개다. 묶음 2(Decorator·Proxy·Adapter)는 "감싸는 객체"였고, 이번 넷은 각각 다른 질문에 답한다: 트리로 묶기(Composite), 창구 하나 두기(Facade), 두 갈래로 쪼개기(Bridge), 공유로 아끼기(Flyweight).

§0 · 워밍업 — 지난 묶음 4문제

신호 요약. 구조: 감싼 뒤 인터페이스가 달라지면 Adapter / 같으면 기능 추가는 Decorator, 접근 통제는 Proxy. 행위: 방송은 Observer, 허브는 Mediator, 사슬은 Chain, 요청을 물건으로 만들면 Command.

R1. 요청이 "대리 → 과장 → 부장"으로 넘어가며, 처리할 수 있는 첫 사람이 처리한다.

R2. 채팅방 객체를 두고 모든 참가자가 방을 통해서만 메시지를 주고받는다.

R3. class Cached implements Repo { private Repo r; private Map m; public Item find(id){ return m.computeIfAbsent(id, r::find); } } — 캐시 적중이면 원본을 아예 호출하지 않는다.

R4. 상태 객체가 return new Shipped();처럼 다음 상태를 스스로 정해 반환한다.

§2 · Composite (컴포지트) — 부분과 전체를 같게

한 문장. 낱개 객체(잎)와 그것들을 묶은 객체(가지)가 같은 인터페이스를 갖게 해서, 호출하는 쪽이 둘을 구별하지 않고 똑같이 쓰게 하는 패턴이다.

구조. 객체들이 트리를 이룬다. 가지는 자기와 같은 타입의 객체를 목록으로 들고, 요청이 오면 목록의 각 자식에게 같은 메서드를 불러서 결과를 합친다(재귀: 자기 안의 같은 종류에게 같은 일을 시키는 것). 잎은 목록 없이 자기 값만 돌려준다.

비유. 컴퓨터의 폴더. 폴더 안에 파일도 있고 폴더도 있다. "용량 확인"은 파일에도 폴더에도 똑같이 누르고, 폴더는 안에 든 것들의 용량을 더한다. 예를 들어 폴더 A(파일 3KB + 폴더 B(파일 2KB))의 size()는 3 + (2) = 5KB다.

interface Node { int size(); }
class FileNode implements Node {                        // 잎
    private final int bytes;
    public int size() { return bytes; }
}
class Folder implements Node {                          // 가지: 같은 인터페이스 + 자식 목록
    private final List<Node> children = new ArrayList<>();
    void add(Node n) { children.add(n); }
    public int size() { int s = 0; for (Node c : children) s += c.size(); return s; }  // 재귀
}

구조 신호: 자기와 같은 타입의 리스트를 필드로 들고 있다. Decorator와 모양이 비슷하지만 Decorator는 자식이 하나이고 기능을 더하며, Composite는 자식 여러 개의 결과를 합친다 (Refactoring.Guru).

§3 · Facade (퍼사드) — 단순한 창구

한 문장. 여러 클래스가 얽힌 복잡한 부분(서브시스템: 함께 쓰이는 클래스 묶음) 앞에, 자주 쓰는 일만 한 번에 처리하는 단순한 창구 클래스를 두는 패턴이다. 서브시스템의 클래스를 직접 쓰는 길은 막지 않는다.

비유. 호텔 컨시어지. 식당 예약, 택시, 공연 티켓을 각각 전화하지 않고 창구 한 곳에 부탁한다. 비유가 맞지 않는 곳: 컨시어지에게 못 맡기는 특별한 요청은 직접 식당에 전화하면 된다. Facade도 같아서, 창구에 없는 기능이 필요하면 서브시스템 클래스를 직접 쓴다.

class HomeTheaterFacade {                        // 창구
    private final Amp amp; private final Projector pj; private final Player player;
    void watchMovie(String m) {                  // 호출 한 번에 여러 서브시스템을 조율
        amp.on(); amp.setVolume(5); pj.on(); player.play(m);
    }
}

구조 신호: 여러 서로 다른 객체를 필드로 들고 순서대로 호출하는 메서드가 있다. Adapter와의 차이: Adapter는 기존 인터페이스를 맞추는 것(보통 객체 1개), Facade는 새 인터페이스를 정의하는 것(서브시스템 전체). Proxy와의 차이: Proxy는 원본과 같은 인터페이스, Facade는 다르다 (Refactoring.Guru).

§4 · Bridge (브리지) — 두 갈래로 쪼갠다

한 문장. 클래스가 서로 독립적인 두 방향으로 늘어날 때, 두 방향을 별개의 클래스 계층으로 나누고 한쪽이 다른 쪽을 필드로 들어 연결하는 패턴이다. 그 필드가 "다리(bridge)"다.

용어 먼저. 이 패턴의 "추상"과 "구현"은 Java의 abstract class와 implements가 아니다. 추상 = 사용자가 직접 다루는 쪽(리모컨), 구현 = 실제로 일을 하는 쪽(TV)이다. 추상이 구현을 필드로 들고 일을 맡긴다. 이 레슨에서는 앞쪽을 "기능 계층", 뒤쪽을 "구현 계층"이라고만 부른다.

왜 쪼개나: 클래스 수를 세어 본다. 리모컨 종류 2개(기본, 고급) × TV 제조사 2곳(삼성, LG)이라고 하자.

  • 상속만 쓰면 조합마다 클래스가 필요하다. 기본삼성, 기본LG, 고급삼성, 고급LG로 4개다.
  • 쪼개면 리모컨 2개 + TV 2개로 4개다. 지금은 같다.
  • 소니 TV가 추가되면 상속은 기본소니, 고급소니 2개가 늘어 6개가 되고, 쪼갠 쪽은 소니 TV 1개만 늘어 5개다. 리모컨 3종 × TV 3사까지 가면 상속 9개 대 쪼갠 쪽 6개다. 곱하기로 늘 것을 더하기로 늘게 만드는 것이 이 패턴의 효과다.

비유가 맞지 않는 곳: 현실의 리모컨은 TV 제조사에 묶여 팔리지만, 이 코드의 리모컨은 생성할 때 new AdvancedRemote(new LgTv())처럼 TV를 골라 끼운다. 조합이 실행 중에 정해진다.

interface Device { void on(); void off(); }               // 구현 계층 (TV 제조사)
class SamsungTv implements Device { ... }
class LgTv implements Device { ... }

class Remote {                                            // 기능 계층
    protected final Device device;                        // 다리
    Remote(Device d) { this.device = d; }
    void power() { device.on(); }
}
class AdvancedRemote extends Remote { void mute() { ... } }
new AdvancedRemote(new LgTv());                           // 조합은 선택

같은 뜻을 Refactoring.Guru는 "추상 = 상위 수준 제어 계층(예: GUI), 구현 = 플랫폼(예: OS API)"이라고 쓴다. Adapter와의 차이: Bridge는 보통 처음부터 두 계층으로 설계하고, Adapter는 이미 있는 것을 맞추는 데 쓴다.

구조 신호. 인터페이스를 필드로 들고 위임하는 모양은 Strategy와 같다. 다른 점은 양쪽이 각자 하위 클래스를 늘려 간다는 것이다. 위 예에서는 리모컨 종류도 늘고 TV 제조사도 는다 (Refactoring.Guru: Bridge).

§5 · Flyweight (플라이웨이트) — 공유로 아낀다

한 문장. 같은 데이터를 가진 객체가 수만 개일 때, 그 같은 데이터를 객체 하나에 담아 모두가 공유해서 메모리를 아끼는 패턴이다.

구조. 객체의 데이터를 둘로 나눈다. 내재 상태(intrinsic)는 모든 객체에서 같고 바뀌지 않아서 공유할 수 있는 부분이다. 외재 상태(extrinsic)는 객체마다 달라서 공유할 수 없는 부분이고, 쓸 때 밖에서 넘겨주거나 따로 보관한다. 내재 상태만 가진 객체(Flyweight)는 종류마다 하나만 만들어 재사용한다.

비유. 게임 속 숲의 나무 1만 그루. 나무 모델과 텍스처(내재)는 소나무용 하나를 1만 그루가 공유하고, 위치와 크기(외재)만 그루마다 따로 가진다. 모델이 1MB라면 1만 그루가 각자 들 때 10GB지만, 공유하면 1MB에 위치 1만 개(작음)만 더해진다.

class TreeType {                                    // Flyweight: 공유되는 내재 상태 (불변)
    final String name; final byte[] texture;
}
class TreeFactory {                                 // 이미 있으면 재사용
    private static final Map<String, TreeType> cache = new HashMap<>();
    static TreeType get(String name) { return cache.computeIfAbsent(name, TreeType::new); }
}
class Tree { int x, y; TreeType type; }            // 위치(외재)만 개별, 모델은 공유

Singleton(인스턴스를 하나만 만드는 생성 패턴, 레슨 0054)과의 차이: Flyweight는 종류마다 하나씩, 여러 종류가 있을 수 있고 불변(만든 뒤 값이 안 바뀜)이다. Singleton은 인스턴스가 전체에서 하나이고 값이 바뀔 수 있다 (Refactoring.Guru: Flyweight).

쌍구분 질문
Composite vs Decorator자식이 여럿이고 결과를 합치면 Composite, 자식이 하나이고 기능을 더하면 Decorator

Facade vs MediatorFacade는 서브시스템끼리는 직접 소통하게 둔다(밖에서 쓰기 편하게 할 뿐). Mediator는 소통을 전부 허브로 모은다
Bridge vs Strategy인터페이스를 필드로 들고 위임하는 모양은 같다. 바뀌는 부분 하나(알고리즘)만 밖으로 뺐으면 Strategy, 양쪽이 각자 하위 클래스를 늘려 가면 Bridge

§8 · 한 문장으로 회수
