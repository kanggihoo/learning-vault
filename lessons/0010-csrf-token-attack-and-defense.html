CSRF 토큰이 막는 문제와 실제 사용 흐름

목표: CSRF를 “쿠키 자동 첨부 때문에 생기는 위조 요청 문제”로 이해하고, CSRF 토큰이 왜 공격자에게 없는 값을 요구해서 요청을 거절할 수 있는지 설명한다.

1. 먼저 문제: 브라우저는 쿠키를 자동으로 보낸다

사용자가 bank.example에 로그인하면 브라우저에는 세션 쿠키가 저장된다. 이후 브라우저가 bank.example로 요청을 보낼 때, 그 요청이 은행 화면에서 시작됐든 공격자 사이트에서 유도됐든 조건이 맞으면 쿠키가 자동으로 붙을 수 있다. 

정상 요청:
사용자 -> bank.example 화면 -> POST /transfer
Cookie: JSESSIONID=사용자의_세션

CSRF 요청:
사용자 -> evil.example 화면 -> 자동 제출 form -> POST https://bank.example/transfer
Cookie: JSESSIONID=사용자의_세션

서버가 “쿠키가 있으니 사용자가 의도한 요청이다”라고만 판단하면 위험하다. 쿠키는 인증된 사용자를 나타내지만, 그 사용자가 지금 이 요청을 의도했는지는 증명하지 못한다.

2. 공격자는 무엇을 할 수 있나?

공격자 사이트는 사용자의 쿠키 값을 직접 읽지는 못한다. 하지만 브라우저에게 bank.example로 요청을 보내게 만들 수는 있다. 예를 들어 공격자 페이지가 아래 form을 자동 제출하면, 서버 입장에서는 인증된 사용자의 요청처럼 보일 수 있다. 

<form action="https://bank.example/transfer" method="POST">
  <input type="hidden" name="to" value="attacker">
  <input type="hidden" name="amount" value="100000">
</form>
<script>document.querySelector("form").submit();</script>

그래서 CSRF는 “비밀번호를 훔치는 공격”이 아니라, 이미 로그인된 브라우저를 빌려서 상태 변경 요청을 대신 보내게 만드는 공격이다.

3. CSRF 토큰의 직관

서버는 정상 페이지를 내려줄 때 예측하기 어려운 값을 같이 준다. 이 값이 CSRF 토큰이다. 이후 상태를 바꾸는 요청에는 세션 쿠키뿐 아니라 이 토큰도 함께 와야 한다. 

서버가 정상 페이지 응답:
HTML 안에 토큰 포함
<input type="hidden" name="_csrf" value="RANDOM_123">

정상 제출:
Cookie: JSESSIONID=사용자의_세션
_csrf=RANDOM_123

서버 검증:
세션에 저장된 토큰 == 요청의 토큰
같으면 처리, 다르면 거절

공격자는 다른 origin의 HTML 안에 들어 있는 토큰을 읽을 수 없고, 토큰은 예측 불가능해야 한다. 따라서 공격자가 만든 form에는 맞는 토큰을 넣기 어렵다.

4. 예방 원리: “쿠키 + 의도 증명”

쿠키만 검사

취약. 공격자가 브라우저를 유도해도 쿠키는 자동으로 붙을 수 있다.

쿠키와 토큰 검사

방어. 공격자는 사용자의 정상 페이지에 심어진 토큰을 알기 어렵다.

5. 실제 사용 방식 A: 서버 렌더링 form

Thymeleaf, JSP, Rails, Django 같은 서버 렌더링 form에서는 서버가 form 안에 hidden input을 넣고, 제출 시 서버가 세션의 토큰과 비교한다. 

<form method="post" action="/account/email">
  <input type="email" name="email">
  <input type="hidden" name="_csrf" value="서버가_생성한_토큰">
  <button type="submit">변경</button>
</form>

6. 실제 사용 방식 B: SPA와 API

React/Vue 같은 SPA에서는 프론트 JavaScript가 토큰을 읽어서 상태 변경 요청의 커스텀 헤더로 보낸다. Spring Security의 CookieCsrfTokenRepository는 기본적으로 XSRF-TOKEN 쿠키에 토큰을 쓰고, 요청에서는 X-XSRF-TOKEN 헤더를 읽는다. 

초기 응답:
Set-Cookie: XSRF-TOKEN=RANDOM_123; Path=/

프론트 요청:
fetch("/api/profile", {
  method: "POST",
  credentials: "include",
  headers: {
    "Content-Type": "application/json",
    "X-XSRF-TOKEN": tokenFromCookie
  },
  body: JSON.stringify({ nickname: "kim" })
})

서버:
세션/저장소의 CSRF 토큰과 헤더 값을 비교

여기서 XSRF-TOKEN 쿠키는 “JavaScript가 읽어서 헤더로 되돌려 보내는 토큰 운반용”이다. 로그인 세션 쿠키와 역할이 다르다. 세션 쿠키는 인증용이고, CSRF 토큰은 위조 요청 구분용이다.

7. 왜 request header에 담나?

핵심은 custom header가 일반 HTML form으로는 만들어지지 않는다는 점이다. 공격자 페이지는 form 자동 제출로 application/x-www-form-urlencoded 요청을 만들 수 있지만, X-XSRF-TOKEN 같은 header를 붙이려면 JavaScript fetch가 필요하다. cross-origin fetch가 custom header를 붙이면 브라우저는 먼저 CORS preflight를 보내고, 서버가 공격자 origin과 header를 허용하지 않으면 실제 요청을 보내지 않는다. 

공격자 form:
  POST /api/profile 가능
  Cookie 자동 첨부 가능
  X-XSRF-TOKEN header 첨부 불가

공격자 fetch:
  X-XSRF-TOKEN header를 붙이려 하면 preflight 필요
  서버가 evil.example을 CORS 허용하지 않으면 실제 요청 전 차단

정상 프론트 fetch:
  허용된 origin에서 실행됨
  토큰을 읽고 X-XSRF-TOKEN header로 전송 가능

8. /csrf API가 공개되어도 왜 공격자는 읽기 어렵나?

공격자 사이트가 GET https://our-api.example/csrf 요청 자체를 유도할 수는 있다. 하지만 브라우저의 same-origin policy와 CORS 때문에, 서버가 공격자 origin을 허용하지 않으면 공격자 JavaScript는 그 응답 body, response header, victim domain 쿠키 값을 읽을 수 없다. 

evil.example에서 실행되는 코드:
fetch("https://our-api.example/csrf", { credentials: "include" })

서버가 CORS 미허용:
  요청은 도착할 수 있음
  응답은 evil.example JS가 읽지 못함
  XSRF-TOKEN 쿠키가 설정돼도 our-api.example 쿠키라서 evil.example JS는 읽지 못함

서버가 CORS를 잘못 허용:
  Access-Control-Allow-Origin: https://evil.example
  Access-Control-Allow-Credentials: true
  이러면 공격자가 토큰을 읽을 수 있어 CSRF 방어가 깨질 수 있음

그래서 /csrf를 만들 때도 CORS 허용 origin은 실제 프론트 origin으로 좁혀야 한다. CSRF 토큰은 “아무도 못 보는 값”이 아니라 “다른 origin의 공격자 JavaScript가 못 읽는 값”에 가깝다.

9. /csrf 응답은 쿠키, header, JSON 중 무엇으로 줘도 되나?

된다. 서버와 프론트가 계약을 맞추면 JSON body, response header, cookie, HTML meta tag 모두 가능하다. 차이는 프론트에서 토큰을 꺼내는 방식과 브라우저/CORS 설정의 복잡도다.

JSON body

명시적이고 이해하기 쉽다. cross-origin이면 응답 body를 읽을 수 있도록 CORS가 정확해야 한다.

Response header

본문 구조와 분리된다. cross-origin이면 필요한 경우 Access-Control-Expose-Headers가 필요하다.

Cookie

프레임워크 관례와 잘 맞는다. JS가 읽어야 하면 HttpOnly를 끄지만, 인증 쿠키와는 다른 토큰 운반용이다.

CSRF 토큰 쿠키가 곧바로 로그인 탈취를 뜻하지는 않는다. 이 쿠키는 인증 권한을 주는 세션 쿠키가 아니라, 프론트가 header로 되돌려 보낼 “검증용 값”이다. 다만 XSS가 있으면 CSRF 토큰도 읽을 수 있으므로, XSS 방어는 여전히 필수다.

10. 토큰은 언제 얻나?

서버 렌더링 화면에서는 form HTML을 받을 때 이미 토큰이 들어 있다. SPA에서는 보통 앱 시작, 로그인 성공 직후, 새로고침 직후, 또는 첫 상태 변경 요청 전에 /csrf 같은 endpoint나 응답 쿠키/헤더를 통해 토큰을 받아 둔다. 

SPA 예시:
1. GET /csrf
   응답: XSRF-TOKEN 쿠키 또는 X-CSRF-TOKEN 헤더

2. POST /api/profile
   Cookie: JSESSIONID=...
   X-XSRF-TOKEN: 위에서 받은 토큰

3. 로그인 성공 또는 로그아웃 후
   기존 토큰이 사라질 수 있으므로 새 토큰을 다시 받음

11. 공격자가 토큰을 알면 끝인가?

맞다. 공격자가 사용자의 유효한 CSRF 토큰을 읽을 수 있으면 CSRF 방어는 깨질 수 있다. 그래서 CSRF 토큰은 URL, 로그, 외부 referrer로 새면 안 되고, XSS를 막아야 한다. 다만 일반적인 cross-site 공격자 페이지는 same-origin policy 때문에 우리 사이트의 HTML, 쿠키, 응답 헤더를 마음대로 읽지 못한다.

CSRF 토큰은 “토큰을 절대 누구도 볼 수 없다”가 아니라, “공격자 origin의 스크립트는 피해자 origin의 토큰을 읽고 custom header로 재현하기 어렵다”에 기대는 방어다.

12. CORS와 Origin 검증의 차이

CORS는 주로 브라우저가 cross-origin JavaScript에게 응답을 읽게 해도 되는지, 그리고 custom header 요청을 허용할지 정하는 규칙이다. 하지만 CSRF의 핵심 위험은 “응답을 읽는 것”이 아니라 “상태 변경 요청이 서버에 도착하는 것”이다. 특히 HTML form 같은 simple request는 preflight 없이 서버까지 전송될 수 있다. CORS가 공격자 origin의 응답 읽기를 막아도, 서버가 이미 이메일 변경, 송금, 삭제 같은 처리를 끝냈다면 방어가 늦다. 그래서 상태 변경 API는 서버 처리 전에 Origin 또는 Referer도 직접 검증한다. 

CORS 허용 목록:
  우리 프론트가 API 응답을 읽고 custom header를 보낼 수 있게 하는 브라우저 정책
  허용되지 않은 origin의 응답 읽기는 막을 수 있지만, simple request 도착 자체를 항상 막는 것은 아님

Origin 검증:
  서버가 실제로 받은 상태 변경 요청의 출발 origin을 보고 처리/거절하는 서버 정책
  허용되지 않은 origin이면 상태 변경 로직 실행 전에 거절함

둘의 관계:
  CORS는 클라이언트 측 문지기
  Origin 검증은 서버 측 문지기

13. SameSite와 CSRF 토큰의 관계

SameSite 쿠키 속성은 cross-site 요청에 쿠키를 붙일지 제한해 CSRF 위험을 낮춘다. 하지만 모든 상황의 완전한 대체재라기보다 방어를 겹치는 수단으로 보는 편이 안전하다. 특히 상태 변경 요청은 GET으로 만들지 말고, 토큰 검증이나 custom header 같은 주 방어를 둔다.

14. 판단 기준

CSRF 방어가 특히 필요:
  쿠키 기반 로그인
  브라우저가 자동으로 credential을 붙임
  POST/PUT/PATCH/DELETE 같은 상태 변경 요청

상대적으로 CSRF 위험이 낮음:
  Authorization: Bearer ... 를 JS가 직접 붙이는 API
  공격자 사이트가 그 header 값을 만들 수 없음
  단, XSS와 token storage 위험은 별도 문제
