마켓 리플레이 백엔드 · 트랙 A(시간) 1/4 · 레슨 0036

가상 시계: 720초 그리드와 절대시각 스케줄링

이 프로젝트의 심장은 가상 시계다. IPO 8건의 공시·마감·상장 시각, 폐장, 정산 발표가 전부 여기에 매달려 있다. 그리고 이 시계에는 기획서 문장 그대로 구현하면 반드시 깨지는 지점이 하나 있다.

이 레슨 하나로 얻는 것. 틱 시각을 계산하는 올바른 식을 쓸 수 있고, @Scheduled(fixedDelay=35000)과 @Scheduled(fixedRate=35000)이 각각 다른 이유로 틀린다는 것을 구분해 설명할 수 있다. AI에게 스케줄러를 맡기면 거의 확실히 이 둘 중 하나를 쓴다.

§1 · 규칙은 하나뿐이고, 35초는 규칙이 아니다

기획서 0장과 4.1.1은 두 값을 나란히 적어 두었다.

실제 12분 = 게임 1개월(종가 틱 약 35초). 하루 약 27개월 재생

이 두 값은 동시에 참일 수 없다. 왜인지 계산해 보자. 

// 규칙 (불변)
1개월 = 720초 (12분)

// 그 달의 거래일 수 — 한국·미국 거래일의 합집합 (기획서 4.1.4)
N = 20 ~ 23일   ← 달마다 다르다

// 그래서 틱 간격은
720 ÷ N = 31 ~ 36초   ← "약 35초"의 정체

35초는 N = 20.6일 때만 나오는 값이다. 즉 35초는 규칙이 아니라 파생값이고, 분모가 달마다 바뀌므로 상수가 아니다. 기획서는 이걸 "약"으로 뭉갰는데, 구현자(또는 AI)가 그 문장을 읽으면 틱 간격 상수 35초를 잡는다. 그러면 1개월이 720초가 아니게 된다.

어느 쪽이 규칙인지 판정하는 방법. 둘 중 다른 것을 고정했을 때 무엇이 깨지는가를 본다. 720초를 고정하면 틱 간격이 유동적이 될 뿐 아무것도 깨지지 않는다. 35초를 고정하면 월 길이가 달마다 달라지고 — 그 위에 얹힌 일정 전부가 밀린다. 다른 것을 못 흔드는 쪽이 규칙이다.

§2 · 어긋남의 크기 — 27개월을 돌리면 폐장을 넘는다

재생 시작 11:05, 하루 27개월 기준이다. 27개월 × 12분 = 324분이므로 720초 그리드에서는 16:29에 재생이 끝나고 폐장(16:40)까지 11분이 운영 버퍼로 남는다.

방식월 길이27개월 재생 종료
720초 그리드 (규칙)720초 = 12분16:29✓ 기획서와 일치
35초 고정 · 월 20거래일700초16:20재생이 9분 일찍 끝난다
35초 고정 · 월 21거래일735초16:35버퍼가 5분으로 줄어든다
35초 고정 · 월 22거래일770초16:51⚠ 폐장(16:40) 초과
35초 고정 · 월 23거래일805초17:07⚠ 정산 발표(17:00)까지 침범

재생 축이 한국·미국 거래일의 합집합이므로 N은 각 시장 단독보다 크다. 실제로는 22~23일 쪽이며 — 재생이 폐장보다 늦게 끝난다. 폐장 시각은 랭킹 확정 스냅샷의 기준이라(기획서 11.4.1) 밀 수 없으므로, 그날 마지막 구간이 통째로 잘린다.

IPO 편성도 같이 무너진다. 리비안 상장은 편성표에서 15:29인데 (게임 2021.11 = 재생 시작으로부터 22개월째, 11:05 + 22×12분):

방식리비안 상장 시각어긋남
720초 그리드15:29✓
35초 고정 · 22거래일15:4718분 늦음
35초 고정 · 23거래일16:0031분 늦음

기획서가 스스로를 증명한다. IPO 8건의 공시·마감·상장 시각이 재생 시작 11:05로부터 전부 정확히 12분의 배수다. 12:17 공시 = 72분 = 6개월, 12:29 마감 = 84분 = 7개월, 12:41 상장 = 96분 = 8개월. 즉 월 경계가 실제 시각에 고정되어야 한다는 제약이 이미 기획서 안에 내장되어 있다 — "35초" 문장만 그걸 모른다.

§3 · fixedRate도 답이 아니다 — 다만 이유가 다르다

여기가 이 레슨의 핵심이고, 프로젝트 문서에 없는 내용이다. market-replay-api/spec-revisions.md R-1은 이렇게 적었다.

간격이 정확하더라도, 다음 틱 시각을 이전 틱에 더해서 구하면 오차가 누적된다. … 하루 500틱이면 틱당 100ms만 밀려도 50초가 쌓인다.

이 설명은 맞다. 그런데 fixedDelay에만 맞다. JDK 표준 스케줄러의 두 메서드는 다음 시각을 서로 다르게 구한다.

다음 실행 예정 시각지연이 누적되나
scheduleWithFixedDelay
@Scheduled(fixedDelay=…)		 앞 실행이 끝난 시점 + 간격 누적된다. 처리 시간이 전부 다음 기준 시각에 흡수된다
scheduleAtFixedRate
@Scheduled(fixedRate=…)		 initialDelay, initialDelay + period, initialDelay + 2×period, …
최초 시각에 앵커된다		 누적되지 않는다. 한 번 밀려도 예정 그리드는 제자리

앞은 javadoc의 "between the termination of one execution and the commencement of the next", 뒤는 "executions will commence after initialDelay, then initialDelay + period, then initialDelay + 2 * period, and so on"이다 (Java 21 javadoc).

그래서 fixedRate는 드리프트 논거로는 탈락하지 않는다. 탈락하는 이유는 다른 것이다 — period가 상수인데, 우리에게 필요한 간격은 720 ÷ N이고 N이 달마다 바뀐다. 

// 22거래일 달에 fixedRate = 35초를 쓰면
월 길이 = 22 × 35초 = 770초        // 720초여야 하는데 50초 초과
27개월  = 50초 × 27 = 22분 30초 밀림   // 드리프트가 아니라 산술 오차

왜 이 구분이 실전에서 중요한가. AI가 @Scheduled(fixedRate=35000)을 써 왔을 때 "fixedRate는 드리프트가 쌓여서 안 된다"고 리뷰 코멘트를 달면 AI가 반박할 수 있고, 그 반박이 맞다. 정확한 지적은 "간격이 상수가 아니다 — 720 ÷ N이고 N이 매달 바뀐다"다. 틀린 이유로 옳은 결론을 내면, 다음 리뷰에서 설득력을 잃는다.

§4 · 절대값으로 계산하고, 매 틱 다시 예약한다

k번째 틱의 실제 시각은 월 시작 시각에서 절대값으로 구한다. 

✗ tickAt(k) = tickAt(k-1) + 간격          // fixedDelay. 지연 누적
✗ tickAt(k) = 월시작 + 35초 × k           // fixedRate. 간격이 상수가 아님

✓ tickAt(k) = 월시작 + round(720초 × k ÷ N)      (k = 1..N)
      N = 그 달의 거래일 수 = 한국·미국 거래일의 합집합

이 식의 두 가지 성질을 확인하자.

  • 월 경계가 정확히 닫힌다. k = N이면 round(720 × N ÷ N) = 720이므로, 몇 거래일이든 마지막 틱이 월 시작 + 720초에 정확히 떨어진다. 반올림 오차가 월을 넘지 않는다 — 이게 27개월을 돌려도 안 밀리는 이유다.
  • 간격이 자연히 유동적이 된다. N=23이면 약 31.3초, N=20이면 36초. 상수를 안 잡았으므로 상수를 맞출 필요도 없다.

Spring에서 이 식을 표현하는 도구는 fixedRate가 아니라 TaskScheduler다. 가변 간격을 다루는 두 가지 시그니처가 이미 있다. 

// ① Trigger — 다음 시각을 매번 우리가 계산해 돌려준다
ScheduledFuture<?> schedule(Runnable task, Trigger trigger);
//   "invoking it whenever the trigger indicates a next execution time"
//   Trigger.nextExecution(TriggerContext) → Instant | null (null이면 끝)

// ② 매 틱 스스로 다시 예약 (self-rearming)
ScheduledFuture<?> schedule(Runnable task, Instant startTime);

둘 다 결과는 같다. Trigger는 "다음이 언제인가"를 한 곳에 모아 두므로 그리드 계산과 발행 로직이 분리되고, self-rearming은 틱 처리 끝에서 다음 것을 잡으므로 흐름이 선형이다. 어느 쪽이든 핵심은 period라는 상수를 프레임워크에 넘기지 않는 것이다.

§5 · 스레드 하나가 가상 시계 전체를 붙잡는다

Spring 스케줄러의 기본 풀은 스레드 1개다 — "If you do not provide a pool-size attribute, the default thread pool has only a single thread" (Spring Framework Reference). 0035 §스레드에서 이미 본 사실인데, 720초 그리드와 만나면 새로운 의미가 붙는다.

한 틱의 처리는 가벼운 일이 아니다. 이 프로젝트에서 틱 하나가 하는 일을 세어 보자.

  • 28종 종가 + 환율 조회 → market.prices 브로드캐스트
  • 그 종목들의 미체결 예약 전건 판정 → 체결 처리 → 개인 order.filled
  • 전 계좌 순회 → 평가액·시즌 순위·일간 순위 재계산 (rank.md)
  • 같은 순회에서 카테고리별 자금 분포 합산 (soc.md 히트맵)
  • 개인별 account.valuation · ranking.me 발행

scheduleAtFixedRate는 겹쳐 실행하지 않는다. javadoc: "If any execution of this task takes longer than its period, then subsequent executions may start late, but will not concurrently execute." 즉 틱 처리가 31초를 넘기면 다음 틱이 그만큼 늦게 나간다. 예정 시각 그리드는 제자리에 있지만 실제 발행이 밀린다.

그리고 이것이 adm.md의 F-ADM-05가 틱 지연을 핵심 지표로 꼽은 이유다. tickAt(k)가 절대 시각이므로 예정과 실제의 차이가 그대로 지표가 된다 — 간격 기반 스케줄링이었다면 밀린 것이 새 기준이 되어 지연이 지표에 안 잡힌다. 절대시각 설계가 관측 가능성까지 만들어 준다.

§6 · 클라이언트 쪽 절반 — 남은 초를 보내지 않는다

같은 원칙이 API 계약에도 나온다. GET /api/v1/game/clock은 "남은 초"가 아니라 절대 시각과 서버 시각을 보낸다. 

{
  "serverTime":   "2026-09-21T05:31:33Z",   // 응답 생성 시각
  "nextTickAt":  "2026-09-21T05:32:07Z",   // 다음 종가 확정
  "phaseEndsAt": "2026-09-21T07:40:00Z"    // 다음 phase 전환
}

이유는 브라우저다. 백그라운드 탭의 타이머는 스로틀된다 — MDN이 조건까지 명시한다.

브라우저비활성 탭에서
Chrome · Throttling타이머를 초당 1회 확인. 비슷한 타임아웃끼리 묶일 수 있다
Chrome · Intensive throttling (88+)분당 1회. 조건: 비가시 5분 초과 + 무음 30초 초과 + 체인 5단 이상 + WebRTC 비활성
Firefox Desktop최소 타임아웃 1초
Firefox for Android최소 15분. 탭을 통째로 언로드할 수도 있다

출처: MDN — Timeouts in inactive tabs. 기획서 문장 "초당 1회 → 분당 1회"는 Chrome의 두 스로틀 단계를 정확히 가리킨다.

남은 초를 받아 클라이언트가 세어 내려가면, 탭을 30분 방치하고 돌아온 사용자의 화면은 거짓이 된다. 폐장까지 40분 카운트다운에서 이 오차는 "예약을 걸다 폐장을 맞는" 결과가 되고, 무료 타임 10분에서는 더 치명적이다.

절대 시각 + 서버 시각을 함께 보내면 클라이언트는 한 번만 계산해 둔다. 

오프셋   = serverTime − 로컬시계          // 한 번 구해 보관
남은시간 = phaseEndsAt − (로컬시계 + 오프셋)   // 매 렌더링마다 다시 계산

백그라운드에서 깨어난 순간 즉시 정확하고, 사용자의 로컬 시계가 틀려 있어도 오프셋이 흡수한다. §4에서 서버가 한 것과 정확히 같은 일이다 — 이전 값에 더하지 말고 절대 기준에서 다시 구한다.
