Strategy · State · Template Method

셋 다 "if/switch로 나누던 동작을 클래스로 빼낸다"는 같은 출발점에서 나온 행위 패턴이다(행위 패턴: 객체들이 일을 나누고 협력하는 방식을 다루는 패턴). 클래스로 뺀 모양이 비슷해서 헷갈린다. 이 레슨의 목표는 하나다: 코드를 보고 셋 중 무엇인지, 구조 신호 두 개로 가른다.

구조 신호 두 개. ① 상속인가 합성인가. 상속은 부모 클래스를 extends하는 것이고, 합성은 다른 객체를 필드로 들고 일을 맡기는 것이다(이 맡기는 일을 위임이라 부른다).
② 합성이라면 누가 갈아끼우는가. 밖(클라이언트)이면 Strategy, 상태 객체 자신이면 State.

§1 · Strategy (전략) — 밖에서 갈아끼운다

한 문장. 같은 일을 하는 방법(알고리즘) 여러 개를 클래스로 만들어 두고, 사용하는 쪽이 그중 하나를 골라 끼우는 패턴이다.

구조. 알고리즘들은 같은 인터페이스를 구현한다. 이것들을 쓰는 객체(이 패턴에서는 Context라고 부른다)가 인터페이스 타입 필드를 하나 들고, 일이 오면 그 필드에 위임한다. 어떤 알고리즘을 넣을지는 클라이언트(Context를 쓰는 코드)가 고른다.

비유. 내비게이션. 본체는 그대로이고 "최단 / 무료 / 고속" 경로 방식을 운전자가 고른다. 비유가 맞지 않는 곳: 내비는 보통 한 번 고르면 끝이지만, Strategy는 실행 중에 setStrategy로 다시 바꿀 수 있다.

interface RouteStrategy { Route find(Point from, Point to); }
class Navi {
    private RouteStrategy strategy;               // 합성
    void setStrategy(RouteStrategy s) { this.strategy = s; }   // 밖에서 교체
    Route go(Point a, Point b) { return strategy.find(a, b); }
}

§2 · State (상태) — 안에서 스스로 바뀐다

한 문장. 객체의 상태(동전 없음, 동전 있음 등)를 클래스 하나씩으로 만들고, 같은 메서드를 불러도 현재 상태 클래스가 알아서 다르게 동작하게 하는 패턴이다.

구조. Context는 현재 상태 객체를 필드로 들고 위임한다. 여기까지는 Strategy와 같다. 다른 점은 상태 객체가 일을 마친 뒤 다음 상태가 무엇인지 스스로 정한다는 것이다. 그래서 상태 클래스들은 서로를 알고 있다(HasCoin이 NoCoin을 만든다). Strategy의 알고리즘들은 서로를 모른다.

비유. 자판기. "버튼 누르기"라는 같은 조작이 동전 없음 / 동전 있음에 따라 다르게 동작한다. 동전 있음 상태에서 버튼을 누르면 음료가 나오고, 그 상태가 스스로 "동전 없음"으로 돌아간다.

interface VendingState { VendingState pressButton(); }   // 처리 후 "다음 상태"를 돌려준다
class NoCoin implements VendingState {
    public VendingState pressButton() { /* "동전을 넣으세요" */ return this; }   // 상태 유지
}
class HasCoin implements VendingState {
    public VendingState pressButton() { /* 음료 배출 */ return new NoCoin(); }   // 다음 상태를 스스로 정함
}
// 자판기(Context)는 state = state.pressButton(); 한 줄로 현재 상태를 갱신한다

전이를 상태 객체 안에서 하는 방식이 가장 흔하다. 위 코드처럼 다음 상태를 반환해도 되고, Q3처럼 o.setState(new Shipped())로 Context에 직접 넣어도 된다. 둘 다 "상태 객체가 다음 상태를 정한다"는 같은 뜻이다. GoF 원전은 전이를 Context가 정하는 변형도 허용한다. 이 레슨에서는 "상태 객체가 정한다"를 기본 신호로 쓴다.

§3 · Template Method (템플릿 메서드) — 순서는 부모, 일부는 자식

한 문장. 일의 순서는 부모 클래스가 정해 두고, 순서 중 달라지는 단계만 자식 클래스가 채우는 패턴이다.

구조. 부모의 메서드가 알고리즘의 순서(골격)를 고정한다. 달라지는 단계는 추상 메서드(몸체 없이 선언만 한 메서드)로 비워 두고, 자식 클래스가 상속해서 채운다. 상속으로 맺은 관계라서 컴파일할 때 이미 정해지고, 실행 중에는 바꿀 수 없다.

클래스 패턴이란? GoF는 패턴을 클래스 패턴(클래스 사이 관계를 상속으로 맺고, 컴파일 때 정해진다)과 객체 패턴(객체 사이 관계를 합성으로 맺고, 실행 중에 바뀔 수 있다)으로 나눈다. Template Method는 클래스 패턴이다. 시험에서는 이 분류가 나오는데, 클래스 패턴은 4개(Factory Method, Adapter, Interpreter, Template Method)뿐이라 이름을 외워 둔다.

비유. 라면 끓이기. 물 끓이기, 면 넣기, 스프 넣기, 먹기 순서는 어느 제품이든 같고, 스프 단계만 제품마다 다르다. 비유가 맞지 않는 곳: 라면 레시피는 사람이 보고 따르지만, Template Method에서는 컴파일러가 "순서는 부모, 빈칸은 자식"을 강제한다(final이 순서 변경을 막는다).

abstract class Ramen {
    final void cook() { boilWater(); addNoodle(); addSoup(); serve(); }  // 골격 고정
    abstract void addSoup();                                              // 이 단계만 자식이 채움
}
class ShinRamen extends Ramen { void addSoup() { /* 매운 스프 */ } }

출처: Refactoring.Guru: Strategy의 "Relations with other patterns". State는 Strategy의 확장 형태이고, Template Method는 상속이라 정적이며(실행 중 안 바뀜), Strategy는 합성이라 실행 중에 바뀐다고 정리한다.

가장 흔한 오해. "Strategy와 State는 코드가 같으니 같은 패턴이다." 틀렸다. 필드 모양은 같지만 바꾸는 주체와 이유가 다르다. Strategy는 클라이언트가 "이 방법으로 해"라고 고르고, State는 객체의 상태가 변해서 상태 객체가 다음으로 넘어간다.

§5 · Spring·JDK에서 찾아보기 (공식 문서로 확인한 것만)

표의 "구조상 ~"는 문서가 패턴 이름을 직접 쓰지는 않았지만, 코드 구조가 그 패턴과 같다는 뜻이다.

어디무엇비고
HttpServletTemplate Method서브클래스가 doGet/doPost를 오버라이드하고, service가 요청 종류에 맞춰 그것들을 호출한다(문서: "almost no reason to override service")
Comparator 를 sort에 전달구조상 Strategy정렬 알고리즘의 "비교 방법"을 밖에서 끼운다. 단 Javadoc이 "strategy"라고 부르지는 않는다
JdbcTemplate이름만 Template, 구조는 Strategy에 가깝다DB 연결 열기와 닫기 같은 고정 흐름은 JdbcTemplate이 처리한다. 결과 한 줄을 객체로 바꾸는 부분은 호출하는 쪽이 콜백 객체(RowMapper 등)로 넘긴다. 상속이 아니라 객체를 받아 쓰는 합성이므로 고전 Template Method가 아니다

이름에 속지 않기. 이름에 Template이 붙어도 Template Method가 아닐 수 있다. JdbcTemplate이 그 예다. 판별은 이름이 아니라 상속인지 합성인지로 한다. RestTemplate이 어느 쪽인지는 이 레슨에서 직접 확인하지 않았으므로 판단하지 않는다.

§7 · 한 문장으로 회수

상속이면 Template Method. 합성이면 누가 바꾸는지를 본다 — 밖에서 고르면 Strategy, 상태 객체가 스스로 전이하면 State.
