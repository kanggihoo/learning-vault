Strategy · State · Template Method

셋 다 "if/switch로 분기하던 동작을 클래스로 빼고 싶다"는 문제에서 나온 행위 패턴이다. 그래서 코드가 닮았고, 그래서 헷갈린다. 이 레슨의 목표는 하나다: 코드를 보고 셋 중 무엇인지 구조 신호로 가른다.

구조 신호 두 개만 기억한다. ① 상속인가 합성인가 (부모 클래스를 상속 / 인터페이스를 필드로 보유) ② 합성이라면 누가 갈아끼우는가 (밖에서 / 상태 객체 스스로)

§1 · Strategy (전략) — 밖에서 갈아끼운다

이론. 알고리즘 여러 개를 각각 클래스로 만들어 같은 인터페이스로 묶고, 사용하는 쪽(Context)이 그중 하나를 필드로 들고 위임한다. 어떤 알고리즘을 쓸지는 클라이언트가 고른다. 별칭 Policy.

비유. 내비게이션. 본체는 그대로이고 "최단 / 무료 / 고속"을 사용자가 고른다.

interface RouteStrategy { Route find(Point from, Point to); }
class Navi {
    private RouteStrategy strategy;               // 합성
    void setStrategy(RouteStrategy s) { this.strategy = s; }   // 밖에서 교체
    Route go(Point a, Point b) { return strategy.find(a, b); }
}

§2 · State (상태) — 안에서 스스로 바뀐다

이론. 객체의 상태를 클래스로 만든다. Context는 현재 상태 객체에 위임하고, 상태 객체가 다음 상태를 정해 전이한다. 그래서 상태가 바뀌면 같은 호출의 행동이 달라진다. 구조는 Strategy와 거의 같지만, 상태끼리 서로를 안다.

비유. 자판기. 같은 "버튼 누르기"가 동전 없음 / 있음 / 품절에 따라 다르게 동작하고, 동전을 넣으면 자판기가 스스로 "있음" 상태가 된다.

interface VendingState { VendingState pressButton(); }
class NoCoin implements VendingState {
    public VendingState pressButton() { /* "동전을 넣으세요" */ return this; }
}
class HasCoin implements VendingState {
    public VendingState pressButton() { /* 음료 배출 */ return new NoCoin(); }  // 스스로 전이
}

§3 · Template Method (템플릿 메서드) — 순서는 부모, 일부는 자식

이론. 부모 클래스의 메서드가 알고리즘의 순서(골격)를 고정하고, 달라지는 단계만 추상 메서드로 남겨 서브클래스가 채운다. 상속이라 컴파일 시점에 정해지고 실행 중에는 못 바꾼다. GoF의 클래스 패턴 4개 중 하나다.

비유. 라면 끓이기. 물 끓이기 → 면 → 스프 → 먹기 순서는 같고 스프만 제품마다 다르다.

abstract class Ramen {
    final void cook() { boilWater(); addNoodle(); addSoup(); serve(); }  // 골격 고정
    abstract void addSoup();                                              // 이 단계만 자식이 채움
}
class ShinRamen extends Ramen { void addSoup() { /* 매운 스프 */ } }

§5 · Spring·JDK에서 찾아보기 (검증한 것만)

어디무엇비고
HttpServletTemplate Method서브클래스가 doGet/doPost를 오버라이드하고, service가 요청 종류에 맞춰 그것들을 호출한다(문서: "almost no reason to override service")
Comparator 를 sort에 전달구조상 Strategy정렬 알고리즘의 "비교 방법"을 밖에서 끼운다. 단 Javadoc이 "strategy"라고 부르지는 않는다
JdbcTemplate이름만 Template고정 흐름은 템플릿이 하고 변하는 부분은 콜백 객체(RowMapper 등)를 받는다 = 상속이 아니라 합성. 고전 Template Method가 아니라 Strategy에 가까운 "콜백 방식"

교정. 앞선 대화에서 "RestTemplate은 Template Method 계열"이라고 했다. JdbcTemplate 문서를 확인해 보니, 이름과 달리 상속이 아니라 콜백 합성 구조다. 이름에 Template이 있다고 Template Method는 아니다. RestTemplate은 직접 확인하지 않았으므로 판단을 보류한다.

§7 · 한 문장으로 회수

상속이면 Template Method. 합성이면 누가 바꾸는지를 본다 — 밖에서 고르면 Strategy, 상태 객체가 스스로 전이하면 State.
