OAuth2 state 쿠키와 프론트 복귀 흐름

목표: 서버 세션이 없을 때 state를 쿠키로 비교하는 구조와, Google callback 처리 후 사용자가 홈 화면으로 돌아오고 AT를 확보하는 구조를 요청/응답 단위로 이해한다.

1. state는 그대로 돌아오나?

정상 흐름에서는 그렇다. 우리 서버가 Google authorization URL에 state=abc123을 넣어 보내면, Google은 로그인/동의 후 우리 callback URL에 같은 state=abc123을 붙여서 브라우저를 돌려보낸다. 

우리 백엔드가 만든 redirect 응답:
302 Location: https://accounts.google.com/o/oauth2/v2/auth
  ?client_id=...
  &redirect_uri=https://api.our-service.com/oauth2/callback/google
  &response_type=code
  &scope=openid%20email%20profile
  &state=abc123

Google 로그인 성공 후 redirect 응답:
302 Location: https://api.our-service.com/oauth2/callback/google
  ?code=GOOGLE_AUTH_CODE
  &state=abc123

하지만 중요한 것은 “돌아온다”가 아니라 “돌아온 값이 내가 시작한 요청의 값과 같은지 검증한다”이다.

2. 서버 세션이 없으면 state를 어디에 두나?

한 가지 방식은 우리 백엔드 도메인의 HttpOnly 임시 쿠키에 저장하는 것이다. 이 쿠키는 Google로 보내지는 게 아니라, 나중에 브라우저가 우리 callback URL로 돌아올 때 우리 백엔드에 자동으로 붙는다. 

1. 브라우저 -> 우리 백엔드
GET https://api.our-service.com/login/google

2. 우리 백엔드 -> 브라우저
Set-Cookie: oauth_state=abc123; HttpOnly; Secure; SameSite=Lax; Max-Age=300; Path=/oauth2/callback
302 Location: https://accounts.google.com/o/oauth2/v2/auth?...&state=abc123

3. 브라우저 -> Google
GET https://accounts.google.com/o/oauth2/v2/auth?...&state=abc123

중요:
  oauth_state 쿠키는 api.our-service.com의 쿠키다.
  따라서 accounts.google.com 요청에는 붙지 않는다.

4. Google -> 브라우저
302 Location: https://api.our-service.com/oauth2/callback/google?code=...&state=abc123

5. 브라우저 -> 우리 백엔드 callback
GET /oauth2/callback/google?code=...&state=abc123
Cookie: oauth_state=abc123

6. 우리 백엔드
query state와 cookie state 비교
일치하면 통과
다르면 거절

이 방식에서 쿠키는 “로그인 완료 쿠키”가 아니다. 잠깐 동안 OAuth 요청과 callback을 연결하기 위한 임시 검증값 저장소다.

3. 쿠키 기반 state 검증 의사코드

GET /login/google:
  state = randomBase64Url(32)

  response.setCookie(
    name = "oauth_state",
    value = state,
    httpOnly = true,
    secure = true,
    sameSite = "Lax",
    maxAge = 300,
    path = "/oauth2/callback"
  )

  redirect(
    "https://accounts.google.com/o/oauth2/v2/auth"
      + "?response_type=code"
      + "&client_id=..."
      + "&redirect_uri=https://api.our-service.com/oauth2/callback/google"
      + "&scope=openid%20email%20profile"
      + "&state=" + state
  )

GET /oauth2/callback/google:
  stateFromQuery = request.query["state"]
  stateFromCookie = request.cookie["oauth_state"]

  if stateFromQuery == null:
      reject

  if stateFromCookie == null:
      reject

  if stateFromQuery != stateFromCookie:
      reject

  response.deleteCookie("oauth_state")
  exchange code with Google
  issue our tokens

운영 환경에서는 단순 비교 외에도 만료 시간, 재사용 방지, redirect 목적지 검증이 필요하다. 완전 무상태에 가깝게 가려면 state 자체를 서명하거나 암호화해서 위변조를 막는다.

4. /login/success는 API인가 화면인가?

https://our-frontend.com/login/success는 예시 이름일 뿐이다. API가 아니라 React/Vue/Next 같은 프론트 애플리케이션의 라우트일 수 있다. 실제 서비스에서는 /, /home, /dashboard, /mypage로 보내도 된다. 

callback 처리 완료 후:
302 Location: https://our-frontend.com/

또는:
302 Location: https://our-frontend.com/dashboard

또는:
302 Location: https://our-frontend.com/login/success?from=oauth

중요한 것은 URL 이름이 아니라 “백엔드 callback 응답이 브라우저에게 프론트 화면 URL로 이동하라고 지시한다”는 점이다.

5. 방식 A: callback에서 RT 쿠키 저장 후 홈으로 redirect

1. Google callback 도착
GET https://api.our-service.com/oauth2/callback/google?code=...&state=...

2. 우리 백엔드
state 검증
Google code 교환
Google id_token 검증
회원 조회/가입
우리 refresh token 발급

3. 우리 백엔드 -> 브라우저
Set-Cookie: refresh_token=RT; HttpOnly; Secure; SameSite=Lax; Path=/auth
302 Location: https://our-frontend.com/

4. 브라우저 -> 프론트
GET https://our-frontend.com/

5. 프론트 앱 시작 코드
POST https://api.our-service.com/auth/refresh
Cookie: refresh_token=RT

6. 우리 백엔드 -> 프론트
200 OK
{
  "accessToken": "AT",
  "user": { ... }
}

여기서 /auth/refresh 호출은 브라우저가 마법처럼 하는 게 아니다. 프론트 앱의 초기화 코드, route guard, React useEffect, Vue router guard 같은 코드가 호출한다. 

프론트 앱 부팅 시:
  accessToken이 메모리에 없으면
      POST /auth/refresh 호출
      성공하면 AT를 메모리에 저장
      /me 또는 홈 데이터 API 호출

RT가 HttpOnly 쿠키에 있으면 JavaScript는 RT 값을 읽지 못한다. 대신 같은 사이트 요청 또는 credentials: "include" 요청에서 브라우저가 쿠키를 자동으로 붙여준다.

6. 방식 B: callback 후 일회성 로그인 티켓으로 교환

방식 B의 핵심은 Google callback 응답에서 바로 RT 쿠키를 심는 대신, 프론트에 매우 짧게 사는 우리 서비스용 일회성 티켓만 넘기고, 프론트가 별도 API로 AT/RT를 교환한다는 것이다. 이 티켓은 Google authorization code가 아니라 우리 백엔드가 만든 값이다. 

1. Google callback 도착
GET https://api.our-service.com/oauth2/callback/google?code=...&state=...

2. 우리 백엔드
state 검증
Google code 교환
Google id_token 검증
회원 조회/가입
login_ticket 생성

3. 우리 백엔드 -> 브라우저
302 Location: https://our-frontend.com/oauth/complete?ticket=LOGIN_TICKET

4. 브라우저 -> 프론트
GET https://our-frontend.com/oauth/complete?ticket=LOGIN_TICKET

5. 프론트 앱 코드
POST https://api.our-service.com/auth/exchange
Content-Type: application/json

{
  "ticket": "LOGIN_TICKET"
}

6. 우리 백엔드 -> 프론트
Set-Cookie: refresh_token=RT; HttpOnly; Secure; SameSite=Lax; Path=/auth
200 OK
{
  "accessToken": "AT",
  "user": { ... }
}

방식 B는 “최종 토큰 발급”을 redirect 응답이 아니라 일반 API 응답에서 처리하고 싶을 때 쓴다. 단, LOGIN_TICKET은 짧은 만료, 1회 사용, 서명/저장소 검증이 필요하다.

7. 방식 A와 B의 차이

방식 A

간단하다. callback에서 바로 RT 쿠키를 심고 홈으로 보낸다.

프론트는 부팅 후 refresh/me API를 호출해야 한다.

방식 B

AT를 일반 API 응답 body로 받기 쉽다.

일회성 티켓 관리가 추가된다.
