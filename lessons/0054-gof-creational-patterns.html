생성 패턴 5개 — Factory Method · Abstract Factory · Builder · Prototype · Singleton

생성 패턴은 한 가지 질문에 답한다: "객체를 어떻게 만들까?" 코드에서 본 적은 있지만 이름과 연결이 안 된다는 전제로, 이 레슨은 새로 가르치기보다 이름과 코드 모양을 연결하는 데 집중한다. "본 적이 있다"와 "구분할 수 있다"는 다르므로 퀴즈가 중심이다.

§0 · 워밍업 — 지난 묶음 4문제 (섞어서)

R1. for (Iterator it = list.iterator(); it.hasNext(); ) it.next();

R2. 상위 클래스가 final 메서드로 순서를 고정하고 한 단계만 abstract로 남긴다.

R3. 서로 다른 인터페이스를 가진 OldApi를 NewApi로 쓰려고 변환 클래스를 끼웠다.

R4. 실행한 요청을 객체로 만들어 스택에 쌓고, undo()를 호출해 되돌린다.

§2 · Factory Method vs Abstract Factory — 가장 헷갈리는 쌍

이름이 비슷하지만 한 번에 만드는 대상의 개수가 다르다. Factory Method는 제품 하나를 만드는 메서드 하나가 핵심이고, Abstract Factory는 서로 어울리는 제품 여러 개(제품군)를 만드는 메서드 여러 개를 가진 공장 객체가 핵심이다. 제품군의 예: 모던 스타일 의자·소파·탁자 세트.

// Factory Method: 한 종류의 제품, 서브클래스가 구체 클래스를 결정 (상속)
abstract class Bakery {
    Bread order() { Bread b = createBread(); b.bake(); return b; }
    protected abstract Bread createBread();                // 이 한 줄이 Factory Method
}
class SeoulBakery extends Bakery { protected Bread createBread() { return new Baguette(); } }

// Abstract Factory: 서로 어울리는 여러 제품군을 한 번에 (합성으로 공장 객체를 받음)
interface FurnitureFactory { Chair createChair(); Sofa createSofa(); Table createTable(); }
class ModernFactory implements FurnitureFactory { /* 모던 스타일 3종 */ }
class VictorianFactory implements FurnitureFactory { /* 빅토리아 스타일 3종 */ }
Factory MethodAbstract Factory
만드는 것제품 하나제품 군(family)
방식부모가 빈칸으로 남긴 메서드를 자식이 오버라이드 (상속, 클래스 패턴)공장 객체를 받아서 씀 (합성, 객체 패턴)
교체 단위서브클래스 하나공장 하나를 바꾸면 세트 전체가 바뀜

Refactoring.Guru: Abstract Factory는 흔히 여러 Factory Method의 집합으로 구성되고, Factory Method는 Template Method의 특수한 형태다. 가이드는 설계가 보통 Factory Method에서 시작해 필요할 때 Abstract Factory·Prototype·Builder로 발전한다고 말한다 (Factory Method, Abstract Factory).

§3 · Builder — 단계별 조립

한 문장. 설정할 항목이 많은 객체를, 항목을 하나씩 이름 붙여 채운 뒤 마지막에 build()로 완성하는 패턴이다.

왜 쓰나. 생성자에 인자가 6개면 new Pizza(12, true, true, false, false, null)처럼 어떤 값이 무엇인지 읽을 수 없고, 선택 항목이 많으면 생성자 조합도 늘어난다. Builder는 .size(12).cheese(true)처럼 항목 이름을 코드에 드러내고, 필요한 것만 채울 수 있게 한다.

Pizza p = new Pizza.Builder()
        .size(12).cheese(true).pepperoni(true)
        .build();                                  // 마지막에 완성품을 받음

GoF 원형에는 조립 순서를 정해 주는 Director라는 역할이 더 있지만 선택 사항이고, 위 코드처럼 Director 없이 쓰는 모양이 흔하다 (Refactoring.Guru). Abstract Factory와의 차이: Abstract Factory는 제품을 호출 즉시 돌려주고, Builder는 제품을 받기 전에 여러 번의 설정 단계를 거친다.

§4 · Prototype — 복제

한 문장. 새 객체를 new로 처음부터 만들지 않고, 이미 있는 객체를 복사해서 만드는 패턴이다.

왜 쓰나. 두 가지 경우다. ① 객체를 설정하는 비용이 커서(파일 읽기, 계산 등) 처음부터 다시 만들기 아깝다. ② 변수가 Shape 타입뿐이라 실제 클래스가 Circle인지 알 수 없는데도 같은 종류를 하나 더 만들고 싶다. a.copy()는 a의 실제 클래스를 알아서 같은 클래스의 복사본을 돌려주므로 new Circle()이라고 쓸 필요가 없다. 이 점이 Factory Method와 다르다. Factory Method는 자식 클래스를 만들어야 하지만, Prototype은 복사만 하면 된다.

interface Shape { Shape copy(); }
class Circle implements Shape {
    int r; String color;
    public Shape copy() { Circle c = new Circle(); c.r = r; c.color = color; return c; }
}
Shape b = a.copy();                                // a의 실제 클래스를 몰라도 복제된다. 약간만 고쳐 쓴다

copy()는 직접 만든 복사 메서드다. Java의 Object.clone()(Cloneable)을 쓰는 방식도 있어서 시험에서는 "clone"이라는 이름으로 나온다. Prototype은 저장할 객체가 단순하고 외부 연결이 적을 때 Memento의 간단한 대안이 되기도 한다 (Refactoring.Guru).

§5 · Singleton — 하나만

한 문장. 클래스의 인스턴스를 프로그램 전체에서 오직 하나만 만들고, 어디서든 같은 것을 꺼내 쓰게 하는 패턴이다.

알아보는 법. private 생성자(밖에서 new 못 함) + static 필드(하나를 담아 둠) + static getInstance()(그 하나를 돌려줌)의 세 가지가 함께 있다. 시험 코드 문제에서는 getInstance()를 여러 번 불러도 같은 객체라서 필드 값이 누적되는 점이 함정으로 나온다(Q4).

class Config {
    private static Config instance;
    private Config() {}
    public static synchronized Config getInstance() {   // 다중 스레드 동시 생성 방지
        if (instance == null) instance = new Config();
        return instance;
    }
}

Spring의 singleton은 GoF Singleton과 다르다. 차이는 "누가 하나로 막는가"다. GoF Singleton은 클래스 코드 자신이 private 생성자로 인스턴스를 하나로 막는다(ClassLoader당 하나). 반면 Spring은 클래스는 평범하게 두고, Spring 컨테이너가 빈 정의 하나당 인스턴스를 하나만 만들어 재사용한다. 그래서 같은 클래스로 빈 정의를 두 개 등록하면 인스턴스가 두 개 생기고, @Service 클래스에는 getInstance()도 없다. 출처: Spring — Bean Scopes.

Refactoring.Guru가 지적하는 단점: 나쁜 설계를 가릴 수 있고, 단위 테스트가 어렵고, 다중 스레드에서는 특별한 처리가 필요하다 (Singleton).

    private int n;
    private Counter() {}

§7 · 한 문장으로 회수
