생성 패턴 5개 — Factory Method · Abstract Factory · Builder · Prototype · Singleton

생성 패턴은 한 가지 질문에 답한다: "객체를 어떻게 만들까?" 이미 어디서 본 적이 있다고 하셨으니, 이 레슨은 새로 가르치기보다 이름과 코드 모양을 연결하는 데 집중한다. "본 적이 있다"와 "구분할 수 있다"는 다르므로 퀴즈가 중심이다.

R2. 상위 클래스가 final 메서드로 순서를 고정하고 한 단계만 abstract로 남긴다.

R3. 서로 다른 인터페이스를 가진 OldApi를 NewApi로 쓰려고 변환 클래스를 끼웠다.

R4. 실행한 요청을 객체로 만들어 스택에 쌓고, undo()를 호출해 되돌린다.

§2 · Factory Method vs Abstract Factory — 가장 헷갈리는 쌍

이름이 비슷하지만 만드는 대상의 개수가 다르다.

// Factory Method: 한 종류의 제품, 서브클래스가 구체 클래스를 결정 (상속)
abstract class Bakery {
    Bread order() { Bread b = createBread(); b.bake(); return b; }
    protected abstract Bread createBread();                // 이 한 줄이 Factory Method
}
class SeoulBakery extends Bakery { protected Bread createBread() { return new Baguette(); } }

// Abstract Factory: 서로 어울리는 여러 제품군을 한 번에 (합성으로 공장 객체를 받음)
interface FurnitureFactory { Chair createChair(); Sofa createSofa(); Table createTable(); }
class ModernFactory implements FurnitureFactory { /* 모던 스타일 3종 */ }
class VictorianFactory implements FurnitureFactory { /* 빅토리아 스타일 3종 */ }
Factory MethodAbstract Factory
만드는 것제품 하나제품 군(family)
방식상속 (클래스 패턴)객체(공장)를 주입 (객체 패턴)
교체 단위서브클래스 하나공장 하나를 바꾸면 세트 전체가 바뀜

Refactoring.Guru: Abstract Factory는 흔히 여러 Factory Method의 집합으로 구성되고, Factory Method는 Template Method의 특수한 형태다. 가이드는 설계가 보통 Factory Method에서 시작해 필요할 때 Abstract Factory·Prototype·Builder로 발전한다고 말한다 (Factory Method, Abstract Factory).

§3 · Builder — 단계별 조립

이론. 생성자 인자가 너무 많거나 선택 항목이 많은 객체를 단계별로 조립한다. 같은 조립 절차로 다른 표현을 만들 수 있다. 조립 순서를 정하는 Director는 선택이다 (Refactoring.Guru).

Pizza p = new Pizza.Builder()
        .size(12).cheese(true).pepperoni(true)
        .build();                                  // 마지막에 완성품을 받음

Abstract Factory와의 차이: Abstract Factory는 제품을 즉시 돌려주고, Builder는 제품을 받기 전에 추가 조립 단계를 둘 수 있다.

§4 · Prototype — 복제

이론. 구체 클래스에 의존하지 않고 기존 객체를 복사해서 새 객체를 만든다. 생성 비용이 크거나 설정이 복잡한 객체를 만들 때 유용하다. 상속이 필요 없다는 점이 Factory Method와 다르다.

interface Shape extends Cloneable { Shape copy(); }
class Circle implements Shape {
    int r; String color;
    public Shape copy() { Circle c = new Circle(); c.r = r; c.color = color; return c; }
}
Shape b = a.copy();                                // a를 복제해서 약간만 고쳐 쓴다

Memento의 단순한 대안이 되기도 한다. 저장할 객체가 단순하고 외부 연결이 적을 때다 (Refactoring.Guru).

§5 · Singleton — 하나만

이론. 클래스의 인스턴스를 오직 하나만 만들고 전역 접근점을 제공한다. 알아볼 표지는 private 생성자 + static 필드 + static getInstance()다. 시험 코드 문제에서는 getInstance()를 여러 번 불러도 같은 객체라 카운트가 누적되는 점이 함정으로 나온다.

class Config {
    private static Config instance;
    private Config() {}
    public static synchronized Config getInstance() {   // 다중 스레드 동시 생성 방지
        if (instance == null) instance = new Config();
        return instance;
    }
}

Spring의 singleton은 GoF Singleton과 다르다. Spring 문서: GoF singleton은 클래스 자체가 ClassLoader당 인스턴스 하나를 강제하지만, Spring의 singleton scope는 컨테이너당·빈 정의당 하나다. 즉 @Service 빈이 하나라고 해서 클래스에 getInstance()가 있는 것이 아니다. 출처: Spring — Bean Scopes.

Refactoring.Guru가 지적하는 단점: 나쁜 설계를 가릴 수 있고, 단위 테스트가 어렵고, 다중 스레드에서는 특별한 처리가 필요하다 (Singleton).

class Counter {
    private static Counter inst;
    private int n;
    private Counter() {}
    static Counter get() { if (inst == null) inst = new Counter(); return inst; }
    int inc() { return ++n; }

§7 · 한 문장으로 회수

상속으로 한 제품을 정하면 Factory Method, 제품군이면 Abstract Factory, 단계별이면 Builder, 복제면 Prototype, 하나뿐이면 Singleton.
