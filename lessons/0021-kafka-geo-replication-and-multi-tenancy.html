여러 클러스터, 여러 팀: Geo-Replication과 Multi-Tenancy

목표: Apache Kafka Documentation: Geo-Replication과 Multi-Tenancy 원문을 근거로, "클러스터 하나로는 부족한 상황"을 두 각도에서 이해한다 — 지리적으로(여러 지역·데이터센터에 Kafka를 흩어둬야 할 때)와 조직적으로(여러 팀이 Kafka 하나를 같이 써야 할 때). 0016 레슨의 Topic·Partition·Consumer Group·Replication과 0019 레슨의 ISR·Quotas를 이미 안다고 가정하고, 그 위에 "클러스터 간(inter-cluster)"과 "같은 클러스터를 나눠쓰기(multi-tenant)"라는 두 개념을 얹는다.

0. 왜 클러스터 하나로 충분하지 않은가

지금까지 배운 Replication(ISR, Leader/Follower)은 전부 같은 클러스터 안에서 일어나는 일이었다. 그런데 실무에서는 이런 요구가 자주 생긴다.

  • 서울 데이터센터가 통째로 죽어도 서비스가 계속되게 하고 싶다 (재해 복구, disaster recovery)
  • 법·규제 때문에 특정 국가의 데이터는 그 나라 안에만 있어야 한다 (데이터 위치 규제)
  • 여러 지역 매장의 로그를 각 지역에서 모았다가, 최종적으로 본사의 클러스터 하나로 합치고 싶다
  • 운영(production) 클러스터와 테스트(testing) 클러스터를 물리적으로 아예 분리하고 싶다

이런 요구는 전부 클러스터와 클러스터 사이(inter-cluster)에서 데이터를 복제해야 풀리는 문제다. 이걸 Geo-Replication이라고 부르고, Kafka는 이를 위해 MirrorMaker 2라는 별도 도구를 제공한다.

헷갈리기 쉬운 지점: 지금까지 배운 클러스터 내부 Replication(ISR)은 "같은 데이터를 여러 Broker가 나눠 갖고 있는 것"이고, 여기서 배울 클러스터 간 Replication(MirrorMaker)은 "완전히 다른 Kafka 클러스터 두 개 사이에서 토픽을 복사해 옮기는 것"이다. 이름은 둘 다 "replication"이지만 하는 일과 쓰는 기술이 전혀 다르다.

1. MirrorMaker 2 — 클러스터 사이에 다리 놓기

MirrorMaker는 한 클러스터(source)에서 읽어서, 다른 클러스터(target)로 그대로 써주는 프로그램이다. 사실 이 프로그램의 정체는 source 클러스터를 구독하는 Consumer + target 클러스터에 쓰는 Producer를 하나로 묶어 자동화한 것뿐이다. Kafka Connect라는 프레임워크 위에 만들어져서, 장애가 나도 알아서 복구되고(fault-tolerant) 여러 대로 늘려 처리량을 늘릴 수 있다(horizontally scalable).

MirrorMaker가 복제해주는 것

  • 토픽 데이터와 설정 — 메시지 내용과 partition 수·retention 같은 topic 설정
  • Consumer Group과 그 offset — 장애로 클러스터를 옮겨 타야 할 때, 어디까지 읽었는지도 같이 옮겨줌
  • ACL(권한 설정)과 새로 생긴 토픽·파티션 자동 감지

왜 offset이 그대로 안 옮겨지나 (가장 헷갈리는 지점)

0016 레슨에서 offset은 "그 Partition 안에서 몇 번째 메시지인가"를 뜻하는 숫자라고 배웠다. 그런데 Cluster A의 topic foo와 Cluster B에 복제된 topic A.foo는 완전히 별개의 로그 파일이다. A에 새 메시지가 계속 쌓이는 동안 B로 복제되는 타이밍은 항상 조금 늦기 때문에, 어느 시점에 A의 offset이 104여도 B는 아직 57까지만 복제됐을 수 있다 — 번호 체계 자체가 다르다.

그래서 MirrorMaker는 "checkpoint"라는 별도 정보로 "A에서 여기까지 읽었다" = "B에서는 몇 번에 해당한다"는 매핑을 함께 복제한다. 이 매핑이 있어야, 평소에는 A를 쓰다가 장애가 나서 Consumer들이 B로 옮겨 타야 하는 순간에도 중복이나 유실 없이 정확히 이어서 읽을 위치를 알 수 있다. 이 매핑 없이 그냥 "B에서도 offset 104부터 읽어라"라고 하면 완전히 엉뚱한 메시지부터 읽게 된다.

2. 복제 흐름(Replication Flow) 패턴 — Active/Passive vs Active/Active

MirrorMaker 설정에서 {source}->{target} 형태로 "어느 클러스터에서 어느 클러스터로" 복제할지를 정의하는데, 이를 replication flow라 부른다. 이 화살표를 어떻게 조합하느냐에 따라 크게 두 가지 배포 패턴이 생긴다.

패턴방향쓰기(write)는 어디로주 용도
Active/Passive (Active/Standby) A -> B (한쪽 방향만) 평소엔 A에만 씀. B는 대기용 복사본 재해 복구 — A가 죽으면 B로 전환(failover)
Active/Active A -> B, B -> A (양방향) 양쪽 다 씀 (사용자를 지역별로 가까운 쪽에 붙임) 지역별 지연 시간(latency) 단축, 상시 이중화

이 외에도 여러 클러스터를 하나로 모으는 Aggregation(A->K, B->K, 지역별 클러스터의 로그를 본사 클러스터로 집계할 때)과, 하나에서 여러 곳으로 퍼뜨리는 Fan-out(K->A, K->B) 조합도 가능하다 — 화살표를 조합하는 것뿐이라 필요한 topology를 자유롭게 만들 수 있다.

Active/Active를 쓸 때 "A에서 B로 복제된 토픽이 다시 B에서 A로 복제되고, 그게 또 A에서 B로..." 처럼 무한 순환(replication loop)이 걱정될 수 있다. 하지만 MirrorMaker는 복제된 토픽 이름 앞에 {source}.를 붙이는 규칙(예: us-west.foo) 덕분에 "이미 한 번 복제된 토픽"을 스스로 구분해서, 별도 설정 없이도 이 무한 루프를 막아준다.

3. 심화 학습 참고 (지금은 개념만, 나중에 실습)

MirrorMaker 실제 설정 파일 문법(clusters, topics, tasks.max 등), exactly-once 옵션, 보안(SSL) 설정, "가까운 클러스터에 생산하라(consume remote, produce local)"는 성능 best practice, 그리고 kafka.connect.mirror 모니터링 지표까지는 지금 단계에서 생략한다. 실제로 MirrorMaker를 띄워볼 때 공식 문서를 그때그때 참고하면 된다.

4. Multi-Tenancy — 클러스터 하나를 여러 팀이 같이 쓰기

Geo-Replication이 "클러스터를 여러 개로 늘리는" 이야기였다면, Multi-Tenancy는 정반대 상황이다 — 비용과 운영 부담 때문에 클러스터 하나를 여러 팀·서비스가 함께 쓰고 싶어한다. 문제는 한 팀이 갑자기 트래픽을 폭주시키면 같은 클러스터를 쓰는 다른 팀까지 피해를 본다는 것("noisy neighbor" 문제). Multi-Tenancy는 결국 "어떻게 서로를 침범하지 않게 격리(isolation)할 것인가"라는 하나의 질문으로 요약된다. Kafka는 이 격리를 세 가지 도구로 만든다.

도구 1 — 이름으로 구역 나누기 (Topic Naming / Namespace)

Kafka에서 topic은 한 번 만들면 이름을 바꿀 수 없다(이름을 바꾸려면 새 topic을 만들고 메시지를 옮긴 뒤 옛 topic을 지워야 함). 그래서 처음부터 계층적인 이름 규칙을 정해두는 게 중요하다. 

<조직>.<팀>.<데이터셋>.<이벤트명>
예: acme.infosec.telemetry.logins   ← InfoSec 팀의 로그인 텔레메트리

<프로젝트>.<제품>.<이벤트명>
예: mobility.payments.suspicious    ← 프로젝트 단위로 나누는 경우

이렇게 공통 prefix(접두사)로 팀 구역을 나눠두면, 뒤에서 볼 "권한(ACL)"을 prefix 하나로 통째로 걸 수 있어서 관리가 훨씬 쉬워진다. 강제하는 방법은 여러 가지다: prefix ACL로 그 prefix가 아닌 topic 생성을 막거나, 아예 일반 사용자의 topic 생성 권한 자체를 막고 자동화 도구가 대신 만들게 하거나, auto.create.topics.enable=false로 의도치 않은 자동 생성을 막는 식이다.

도구 2 — Quotas로 자원 나눠 쓰기

0019 레슨의 10번 섹션에서 이미 배운 그 Quotas다 — (user, client-id) 조합별로 네트워크 대역폭과 요청 처리 시간(CPU)을 제한해서, 한 팀이 클러스터 자원을 독점하지 못하게 막는다. Multi-Tenancy 맥락에서 특히 중요한 건 request rate quota다 — broker의 CPU를 한 팀이 다 써버리면, quota로 막아둔 네트워크 대역폭과 무관하게 브로커 전체의 실질 처리량이 떨어지기 때문이다. 그 밖에 topic 생성·삭제 같은 관리 작업 자체에도 quota(controller_mutation_rate)를 걸어 과도한 topic 조작이 클러스터를 압도하지 않게 할 수 있다.

도구 3 — ACL로 접근 권한 나누기

Authentication(누구인지 확인) 위에 Authorization(그 사용자가 이 topic에 쓰거나 읽을 수 있는지 확인)을 건다. 앞서 만든 이름 규칙과 짝을 이루면 강력해진다 — "prefix가 acme.infosec.로 시작하는 모든 topic에 쓰기 권한을 준다"처럼 prefix ACL 하나로 팀 전체의 topic을 한 번에 관리할 수 있기 때문이다. 

$ bin/kafka-acls.sh --bootstrap-server localhost:9092 \
    --add --allow-principal User:Alice --producer \
    --resource-pattern-type prefixed --topic acme.infosec.
# → Alice는 "acme.infosec."로 시작하는 모든 topic에 쓸 수 있음

관리자는 이 지점에서 개발 편의성(넓고 느슨한 ACL 소수) vs 보안(좁고 엄격한 ACL 다수) 사이의 트레이드오프를 팀 상황에 맞게 고른다.

이 세 가지 도구(이름 규칙, Quotas, ACL)는 서로 독립이 아니라 이름 규칙을 뼈대로 삼아 Quotas와 ACL을 그 위에 얹는 방식으로 함께 동작한다는 걸 기억하자. 여기에 더해 실무에서는 Schema Registry(producer와 consumer가 메시지 형식을 서로 약속하는 도구, Kafka 자체엔 포함 안 됨)로 팀 간 "데이터 계약"까지 관리하는 경우가 많다 — 지금은 존재만 알아두면 된다.
