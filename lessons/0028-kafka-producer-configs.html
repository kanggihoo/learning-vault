Producer 설정: 안전성과 처리량 사이에서 고르기

0019 레슨에서 이미 배운 개념들 — batching(batch.size/linger.ms), key 기반 partitioning, ISR 커밋 모델 (acks/min.insync.replicas), idempotent producer, transaction — 은 다시 설명하지 않는다. 이 레슨은 그 개념들이 실제로 어떤 config 이름과 기본값으로 Java client에 나타나는지 대응표를 만들고, 0019에서 다루지 않았던 새로운 config 4가지(buffer.memory, max.in.flight.requests.per.connection, delivery/request timeout의 관계, partitioner.class)를 추가로 다룬다. 원문: Apache Kafka Documentation: Producer Configs.

0. 지도 — Producer 설정을 4가지 질문으로 나누기

887줄짜리 원문을 처음부터 다 읽을 필요는 없다. 실제로 Producer를 설정할 때 하는 고민은 이 4가지뿐이다. 

1. 얼마나 안전하게 보낼까?        → acks, min.insync.replicas, enable.idempotence  (0019에서 이미 배움)
2. 얼마나 빠르게 보낼까?          → batch.size, linger.ms, compression.type        (0019에서 이미 배움)
3. 실패하면 언제까지 재시도할까?  → retries, delivery.timeout.ms, request.timeout.ms  (새로 배움)
4. 순서를 지킬까?                → max.in.flight.requests.per.connection            (새로 배움)

1. "얼마나 안전하게" — 이미 배운 개념의 config 이름

Config기본값0019에서 배운 개념
acksallISR 전체가 받아야 커밋 — 0019 §8 "acks와 min.insync.replicas"
enable.idempotencetrue같은 요청 여러 번 보내도 결과가 한 번 보낸 것과 같음 — 0019 §5 "멱등성 Producer"
transactional.id없음(설정 안 하면 트랜잭션 비활성)정확히 한 번(exactly-once) — 0019 §6

기본값이 acks=all + enable.idempotence=true라는 게 중요하다 — 최신 Kafka는 아무 설정도 안 건드리면 이미 안전한 쪽으로 동작한다. "더 빠르게"를 원할 때만 일부러 낮추는 것이지, 안전하게 만들려고 뭔가를 켤 필요는 없다.

2. "얼마나 빠르게" — 이미 배운 개념의 config 이름

Config기본값0019에서 배운 개념
batch.size16384 (bytes)묶어서 보내기 — 0019 §Producer/비동기 전송
linger.ms5양이 안 차도 이 시간 지나면 전송 — 같은 절
compression.typenone묶음째 압축 — 0019 §효율/"묶어서 압축하기"

batch.size보다 linger.ms가 더 만지기 쉬운 손잡이다 — batch가 이미 다 찼으면 linger.ms와 상관없이 즉시 전송되므로, "얼마나 기다렸다 보낼지"는 사실상 linger.ms가 결정한다.

3. "실패하면 언제까지" — timeout 3형제의 관계 (새로운 내용)

여기가 초보자가 가장 자주 헷갈리는 지점이다. "요청 하나가 시간 초과되는 것"과 "이 메시지를 아예 포기하는 것"은 다른 시간 단위로 관리된다.

Config기본값뭘 재는가
request.timeout.ms30초네트워크 요청 한 번의 응답을 얼마나 기다릴지
retries사실상 무한(2147483647)실패한 요청을 몇 번 다시 보낼지 — 보통 직접 안 만지고 아래 timeout으로 제어
delivery.timeout.ms120초(2분)send() 호출 뒤 성공/실패를 최종 확정하기까지의 전체 상한 — 재시도 전부 포함

규칙: delivery.timeout.ms ≥ request.timeout.ms + linger.ms여야 한다. 그래서 실무에서는 retries를 직접 세는 대신 "이 메시지가 몇 초 안에 확정되길 원하는가"만 delivery.timeout.ms로 정하고, 그 안에서 재시도가 알아서 몇 번이든 일어나게 두는 게 권장 방식이다.

4. "순서를 지킬까" — max.in.flight.requests.per.connection (새로운 내용, 가장 중요)

Producer는 응답을 기다리지 않고 여러 요청을 동시에(in-flight) 미리 보낼 수 있다 — 이 config가 "한 connection에 동시에 띄워둘 수 있는 미확인 요청 수"를 정한다(기본값 5).

기본값 enable.idempotence=true인 상태에서는 이 config가 최대 5까지 어떤 값이어도 순서가 보존된다(Broker가 producer별 일련번호로 순서를 강제하기 때문). 문제는 누군가 enable.idempotence=false로 명시적으로 끄면서 이 값은 그대로 5(또는 1보다 큰 값)로 둘 때 생긴다 — 재시도 중인 배치를 나중에 보낸 배치가 추월할 수 있다. 순서가 중요한 토픽이라면 idempotence를 끄지 않는 것이 정답이지, 이 값을 1로 낮추는 건 차선책이다 (1로 낮추면 순서는 지켜지지만 동시 전송이 안 돼 처리량이 크게 떨어진다).

5. Partitioner — key가 없을 때 어디로 보낼지 (새로운 내용)

6. buffer.memory — 보내는 속도가 안 따라올 때 (새로운 내용)

Producer는 보낼 메시지를 메모리에 잠깐 쌓아두는 buffer를 갖는다(기본 32MB). Broker가 받는 속도보다 애플리케이션이 만드는 속도가 더 빠르면 이 buffer가 가득 찬다 — 이때 Producer는 예외를 던지지 않고 max.block.ms(기본 1분) 동안 잠깐 멈춰서(block) 기다린다. 그래도 안 풀리면 그제서야 예외로 실패한다.

이건 자연스러운 배압(backpressure) 메커니즘이다 — Broker가 못 따라오면 애플리케이션 쪽도 같이 느려지게 만들어서, 무한정 메모리에 쌓이다가 out-of-memory로 죽는 걸 막는다. 이 block이 자주 보이면 "Broker가 못 따라오고 있다"는 신호이므로, buffer를 늘리기보다 모니터링 지표로 Broker 쪽 병목을 먼저 확인하는 게 순서다.
