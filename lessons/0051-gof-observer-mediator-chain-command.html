Observer · Mediator · Chain of Responsibility · Command

넷 다 "요청(메시지)이 보내는 쪽에서 받는 쪽으로 어떻게 가는가"를 다룬다. 구분은 코드 모양이 아니라 요청이 가는 길의 모양으로 한다: 1:N 방송, 허브 경유, 사슬, 포장된 물건.

§0 · 워밍업 — 지난 두 묶음에서 4문제

신호 요약. 행위(묶음 1): 상속이면 Template Method / 합성이면 밖에서 갈아끼우면 Strategy, 상태 객체가 스스로 전이하면 State. 구조(묶음 2): 감싼 뒤 인터페이스가 달라지면 Adapter / 같으면서 기능 추가는 Decorator, 접근 통제는 Proxy.

R1. class Cart { private Discount d; void setDiscount(Discount d){this.d=d;} int total(){ return d.apply(sum()); } }

R2. class Bold implements Text { private Text t; public String render(){ return "<b>" + t.render() + "</b>"; } } — 클라이언트가 new Bold(new Italic(new Plain("hi")))처럼 겹쳐 쌓는다.

R3. 기존 OldPrinter.printText(String)을 새 인터페이스 Printer.print(Doc)로 쓰고 싶어서 변환 클래스를 만들었다.

R4. 상위 클래스가 final 메서드로 순서를 고정하고, 한 단계만 abstract로 남겼다.

§1 · 먼저 하나의 그림: 요청이 가는 길

패턴요청이 가는 길한 줄 비유
Observer한 곳에서 여러 구독자에게 동시에 (1:N)유튜브 구독 알림
Mediator모두가 허브 하나를 거쳐서 (N:N → 허브)공항 관제탑
Chain of Responsibility처리할 사람이 나올 때까지 한 줄로 넘김대리 → 과장 → 부장 결재
Command요청을 물건(객체)으로 포장해서 저장·전달식당 주문서

출처: Refactoring.Guru — Mediator의 "Relations with other patterns"가 이 네 패턴을 "보내는 쪽과 받는 쪽을 연결하는 서로 다른 방식"으로 비교한다.

§2 · Observer (옵서버) — 바뀌면 구독자 전원에게 알린다

이론. 한 객체(Subject, 주제)의 상태가 바뀌면 미리 등록한 모든 구독자(Observer)에게 자동으로 알린다. 구독자는 런타임에 등록·해지할 수 있다. 별칭 Publish-Subscribe, Dependents.

비유. 유튜브 구독. 채널(주제)이 영상을 올리면 구독 버튼 누른 사람 전원에게 알림이 간다. 채널은 구독자가 누군지 몰라도 되고, 구독자는 언제든 해지한다.

interface Observer { void update(String news); }
class Channel {                                    // Subject
    private final List<Observer> subs = new ArrayList<>();
    void subscribe(Observer o) { subs.add(o); }    // 등록
    void upload(String v) { for (Observer o : subs) o.update(v); }  // 전원에게 통지
}

§3 · Mediator (중재자) — 허브를 거친다

이론. 객체들이 서로를 직접 참조하면 선이 N×N으로 얽힌다. 중재자 한 객체를 두고 모두가 중재자하고만 소통하게 해서 얽힘을 N:1로 줄인다. 목표는 "서로에 대한 의존 제거"다.

비유. 공항 관제탑. 비행기끼리 무전하지 않고 관제탑하고만 통신한다. 채팅방도 같다. 참가자끼리 직접 보내지 않고 방(중재자)이 전달한다.

class ChatRoom {                                   // Mediator
    private final List<User> users = new ArrayList<>();
    void join(User u) { users.add(u); }
    void send(User from, String msg) {            // 모든 소통이 여기를 지남
        for (User u : users) if (u != from) u.receive(msg);
    }
}

§4 · Chain of Responsibility (책임 연쇄) — 한 줄로 넘긴다

이론. 요청을 핸들러의 사슬에 흘려보낸다. 각 핸들러는 "내가 처리한다" 또는 "다음 핸들러로 넘긴다"를 고른다. 보내는 쪽은 누가 처리할지 모른다.

비유. 결재 라인. 100만 원 이하는 대리가, 아니면 과장에게, 그래도 안 되면 부장에게 넘어간다.

abstract class Approver {
    private Approver next;
    Approver setNext(Approver n) { this.next = n; return n; }
    void handle(int amount) {
        if (canApprove(amount)) approve(amount);
        else if (next != null) next.handle(amount);   // 못 하면 다음 사람에게
    }
    abstract boolean canApprove(int amount);
    abstract void approve(int amount);
}

§5 · Command (커맨드) — 요청을 물건으로 만든다

이론. "무엇을 할지"를 객체 하나로 포장한다. 객체가 되었으니 변수에 담고, 큐에 줄 세우고, 기록하고, 실행 취소(undo)할 수 있다. 별칭 Action, Transaction.

비유. 식당 주문서. 말로 주문하면 사라지지만, 종이 한 장(요청)이 되면 줄 세우고, 취소하고, 기록으로 남긴다.

interface Command { void execute(); void undo(); }
class LightOn implements Command {
    private final Light light;
    public void execute() { light.on(); }
    public void undo()    { light.off(); }       // 되돌리는 법도 명령이 안다
}
// 리모컨은 Command만 안다 (누구를 켜는지 모른다)
Deque<Command> history = new ArrayDeque<>();  // 실행한 명령을 쌓아 undo

출처: Refactoring.Guru — Command. undo는 "실행 전 상태를 백업해 히스토리 스택에 쌓고, 되돌릴 때 pop해서 undo를 호출"하는 방식으로 설명한다.

§6 · 헷갈리는 쌍

쌍구분 질문
Observer vs Mediator한 방향 1:N 방송이면 Observer, 서로 주고받는 관계를 허브로 정리하는 것이면 Mediator. 가이드: 둘은 헷갈리기 쉽고 Mediator를 Observer로 구현하기도 한다(중재자=발행자, 컴포넌트=구독자)
Observer vs Chain구독자 전원이 받으면 Observer, 한 명이 처리할 때까지 넘기면 Chain
Command vs Strategy같은 일을 하는 방법을 갈아끼우면 Strategy, "무엇을 할지" 자체를 물건으로 만들어 저장·취소하면 Command
Chain vs Decorator둘 다 재귀적으로 감싼다. Chain의 핸들러는 흐름을 끊을 수 있다(처리하고 종료). Decorator는 흐름을 끊지 않는다 (Guru)

§7 · Spring·JDK에서 찾아보기 (문서 확인)

어디무엇비고
Spring ApplicationListenerObserver문서가 직접 "this is the standard Observer design pattern"이라고 쓴다. 기본은 동기라서 publishEvent()가 모든 리스너가 끝날 때까지 막힌다
Servlet FilterChain구조상 Chain of Responsibility각 필터가 doFilter로 "사슬의 다음 필터를 호출"하거나, 마지막이면 자원을 호출한다. Javadoc이 패턴 이름을 쓰지는 않는다

주의. 고전 Chain은 "처리하면 멈춘다"인데 서블릿 필터는 보통 "자기 일을 하고 다음으로도 넘긴다"는 점에서 변형이다. 이름만으로 판정하지 말고 구조(다음에게 넘기는가)로 본다.

§8 · 판별 퀴즈

Q1.

class Stock {
    private List<Listener> ls = new ArrayList<>();
    void add(Listener l) { ls.add(l); }
    void setPrice(int p) { for (Listener l : ls) l.onChange(p); }
}

Q2.

abstract class Handler {
    protected Handler next;
    void handle(Req r) {
        if (can(r)) process(r);
        else if (next != null) next.handle(r);
    }
}

Q3.

class Remote {
    private final Deque<Command> history = new ArrayDeque<>();
    void press(Command c) { c.execute(); history.push(c); }
    void undo() { if (!history.isEmpty()) history.pop().undo(); }
}

Q4. 시험 지문: "객체 간의 직접 통신을 제한하고 중재 객체를 통해서만 협력하게 하여 결합도를 낮춘다."

Q5. 시험 지문: "요청을 처리할 수 있는 객체가 나올 때까지 객체 사슬을 따라 요청을 넘긴다."

Q6. 시험 지문: "요청 자체를 객체로 캡슐화하여 매개변수화, 큐잉, 로그, 실행 취소를 지원한다."

§9 · 한 문장으로 회수

전원에게 방송이면 Observer, 허브 경유면 Mediator, 처리할 때까지 넘기면 Chain, 요청을 물건으로 만들면 Command.
