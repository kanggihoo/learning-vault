React에서 OAuth2 로그인 후 인증 상태 복원하기

목표: OAuth2 callback에서 RT를 HttpOnly 쿠키로 받은 뒤, React 앱이 어떻게 로그인 상태를 알아내고 헤더를 “로그인”에서 “로그아웃/환영 메시지”로 바꾸는지 이해한다.

1. state 쿠키 이해 확인

사용자의 이해는 거의 맞다. 다만 한 문장만 더 정확히 해야 한다.

“구글로 가는 요청에 쿠키를 담는다”가 아니라, 우리 백엔드의 /login/google 응답이 Set-Cookie와 302 Location을 같이 내려준다. 브라우저는 먼저 우리 도메인 쿠키를 저장하고, 그 다음 Google로 이동한다. 

1. 브라우저 -> 우리 백엔드
GET https://api.our-service.com/login/google

2. 우리 백엔드 -> 브라우저
Set-Cookie: oauth_state=abc123; HttpOnly; Secure; SameSite=Lax; Max-Age=300; Path=/oauth2/callback
302 Location: https://accounts.google.com/o/oauth2/v2/auth?...&state=abc123

3. 브라우저
oauth_state 쿠키를 api.our-service.com 쿠키 저장소에 저장
Location을 따라 Google로 이동

4. 브라우저 -> Google
GET https://accounts.google.com/o/oauth2/v2/auth?...&state=abc123

중요:
  oauth_state는 api.our-service.com 쿠키다.
  accounts.google.com 요청에는 붙지 않는다.

2. callback 때 쿠키와 query state를 비교한다

5. Google -> 브라우저
302 Location: https://api.our-service.com/oauth2/callback/google?code=...&state=abc123

6. 브라우저 -> 우리 백엔드 callback
GET /oauth2/callback/google?code=...&state=abc123
Cookie: oauth_state=abc123

7. 우리 백엔드
query state: abc123
cookie state: abc123

if query state == cookie state:
    통과
else:
    거절

SameSite=Lax는 이런 “외부 사이트에서 우리 사이트로 돌아오는 최상위 GET navigation”에서 쿠키가 붙을 수 있게 하는 데 자주 맞는다. SameSite=Strict로 두면 Google에서 우리 callback으로 돌아오는 상황에서 쿠키가 기대대로 안 붙을 수 있다.

3. 임시 state 쿠키는 지운다

검증 후에는 OAuth state 쿠키를 지운다. 보통 같은 이름, 같은 Path, 같은 Domain 조건으로 만료시킨다.

검증 성공 또는 실패 후:
Set-Cookie: oauth_state=; Max-Age=0; HttpOnly; Secure; SameSite=Lax; Path=/oauth2/callback

oauth_state 쿠키와 refresh_token 쿠키는 목적이 다르다. oauth_state는 OAuth callback 검증용 임시 쿠키이고, refresh_token은 로그인 유지용 쿠키다.

4. callback 이후 RT 쿠키만 있으면 프론트는 아직 모른다

callback 처리 완료:
Set-Cookie: refresh_token=RT; HttpOnly; Secure; SameSite=Lax; Path=/auth
302 Location: https://our-frontend.com/

브라우저:
refresh_token 쿠키를 저장
프론트 홈으로 이동

React 앱:
JavaScript로 refresh_token 값을 읽을 수 없음
따라서 첫 렌더링 시점에는 로그인 여부를 아직 모름

그래서 React 앱에는 loading, authenticated, anonymous 같은 인증 상태가 필요하다. 처음에는 loading으로 시작하고, 서버에 물어본 뒤 상태를 바꾼다.

5. React AuthProvider 구조

React에서는 보통 전역 인증 상태를 Context에 두고, 앱 시작 시 useEffect에서 /auth/refresh를 호출한다. useEffect는 컴포넌트가 화면에 추가된 뒤 외부 시스템과 동기화할 때 쓰는 Hook이다. 

import { createContext, useContext, useEffect, useMemo, useState } from "react";

const AuthContext = createContext(null);

export function AuthProvider({ children }) {
  const [status, setStatus] = useState("loading");
  const [accessToken, setAccessToken] = useState(null);
  const [user, setUser] = useState(null);

  useEffect(() => {
    let ignore = false;

    async function bootstrapAuth() {
      try {
        const response = await fetch("https://api.our-service.com/auth/refresh", {
          method: "POST",
          credentials: "include"
        });

        if (!response.ok) {
          throw new Error("Not authenticated");
        }

        const data = await response.json();

        if (!ignore) {
          setAccessToken(data.accessToken);
          setUser(data.user);
          setStatus("authenticated");
        }
      } catch {
        if (!ignore) {
          setAccessToken(null);
          setUser(null);
          setStatus("anonymous");
        }
      }
    }

    bootstrapAuth();

    return () => {
      ignore = true;
    };
  }, []);

  const value = useMemo(() => ({
    status,
    accessToken,
    user,
    isAuthenticated: status === "authenticated"
  }), [status, accessToken, user]);

  return (
    <AuthContext.Provider value={value}>
      {children}
    </AuthContext.Provider>
  );
}

export function useAuth() {
  const context = useContext(AuthContext);

  if (context == null) {
    throw new Error("useAuth must be used inside AuthProvider");
  }

  return context;
}

6. 헤더는 AuthContext를 보고 바뀐다

function Header() {
  const { status, user, isAuthenticated } = useAuth();

  if (status === "loading") {
    return <header>확인 중...</header>;
  }

  return (
    <header>
      {isAuthenticated ? (
        <>
          <span>{user.name}님 환영합니다</span>
          <button>로그아웃</button>
        </>
      ) : (
        <a href="https://api.our-service.com/login/google">로그인</a>
      )}
    </header>
  );
}

여기서 “로그인 되었음을 증명”하는 것은 프론트가 RT 쿠키를 읽어서 하는 게 아니다. 프론트가 /auth/refresh 또는 /me를 호출했고, 서버가 유효한 RT 쿠키를 확인한 뒤 사용자 정보를 응답했기 때문에 React state를 authenticated로 바꾸는 것이다.

7. access token은 API 호출에 붙인다

async function apiFetch(path, { accessToken, ...options }) {
  return fetch("https://api.our-service.com" + path, {
    ...options,
    headers: {
      ...options.headers,
      Authorization: `Bearer ${accessToken}`
    }
  });
}

이 설계에서 RT는 쿠키에 있고 JavaScript가 읽지 않는다. AT는 응답 body로 받아 메모리에 저장하고, API 요청의 Authorization 헤더에 붙인다. 새로고침하면 메모리의 AT는 사라지므로 다시 /auth/refresh를 호출한다.

8. credentials: include가 필요한 이유

프론트와 백엔드가 다른 origin이면 fetch가 쿠키를 자동으로 보내지 않을 수 있다. 그래서 credentials: "include"를 명시한다. 

await fetch("https://api.our-service.com/auth/refresh", {
  method: "POST",
  credentials: "include"
});

이 경우 백엔드 CORS 설정도 쿠키 허용에 맞아야 한다. 예: Access-Control-Allow-Credentials: true, 그리고 Access-Control-Allow-Origin: *는 사용할 수 없다.

9. 방식 B는 자주 쓰나?

방식 B, 즉 callback 후 일회성 로그인 티켓을 프론트로 넘기고 /auth/exchange에서 토큰을 교환하는 방식은 실무에서 사용할 수 있다. 다만 방식 A보다 구현 요소가 많다.

방식 A가 어울리는 경우

백엔드 callback에서 바로 RT 쿠키를 심고 홈으로 보내면 충분한 일반적인 SPA 로그인.

방식 B가 어울리는 경우

토큰 발급 결과를 일반 API 응답으로 통제하고 싶거나, OAuth 완료 화면에서 명시적인 후처리를 하고 싶을 때.

방식 B의 티켓은 URL에 노출되므로 짧은 만료, 1회 사용, 재사용 방지, 로그 마스킹이 필요하다. 단순 서비스라면 방식 A가 더 단순하다.
