STOMP와 Spring 메시징의 어휘: 프레임, Message, Channel, Handler

0031 레슨에서 "StompSubProtocolHandler가 STOMP 프레임을 Spring Message로 번역해서 clientInboundChannel에 싣고, SimpleBrokerMessageHandler가 그걸 집어간다"고 했다. 그런데 Message가 뭔지, Channel이 뭔지, Handler가 뭔지를 모르면 그 문장은 그냥 외운 주문일 뿐이다.

이 레슨의 목표. STOMP가 무엇인지 먼저 잡고, 그다음 Spring 메시징의 세 단어 (Message · MessageChannel · MessageHandler)를 "이건 사실 이렇게 생긴 자바 코드다" 수준까지 내려가서 이해한다. 이 셋만 알면 0031의 배관도가 전부 읽힌다.

1. STOMP란 무엇인가 — WebSocket이 정해주지 않는 것

WebSocket은 "이 연결로 양쪽이 아무 때나 바이트를 보낼 수 있다"까지만 정한다. 그 바이트가 무슨 뜻인지는 하나도 정해주지 않는다. 파이프만 뚫어주고 끝이다.

그래서 순수 WebSocket만 쓰면, 다음을 전부 직접 발명해야 한다.

직접 정해야 하는 것순수 WebSocket에서는STOMP에서는
"이 메시지가 무슨 요청인가" {"type":"subscribe", ...} 같은 걸 직접 정하고 서버에서 switch 프레임 첫 줄의 명령어가 이미 규격
"어느 주제를 원하는가" {"code":"005930"} 직접 파싱 destination 헤더가 이미 규격
"누가 무엇을 구독 중인가" Map<String, Set<Session>>을 손으로 관리 브로커가 대신 관리 (Spring이 구현해 줌)
"연결이 살아 있는가" ping/pong 규칙을 직접 정의 heart-beat 헤더로 협상
클라이언트 라이브러리 직접 작성 이미 존재 (여러 언어)

STOMP는 Simple Text Oriented Messaging Protocol의 약자다. 이름 그대로 텍스트 기반이고, 생김새가 HTTP와 거의 똑같다 — 명령어 한 줄 + 헤더들 + 빈 줄 + 본문.

SUBSCRIBE ← ① 명령어 (HTTP의 GET/POST 자리) id:sub-0 ← ② 헤더 destination:/topic/ticks/005930 ← ② 헤더 ← ③ 빈 줄: 여기부터 본문 (SUBSCRIBE는 본문이 없다) ^@ ← ④ NULL 바이트 하나로 프레임 종료

명령어는 전부 합쳐 10개 남짓이다. 이게 프로토콜의 전부다.

방향명령어뜻
클라이언트 →CONNECT세션 시작하자
SUBSCRIBE / UNSUBSCRIBE이 주소 구독할게 / 그만할게
SEND이 주소로 뭐 좀 보낼게
DISCONNECT끊을게
← 서버CONNECTED세션 시작됐다
MESSAGE네가 구독한 주소에 뭔가 왔다
ERROR / RECEIPT문제 생겼다 / 잘 받았다

STOMP는 WebSocket 전용이 아니다. 그냥 TCP 소켓 위에서도 돈다. WebSocket은 STOMP를 실어 나르는 운반 수단(transport) 중 하나일 뿐이다. 이 구분이 중요한 이유 — 서버가 2대가 되어 RabbitMQ 같은 진짜 브로커로 갈아탈 때, 클라이언트 코드는 한 줄도 안 바뀐다. 같은 STOMP 프레임을 그대로 쓴다.

비유하자면 WebSocket은 두 건물 사이에 뚫어둔 파이프고, STOMP는 그 파이프로 주고받을 편지의 양식이다 — 겉봉에 뭘 적을지(헤더), 내용은 어디서부터인지(빈 줄 다음), 편지 끝을 어떻게 표시할지(NULL 바이트). 파이프는 종이든 벽돌이든 다 통과시키지만, 양식이 있어야 받는 쪽이 읽을 수 있다.

2. Spring Message — 프레임을 자바 객체로 뜯어놓은 것

소켓에서 읽힌 것은 그냥 글자다. 자바 코드가 그 글자를 계속 문자열로 다루면 지옥이 된다. 그래서 StompSubProtocolHandler가 (내부적으로 StompDecoder를 써서) 딱 한 번 파싱해 객체로 바꾼다. 그 객체 타입이 org.springframework.messaging.Message다. 이 둘이 서로 다른 모듈에 산다는 사실은 §6에서 다시 본다.

인터페이스 전체가 이게 다다. 메서드 두 개.

public interface Message<T> { T getPayload(); // 내용물 MessageHeaders getHeaders(); // 겉봉에 적힌 것들 (Map<String, Object>) }

편지 봉투다. 겉봉(headers)에 배달 정보가 적혀 있고, 안에 내용물(payload)이 들어 있다. 그 이상도 이하도 아니다.

simpSessionId는 어디서 왔나? 클라이언트는 이 값을 보낸 적이 없다. 서버가 붙인 것이다 — 서버는 이 프레임이 어느 소켓으로 들어왔는지를 알기 때문이다. 브로커가 나중에 "누구에게 보낼지"를 아는 근거가 정확히 이 헤더 하나다. simpUser도 마찬가지로, 핸드셰이크 때 확정된 로그인 사용자가 여기 실린다.

payload는 왜 byte[]인가 — convertAndSend의 "convert"

프로토콜 경계에서 payload는 항상 바이트다. 소켓으로 나가는 것이 바이트이니 당연하다. 그런데 우리가 쓰는 코드는 Tick 같은 자바 객체를 다룬다. 그 사이를 메꾸는 것이 MessageConverter다.

방향변환일어나는 시점
들어올 때byte[] → OrderRequest @MessageMapping 메서드를 호출하기 직전
나갈 때Tick → byte[] (JSON) convertAndSend(...)를 호출하는 그 자리에서 바로

convertAndSend라는 이름이 그래서 붙었다 — convert(객체를 바이트로) 하고 send(채널에 넣기) 한다는 뜻이다. 두 동작이 이름에 그대로 들어 있다. 중요한 결과: JSON 직렬화는 발행 시점에 한 번만 일어나고, 브로커가 500명에게 복제할 때는 이미 만들어진 바이트 배열을 재사용한다. 직렬화가 500번 일어나지 않는다.

3. MessageChannel — 소켓이 아니라 JVM 안의 우편함이다

이름 때문에 가장 많이 오해하는 지점. clientInboundChannel의 "Channel"은 네트워크 채널이 아니다. TCP 연결도, 소켓도, NIO Channel도 아니다. 같은 JVM 안에서 객체를 다음 사람에게 넘기는 손잡이일 뿐이다.

인터페이스는 이번에도 어이없이 단순하다.

public interface MessageChannel { boolean send(Message<?> message); // 넣는다 } public interface SubscribableChannel extends MessageChannel { boolean subscribe(MessageHandler handler); // 받을 사람을 등록한다 }

Spring이 실제로 쓰는 구현체는 ExecutorSubscribableChannel이고, 안에는 딱 두 가지가 들어 있다 — 등록된 핸들러 목록과 스레드 풀.

그럼 왜 세 개인가

하나로 합쳐도 동작은 한다. 세 개로 나눈 이유는 방향과 목적이 다르고, 서로의 스레드 풀을 빼앗으면 안 되기 때문이다.

채널누가 넣나누가 꺼내나우체국 비유
clientInboundChannel StompSubProtocolHandler
(소켓에서 읽은 것)		 핸들러 3종
(/app, /user, 브로커)		 접수 창구 — 밖에서 들어온 우편물이 쌓이는 곳
brokerChannel 내 애플리케이션 코드
(SimpMessagingTemplate)		 SimpleBrokerMessageHandler 사내 발송함 — 안에서 만든 우편물을 넣는 곳
clientOutboundChannel 브로커
(복제된 메시지들)		 StompSubProtocolHandler 발송 창구 — 밖으로 나갈 우편물이 쌓이는 곳

이게 왜 실무에서 중요한가. 셋이 별도 스레드 풀이라서, 주문이 폭주해도 (inbound 포화) 시세 전송(outbound)은 계속 나간다. 반대로 outbound가 막혀도 주문 접수는 살아 있다. 하나로 합쳤다면 한쪽 폭주가 반대쪽을 굶겼을 것이다.

동시에 이건 0031 §9의 "느린 클라이언트 한 명이 남의 시세를 늦춘다" 문제의 정체이기도 하다 — clientOutboundChannel의 풀은 모든 사용자가 공유하기 때문이다.

4. MessageHandler — 그렇다, 콜백이 맞다

"Handler는 특정 이벤트가 발생했을 때 수행하는 콜백 같은 것 아닌가?" — 정확히 맞다. 인터페이스가 이렇게 생겼다.

public interface MessageHandler { void handleMessage(Message<?> message); }

메서드 하나짜리 인터페이스. channel.subscribe(handler)로 채널에 등록해 두면, 그 채널에 메시지가 들어올 때마다 채널이 handleMessage()를 불러준다. 등록해두면 알아서 불리는 함수 — 콜백의 정의 그대로다.

다만 한 가지만 보정하자. 콜백을 "상태 없는 함수"로 생각하기 쉬운데, SimpleBrokerMessageHandler는 상태를 가진 오래 사는 객체다. 애플리케이션이 뜰 때 한 번 만들어져서 죽을 때까지 살아 있고, 내부에 DefaultSubscriptionRegistry를 필드로 들고 있다.

그래서 정확한 표현은 "콜백 함수"가 아니라 "콜백 메서드를 가진, 구독 명부를 들고 있는 담당자"다. 우체국 비유로는 — 배달원이 아니라 구독자 명부를 관리하는 창구 직원.

SimpleBrokerMessageHandler가 실제로 하는 일 전부

handleMessage() 안은 사실상 메시지 타입에 따른 분기 하나다. 이게 브로커의 전부다.

들어온 메시지의 simpMessageType하는 일어느 채널에서 왔나
SUBSCRIBE레지스트리에 한 줄 추가
(목적지, 세션ID, 구독ID)		clientInbound
UNSUBSCRIBE레지스트리에서 그 한 줄 삭제clientInbound
DISCONNECT그 세션의 모든 줄 삭제clientInbound
MESSAGE레지스트리 조회 → 매칭된 구독 수만큼 복제해서
clientOutboundChannel로 send()		broker

여기서 가장 중요한 한 문장 — 브로커는 메시지를 저장하지 않는다.

브로커가 오래 보관하는 것은 구독 목록뿐이다. 틱 메시지는 들어와서 복제되고 clientOutboundChannel로 넘어가면 그 자리에서 끝이고, 곧 GC 대상이 된다.

그래서 구독하기 전에 발행된 틱은 영원히 볼 수 없다. (Kafka와 결정적으로 다른 지점이다 — Kafka는 로그에 남겨두고 나중에 온 컨슈머도 과거를 읽을 수 있다.) 0031 §4의 "스냅샷 공백" 문제가 존재하는 이유가 바로 이것이다.

브로커는 소켓을 만지지 않는다

"브로커가 매칭된 세션의 소켓에 바로 쓰는 건가?" — 아니다. 한 단계가 더 있다. 브로커는 소켓의 존재를 모른다. 세션 ID라는 문자열만 안다. 복제한 메시지의 헤더에 simpSessionId=s1을 박아서 clientOutboundChannel에 넣을 뿐이다.

그 문자열을 실제 소켓으로 바꾸는 것은 StompSubProtocolHandler다. 이 분리 덕분에 브로커는 WebSocket을 몰라도 된다 — 운반 수단이 바뀌어도 브로커 코드는 그대로다.

5. destination은 주소가 아니라 이름표다

SUBSCRIBE에 적은 목적지와, 나중에 서버가 보내는 MESSAGE의 목적지가 같은 문자열이라는 걸 눈치챘다면 정확하다. 그게 바로 매칭이 일어나는 원리다 — 같은 글자니까 레지스트리에서 찾아지는 것이다.

다만 SEND는 성격이 다르다. 세 프레임에서 destination이 하는 일이 각각 다르다.

프레임destination의 역할예MESSAGE와 같은 값인가
SUBSCRIBE등록 — "이 이름표를 내 옆에 적어줘" /topic/ticks/005930예 — 같아야 매칭된다
SEND라우팅 — "이 요청을 어느 핸들러로" /app/order아니오 — 전혀 다른 목적지로 답이 온다
MESSAGE출처 표시 — "이 메시지는 이 이름표로 발행됐다" /topic/ticks/005930—

SEND /app/order로 주문을 보냈다고 해서 /app/order로 답이 오지 않는다. /app은 애초에 브로커 주소가 아니라 아무도 구독할 수 없다. 답은 /user/queue/execution 같은 완전히 다른 목적지로 온다. 요청과 응답이 같은 주소를 쓰는 HTTP와 여기서 갈라진다.

그럼 destination은 무엇을 가리키는가 — 아무것도 안 가리킨다

HTTP의 URL은 장소를 가리킨다. 서버 어딘가에 그 리소스가 실제로 있다. STOMP의 destination은 아무것도 가리키지 않는다. 서버 안에 /topic/ticks/005930이라는 이름의 객체는 존재하지 않는다. 큐도 아니고 폴더도 아니고 방도 아니다. 그냥 비교당하는 문자열이다.

  • SUBSCRIBE 때 — "이 문자열을 내 이름 옆에 적어둬"
  • 발행 때 — "이 문자열이 적힌 사람 전부 찾아줘"

둘이 같으면 매칭. 그게 전부다. 서버도 브로커도 그 문자열의 의미는 모른다 — 005930이 삼성전자라는 건 사람만 안다. 목적지는 번지수가 아니라 잡지 이름에 가깝다. "005930 시세지"를 구독 신청하면 명부에 적히고, 그 잡지가 나올 때 명부에 적힌 사람에게 배달된다. "005930 시세지"라는 장소는 어디에도 없다.

"내가 구독한 것 중 어디"를 말하는 헤더는 따로 있다

MESSAGE 프레임에는 두 헤더가 같이 온다. 보통은 값이 1:1로 대응해서 구분이 안 보이지만, 나르는 정보가 다르다.

헤더뜻클라이언트가 쓰는 용도
subscription: sub-0"네가 등록한 구독 중 이거" 어느 콜백 함수로 넘길지 — 실제 라우팅 키
destination: /topic/ticks/005930"이 메시지는 이 이름표로 발행됐다" 그래서 구체적으로 무엇인지 식별

둘이 갈라지는 순간이 와일드카드 구독이다.

--- 클라이언트가 전 종목을 한 번에 구독 --- SUBSCRIBE id:sub-0 destination:/topic/ticks/* --- 그 뒤 도착하는 프레임들 --- MESSAGE subscription:sub-0 destination:/topic/ticks/005930 MESSAGE subscription:sub-0 destination:/topic/ticks/000660 MESSAGE subscription:sub-0 destination:/topic/ticks/035720 subscription 은 항상 같다 (내 구독은 하나니까) destination 은 매번 다르다 (실제로 어느 종목인지)

그래서 질문의 답은 — 반은 맞고, 헤더가 하나 더 있다. "클라이언트가 구독한 것 중 어디인가"를 말하는 것은 subscription 헤더이고, destination은 그와 별개로 "그게 구체적으로 무엇인지"를 알려준다. 와일드카드가 없으면 둘이 항상 짝지어 다녀서 같은 말처럼 보일 뿐이다.

실무 규칙: 클라이언트에서 메시지를 분기할 때는 destination 문자열이 아니라 구독 콜백 단위로 처리하자. 특히 /user 목적지는 브로커 내부에서 세션별 주소로 재작성되므로, 프레임에 실려 오는 destination이 구독할 때 적었던 /user/queue/execution과 다를 수 있다.

6. 지금까지 배운 것 중 WebSocket 기술은 하나도 없다

여기서 한 걸음 물러나면 놀라운 사실이 보인다. §2~§4에서 배운 Message · MessageChannel · MessageHandler · SimpleBrokerMessageHandler 중에서 WebSocket에 속한 것은 하나도 없다. 전부 spring-messaging이라는 별개 모듈의 것이다.

패키지 이름이 증거다. org.springframework.messaging.MessageChannel — web.socket이 어디에도 없다.

StompDecoder, StompEncoder, StompCommand …messaging.simp.stompspring-messaging
StompSubProtocolHandler, WebSocketAnnotationMethodMessageHandler org.springframework.web.socket.messagingspring-websocket

여기서 흔히 잘못 요약하는 것. "spring-websocket은 그냥 연결만 맺고 글자를 받아오고, 파싱부터는 spring-messaging이 한다"고 말하기 쉬운데 — STOMP 파싱조차 spring-messaging의 것이다. StompDecoder·StompEncoder가 거기 있다.

spring-websocket이 가진 것은 어댑터다. StompSubProtocolHandler는 "WebSocket 세션에서 읽은 바이트를 StompDecoder에 넘기고, 나온 Message를 clientInboundChannel에 태우는" 연결 담당이다. 파싱 자체를 하지 않는다.

상속 관계를 보면 더 분명하다 — WebSocketAnnotationMethodMessageHandler는 SimpAnnotationMethodMessageHandler(spring-messaging)를 상속한다. 프로토콜 중립 로직이 아래, WebSocket 특화가 위라는 층이 코드에 그대로 새겨져 있다.

이 분리가 실제로 만들어내는 것 세 가지

결과왜 가능한가
SimpleBroker → RabbitMQ 릴레이로 교체해도
컨트롤러 코드가 안 바뀐다		 StompBrokerRelayMessageHandler도 같은 MessageHandler다. brokerChannel에 등록되는 객체만 바뀐다. (0031 §9의 "서버 2대" 시나리오)
WebSocket 없이 TCP 위에서 STOMP를 써도 같은 코드 STOMP 관련 클래스가 전부 spring-messaging에 있어서 WebSocket을 안 끌어와도 된다.
여기서 배운 어휘가 Spring Integration에서도 그대로 통한다 Spring Integration도 같은 Message/MessageChannel 위에 서 있다. 이 레슨은 WebSocket 지식이 아니라 스프링 메시징 지식이다.

7. 한 장으로 정리 — 우체국 비유

Spring 용어정체우체국이라면
WebSocket양방향 바이트 통로건물 사이에 뚫린 기송관

이 비유로 0031의 틱 전달을 다시 읽으면 이렇게 된다 — 스케줄러가 "005930 앞으로" 라고 겉봉에 적은 편지 한 통을 사내 발송함에 넣는다. 창구 직원이 그걸 꺼내 명부를 펼치고, 005930을 구독한 사람이 s1과 s2임을 확인한다. 편지를 두 부 복사해 각각 "s1 앞", "s2 앞"이라 겉봉을 고쳐 쓰고 발송 창구에 놓는다. 기송관 담당자가 그걸 집어 각 건물로 쏘아 보낸다. 원본 편지는 버린다.
