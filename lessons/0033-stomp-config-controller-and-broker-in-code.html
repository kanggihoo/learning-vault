코드로 보는 전체 흐름: 설정, 컨트롤러, SimpleBroker

0031에서 흐름을, 0032에서 어휘를 봤다. 이번엔 그 둘을 실제 코드 위에 얹는다 — 설정 파일 한 장과 컨트롤러 한 장이 지금까지 배운 부품들을 어떻게 조립하는지, 그리고 메서드가 끝나면 메시지가 어디까지 가는지.

1. 먼저 오해 하나 — /app/chat/send는 URL이 아니다

@MessageMapping("/chat/send")를 보면 ws://localhost:8080/chat/send 같은 주소가 생긴다고 착각하기 쉽다. 그렇지 않다.

건물 정문은 하나고, 호실 번호가 여러 개다. 정문을 통과한 뒤 편지 겉봉에 "302호"라고 적는 것이 destination이다. 302호로 가는 따로 난 문이 있는 게 아니다.

2. 설정 한 장이 부품을 조립한다

0032에서 배운 채널과 핸들러들이 어디서 만들어지는가에 대한 답이 이 파일이다. 세 줄이 전부다. 

@Configuration
@EnableWebSocketMessageBroker          // 이 한 줄이 3개 채널을 만든다
public class WebSocketConfig implements WebSocketMessageBrokerConfigurer {

    // ① 정문 — 진짜 URL. 여기로 핸드셰이크가 들어온다.
    @Override
    public void registerStompEndpoints(StompEndpointRegistry registry) {
        registry.addEndpoint("/ws-stomp")
                .setAllowedOrigins("https://trade.example.com");   // CSWSH 방어 (0031 §2)
    }

    @Override
    public void configureMessageBroker(MessageBrokerRegistry registry) {
        // ② "/app" 으로 시작하면 → @MessageMapping 컨트롤러로
        registry.setApplicationDestinationPrefixes("/app");

        // ③ "/topic", "/queue" 로 시작하면 → SimpleBroker 로
        //    ⭐ 이 한 줄이 SimpleBrokerMessageHandler 를 만들어 채널에 등록한다
        registry.enableSimpleBroker("/topic", "/queue");

        // ④ "/user" 는 세션별 주소로 재작성 (0031 §6)
        registry.setUserDestinationPrefix("/user");
    }
}
이 줄이만드는 것어느 채널에 등록되나
@EnableWebSocketMessageBroker3개 채널 자체—
addEndpoint("/ws-stomp")StompSubProtocolHandler를 물린 소켓 핸들러clientOutbound를 구독
setApplicationDestinationPrefixes("/app")SimpAnnotationMethodMessageHandlerclientInbound
enableSimpleBroker("/topic","/queue")SimpleBrokerMessageHandlerclientInbound + broker
setUserDestinationPrefix("/user")UserDestinationMessageHandlerclientInbound + broker

enableSimpleBroker()를 지우면 브로커가 아예 없어진다. 그러면 /topic/...을 구독해도 아무 일도 안 일어나고, convertAndSend("/topic/...")은 갈 곳이 없다. 이 한 줄을 enableStompBrokerRelay("/topic","/queue")로 바꾸면 RabbitMQ 같은 외부 브로커로 갈아탄다 — 컨트롤러 코드는 한 줄도 안 바뀐다. (0032 §6의 모듈 분리가 만들어낸 결과)

정확히 하면 — "SimpleBroker = 장부"가 아니라 "SimpleBroker = 장부를 들고 있는 담당자"다. Spring 문서가 Simple Broker라고 부르는 것의 실제 클래스 이름은 SimpleBrokerMessageHandler이고, 장부는 그 안에 필드로 들어 있는 DefaultSubscriptionRegistry다.

이 구분이 실제로 쓸모 있는 순간 — "브로커를 재시작하면 구독이 날아간다"는 말의 정확한 의미는 브로커 객체가 새로 만들어지면서 그 안의 레지스트리도 빈 상태로 다시 생긴다는 뜻이다. (0032 §4의 "상태를 가진 콜백")

4. 갈림길 — destination 앞글자가 목적지를 정한다

컨트롤러를 찾아 실행해 주는 것은 브로커가 아니다. 그 일은 SimpAnnotationMethodMessageHandler가 한다 — HTTP에서 DispatcherServlet이 URL을 보고 컨트롤러를 찾아 부르는 것과 같은 역할이다. 브로커는 @MessageMapping이 존재하는지도 모르고, 컨트롤러가 brokerChannel에 뭔가 넣어야 비로소 움직인다.

또 하나 — SimpleBroker에서 /queue는 /topic과 동작이 똑같다. "큐라서 1:1이고 저장된다"는 건 RabbitMQ 같은 외부 브로커로 바꿨을 때의 이야기다 (0034). 지금은 /queue가 개인용이라는 이름 관례일 뿐이다.

5. @MessageMapping도 컨트롤러다

HTTP 컨트롤러와 완전히 같은 개념이고, 실제로 같은 @Controller 어노테이션을 쓴다.

도는 스레드서블릿 요청 스레드clientInboundChannel 워커 스레드
 
@Controller
public class ChatController {

    // 클라이언트가 보낸 destination:/app/chat/send 에서
    // "/app" 이 떨어지고 남은 "/chat/send" 가 여기 매칭된다
    @MessageMapping("/chat/send")
    public void sendMessage(ChatMessage message, Principal principal) {
        // JSON 본문 → ChatMessage 로 변환된 채로 들어온다 (MessageConverter)
        // principal 은 핸드셰이크 때 확정된 로그인 사용자 (0031 §2)
        String username = principal.getName();
        log.info("{}님이 메시지를 보냈습니다: {}", username, message.getContent());
    }
}

여기서 오래 걸리는 일을 하면 안 된다. 이 메서드는 clientInboundChannel의 공용 워커 스레드에서 돈다 (0032 §3). 무거운 DB 조회나 외부 API 호출을 여기서 직접 하면 그 스레드가 묶이고, 다른 사용자의 주문 접수까지 밀린다. 오래 걸리는 일은 별도 실행기로 넘기고, 결과는 나중에 SimpMessagingTemplate으로 밀어주는 게 맞다.

6. 그래서 어디까지 진행되는가 — 반환값이 만드는 차이

위 코드는 void이고 아무것도 보내지 않는다. 그래서 서버 콘솔에 로그만 남고 완전히 끝난다. 다른 사람은커녕 보낸 사람에게도 아무것도 가지 않는다.

[클라이언트] │ ① SEND destination:/app/chat/send ▼ [StompSubProtocolHandler] → Message 로 변환 → clientInboundChannel │ ② 접두사 /app → SimpAnnotationMethodMessageHandler ▼ [ChatController.sendMessage() 실행] │ ③ JSON → ChatMessage 변환 │ ④ Principal 주입 │ ⑤ log.info(...) ▼ 🛑 여기서 끝. brokerChannel 로 아무것도 안 들어간다.

메시지가 더 나아가려면 다섯 가지 방법 중 하나를 써야 한다.

메서드 모양반환값이 가는 곳쓸 곳
void + 아무것도 안 함아무 데도 안 간다기록만 남기는 경우
return X; (어노테이션 없음) 기본 목적지 — 입력의 /app을 브로커 접두사로 치환.
/app/chat/send → /topic/chat/send		 규칙이 단순할 때
@SendTo("/topic/room/1")명시한 목적지의 구독자 전원채팅방 브로드캐스트
@SendToUser("/queue/errors")그 사용자의 세션(들)개인 응답·에러
SimpMessagingTemplate 직접 호출 원하는 곳에, 몇 번이든, 나중에라도 실무에서 가장 많이 쓴다

어느 방법을 쓰든 그다음 길은 똑같다. 반환값이든 convertAndSend든 결국 brokerChannel → SimpleBrokerMessageHandler → 레지스트리 조회 → clientOutboundChannel을 탄다. 0031 §5에서 본 틱 스케줄러와 정확히 같은 경로다 — 출발점만 다를 뿐이다.

7. 모의투자로 옮기면 — 주문 한 건의 전체 여정

@Controller
@RequiredArgsConstructor
public class OrderController {

    private final OrderService orderService;

    @MessageMapping("/order")                // destination:/app/order
    public void submit(OrderRequest req, Principal principal) {
        orderService.submit(principal.getName(), req);
        // void 다. 여기서 응답을 만들지 않는다 — 왜인지는 아래에
    }
}

@Service
@RequiredArgsConstructor
public class OrderService {

    private final SimpMessagingTemplate template;   // 스케줄러가 쓰는 것과 같은 도구

    public void submit(String userId, OrderRequest req) {
        Order order = orderBook.place(userId, req);
        // ① 접수됨을 즉시 알린다 → 그 사용자에게만
        template.convertAndSendToUser(userId, "/queue/orders", OrderAccepted.of(order));
    }

    // ② 체결은 나중에, 가상 시계가 그 가격에 닿았을 때 일어난다
    public void onFilled(Order order) {
        template.convertAndSendToUser(order.userId(), "/queue/executions", Fill.of(order));
        template.convertAndSend("/topic/ticks/" + order.code(), Tick.of(order));
    }
}

왜 @SendToUser가 아니라 template인가. @SendToUser는 메서드가 리턴하는 그 순간에 한 번 보낸다. 그런데 모의투자에서 체결은 주문 접수와 다른 시점에 일어난다 — 지정가 주문은 가상 시계가 그 가격에 닿아야 체결된다. 메서드가 리턴할 때는 아직 결과가 없다.

그래서 "접수됐다"와 "체결됐다"를 각각 다른 시점에 보내야 하고, 그건 반환값으로는 불가능하다. SimpMessagingTemplate은 아무 때나, 몇 번이든, 어느 스레드에서든 보낼 수 있다 — 이게 틱 스케줄러가 쓰는 도구와 같은 이유이기도 하다.

정리하면 이 주문 한 건이 지나는 길은 이렇다.

SEND /app/order → clientInboundChannel (접두사 /app) → OrderController.submit() (inbound 워커 스레드) → OrderService.submit() → template.convertAndSendToUser(...) → brokerChannel → UserDestinationMessageHandler → /queue/orders-s1 로 재작성 → SimpleBrokerMessageHandler → 레지스트리 조회 → clientOutboundChannel → StompSubProtocolHandler → MESSAGE 프레임 인코딩 → 소켓 s1 ...그리고 한참 뒤, 가상 시계가 그 가격에 닿으면 onFilled() → template → brokerChannel → ... (같은 길을 다시)
