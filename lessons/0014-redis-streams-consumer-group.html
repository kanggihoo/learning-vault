Redis Streams Consumer Group: 작업 분배와 회수

목표: 이전 레슨에서 Outbox가 메시지를 Redis Stream에 발행하는 것까지 봤다. 이제 그 메시지를 여러 Worker가 어떻게 나눠 가져가고, 한 Worker가 죽었을 때 그 작업을 누가 어떻게 회수하는지를 설명할 수 있게 된다. 핵심은 Consumer Group, PEL(Pending Entries List), XACK, XAUTOCLAIM 네 개다.

📐 그림으로 먼저 보고 싶다면: Redis Streams 내부 구조 시각화 — Producer/Redis/Worker 배치도, Stream 엔트리 해부, PEL이 시간에 따라 변하는 5단계 타임라인, 그리고 "worker 개수 = 서버 개수인가?"에 대한 답이 SVG로 그려져 있다. 이 레슨의 3~5절을 읽다 막히면 그 그림으로 돌아오면 된다.

0. 이전 레슨과의 연결 — 발행까지는 봤다, 그 다음?

Outbox 레슨(0013)의 끝:
  DB commit → Spring이 즉시 XADD → Redis Stream jobs:ai 에 메시지 한 줄 추가

질문: 그 메시지는 이제 누가 가져가나?
  → jobs:ai Stream을 "구독"하고 있는 Python AI Worker 들이 가져간다.
  → 그런데 Worker가 3대면, 한 작업이 3번 다 실행되나? 아니면 1번?
  → 이걸 결정하는 것이 Consumer Group 이다.

Consumer Group이 없는 plain XREAD는 모든 Worker가 모든 메시지를 다 받는다. 같은 AI 분석이 3번 실행되는 셈. Worker가 작업을 "나눠" 가져가려면 Consumer Group이 필요하다.

1. Consumer Group이 푸는 문제: "한 작업은 한 Worker만"

Sixmen 아키텍처 문서에 이 문장이 있다:

"여러 Python Worker가 있어도 하나의 AI 작업은 한 Worker만 처리합니다."

이 보장을 만드는 장치가 Consumer Group이다. Stream을 하나의 그룹으로 묶어서 구독하면, Redis가 들어오는 메시지를 그룹 안의 Worker들에게 하나씩만 분배한다. Stream이 곧 분배 단위가 아니라, "이 그룹이 아직 안 읽은 메시지"를 추적한다. 

Stream: jobs:ai   (메시지 줄: A → B → C → D)

Consumer Group: ai-workers
  ├─ ai-worker-1
  ├─ ai-worker-2
  └─ ai-worker-3

XADD로 A,B,C,D가 순서대로 들어오면 Redis가 분배:
  ai-worker-1 ← A, D      (2개)
  ai-worker-2 ← B         (1개)
  ai-worker-3 ← C         (1개)
→ 각 메시지는 정확히 한 Worker에게만 간다. 중복 실행 없음.

비유: Stream은 컨베이어 벨트 위의 상자 줄. Consumer Group은 "이 벨트를 감시하는 작업반". 작업반장(Redis)이 상자를 작업반원(Worker)들에게 하나씩만 돌린다. 같은 상자를 두 사람이 동시에 여는 일이 없다.

2. 핵심 명령어 네 개 — 이것만 기억하면 흐름이 보인다

Consumer Group의 동작은 명령어 네 개로 완성된다. 각각 "누가 언제 호출하느냐"가 핵심이다.

① XGROUP CREATE

최초 한 번, Stream에 Consumer Group을 만든다.
XGROUP CREATE jobs:ai ai-workers $ MKSTREAM
$ = "이 그룹은 만들어진 시점 이후의 새 메시지만 본다" (과거 것 무시).

② XREADGROUP

Worker가 계속 호출. 메시지를 가져온다.
XREADGROUP GROUP ai-workers worker-1 BLOCK 0 COUNT 10 STREAMS jobs:ai >
> = "아무에게도 배달 안 된 새 메시지". 이게 핵심 특수 기호.
BLOCK은 폴링 주기가 아니라 최대 대기 시간 — 시각화 3절.

③ XACK

Worker가 처리 성공 후 호출. "다 했다" 알림.
XACK jobs:ai ai-workers <message-id>
안 하면 메시지가 영원히 PEL에 남는다.

④ XAUTOCLAIM

정기적으로 호출 (보통 다른 Worker 또는 별도 스레드).
죽은 Worker의 메시지를 회수.
XAUTOCLAIM jobs:ai ai-workers worker-2 60000 0

3. 왜 XACK를 명시적으로 해야 하나? — PEL(Pending Entries List)

가장 많이 헷갈리는 점: "메시지를 읽으면(XREADGROUP) 자동으로 끝나는 거 아닌가?" 아니다. 읽는 것과 "처리 완료"는 다르다. 읽기만 하면 메시지는 사라지지 않는다.

XREADGROUP으로 메시지를 받는 순간, Redis는 그 메시지를 PEL(Pending Entries List)라는 목록에 적는다. "이 메시지를 Worker에게 줬는데, 처리 끝났는지는 아직 모른다"는 뜻이다. 메시지가 PEL에서 빠지는 유일한 방법은 Worker가 XACK를 호출하는 것이다. 

Worker 정상 루프:
  1. XREADGROUP ... STREAMS jobs:ai >     → 메시지 M 수신, M은 PEL에 들어감
  2. AI 작업 실행 (수 분 걸림)
  3. XACK jobs:ai ai-workers M             → "성공, 끝" → M이 PEL에서 제거됨

만약 2번 도중 Worker가 죽으면?
  → XACK 호출 못 함 → M은 PEL에 영원히 남음
  → "누군가 저 M을 다시 처리해야 한다"는 신호가 됨

왜 이렇게 번거롭게? Worker가 메시지를 받자마자 "끝"으로 표시하면, 처리 도중 죽었을 때 그 작업은 영영 사라진다. PEL + XACK는 "확실히 끝났다는 확인이 있기 전까지는 미완료로 간주하겠다"는 보수적 설계다. at-least-once를 만드는 장치 중 하나.

PEL 안에 정확히 무엇이 들어 있는지(소유 consumer · idle 시간 · delivery count)와 엔트리 하나가 XADD → 배달 → 사망 → 회수 → XACK를 거치며 PEL이 어떻게 변하는지는 시각화 자료의 3~4절에 표와 타임라인으로 그려두었다.

여기서 자주 놓치는 것: XACK는 PEL에서만 지운다. Stream에서는 엔트리가 그대로 남는다. 즉 Stream은 읽어도 줄어들지 않는다. XADD jobs:ai MAXLEN ~ 10000 * 처럼 길이를 잘라주지 않으면 메모리가 무한히 늘어난다.

4. Worker가 죽었을 때 — PEL이 회수의 단서가 된다

Sixmen 아키텍처 문서의 이 문장이 PEL과 직결된다:

"Worker가 죽어 ACK하지 못한 메시지는 Pending 상태가 되고, 다른 Worker가 일정 시간 뒤 XAUTOCLAIM으로 회수합니다." 
상황: ai-worker-1이 메시지 M을 받고 AI 분석 도중 OOM으로 사망
  → M은 PEL에 남음, 소유자 = ai-worker-1, idle time = 계속 증가

시간 경과 (예: 60초)
  → 다른 Worker(또는 회수 전용 루프)가 주기적으로 XPENDING / XAUTOCLAIM 실행
  → "ai-worker-1 소유의 M이 60초 이상 idle 이네? 아마 죽었거나 멈췄다"
  → XAUTOCLAIM이 M의 소유권을 회수 Worker로 가져옴
  → 회수 Worker가 M을 다시 처리 → 성공 시 XACK

XAUTOCLAIM의 핵심: min-idle-time

XAUTOCLAIM jobs:ai ai-workers worker-2 60000 0에서 60000이 바로 이 장치의 심장이다. "idle time이 최소 60초 지난 pending 메시지만 회수하라"는 뜻이다.

왜 최소 시간을 두나? Worker가 정상적으로 천천히 처리 중일 수도 있기 때문이다. 긴 AI 작업은 수 분 걸린다. "5초 동안 ack 없다"고 해서 죽었다고 단정하면, 돌아가고 있는 Worker의 작업을 빼앗아 중복 처리가 된다. min-idle-time은 "이 정도면 정상 처리가 아니라 죽었거나 멈춘 것으로 보자"는 임계값이다.

회수 조건

메시지가 PEL에 있고 (마지막 배달 시점으로부터) idle time ≥ min-idle-time. Sixmen에선 보통 lease 만료 시간과 짝을 맞춘다 (아키텍처의 "PROCESSING 작업에 lease 만료 시간").

회수 부작용

delivery count가 증가한다. M이 3번 회수됐다 = 3번 재시도됐다. 이 카운트가 한계치를 넘으면 DLQ로 보낸다 (Outbox 레슨의 FAILED/DLQ와 동일 맥락).

5. XREADGROUP의 두 모드 — >와 0 (이 구분이 자주 틀림)

XREADGROUP의 마지막 인자가 >냐 0냐에 따라 완전히 다른 메시지가 온다. 이 둘을 헷갈리면 "왜 내 pending 메시지가 안 보이지?"가 된다.

> = 새 메시지만

"아직 아무에게도 배달되지 않은" 메시지.
정상 작업 루프에서 쓴다. 다른 Worker가 이미 가져간 것은 안 온다.
STREAMS jobs:ai >

0 = 내 pending만

"이전에 내게 배달됐는데 아직 XACK 안 한" 메시지.
Worker 재시작 직후 자기 PEL을 복구할 때 쓴다.
STREAMS jobs:ai 0

Worker 재시작 직후 표준 패턴 (공식 문서의 권장 루프):

1. 먼저 자기 PEL을 비운다: XREADGROUP ... STREAMS jobs:ai 0
   → 이전에 받아놓고 죽기 직전이던 메시지들을 먼저 처리 + XACK
2. PEL이 비면 (0이 빈 응답 주면) 그제야 새 메시지: XREADGROUP ... STREAMS jobs:ai >

→ 순서 중요: 자기가 미처 못 끝낸 것을 먼저, 그 다음 새 것.
  안 그러면 재시작 때마다 이전 작업이 방치된다.

정리: >는 "앞으로 들어올 새 작업", 0는 "내가 과거에 받았지만 아직 못 끝낸 작업". Worker는 두 모드를 상황에 따라 쓴다. 죽은 남의 작업 회수는 XREADGROUP이 아니라 XAUTOCLAIM이 한다.

6. 전체 흐름 — Outbox 발행부터 Worker 회수까지 한 줄로

[발행 쪽 — Outbox 레슨 0013]
  DB commit → Spring 즉시 XADD → Stream jobs:ai 에 메시지 M 추가

[분배 쪽 — 이 레슨]
  M → Consumer Group ai-workers 가 "아직 안 읽은 메시지"로 추적
    → XREADGROUP ... > 로 worker-1 이 M을 가져감 → M은 PEL로 (소유자=worker-1)

[정상 처리]
  worker-1 이 AI 실행 → 성공 → XACK → M이 PEL에서 제거. 끝.

[Worker 사망 시 회수]
  worker-1 이 XACK 전 사망 → M은 PEL에 남음, idle time 증가
    → 회수 루프가 XAUTOCLAIM ... 60000 0 실행 (idle ≥ 60초인 것 회수)
    → worker-2 가 M 소유권 획득, delivery count 증가
    → worker-2 가 M 재처리 → 성공 → XACK
    → 반복 실패로 delivery count 한계 도달 → DLQ (Outbox 레슨의 FAILED와 합류)

7. XPENDING — PEL을 들여다보는 창

XPENDING은 PEL의 상태를 보여주는 읽기 전용 명령이다. 운영에서 "뭐가 안 끝나고 있나?" "어느 Worker가 작업을 들고 있나?"를 확인할 때 쓴다. 

요약 형태 (인자 최소):
  XPENDING jobs:ai ai-workers
  → 1) 총 pending 수
    2) 가장 오래된/최신 pending ID
    3) consumer별 pending 수  (누가 작업 들고 있는지 한눈에)

상세 형태 (범위 지정):
  XPENDING jobs:ai ai-workers - + 10
  → 메시지별: ID, 소유자 consumer, idle 시간(ms), delivery 횟수
  → "이 메시지가 5번이나 재전달됐네? 뭔가 처리가 계속 실패하고 있다"를 발견

XPENDING 자체는 회수를 안 한다. 상태를 보는 것이다. 실제 회수 동작은 XAUTOCLAIM(또는 XCLAIM)이 한다. XPENDING은 "점검", XAUTOCLAIM은 "실행"으로 나누면 된다.

8. Sixmen 아키텍처와 연결 — 왜 이렇게 됐는가

Stream을 왜 4개로 나눴나

아키텍처 문서: jobs:integration, jobs:notification, jobs:ai, events:ai-result.
하나의 거대 Stream + Consumer Group으로도 분배는 되지만, 종류별 Worker 풀을 분리하려면 Stream 자체를 나누는 게 자연스럽다. AI 작업과 동기화 작업이 서로를 블록킹하지 않는다.

ai-worker-N 은 왜 여러 개인가

LLM 호출은 길고(수 분) CPU/GPU 바운드. 한 Worker가 한 작업을 붙잡고 있으면 병목. Consumer Group으로 여러 Worker가 작업을 병렬 분산 → 처리량 확장. 아키텍처의 "AI 작업량이 늘면 Python Worker만 수평 확장"이 이걸 가리킨다.
Worker 개수만큼 서버가 필요한 건 아니다 — 시각화 5절 참고.

lease 만료 = min-idle-time

아키텍처 "PROCESSING 작업에 lease 만료 시간"과 XAUTOCLAIM의 min-idle-time은 같은 임계값을 가리킨다. "이 시간 지나도 ack 없으면 죽은 것으로 보고 회수" — DB lease와 Redis PEL이 짝.

DLQ 합류점

Outbox 레슨의 "발행 실패 DLQ"와 Consumer Group의 "처리 재시도 실패 DLQ"는 결국 같은 개념. delivery count가 한계치를 넘으면 FAILED 상태 + DLQ로 에스컬레이션. 운영자 개입 지점.

9. "Consumer Group 없이 그냥 XREAD만 쓰면 안 되나?"

자연스러운 질문. XREAD만 쓰면 Consumer Group 없이도 Stream에서 읽을 수 있다. 하지만 분배/추적/회수 세 가지가 전부 안 된다.

분배

XREAD만: 모든 Worker가 모든 메시지 수신 → 같은 작업 N번 실행.
Consumer Group: 한 메시지 = 한 Worker. 중복 없음.

추적(PEL)

XREAD만: 누가 뭘 처리 중인지 Redis가 모름.
Consumer Group: PEL로 "누가 어떤 메시지 들고 있나" 추적.

회수

XREAD만: Worker 죽으면 그 메시지는 그냥 없어짐. 회수 불가.
Consumer Group: PEL에 남아있으니 XAUTOCLAIM이 회수 가능.

XACK(확정)

XREAD만: "읽었다"의 개념 자체가 없음.
Consumer Group: XACK로 "확실히 끝냄" 명시 → at-least-once의 짝.

결론: Worker 분산 + 장애 복구가 필요하면 Consumer Group은 선택이 아니라 전제다. XREAD만 쓰는 건 "브로드캐스트 구독"(모두가 다 받음)이지 작업 분배가 아니다.

10. 판단 기준 요약

Consumer Group이 필요한 신호:
  - 하나의 Stream을 여러 Worker가 나눠 처리해야 한다
  - 같은 작업이 두 번 실행되면 안 된다
  - Worker가 죽어도 그 작업을 잃지 않고 회수해야 한다

Consumer Group이 주는 것:
  - 메시지 분배: 한 메시지 = 한 Worker
  - PEL: "배달됐지만 아직 ack 안 됨" 추적
  - XACK: "확실히 처리 완료" 명시
  - XAUTOCLAIM: 죽은 Worker의 작업 회수 (min-idle-time 임계값)

대가:
  - at-least-once → Consumer는 멱등해야 한다 (다음 레슨)
  - 회수된 메시지는 delivery count 증가 → DLQ로 에스컬레이션
