목표: Apache Kafka Documentation: Kafka Connect Configs 원문 중 실제로 자주 마주치는 설정만 골라, "Kafka Connect가 뭘 하는 도구인지"부터 시작해서 이해한다. 0016 레슨의 Consumer Group 개념과 0019 레슨의 복제·offset 개념을 발판으로 쓴다.

0. Kafka Connect가 뭔가 — 왜 코드를 직접 안 짜도 되나

Kafka로 데이터를 넣거나(예: PostgreSQL의 변경 내용을 Kafka로) 꺼내는(예: Kafka에 쌓인 데이터를 S3로) 작업은 사실 아주 흔한 패턴이다. 이걸 매번 Producer/Consumer 코드를 직접 짜서 만들면, 재시도·재연결· 스키마 변환 같은 뻔한 처리를 팀마다 반복해서 구현하게 된다. Kafka Connect는 이런 "Kafka 안으로 넣기(source)"와 "Kafka 밖으로 꺼내기(sink)"를 이미 만들어진 커넥터(플러그인)를 설정 파일만 채워서 쓰는 방식으로 표준화한 프레임워크다.

용어뜻
Source Connector외부 시스템 → Kafka로 데이터를 밀어넣는 커넥터 (예: DB 변경 감지 → Kafka)
Sink ConnectorKafka → 외부 시스템으로 데이터를 꺼내는 커넥터 (예: Kafka → S3, Kafka → Elasticsearch)
Worker커넥터를 실제로 실행하는 프로세스 — Standalone(1대) 또는 Distributed(여러 대) 모드로 뜬다
Task커넥터 하나가 내부적으로 나뉘는 병렬 작업 단위 — tasks.max로 개수 조절

Standalone vs Distributed — Worker도 사실 Consumer Group처럼 조율된다

Standalone mode는 워커 프로세스 하나가 혼자 커넥터를 실행한다 — 로컬 테스트나 간단한 용도에 적합하고, 상태는 로컬 파일에 저장된다. Distributed mode는 여러 워커가 group.id로 지정된 하나의 Connect 클러스터를 이루고, 커넥터·task를 서로 나눠 맡는다. 이 조율 방식은 0016 레슨에서 배운 Consumer Group의 파티션 재배정과 원리가 같다 — 워커 하나가 죽으면 그 워커가 맡던 커넥터/task가 살아있는 다른 워커에게 재배정된다. 그래서 실무에서는 거의 항상 Distributed mode를 쓴다.

왜 Connect 자신도 Kafka 토픽에 상태를 저장하나

Distributed mode의 워커들은 로컬 디스크에 상태를 저장하면 서로 그 상태를 공유할 방법이 마땅치 않다. 그래서 Connect는 자기 자신의 상태(어디까지 처리했는지, 커넥터 설정이 뭔지, 지금 커넥터가 정상인지)를 전부 Kafka 내부 토픽에 저장한다 — 이건 0019 레슨에서 봤던 "Kafka Streams가 자기 offset도 Kafka 토픽에 저장해서 정확히 한 번 처리를 얻는다"는 아이디어와 같은 결이다. 워커가 죽었다 다른 곳에서 다시 뜨더라도, 이 토픽들만 읽으면 어디까지 했는지 그대로 복구된다.

이 세 토픽(offset/config/status)이 유실되면 Connect 클러스터 전체가 자기 상태를 잃는 것과 같다. 그래서 replication factor 기본값이 3이다 — 0019 레슨 §8의 ISR/복제 안전성 원칙이 여기에도 그대로 적용된다.

1. Worker 설정 핵심

설정뜻
bootstrap.serversKafka 클러스터 접속 주소 목록 (Producer/Consumer와 동일한 개념)
group.id이 워커가 속한 Connect 클러스터 식별자 — Distributed mode 필수
key.converter / value.converterKafka에 넣고 뺄 때 어떤 포맷(JSON, Avro 등)으로 변환할지 — 커넥터와 무관하게 독립적으로 지정
offset.storage.topic / config.storage.topic / status.storage.topic위에서 설명한 Connect의 "기억" 토픽 3종
{offset|config|status}.storage.replication.factor기본값 3 — 함부로 낮추지 말 것
plugin.path커넥터 플러그인 jar들이 있는 경로

보안 설정(security.protocol, sasl.*, ssl.*)은 Producer/Consumer와 완전히 동일한 구조를 그대로 쓴다 — 새로 배울 게 없다.

2. Connector 설정 핵심 — Source/Sink 공통

설정뜻
name커넥터의 고유 이름
connector.class어떤 커넥터 구현체를 쓸지 (예: FileStreamSinkConnector)
tasks.max이 커넥터를 몇 개 task로 병렬화할지 — 기본값 1, 처리량이 부족하면 늘림
topics / topics.regex (sink 전용)이 sink connector가 읽어올 토픽 목록 또는 정규식 — 둘 중 하나만 지정

에러 처리 — 하나가 실패하면 커넥터 전체가 멈춰야 하나?

기본값(errors.tolerance=none)은 레코드 하나만 잘못돼도 커넥터 task 전체가 멈춘다 — 안전하지만 운영 부담이 크다. errors.tolerance=all로 바꾸면 문제가 있는 레코드는 건너뛰고 계속 진행한다. 이때 건너뛴 레코드를 그냥 버리지 않고 errors.deadletterqueue.topic.name으로 지정한 별도 토픽(DLQ, Dead Letter Queue)에 따로 쌓아두면, 나중에 그 레코드들만 골라서 원인을 조사하거나 재처리할 수 있다 — sink connector에서만 쓸 수 있는 옵션이다.

SMT(Single Message Transform) — 메시지를 살짝 가공해서 흘려보내기

transforms 설정에 alias를 나열하면, 커넥터를 거치는 각 메시지에 필드 이름 바꾸기, 값 마스킹, 라우팅 대상 토픽 바꾸기 같은 가벼운 가공을 커넥터 코드 수정 없이 적용할 수 있다. 무거운 변환(join, 집계 등)은 SMT 대상이 아니고, Kafka Streams 같은 별도 처리 계층에서 하는 게 맞다 — SMT는 "살짝 다듬기" 용도로만 쓴다.

Source connector의 Exactly-once — exactly.once.source.support

0019 레슨 §6에서 본 "Producer transaction으로 정확히 한 번을 만드는" 원리가 Source Connector에도 그대로 적용된다. 이 설정을 켜면 Connect가 레코드와 offset을 하나의 transaction으로 묶어 쓰고, 재시작 시 이전 task를 확실히 걷어낸(fencing) 뒤 새 task를 시작한다. 기존 클러스터에 켤 때는 preparing → enabled 순서로 단계적으로 올려야 한다는 점만 기억해두자.
