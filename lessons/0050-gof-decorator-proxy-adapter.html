Decorator · Proxy · Adapter

셋 다 "다른 객체를 필드로 들고 감싸는(wrap) 객체"다. 그래서 코드 모양이 거의 같다. 구분은 모양이 아니라 ① 감싼 뒤 인터페이스가 어떻게 되는가, ② 무엇을 하려고 감쌌는가로 한다.

§0 · 워밍업 — 지난 레슨 3문제

지난 퀴즈가 많이 틀렸다면 정상이다. 틀린 것을 다시 꺼내 보는 것 자체가 연습이다. 판별 신호는 둘뿐이다: 상속이면 Template Method / 합성이면 누가 바꾸나(밖=Strategy, 상태 객체 스스로=State).

R1.

class Sorter {
    private final Comparator c;
    Sorter(Comparator c) { this.c = c; }
    void sort(List l) { l.sort(c); }
}

R2.

abstract class Game {
    final void play() { init(); loop(); end(); }
    abstract void loop();
}

R3.

class TrafficLight {
    private Light light = new Red();
    void tick() { light = light.next(); }   // Red → Green → Yellow ...
}

§1 · 먼저 하나의 그림: "감싸는 객체"

선물을 포장지로 싸는 것과 같다. 안에 든 물건(원본)이 있고, 겉에서 싸는 것(래퍼)이 있다. 사용하는 쪽은 겉만 본다. 세 패턴은 "무엇을 하려고 싸는가"가 다르다.

싸는 목적싼 뒤의 인터페이스
Adapter모양이 안 맞는 것을 맞추려고달라진다 (바깥이 원하는 모양으로)
Decorator기능을 더하려고같다
Proxy접근을 통제하려고같다

구조 신호. ① 원본과 래퍼가 같은 인터페이스를 구현하는가? 아니면 Adapter. ② 같다면 래퍼가 하는 일이 "기능 추가"인가(Decorator) "접근 통제"인가(Proxy)?

§2 · Adapter (어댑터) — 모양을 맞춘다

이론. 이미 있는 클래스의 인터페이스가 내가 기대하는 것과 다를 때, 그 사이에 변환 객체를 끼운다. 기존 코드를 고치지 않고 재사용하는 것이 목적이다. 별칭 Wrapper.

비유. 해외여행 돼지코. 콘센트(내가 가진 것)와 플러그(기대하는 것)의 모양이 달라서 사이에 끼운다. 전기(기능)는 그대로고 모양만 바뀐다.

interface WavPlayer { void playWav(String file); }      // 내가 기대하는 모양
class Mp3Player { void playMp3(String file) { ... } }   // 이미 있는 클래스(모양이 다름)

class Mp3ToWavAdapter implements WavPlayer {            // 기대하는 모양을 구현
    private final Mp3Player mp3 = new Mp3Player();     // 원본을 들고 있음
    public void playWav(String file) { mp3.playMp3(convert(file)); }  // 변환해서 위임
}

두 가지 형태: 객체 어댑터(위처럼 필드로 들고 있음, 합성)와 클래스 어댑터(상속). 시험에서 Adapter가 "클래스 패턴"으로 분류되는 것은 클래스 어댑터 때문이다. 출처: Refactoring.Guru — Adapter.

§3 · Decorator (데코레이터) — 기능을 겹겹이 더한다

이론. 원본과 같은 인터페이스를 구현하는 래퍼가 원본을 들고, 원본의 동작 앞뒤에 기능을 덧붙인다. 같은 인터페이스라서 래퍼를 또 래퍼로 감쌀 수 있다(겹겹이). 어떤 조합으로 쌓을지는 클라이언트가 정한다. 기능 확장을 위해 서브클래스를 만드는 것의 대안이다.

비유. 카페 주문. 에스프레소 위에 "우유 추가", 거기에 "휘핑 추가"를 얹는다. 결과물은 여전히 "커피"이고, 가격만 합쳐진다.

interface Coffee { int cost(); }
class Espresso implements Coffee { public int cost() { return 3000; } }

class Milk implements Coffee {                       // 같은 인터페이스
    private final Coffee base;                       // 감쌀 대상(또 다른 Coffee)
    Milk(Coffee base) { this.base = base; }
    public int cost() { return base.cost() + 500; }  // 원본 호출 + 기능 추가
}
Coffee order = new Whip(new Milk(new Espresso()));   // 클라이언트가 겹겹이 쌓음

§4 · Proxy (프록시) — 접근을 통제한다

이론. 원본과 같은 인터페이스를 가진 대리자가 원본 앞에 서서, 원본에 닿기 전에 가로채 통제한다. 종류: 가상(필요할 때 늦게 생성), 보호(권한 검사), 원격(다른 서버 객체를 로컬처럼), 로깅, 캐싱. 별칭 Surrogate.

비유. 연예인 매니저. 섭외 전화는 매니저가 받고, 일정과 조건이 맞을 때만 연예인에게 전달한다. 연예인과 같은 "섭외 창구" 역할을 하지만, 연예인을 언제 만날지는 매니저가 정한다.

interface Image { void show(); }
class RealImage implements Image { /* 생성 시 파일을 읽어 무거움 */ public void show() { ... } }

class LazyImage implements Image {                   // 같은 인터페이스
    private final String path;
    private RealImage real;                          // 아직 안 만듦
    LazyImage(String path) { this.path = path; }
    public void show() {
        if (real == null) real = new RealImage(path); // 필요할 때 처음 생성 (가상 프록시)
        real.show();
    }
}

§5 · Decorator vs Proxy — 가장 헷갈리는 쌍

둘은 코드 모양이 거의 같다. 같은 인터페이스 + 원본을 필드로 보유 + 위임이다. 차이는 의도와 책임자에 있다.

DecoratorProxy
목적기능 추가접근 통제
원본 생성·수명클라이언트가 원본을 만들어 넘긴다프록시가 스스로 관리하기도 한다 (§4의 new RealImage)
쌓기클라이언트가 여러 겹으로 쌓는다보통 한 겹

출처: Refactoring.Guru — Decorator, Proxy의 "Relations with other patterns". Proxy는 "usually manages the life cycle of its service object on its own"이고 Decorator의 구성은 "controlled by the client"라고 정리한다.

§6 · Spring·JDK에서 찾아보기

어디무엇비고
Spring AOP (@Transactional 등)Proxy문서: "Spring AOP is proxy-based". 인터페이스가 있으면 JDK 동적 프록시, 없으면 CGLIB. 호출 앞뒤에서 트랜잭션을 열고 닫는 것은 접근 통제(가로채기)다
InputStreamReader구조상 Adapter바이트 스트림(InputStream)을 문자 스트림(Reader)으로 인터페이스를 바꿔 준다. Javadoc은 이걸 "bridge"라고 부르는데, GoF의 Bridge 패턴과는 다른 일상적 의미의 단어다

주의. new BufferedReader(new FileReader(...))처럼 같은 종류(Reader)끼리 겹쳐 쓰는 Java I/O는 Decorator의 고전 사례로 흔히 인용된다. 다만 이 레슨에서는 공식 문서로 그 명칭을 직접 확인하지 않았으므로 "구조상 그렇다"까지만 말한다.

§8 · 한 문장으로 회수

인터페이스가 달라지면 Adapter. 같다면 기능을 더하면 Decorator, 접근을 통제하면 Proxy.
