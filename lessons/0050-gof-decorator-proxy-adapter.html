Decorator · Proxy · Adapter

셋 다 "다른 객체를 필드로 들고 감싸는(wrap) 객체"다. 그래서 코드 모양이 거의 같다. 구분은 모양이 아니라 ① 감싼 뒤 인터페이스가 어떻게 되는가, ② 무엇을 하려고 감쌌는가로 한다.

§0 · 워밍업 — 지난 레슨 3문제

지난 퀴즈가 많이 틀렸다면 정상이다. 틀린 것을 다시 꺼내 보는 것 자체가 연습이다. 판별 신호는 둘뿐이다: 상속이면 Template Method / 합성이면 누가 바꾸나(밖=Strategy, 상태 객체 스스로=State).

R1.

class Sorter {
    private final Comparator c;
    Sorter(Comparator c) { this.c = c; }
    void sort(List l) { l.sort(c); }
}

R2.

abstract class Game {
    final void play() { init(); loop(); end(); }
    abstract void loop();
}

R3.

class TrafficLight {
    private Light light = new Red();
    void tick() { light = light.next(); }   // Red → Green → Yellow ...
}

§1 · 먼저 하나의 그림: "감싸는 객체"

세 패턴은 모두 원본 객체를 필드로 들고, 호출을 원본에 넘기는 객체(래퍼)를 만든다. 선물 포장에 빗대면, 안에 든 물건이 원본이고 겉에서 싸는 것이 래퍼다. 사용하는 쪽은 겉만 본다. 세 패턴은 "무엇을 하려고 싸는가"가 다르다. 비유가 맞지 않는 곳: 포장지는 물건을 바꾸지 못하지만, 래퍼는 호출을 가로채 값을 바꾸거나 원본을 아예 부르지 않을 수 있다.

싸는 목적싼 뒤의 인터페이스
Adapter모양이 안 맞는 것을 맞추려고달라진다 (바깥이 원하는 모양으로)
Decorator기능을 더하려고같다
Proxy접근을 통제하려고같다

구조 신호. ① 래퍼와 원본이 같은 인터페이스를 구현하는가? 다르면 Adapter.
② 같다면 래퍼가 원본 호출을 어떻게 다루는가. 원본을 항상 부르고 그 앞뒤에 기능을 얹으면 Decorator. 원본을 부를지 말지, 언제 만들지를 래퍼가 정하면 Proxy.
③ ②로 안 갈리면(로깅·캐시처럼 둘 다 되는 경우) 누가 감쌌는가를 본다. 클라이언트가 직접 new로 쌓으면 Decorator, 프레임워크나 대리자가 원본을 만들고 관리하면 Proxy(§5).

§2 · Adapter (어댑터) — 모양을 맞춘다

한 문장. 이미 있는 클래스를 고치지 않고, 내가 기대하는 인터페이스로 쓸 수 있게 중간에 변환 객체를 끼우는 패턴이다. 별칭 Wrapper.

비유. 해외여행용 돼지코. 내 기기의 플러그(이미 있는 것)가 현지 콘센트(기대하는 모양)와 맞지 않아 사이에 끼운다. 전기는 그대로 흐르고 모양만 바뀐다. 비유가 맞지 않는 곳: 돼지코는 모양만 맞추지만, Adapter는 메서드 이름이나 인자 타입을 바꾸는 변환 코드를 직접 가진다.

interface Printer { void print(Doc d); }                 // 내가 기대하는 모양
class OldPrinter { void printText(String s) { ... } }    // 이미 있는 클래스 (모양이 다름, 고칠 수 없음)

class OldPrinterAdapter implements Printer {             // 기대하는 모양을 구현
    private final OldPrinter old = new OldPrinter();     // 원본을 들고 있음
    public void print(Doc d) { old.printText(d.toText()); }   // 인자를 변환해서 원본에 위임
}
// 클라이언트는 Printer만 알고, OldPrinter가 뒤에 있다는 걸 모른다

두 가지 형태가 있다. 객체 어댑터는 위처럼 원본을 필드로 들고 위임한다(합성). 클래스 어댑터는 원본 클래스를 상속해서 만든다. 시험에서 Adapter가 "클래스 패턴"으로 분류되는 것은 클래스 어댑터 형태가 상속을 쓰기 때문이다(클래스 패턴의 뜻은 레슨 0049 §3). 출처: Refactoring.Guru: Adapter.

§3 · Decorator (데코레이터) — 기능을 겹겹이 더한다

한 문장. 원본과 같은 인터페이스를 가진 래퍼로 원본을 감싸서, 원본은 그대로 부르면서 그 앞뒤에 기능을 덧붙이는 패턴이다.

구조. 래퍼가 원본과 같은 인터페이스라서, 래퍼를 또 다른 래퍼로 감쌀 수 있다(겹겹이). 어떤 조합으로 쌓을지는 클라이언트가 정한다. 기능을 더하려고 서브클래스를 조합별로 만드는 방식의 대안이다.

비유. 카페 주문. 에스프레소 위에 "우유 추가", 거기에 "휘핑 추가"를 얹는다. 결과물은 여전히 "커피"이고, 가격만 합쳐진다. 비유가 맞지 않는 곳: 우유를 넣은 뒤에도 안의 에스프레소는 그대로 있다. 코드에서도 Decorator는 원본을 반드시 호출하고 그 결과에 얹는다.

interface Coffee { int cost(); }
class Espresso implements Coffee { public int cost() { return 3000; } }

class Milk implements Coffee {                       // 같은 인터페이스
    private final Coffee base;                       // 감쌀 대상(또 다른 Coffee)
    Milk(Coffee base) { this.base = base; }
    public int cost() { return base.cost() + 500; }  // 원본 호출 + 기능 추가
}
Coffee order = new Whip(new Milk(new Espresso()));   // 클라이언트가 겹겹이 쌓음

§4 · Proxy (프록시) — 접근을 통제한다

한 문장. 원본과 같은 인터페이스를 가진 대리자가 원본 앞에 서서, 호출이 원본에 닿기 전에 "원본을 부를지, 언제 부를지, 아예 만들지"를 정하는 패턴이다. 별칭 Surrogate.

종류. 가상 프록시(원본을 필요할 때 처음 만든다), 보호 프록시(권한이 없으면 원본을 안 부른다), 원격 프록시(다른 서버의 객체를 같은 서버에 있는 것처럼 쓰게 한다), 캐싱 프록시(저장된 값이 있으면 원본을 안 부른다). 로깅 프록시도 있지만 이것은 Decorator와 구조가 같아서 ③으로 가른다(§5).

비유. 연예인 매니저. 섭외 전화는 매니저가 받고, 일정과 조건이 맞을 때만 연예인에게 전달한다. 의뢰인은 매니저에게든 연예인에게든 같은 방식("섭외 요청")으로 말하므로 인터페이스가 같다. 비유가 맞지 않는 곳: 매니저는 일부 요청을 연예인에게 알리지 않고 혼자 거절하거나 답한다. 캐싱 프록시가 원본을 안 부르고 저장된 값을 돌려주는 것과 같다.

interface Image { void show(); }
class RealImage implements Image { /* 생성 시 파일을 읽어 무거움 */ public void show() { ... } }

class LazyImage implements Image {                   // 같은 인터페이스
    private final String path;
    private RealImage real;                          // 아직 안 만듦
    LazyImage(String path) { this.path = path; }
    public void show() {
        if (real == null) real = new RealImage(path); // 필요할 때 처음 생성 (가상 프록시)
        real.show();
    }
}

§5 · Decorator vs Proxy — 가장 헷갈리는 쌍

둘은 코드 모양이 거의 같다. 같은 인터페이스를 구현하고, 원본을 필드로 들고, 호출을 원본에 위임한다. 그래서 모양으로는 못 가르고 래퍼가 원본 호출을 어떻게 다루는지와 누가 감쌌는지로 가른다.

DecoratorProxy
원본 호출항상 부른다. 앞뒤에 기능만 얹는다부를지 말지 정한다 (권한 없음, 캐시 적중이면 안 부름)
원본 생성·수명클라이언트가 원본을 만들어 넘긴다프록시가 스스로 만들고 관리하기도 한다 (§4의 new RealImage)
쌓기클라이언트가 여러 겹으로 쌓는다보통 한 겹

출처: Refactoring.Guru: Decorator, Proxy의 "Relations with other patterns". Proxy는 "usually manages the life cycle of its service object on its own"(보통 원본의 생애를 스스로 관리한다)이고 Decorator의 구성은 "controlled by the client"(클라이언트가 정한다)라고 정리한다.

가장 흔한 오해. "기능을 더하면 Decorator, 접근을 통제하면 Proxy"만 외우면 로깅·트랜잭션처럼 기능을 더하면서 호출을 가로채는 경우에서 막힌다. 이런 경우는 구조가 같아서 이름으로만 판단할 수 없다. 이때는 "누가 감쌌는가"를 본다. 클라이언트가 new Whip(new Milk(...))로 쌓았으면 Decorator, 프레임워크가 만들어 원본 자리에 끼워 넣었으면 Proxy다.

§6 · Spring·JDK에서 찾아보기

어디무엇비고
Spring AOP (@Transactional 등)Proxy문서: "Spring AOP is proxy-based". 인터페이스가 있으면 JDK 동적 프록시, 없으면 CGLIB로 프록시를 Spring이 실행 중에 만들어 원본 빈 자리에 끼운다. 호출 앞뒤에 트랜잭션을 여닫는 일은 기능 추가처럼 보이지만, 클라이언트가 쌓은 것이 아니라 프레임워크가 만들어 끼웠으므로 Proxy로 센다(§5의 ③)
InputStreamReader구조상 Adapter바이트를 읽는 InputStream을 글자를 읽는 Reader로 인터페이스를 바꿔 준다. Javadoc은 이것을 "bridge"(다리)라고 설명하는데, 여기서는 일상 단어일 뿐 GoF의 Bridge 패턴(레슨 0052)을 뜻하지 않는다

확인하지 못한 것. new BufferedReader(new FileReader(...))처럼 같은 Reader 종류끼리 겹쳐 쓰는 Java I/O는 Decorator의 대표 사례로 흔히 인용된다. 이 레슨에서는 공식 문서에서 그 명칭을 확인하지 못했으므로 "구조가 Decorator와 같다"까지만 말한다.

§8 · 한 문장으로 회수

인터페이스가 달라지면 Adapter. 같다면 원본을 항상 부르며 기능을 얹으면 Decorator, 원본을 부를지 말지·언제 만들지 정하면 Proxy. 둘 다 해당하면 클라이언트가 쌓았는지(Decorator) 프레임워크·대리자가 만들었는지(Proxy)로 가른다.
