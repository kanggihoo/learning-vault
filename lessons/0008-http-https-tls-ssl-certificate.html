HTTP가 HTTPS가 될 때 TLS와 인증서가 하는 일

목표: HTTPS를 “HTTP를 TLS 보안 터널 안에 넣은 것”으로 이해하고, 인증서가 암호화 자체가 아니라 서버 신원 확인과 키 합의의 출발점이라는 점을 구분한다.

1. HTTPS는 HTTP를 바꾸는 게 아니다

HTTPS는 새로운 요청 형식이 아니다. 브라우저와 서버가 먼저 TLS 연결을 만든 뒤, 그 안전한 연결 안에서 평소의 HTTP 요청과 응답을 주고받는 방식이다. MDN도 HTTPS를 TLS로 암호화된 HTTP라고 설명한다. 

HTTP:
브라우저 ───── GET /api/me ─────> 서버
        평문으로 지나감

HTTPS:
브라우저 ── TLS handshake ──> 서버
브라우저 == 암호화된 TLS 터널 == 서버
브라우저 ── { GET /api/me } ──> 서버
              암호화된 HTTP 메시지

그래서 “HTTP를 HTTPS로 변환한다”는 표현은 두 가지를 섞기 쉽다. 포트 80의 HTTP 요청을 301/308로 HTTPS URL에 보내는 것은 redirect이고, 실제 보호는 HTTPS URL에서 TLS 연결이 새로 만들어질 때 시작된다.

2. TLS handshake에서 일어나는 일

현대 TLS의 핵심은 “공개키로 모든 데이터를 직접 암호화”가 아니다. 공개키 기반 인증서로 서버가 진짜인지 확인하고, Diffie-Hellman 계열 key exchange로 양쪽만 아는 대칭키를 만든 뒤, 실제 HTTP 데이터는 그 대칭키로 빠르게 암호화한다. 

1. 브라우저: 지원하는 TLS 버전, 암호 스위트, 랜덤값, 접속할 서버명 전송
2. 서버: 인증서와 key exchange 재료 전송
3. 브라우저: 인증서가 이 도메인에 유효하고 신뢰 가능한 CA가 서명했는지 검증
4. 양쪽: key exchange 결과로 같은 session traffic key 계산
5. 이후: HTTP 요청/응답을 TLS record로 쪼개 암호화해서 주고받음

복호화도 같은 원리다. 브라우저와 서버는 handshake 결과로 얻은 session key를 가지고 자신에게 도착한 TLS record를 복호화한다. 서버 인증서의 개인키로 매 HTTP 메시지를 풀어보는 구조가 아니다.

3. 어디까지 암호화되는가?

TLS 연결이 성립된 뒤의 HTTP 메시지는 거의 통째로 보호된다. 요청 라인, path, query string, headers, cookies, body, 응답 headers, 응답 body가 모두 TLS application data 안에 들어간다.

암호화됨

  • GET /orders?user=1의 path와 query
  • Cookie, Authorization 같은 HTTP header
  • POST/PUT 요청 body
  • 응답 header와 응답 body

노출될 수 있음

  • 상대 서버 IP와 port
  • DNS 질의의 도메인명, 별도 보호가 없을 때
  • TLS SNI의 서버명, ECH가 없을 때
  • 통신 시각, 크기, 빈도 같은 메타데이터

따라서 HTTPS여도 “어느 서버와 통신했는지” 같은 네트워크 메타데이터까지 완전히 숨기는 것은 아니다. 하지만 HTTP 내용 자체, 특히 쿠키와 Authorization header와 body는 보호된다.

4. SSL 인증서는 무엇인가?

실무에서 “SSL 인증서”라고 부르지만, 현재는 보통 TLS 인증서라고 이해하면 된다. SSL은 오래된 프로토콜 이름이고, 현대 HTTPS는 TLS를 사용한다. 

인증서가 담는 것:
  - 이 인증서가 유효한 도메인명: example.com, www.example.com
  - 서버의 공개키
  - 발급자: CA
  - 유효 기간
  - CA의 디지털 서명

파일 형태로는 보통 .crt, .cer, .pem 같은 이름으로 본다. 내부 표준 구조는 X.509 인증서다. 사람이 읽기 좋은 설정 파일이라기보다, ASN.1/DER로 인코딩된 구조화된 바이너리 데이터이고, PEM은 그 DER 바이너리를 Base64 텍스트로 감싼 형태다. 

PEM 형태 예시:
-----BEGIN CERTIFICATE-----
MIIF...
...base64...
-----END CERTIFICATE-----

DER 형태:
  같은 인증서 내용을 바이너리 bytes로 저장
X.509 인증서 주요 필드:
  version
    X.509 버전

  serial number
    CA가 부여한 인증서 고유 번호

  issuer
    인증서를 발급한 CA 이름

  subject
    인증서 대상 이름

  subject alternative name(SAN)
    실제 도메인 목록: example.com, www.example.com
    현대 브라우저는 hostname 검증 때 SAN을 본다

  validity
    notBefore / notAfter 유효 기간

  subject public key info
    서버 공개키와 알고리즘

  key usage / extended key usage
    이 인증서가 서버 인증에 쓰일 수 있는지 같은 용도 제한

  signature algorithm
    CA가 어떤 알고리즘으로 서명했는지

  signature value
    CA의 디지털 서명값

브라우저는 인증서를 보고 “내가 접속한 도메인과 인증서의 도메인이 맞는가?”, “이 인증서를 신뢰 가능한 CA 체인으로 검증할 수 있는가?”, “유효 기간과 사용 목적이 맞는가?”를 확인한다. 이 검증이 실패하면 브라우저는 인증서 경고를 보여준다.

5. Let's Encrypt는 무엇인가?

Let's Encrypt는 무료, 자동화, 공개 Certificate Authority(CA)다. 즉, “HTTPS 자체”나 “암호화 알고리즘”이 아니라, 브라우저가 신뢰할 수 있는 TLS 인증서를 발급해 주는 기관이다. 운영 주체는 비영리 단체 ISRG다. 

Let's Encrypt가 하는 일:
  1. ACME client가 서버에서 실행됨
  2. Let's Encrypt CA가 도메인 소유/제어 증명 challenge를 줌
  3. 서버가 DNS record 또는 HTTP well-known path로 증명
  4. CA가 여러 네트워크 위치에서 challenge 확인
  5. 성공하면 해당 도메인용 TLS 인증서 발급
  6. 서버는 그 인증서를 HTTPS handshake 때 브라우저에 제시

직관: Let's Encrypt는 “이 서버가 이 도메인을 제어한다”를 확인하고, 그 도메인에 쓸 인증서를 자동 발급해 주는 CA다. 발급된 인증서는 handshake에서 서버 신원 확인 재료로 쓰인다.

Let's Encrypt가 매 요청 데이터를 대신 암호화/복호화하지 않는다. 실제 요청 데이터 보호는 TLS handshake로 만든 session key가 담당한다.

6. 인증서가 HTTPS 과정에서 하는 역할

인증서는 데이터를 직접 계속 암호화하는 물건이라기보다, 서버 신원을 증명하고 안전한 key exchange를 가능하게 하는 신뢰 재료다. 

브라우저가 알고 싶은 것:
  "내가 진짜 api.example.com과 말하고 있나?"

인증서가 도와주는 것:
  api.example.com의 공개키와 도메인명을 CA가 서명해 줌

handshake가 만드는 것:
  이 연결에서만 쓸 session key

실제 데이터 보호:
  session key로 HTTP 메시지를 암호화하고 위변조를 검출

7. HTTP에서 HTTPS로 강제하는 방법

Redirect

서버가 http:// 요청에 301 또는 308과 Location: https://...를 응답한다. 단, 첫 HTTP 요청 자체는 이미 평문이었다.

HSTS

HTTPS 응답에 Strict-Transport-Security를 넣으면, 브라우저는 이후 같은 사이트 요청을 HTTP로 보내기 전에 HTTPS로 바꾼다.

한 문장으로 정리하면: HTTPS는 HTTP 메시지를 TLS로 감싸는 것이고, 인증서는 “이 서버가 그 도메인의 서버인지”를 검증하게 해 주며, 실제 암복호화는 handshake로 만들어진 session key가 담당한다.
