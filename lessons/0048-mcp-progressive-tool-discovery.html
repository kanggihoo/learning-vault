MCP 2026-07-28 · 2/2 · 레슨 0048 · 용어집·변경 지도(레퍼런스 0023)의 §3·§5를 판다

점진적 도구 로딩은 어디서 일어나나

"MCP가 이제 모든 도구를 한 번에 세션에 불러오지 않고 필요한 것만 점진적으로 가져온다더라." 이 문장은 절반은 정확하고, 절반은 층이 다르다. 점진적 로딩은 실제로 있고 MCP 공식 문서에도 이름이 있다(Progressive Tool Discovery). 그러나 그것은 서버가 보내는 것이 바뀐 게 아니라 호스트가 모델에게 보여 주는 것이 바뀐 것이다. 이 레슨은 그 내부 동작을 층별로 열어 본다 — 무엇이 어디에 저장되고, 무엇이 언제 모델의 컨텍스트에 들어가는가.

이 레슨 하나로 얻는 것. ① "세션에 불러온다"의 세션이 프로토콜 세션이 아니라 LLM 컨텍스트 창임을 구분한다. ② 카탈로그 → 상세 → 실행의 3계층 흐름을 시퀀스로 그릴 수 있다. ③ Anthropic API의 defer_loading·tool_reference가 프롬프트 캐시를 깨지 않고 정의를 끼워 넣는 방법을 설명할 수 있다. ④ 2026-07-28 스펙이 이 패턴을 돕는 세 장치를 짚을 수 있다.

§0 · 이 레슨에서 쓰는 용어 여섯 개

컨텍스트 창
모델이 한 호출에서 읽는 토큰 총량. 시스템 프롬프트·도구 정의·대화·도구 결과가 여기서 자리를 다툰다.
도구 정의
이름 + 설명 + 입력 JSON Schema. 하나에 수백 토큰. 서버 5개면 수만 토큰.
호스트
Claude Code 같은 AI 앱. 서버에서 받은 도구 전부를 보유하지만 모델에게는 골라서 보여 줄 수 있다.
메타툴
도구를 찾거나 부르기 위한 도구. search_tools, get_tool_details, Claude Code의 ToolSearch.
defer_loading
Anthropic API 옵션. 정의를 요청에 보내되 컨텍스트에 넣지 않음. 검색으로 찾을 때만 들어감.
프롬프트 캐시
같은 프롬프트 앞부분(프리픽스)을 재사용해 비용·지연을 줄이는 기능. 도구 배열이 바뀌면 깨진다.

전체 용어는 레퍼런스 0023 §1의 "점진적 도구 로딩의 말들".

§1 · 문제 — 사용자가 한 글자 치기 전에 사라지는 토큰

호스트의 순진한 구현은 이렇다. 시작할 때 연결된 모든 서버에 tools/list를 보내고, 받은 정의를 전부 모델의 tools 배열에 넣는다. 도구가 열 개면 괜찮다. 서버가 다섯 개면 이렇게 된다 (Anthropic 실측):

GitHub (35 tools)
~26K
Slack (11 tools)
~21K
Sentry (5)
~3K
Grafana (5)
~3K
Splunk (2)
~2K
합계
~55K

출처: Anthropic Engineering — Advanced tool use. 같은 글에서 내부 최적화 전 134K 토큰 사례도 보고한다. MCP 공식 문서의 그림은 더 극단적으로 "전부 선로딩 ~150,000 vs 점진 발견 ~2,000"을 대비시킨다.

토큰만 문제가 아니다. 두 번째 문제가 더 아프다.

  • 선택 정확도. 도구가 30~50개를 넘으면 모델이 비슷한 이름 사이에서 잘못 고르기 시작한다. 정의가 많을수록 나쁘다.
  • 지연·비용. 매 턴 55K 토큰을 다시 읽는다(프롬프트 캐시가 없으면).

Anthropic의 MCP 평가에서 tool search 적용 후 정확도가 Opus 4 기준 49% → 74%, Opus 4.5 기준 79.5% → 88.1%로 올랐다. 정의를 줄였는데 정확도가 올랐다 — 모델이 볼 게 적어졌기 때문.

§2 · 핵심 구분 — 서버는 그대로, 바뀐 건 호스트의 "주입"

MCP 공식 문서(Client Best Practices)의 정의를 그대로 옮긴다:

"호스트는 평소처럼 tools/list로 도구 정의를 가져오지만, 모델 컨텍스트에 주입하는 것은 미룬다. 호스트는 모델에게 가벼운 search_tools 메타툴을 제공한다. 호스트는 필요할 때만 전체 정의를 컨텍스트에 로드한다."

세 문장에 세 층이 다 있다. 그림으로 놓으면:

§3 · 내부 동작 — 카탈로그 → 상세 → 실행

MCP 문서가 "가장 흔한 구현"으로 드는 3계층을, 모델 입장의 시퀀스로 그리면 이렇다.

문서가 함께 적어 둔 구현 지침 넷은 백엔드의 캐시 설계 그대로다.

지침이유
상세 수준을 여러 단계로이름만 / 이름+설명 / 전체 스키마 중 모델이 고르게. Layer 1·2가 그 두 단계.
정의를 호스트에 캐시한 번 받은 정의는 메모이즈. 나중에 다시 주입할 때 tools/list 왕복이 없다. "모델 컨텍스트에 있는 것"과는 별개의 저장소.
list_changed에 재색인서버가 도구 목록 변경을 알리면 검색 인덱스를 다시 만든다.
서버별로 묶어 제시모델이 "관련 기능 묶음"으로 추론할 수 있게. 이름 접두어(github_, slack_)가 검색 한 번에 묶음을 잡게 해 준다.

한 단계 더 나간 것이 동적 서버 관리다 — 시작 때 모든 서버에 연결하지 않고, 모델이 enable_server("salesforce")를 부르면 그때 server/discover → tools/list를 하고, 끝나면 연결을 내려 컨텍스트를 비운다. 도구 단위 지연이 서버 단위 지연으로 확장된 것. 같은 문서 §Dynamic Server Management.

§4 · Anthropic API에서는 이렇게 구현됐다 — defer_loading과 tool_reference

위 3계층을 호스트가 직접 짜도 되지만, 제공자가 내장한 것을 쓸 수도 있다. Claude API의 tool search tool은 이렇게 동작한다 (플랫폼 문서):

  1. tools 배열에 검색 도구(tool_search_tool_regex_20251119 또는 _bm25_)를 넣는다.
  2. 모든 도구 정의를 여전히 배열에 넣되, 미룰 것에 "defer_loading": true를 붙인다. 최소 하나(보통 검색 도구)는 미루지 않는다.
  3. 처음 모델의 컨텍스트에는 검색 도구와 비지연 도구만 있다.
  4. 모델이 검색하면 API가 서버 쪽에서 매칭을 돌려 tool_reference 블록(기본 최대 5개)을 돌려준다.
  5. API가 그 참조를 전체 정의로 펼쳐 모델에게 보여 준다. 모델이 그중 하나를 부른다.
"tools": [
  { "type": "tool_search_tool_regex_20251119", "name": "tool_search_tool_regex" },   // 항상 상주
  { "name": "get_weather", "description": "…", "input_schema": {…}, "defer_loading": true },
  { "name": "search_files", "description": "…", "input_schema": {…}, "defer_loading": true }
]

여기가 "내부적으로 어떻게"의 핵심이다. 문서 원문: "defer_loading은 컨텍스트 창에 무엇이 들어가는지를 제어하고, 요청에 무엇을 보내는지를 제어하지 않는다." 정의는 매 요청 전부 전송된다(API가 검색을 돌리려면 갖고 있어야 하니까). 다만 "API는 지연된 도구를 시스템 프롬프트 프리픽스에서 제외한다. 모델이 검색으로 찾으면 API가 tool_reference 블록을 대화 중간에 인라인으로 덧붙이고 전체 정의로 펼친다. 프리픽스는 건드리지 않으므로 프롬프트 캐시가 보존된다."

Claude Code에서는

항목동작 (Agent SDK 문서)
기본tool search 켜짐. 도구 정의는 컨텍스트에서 보류되고, 모델은 "사용 가능한 도구 요약"을 받은 뒤 필요할 때 ToolSearch로 찾는다. 검색당 기본 5개 로드.

§5 · 그래서 2026-07-28 스펙은 무엇을 했나 — "돕는" 세 장치

다시 첫 문장으로. 스펙이 점진 로딩을 도입한 건 아니다. 그러나 호스트가 이 패턴을 싸고 안전하게 구현하도록 세 가지를 넣었다. 전부 tools/list 주변이다.

스펙 장치무엇점진 로딩에서 하는 일
ttlMs + cacheScope
SEP-2549 · 필수		"이 목록은 300000ms 동안 신선하다", public(공유 가능) / private(같은 토큰만). HTTP Cache-Control: max-age · public/private과 같은 의미.호스트 카탈로그의 캐시 정책. 재주입할 때 서버에 다시 안 묻는다. TTL은 폴링 간격이 아니라 신선도 힌트 — "필요할 때 확인, 지났으면 재요청". 알림이 오면 TTL이 남아도 즉시 무효.
결정적 순서
SHOULD		도구 집합이 안 바뀌었으면 tools/list는 같은 순서로 돌려준다.스펙 원문: "클라이언트가 목록을 안정적으로 캐시하고, 도구가 모델 컨텍스트에 포함될 때 LLM 프롬프트 캐시 히트율을 높인다." 순서가 바뀌면 같은 도구라도 프리픽스가 달라져 캐시가 깨진다.
subscriptions/listen
SEP-2575		toolsListChanged: true로 옵트인하면 서버가 notifications/tools/list_changed를 보낸다.캐시 무효화 신호. 받으면 tools/list 재요청 → 인덱스 재구축. MCP docs: "list_changed가 오면 TTL 전이라도 stale로 취급."
페이지네이션
기존		cursor(불투명) / nextCursor. 페이지 크기는 서버가 정함.큰 카탈로그를 조각으로 받는다. 페이지마다 독립 ttlMs. 커서가 무효가 되면 전부 버리고 처음부터.

한 번 더 층을 확인하자. 위 넷은 모두 ①서버 → ②호스트 화살표의 효율·정합성을 위한 것이다. ②호스트 → ③모델 화살표(무엇을 언제 주입하나)는 스펙이 규정하지 않는다 — 그건 docs의 "best practice"이고, 제공자별 구현(defer_loading, ENABLE_TOOL_SEARCH)이다. "스펙이 점진 로딩으로 바뀌었다"고 말하면 리뷰에서 반박당한다. "스펙이 호스트의 점진 로딩을 돕는 캐시·순서·알림 장치를 넣었다"가 정확하다.

§6 · 서버 개발자인 나는 무엇을 하면 되나

  • 이름·설명이 곧 검색 인덱스다. 두 변형(regex·BM25) 모두 이름·설명·인자명·인자 설명을 검색한다. query_slack보다 search_slack_messages가, "Query Slack"보다 "Search Slack messages by keyword, channel, or date range"가 더 많은 질의에 걸린다.
  • 접두어로 묶어라. github_*, slack_*. 검색 한 번에 묶음이 잡히고 서버별 그룹화도 쉬워진다. 서버 간 이름 충돌은 호스트가 접두어로 풀어야 하니 애초에 구체적인 이름이 좋다.
  • ttlMs를 정직하게. 정적 도구 집합이면 길게(수 분~시간), 권한별로 달라지면 cacheScope: "private". public은 다른 토큰의 캐시와 공유될 수 있음을 기억.
  • 순서를 고정하라. DB에서 읽어 내놓는다면 ORDER BY name 하나가 상대편 프롬프트 캐시를 살린다.
  • outputSchema를 주면 호스트가 "코드 모드"(모델이 도구를 호출하는 코드를 써서 중간 결과를 컨텍스트 밖에서 처리)에 정확한 타입을 만들 수 있다 — 같은 문서의 두 번째 패턴.
