Tiered Storage: 로컬 디스크와 무한한 창고를 나눠 쓰기

목표: Apache Kafka Documentation: Tiered Storage 원문을 근거로, "오래된 데이터를 어디에 두면 싸고 안전한가"라는 운영 판단을 할 수 있는 수준으로 이해한다. 0019 레슨의 "저장 방식(Persistence)"에서 배운 append-only 로그 + OS 캐시 구조와, "Log Compaction" 섹션에서 본 보관 기간(retention) 개념을 그대로 이어받아, "그 로그를 물리적으로 어디에 나눠 저장할까"라는 질문에 답한다.

0. 문제 — 로컬 디스크 하나에 모든 걸 다 담으면 생기는 일

0016 레슨과 0019 레슨에서 봤듯, Kafka는 기본적으로 Partition의 로그 전체(최신 메시지부터 보관 기간이 끝나지 않은 오래된 메시지까지)를 Broker의 로컬 디스크 한 곳에 그대로 쌓아둔다. 이 구조에는 두 가지 압박이 있다. 

보관 기간(retention)을 늘리고 싶다 → 로컬 디스크 용량을 그만큼 계속 늘려야 함
클러스터를 확장하거나 죽은 Broker를 교체한다 → 그 디스크에 쌓인 데이터 전체를 다른 Broker로 통째로 다시 복제해야 함
                                                → 데이터가 많을수록 이 복제 작업이 오래 걸리고 무거워짐

그런데 실제로 읽히는 데이터 대부분은 최근 데이터다. 0019에서 봤듯 Consumer는 대부분 "지금 막 쌓인 메시지"를 뒤쫓아가며 읽고(tail read, OS 캐시로 처리됨), 오래된 데이터는 장애 복구나 재처리 같은 드문 상황에서만 디스크를 직접 읽는다. 즉 거의 안 읽히는 오래된 데이터까지 비싼 로컬 디스크에 붙잡아 둘 필요가 없다는 게 Tiered Storage의 출발점이다.

1. 해법 — 로그를 두 계층(tier)으로 나누기

Tiered Storage는 하나의 Partition 로그를 local tier와 remote tier 두 창고로 나눈다.

계층담당 데이터저장소
Local tier가장 최근에 쓰인, 아직 안 채워진 segment(파일 조각)Broker의 로컬 디스크 (기존과 동일)
Remote tier다 채워져서 완료된(closed) 오래된 segmentS3, HDFS 같은 저렴하고 사실상 무제한인 외부 저장소

핵심은 이 구분이 Consumer에게 보이지 않는다(transparent)는 점이다. Consumer는 그냥 "이 offset부터 읽어줘"라고 요청할 뿐, 그 데이터가 로컬 디스크에 있는지 S3에 있는지는 신경 쓸 필요가 없다. Kafka가 내부적으로 위치를 찾아 가져다준다.

2. 동작 방식 — segment는 언제 옮겨지고, 언제 지워지나

완료된 segment만 이동한다

아직 메시지가 계속 쓰이고 있는 활성(active) segment는 절대 옮기지 않는다. segment 하나가 다 채워져 "완료(closed)" 상태가 되어야 비로소 remote tier로 업로드 대상이 된다. 그리고 로컬에 있던 원본은 remote 업로드가 끝난 뒤에만 삭제 대상이 된다 — 옮기기도 전에 먼저 지워서 데이터를 잃는 일은 없다.

보관 기간(retention)이 로컬용/전체용으로 나뉜다

Tiered Storage를 켠 Topic은 기존 retention.ms/retention.bytes(전체 보관 기간 — 결국 remote에서까지 삭제되는 기준) 외에, local.retention.ms/local.retention.bytes라는 로컬 전용 보관 기간을 추가로 갖는다. 이 값은 "remote로 이미 옮겨진 segment를 로컬에서는 얼마나 더 들고 있다가 지울지"를 정한다 — 즉 local 값은 항상 전체 값보다 작거나 같다.

트레이드오프: remote tier 읽기는 네트워크를 거쳐 외부 저장소에서 가져오는 것이라 로컬 디스크(+OS 캐시) 읽기보다 느리다. 그래서 Tiered Storage는 "최근 데이터는 여전히 빠르게, 오래된 데이터는 느려도 되니 싸게"라는 계층별 트레이드오프를 명시적으로 받아들이는 설계다 — 모든 데이터를 항상 빠르게 만들어주는 마법은 아니다.

3. 아직 알아둘 것 — 새 기능이라 생기는 제약

  • Log Compaction Topic(0019에서 배운, key별 최신 값만 남기는 Topic)은 아직 지원 안 됨 — Tiered Storage는 지금은 "그냥 오래되면 지우는" 보관 방식의 Topic에만 쓸 수 있다.
  • 기본 제공 구현체가 없다 — S3/HDFS와 실제로 연결하는 부분(RemoteStorageManager)은 직접 구현하거나 벤더/커뮤니티 구현체를 붙여야 한다.
  • 브로커 단위로 기능을 끄려면, 그 전에 이 기능을 쓰는 Topic을 먼저 전부 정리해야 한다(그냥 끄면 시작할 때 에러가 남).

심화 학습 참고: 실제 broker/topic 설정 이름(remote.log.storage.system.enable, remote.storage.enable 등)과 구성 절차, RemoteStorageManager/RemoteLogMetadataManager 구현 방법은 실제 도입 단계에서 공식 문서와 KIP-405를 직접 보며 다루면 된다.
