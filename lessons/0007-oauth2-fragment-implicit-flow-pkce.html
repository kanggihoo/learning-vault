OAuth2 fragment, implicit flow, PKCE 이해하기

목표: URL의 #access_token=...이 왜 예전 implicit flow에서 쓰였고, 왜 현대 웹 로그인에서는 authorization code flow + PKCE를 우선하는지 이해한다.

1. URL의 fragment란?

URL에서 # 뒤쪽을 fragment라고 부른다. 예를 들어 아래 URL에서 fragment는 access_token=... 부분이다. 

https://our-frontend.com/callback#access_token=GOOGLE_AT&token_type=Bearer
                           └──────────────────────────────────────────────
                                      fragment

fragment는 HTTP 요청으로 서버에 전송되지 않는다. 브라우저 안에만 남고, 프론트 JavaScript가 window.location.hash로 읽을 수 있다. 

브라우저 주소창:
https://our-frontend.com/callback#access_token=abc

실제 서버로 가는 HTTP 요청:
GET /callback HTTP/1.1
Host: our-frontend.com

서버가 못 보는 부분:
#access_token=abc

2. implicit flow는 무엇이었나?

예전에는 SPA가 백엔드 없이 브라우저 JavaScript만으로 OAuth 로그인을 처리하는 경우가 많았다. 이때 authorization code를 백엔드가 교환하는 구조가 아니라, authorization server가 access token을 브라우저로 바로 돌려줬다. 

Implicit flow:

1. 브라우저 -> Google
GET /auth?response_type=token&client_id=...

2. Google 로그인/동의

3. Google -> 브라우저
302 Location: https://our-frontend.com/callback#access_token=GOOGLE_AT

4. 프론트 JavaScript
window.location.hash에서 access_token을 읽음

5. 프론트 JavaScript
그 access_token으로 Google API 호출

여기서 핵심은 code가 아니라 access_token이 바로 브라우저에 도착한다는 점이다.

3. 왜 fragment를 썼나?

fragment는 서버에 전송되지 않으므로, access token이 프론트 호스팅 서버의 HTTP 요청 로그에 남을 위험을 줄일 수 있었다. 그래서 예전 implicit flow에서는 토큰을 query string이 아니라 fragment에 넣었다.

Query string

/callback?access_token=abc

서버 요청에 포함된다. 서버 로그, 프록시 로그 등에 남기 쉽다.

Fragment

/callback#access_token=abc

서버 요청에는 빠진다. 프론트 JavaScript만 읽을 수 있다.

4. 그런데 왜 이제 피하나?

fragment가 서버에 안 간다고 해서 안전한 것은 아니다. access token이 브라우저 주소창과 JavaScript 환경에 직접 노출된다. 브라우저 안의 스크립트, 확장 프로그램, XSS, 잘못된 리다이렉트 처리에 더 민감하다. 

문제의 핵심:
  access token이 브라우저 앞단에 바로 도착함
  백엔드가 token endpoint에서 교환하고 검증할 기회가 약함
  token이 URL 조각에 잠깐이라도 노출됨
  프론트 코드가 token을 직접 다루게 됨

그래서 최신 보안 권고에서는 authorization response에서 access token을 바로 주는 implicit 방식을 피하고, authorization code flow와 PKCE를 사용하라고 권고한다.

5. 현대 방식: code flow + PKCE

현대 SPA 또는 웹 앱에서는 브라우저가 access token을 바로 받는 대신, 먼저 authorization code를 받는다. 그리고 그 code를 token endpoint에서 access token으로 교환한다. PKCE는 이 code를 훔친 사람이 마음대로 토큰으로 교환하지 못하게 묶는 장치다. 

Authorization code flow + PKCE:

1. 프론트 또는 백엔드
code_verifier 생성
code_challenge = hash(code_verifier)

2. 브라우저 -> Google
GET /auth
  ?response_type=code
  &client_id=...
  &code_challenge=...
  &code_challenge_method=S256

3. Google -> callback
302 Location: https://our-app.com/callback?code=AUTH_CODE&state=...

4. token endpoint 요청
POST /token
  code=AUTH_CODE
  code_verifier=원래값

5. Google
code_challenge와 code_verifier가 맞는지 확인 후 token 발급

PKCE의 직관은 “처음 요청한 사람이 가진 비밀 조각을 나중에 다시 증명해야 code를 토큰으로 바꿔준다”이다.

6. 지금 우리가 다룬 백엔드 로그인과 비교

예전 implicit

callback#access_token=...

브라우저가 access token을 바로 받는다. 프론트 JS가 fragment를 읽는다.

지금 배운 백엔드 code flow

callback?code=...

브라우저는 code만 운반한다. 백엔드가 Google token endpoint와 서버 간 통신한다.

7. 한 문장 정리

#access_token=...은 “브라우저 프론트가 토큰을 직접 받던 예전 방식”의 흔적이고, 지금은 “브라우저는 code만 받고, 토큰은 token endpoint에서 교환한다”는 방식이 기본 방향이다.
