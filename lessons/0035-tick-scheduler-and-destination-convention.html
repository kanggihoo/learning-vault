틱 재생 스케줄러: destination은 누가 정하는가

0031 §5에서 "스케줄러가 convertAndSend("/topic/ticks/005930", tick)을 호출한다"고 하고 넘어갔다. 그런데 스케줄러는 그 문자열을 어떻게 아는가?

이 질문의 답이 이 시리즈에서 가장 실전적인 부분이다 — 그리고 답을 알고 나면 "구독은 되는데 메시지가 안 와요"라는 흔한 버그의 정체도 같이 보인다.

1. 스케줄러도 그냥 발행자다

먼저 확인 — "스케줄러 → 브로커 → 구독 중인 클라이언트들 순회 전달"이 맞다. 그리고 이 길은 0033에서 본 컨트롤러의 길과 완전히 같다.

컨트롤러틱 스케줄러
계기클라이언트가 SEND를 보냄시간 (@Scheduled)
도는 스레드clientInboundChannel 워커스케줄러 스레드
발행 방법반환값 or SimpMessagingTemplateSimpMessagingTemplate
그다음 길brokerChannel → 브로커 → 레지스트리 조회 → clientOutboundChannel → 소켓 (동일)

브로커 안에서 일어나는 일도 0032 §4에서 본 그대로다 — 레지스트리에서 그 목적지에 매칭되는 구독을 찾아 세션 수만큼 복제한다. "for문으로 순회한다"는 표현이 정확하다. 다만 순회하는 대상은 접속자 전원이 아니라 그 목적지를 구독한 세션들이다.

2. 핵심 질문 — destination은 아무도 알려주지 않는다

서버 어딘가에 /topic/ticks/005930이라는 목적지가 미리 만들어져 있지 않다. 0032 §5에서 본 대로 destination은 주소가 아니라 이름표이고, 그 이름표는 양쪽이 각자 문자열을 만들어 브로커에서 비교당할 뿐이다.

그래서 답은 시시하지만 중요하다 — 스케줄러는 DB에서 읽은 종목 코드로 문자열을 직접 조립한다. 그리고 그 조립 규칙이 프론트엔드가 구독할 때 쓰는 규칙과 글자 하나까지 같아야 한다.

규약이 어긋나면 어떻게 실패하는가

가장 무서운 점 — 에러가 나지 않는다. HTTP였다면 404가 났을 상황에서 STOMP는 아무 말도 하지 않는다. 존재하지 않는 목적지를 구독하는 것도, 아무도 구독하지 않은 목적지로 발행하는 것도 완전히 합법이기 때문이다.

어긋난 곳증상서버 로그
프론트: /topic/tick/005930
서버: /topic/ticks/005930		 구독은 성공. 데이터만 안 옴.아무것도 안 남음
종목 코드 포맷 불일치
(5930 vs 005930)		 특정 종목만 안 옴아무것도 안 남음
프론트가 /app/ticks/...를 구독 구독 자체가 브로커에 등록조차 안 됨아무것도 안 남음
브로커 접두사에 /topic이 없음 전부 안 옴아무것도 안 남음

그래서 규약을 문서가 아니라 코드로 강제해야 한다. §4에서 다룬다.

3. 가장 단순한 스케줄러

@Component
@RequiredArgsConstructor
public class TickPlaybackScheduler {

    private final SimpMessagingTemplate template;
    private final TickRepository tickRepository;
    private final VirtualClock clock;          // 전 사용자 공용 가상 시계

    @Scheduled(fixedRate = 1000)
    public void playback() {
        // ① 가상 시계를 한 칸 민다
        Instant from = clock.now();
        Instant to   = clock.advance();

        // ② 그 구간의 틱을 한 번에 읽는다 — 접속자 수와 무관한 쿼리 1회
        List<Tick> ticks = tickRepository.findBetween(from, to);

        for (Tick tick : ticks) {
            // ③ ⭐ 약속된 규칙대로 destination 을 조립한다
            String destination = "/topic/ticks/" + tick.getCode();

            // ④ brokerChannel 로. 여기서 리턴은 "전송 완료"가 아니라 "큐에 넣음"
            template.convertAndSend(destination, tick);
        }
    }
}

이게 전부다. 구독자가 몇 명인지 알 필요도 없고, 세션을 뒤질 필요도 없다. "누구에게 보낼지"는 이미 구독 시점에 결정됐다.

4. 이 코드의 문제 네 가지

  1. 규약 문자열이 코드베이스에 흩어진다. "/topic/ticks/"가 스케줄러에도, 주문 서비스에도, 프론트에도 따로 적혀 있다. 한 곳에서 오타가 나면 §2의 조용한 실패가 된다.

    고치는 법: 목적지를 만드는 함수를 하나만 두고 서버 코드 전체가 그것만 쓰게 한다. 문자열 리터럴이 서버에 딱 한 번만 등장하게 만드는 것이 목표다. 프론트에도 같은 헬퍼를 두고, 규칙 자체는 API 명세에 적어 둔다.
  2. 아무도 안 보는 종목까지 DB에서 읽고 발행한다. 코스피 전 종목을 재생하는데 실제로 열려 있는 화면이 30종목이라면, 나머지는 전부 낭비다. 브로커가 빈 목록을 받아 아무 일도 안 하긴 하지만 — DB 조회와 JSON 직렬화는 이미 끝난 뒤다.

    고치는 법: SessionSubscribeEvent / SessionUnsubscribeEvent / SessionDisconnectEvent로 종목별 구독자 수를 세어 두고, 0명인 종목은 쿼리에서부터 뺀다.
  3. @Scheduled는 기본이 스레드 하나다. 그리고 convertAndSend의 JSON 직렬화는 이 스케줄러 스레드에서 일어난다 (0032 §2). DB 조회가 느리거나 틱이 많으면 다음 틱이 통째로 밀린다 — 가상 시계가 느려지는 것이다.

    고치는 법: 스케줄러 풀 크기를 늘리거나, 조회·직렬화를 가볍게 유지한다. "1초에 한 번 도는 일이 1초 안에 끝나는가"를 반드시 측정한다.
  4. 배속과 일시정지를 넣을 자리가 없다. fixedRate = 1000은 실제 1초다. 가상 시계를 2배속으로 돌리고 싶다면 이 값을 건드리는 게 아니라 한 번에 미는 가상 시간의 폭을 바꿔야 한다.

    고치는 법: "얼마나 자주 도는가"(실제 시간)와 "한 번에 얼마나 미는가"(가상 시간)를 분리한다. 일시정지는 가상 시계를 안 미는 것으로 구현한다 — 스케줄러는 계속 돌되 할 일이 없는 상태가 되는 편이 껐다 켜는 것보다 다루기 쉽다.

여기서 걸리는 함정 하나 — UNSUBSCRIBE에는 destination이 없다

2번의 "종목별 구독자 수 세기"를 구현하려 하면 바로 벽에 부딪힌다. 0031 §7에서 봤듯이 UNSUBSCRIBE 프레임에는 id만 있고 destination이 없다.

SUBSCRIBE id:sub-0 destination:/topic/ticks/005930 ← 여기엔 있다. 카운터 +1 가능. UNSUBSCRIBE id:sub-0 ← 이것뿐. 어느 종목인지 알 수 없다! 무엇을 -1 해야 하지?

그래서 카운터를 유지하려면 (세션ID, 구독ID) → 목적지 매핑을 직접 기억해 둬야 한다. SessionSubscribeEvent에서 그 매핑을 저장하고, SessionUnsubscribeEvent에서 그 키로 목적지를 되찾아 카운터를 내린다. 그리고 SessionDisconnectEvent에서는 그 세션에 딸린 매핑 전부를 훑어 일괄로 내려야 한다.

이게 브로커가 이미 하고 있는 일과 똑같다는 걸 눈치챘다면 정확하다. 브로커의 DefaultSubscriptionRegistry가 바로 그 매핑이다. 그래서 대안도 있다 — 카운터를 따로 두지 않고 SimpUserRegistry를 조회하는 방법. 다만 매 틱마다 조회하는 것은 비싸다. 틱은 초당 수십~수백 번 발생하고 구독 변화는 훨씬 드물다. 드물게 바뀌는 것을 미리 세어 두고, 잦은 쪽에서는 읽기만 하는 것이 이 상황의 정석이다.

5. 고친 스케줄러

// ── 규약을 코드로 강제한다. 문자열 리터럴은 여기 한 번만 등장. ──
public final class Destinations {
    private static final String TICKS = "/topic/ticks/";

    public static String ticks(String code) { return TICKS + code; }
    public static Optional<String> codeOf(String destination) {   // 역변환도 여기서
        return destination.startsWith(TICKS)
             ? Optional.of(destination.substring(TICKS.length()))
             : Optional.empty();
    }
}

// ── 종목별 구독자 수를 이벤트로 유지한다 ──
@Component
public class TickSubscriberCounter {

    private final Map<String, AtomicInteger> countByCode = new ConcurrentHashMap<>();
    // UNSUBSCRIBE 엔 destination 이 없으므로 (세션ID, 구독ID) → 종목코드 를 직접 기억한다
    private final Map<SubKey, String> codeBySubscription = new ConcurrentHashMap<>();

    @EventListener
    public void onSubscribe(SessionSubscribeEvent e) {
        StompHeaderAccessor h = StompHeaderAccessor.wrap(e.getMessage());
        Destinations.codeOf(h.getDestination()).ifPresent(code -> {
            codeBySubscription.put(new SubKey(h.getSessionId(), h.getSubscriptionId()), code);
            countByCode.computeIfAbsent(code, k -> new AtomicInteger()).incrementAndGet();
        });
    }

    @EventListener
    public void onUnsubscribe(SessionUnsubscribeEvent e) {
        StompHeaderAccessor h = StompHeaderAccessor.wrap(e.getMessage());
        // destination 이 없으니 아까 저장해 둔 매핑에서 되찾는다
        release(new SubKey(h.getSessionId(), h.getSubscriptionId()));
    }

    @EventListener
    public void onDisconnect(SessionDisconnectEvent e) {
        // 그 세션에 딸린 매핑을 전부 정리. 안 하면 카운터가 영원히 안 내려간다.
        codeBySubscription.keySet().removeIf(key -> {
            if (!key.sessionId().equals(e.getSessionId())) return false;
            decrement(codeBySubscription.get(key));
            return true;
        });
    }

    public Set<String> watchedCodes() {           // 스케줄러가 매 틱 읽는 값 — O(1) 조회
        return countByCode.entrySet().stream()
                .filter(en -> en.getValue().get() > 0)
                .map(Map.Entry::getKey).collect(toSet());
    }
}

// ── 스케줄러 ──
@Component
@RequiredArgsConstructor
public class TickPlaybackScheduler {

    private final SimpMessagingTemplate template;
    private final TickRepository tickRepository;
    private final TickSubscriberCounter counter;
    private final VirtualClock clock;

    @Scheduled(fixedRate = 200)                 // 실제 시간: 200ms 마다 깨어난다
    public void playback() {
        if (clock.isPaused()) return;                // 일시정지 = 시계를 안 민다

        Set<String> codes = counter.watchedCodes();
        if (codes.isEmpty()) { clock.advance(); return; }   // 보는 사람이 없으면 조회조차 안 한다

        Instant from = clock.now();
        Instant to   = clock.advance();               // 가상 시간: 배속만큼 민다

        // 구독 중인 종목만, 마지막 값 하나로 눌러서 (틱 폭주 대응)
        tickRepository.findLatestPerCode(from, to, codes)
            .forEach(tick -> template.convertAndSend(Destinations.ticks(tick.getCode()), tick));
    }
}
바뀐 점효과
Destinations.ticks(code)규약 문자열이 서버에 한 번만 존재 → 오타로 인한 조용한 실패 차단
watchedCodes()로 필터보는 사람 없는 종목은 DB 조회조차 안 한다
fixedRate=200 + clock.advance()실제 주기와 가상 시간 진행을 분리 → 배속 구현 가능
isPaused()스케줄러는 계속 돌되 시계만 멈춤 → 껐다 켜는 것보다 안전
findLatestPerCode200ms 창의 틱을 마지막 값으로 눌러 브라우저 폭주 방지

6. "구독은 되는데 메시지가 안 와요" 진단 순서

이 시리즈에서 배운 것을 순서대로 확인하면 대부분 여기서 잡힌다.

순서확인할 것어디서 배웠나
1브라우저 개발자도구 → 그 WebSocket 연결 → Messages에서 SUBSCRIBE 프레임이 실제로 나갔는지, destination 글자가 정확한지 0033 §1
2그 destination이 브로커 접두사(/topic, /queue)로 시작하는지. /app으로 구독하고 있진 않은지 0033 §4
3서버가 발행하는 문자열과 글자 단위로 같은지. 로그를 찍어 눈으로 대조 이 레슨 §2
4컨트롤러가 void인데 아무것도 발행하지 않고 끝나는 건 아닌지 0033 §6
5개인 데이터라면 — /user 접두사 설정과 브로커 접두사에 /queue가 있는지 0031 §6
6구독보다 발행이 먼저였던 건 아닌지. 브로커는 저장하지 않는다 0032 §4
7앱 서버가 2대 이상인데 SimpleBroker를 쓰고 있진 않은지 0034 §5
