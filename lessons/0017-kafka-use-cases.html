Kafka를 실제로 어디에 쓰는가: 대표 사용 사례 7가지

목표: 이전 레슨에서 배운 Topic/Partition/Producer/Consumer가 실무에서 어떤 문제를 풀 때 쓰이는지 7가지 대표 사례로 감을 잡는다. 마지막에는 당신이 실제로 도입하려는 상황에 대입해본다.

1. 일곱 가지 대표 사용 사례

Apache Kafka 공식 문서(Use Cases)가 정리한 사례들이다. 각 사례가 왜 Kafka로 풀리는지에 집중해서 보자.

① 메시징

전통적인 메시지 브로커(ActiveMQ, RabbitMQ)의 대체. 처리를 producer와 분리하거나, 처리되지 않은 메시지를 버퍼링하는 용도.
Kafka는 더 나은 처리량, 내장 파티셔닝, 복제, 내결함성을 제공해 대규모 메시지 처리에 강하다.
특징: 처리량은 낮아도 낮은 지연 시간 + 강한 내구성 보장이 필요한 경우가 많다.

② 웹사이트 활동 추적

Kafka의 원래 사용 사례. 페이지 조회, 검색 등 사용자 활동을 활동 유형별 Topic에 발행 → 실시간 처리/모니터링, 오프라인 리포팅(Hadoop 등)에서 구독.
특징: 페이지 조회마다 이벤트가 발생해 볼륨이 매우 크다.

③ 메트릭

운영 모니터링 데이터에 자주 사용. 분산 애플리케이션들의 통계를 집계해 중앙 집중식 피드를 만든다.

④ 로그 집계

여러 서버의 물리적 로그 파일을 모아 중앙(파일 서버, HDFS 등)에 저장하는 전통적 방식의 대체. Scribe, Flume과 비교됨.
Kafka는 파일 세부사항을 추상화해 로그를 메시지 스트림으로 다루므로 더 낮은 지연 시간과 다중 데이터 소스 지원이 쉽다.

⑤ 스트림 처리

여러 단계로 구성된 처리 파이프라인: 원시 데이터를 Topic에서 소비 → 집계·보강·변환 → 새 Topic에 발행 → 다음 단계가 다시 소비.
Kafka Streams 라이브러리가 이를 지원. 대안으로 Apache Storm, Apache Samza.

⑥ 이벤트 소싱

Event sourcing은 상태 변경을 시간순 레코드 시퀀스로 기록하는 애플리케이션 설계 방식.
Kafka의 큰 저장 로그를 지지하는 특성이 이런 애플리케이션의 백엔드로 적합하게 만든다.

⑦ 커밋 로그

분산 시스템을 위한 외부 commit-log 역할. 노드 간 데이터 복제를 돕고, 장애 노드의 재동기화 메커니즘으로 동작.
log compaction 기능이 이 용도를 지원. Apache BookKeeper와 유사한 위치.

2. 왜 이렇게 다양한 사례에 쓰이는가

표면적으로 "메시징"과 "커밋 로그"는 완전히 다른 문제처럼 보인다. 하지만 둘 다 이전 레슨에서 본 같은 하나의 성질에서 나온다. 

Kafka의 본질: "순서가 보장된, 삭제되지 않는, 분산 저장된 append-only 로그"

  이 로그를 —
    빨리, 짧게 소비하면            → 메시징
    유형별로 나눠서 쌓으면          → 활동 추적 / 메트릭 / 로그 집계
    단계별로 다시 발행하며 이어가면  → 스트림 처리
    "상태"가 아니라 "변경 사건"으로 다루면 → 이벤트 소싱
    노드 간 복제 순서의 기준으로 쓰면 → 커밋 로그

→ 하나의 데이터 구조가 관점에 따라 일곱 가지 얼굴로 보이는 것이다.

3. 비교 대상으로 감 잡기

Kafka 사용 사례전통적으로 쓰던 것Kafka가 더 나은 점
메시징 ActiveMQ, RabbitMQ 더 나은 처리량, 내장 파티셔닝·복제·내결함성.
로그 집계 Scribe, Flume, 파일 서버/HDFS 직접 적재 낮은 지연 시간, 여러 데이터 소스·분산 소비를 쉽게 지원.
스트림 처리 Apache Storm, Apache Samza Kafka Streams는 Kafka에 내장되어 별도 클러스터 운영이 필요 없다.
커밋 로그 Apache BookKeeper 같은 시스템으로 메시징·스트림 처리까지 함께 커버.

4. 당신의 상황에 대입해보기

당신은 백엔드 개발자로서 실제 Kafka 도입을 계획하고 있다. 지금 겪고 있거나 예상되는 문제가 위 7가지 중 어느 것에 가장 가까운지 스스로 짚어보자. 이후 레슨의 방향(Consumer Group 상세, Kafka Streams, 특정 도입 패턴 등)을 여기서 정할 수 있다.

서비스 간 이벤트 전달이 목적이라면

→ 메시징 또는 이벤트 소싱 쪽에 가깝다. Producer/Consumer, Consumer Group 소비 방식을 깊게 다루는 레슨이 유용하다.

여러 소스의 로그·지표를 모으는 게 목적이라면

→ 로그 집계 / 메트릭에 가깝다. Producer 다중화, retention 정책, Kafka Connect(source connector) 쪽 레슨이 유용하다.

데이터를 단계별로 가공해 전달하는 게 목적이라면

→ 스트림 처리에 가깝다. Kafka Streams API, topic-to-topic 파이프라인 구조를 다루는 레슨이 유용하다.
