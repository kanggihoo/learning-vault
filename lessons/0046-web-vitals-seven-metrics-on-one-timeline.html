Web Vitals · 1/N · 레슨 0046 · 지도 레퍼런스 0022의 §1–§4를 판다

일곱 지표를 한 타임라인 위에 놓기

LCP, INP, CLS, TTFB, FCP, TBT, DCL. 이름이 일곱 개나 되는 이유는 하나다 — "페이지가 빠르다"는 말이 사실 서로 다른 세 질문이기 때문이다. 보이나? 반응하나? 흔들리나? 이 레슨은 일곱 이름을 그 세 질문에 배정하고, 페이지 하나의 타임라인 위 어디에 있는지 가리킬 수 있게 만든다. 그게 되면 리포트가 읽힌다.

이 레슨 하나로 얻는 것. ① 일곱 이름을 들으면 타임라인 어디인지 가리킬 수 있다. ② 셋만 "Core"인 이유를 판별 기준 두 개로 말할 수 있다. ③ Lighthouse 점수와 실제 사용자 데이터가 다른 수치인 이유를 안다. ④ 나쁜 지표 하나를 보고 "서버 몫인가 프론트 몫인가"를 첫 질문으로 던질 수 있다.

§1 · 서버 로그가 아니라 사용자의 눈과 손

백엔드에서 "빠르다"는 p99 응답 300ms처럼 서버가 응답을 보낸 시각으로 잰다. Web Vitals는 기준점이 다르다. 구글이 정의한 이 지표들은 전부 사용자 브라우저에서, 사용자가 체감하는 순간을 잰다. 서버가 100ms에 응답해도 이미지가 4초 뒤에 뜨면 LCP는 4초다. 이 관점 전환이 이 주제의 전부다.

구글은 사용자 경험을 세 질문으로 쪼갰고, 각 질문에 Core Web Vital 하나씩을 배정했다.

보이나? — 로딩

LCP (Largest Contentful Paint)

뷰포트 안 가장 큰 이미지·텍스트 블록이 렌더된 시각. "주요 콘텐츠가 보였다."

good ≤ 2.5s · poor > 4.0s

반응하나? — 상호작용

INP (Interaction to Next Paint)

클릭·탭·키 입력 후 다음 프레임이 그려질 때까지. 페이지 수명 전체에서 최악값.

good ≤ 200ms · poor > 500ms

흔들리나? — 시각 안정

CLS (Cumulative Layout Shift)

읽는 중 내용이 예고 없이 밀린 정도의 누적. 유일하게 시간이 아닌 무단위 점수.

good ≤ 0.1 · poor > 0.25

출처: web.dev — Web Vitals. 세 질문 프레임(loading · interactivity · visual stability)은 구글의 원문 분류다.

§2 · 타임라인 — 일곱 개가 놓이는 자리

이제 나머지 넷을 얹는다. 페이지 하나를 주소창 엔터부터 사용자가 떠날 때까지 한 줄로 펴면 이렇다.

왼쪽에서 오른쪽으로 읽으면 한 페이지의 이야기가 된다.

  1. TTFB — 브라우저가 요청을 보내고 HTML 응답의 첫 바이트를 받은 시각. 리다이렉트·DNS·TCP/TLS 연결·서버 처리 시간이 전부 이 안에 있다. 서버가 대답을 시작했다.
  2. FCP — 텍스트든 이미지든 배경색 아닌 무엇이든 처음 화면에 그려진 시각. 흰 화면이 끝났다.
  3. LCP — 뷰포트 안 가장 큰 요소가 그려진 시각. 진짜 내용이 보인다. 여기까지가 "로딩 축"이고, 앞의 둘은 LCP의 부분 구간이다.
  4. TBT — FCP 이후 main thread가 50ms 넘게 막힌 태스크들의 초과분 합. 250ms 태스크는 200ms를 기여한다. 클릭해도 먹통일 시간의 총량. Lighthouse(lab)에서만 나온다.
  5. INP — 사용자가 실제로 누른 모든 상호작용 중 가장 느렸던 것(50회당 1회는 제외). 로드가 끝난 뒤에도 페이지를 떠날 때까지 계속 잰다. 눌렀을 때 반응했나.
  6. CLS — 시간축 위가 아니라 전체를 덮는 띠다. 언제든 이미지·광고·폰트가 늦게 도착해 내용을 밀면 점수가 쌓인다. 읽다가 밀렸나.
  7. DCL — HTML 파싱이 끝나고 defer 스크립트까지 실행된 순간을 알리는 브라우저 이벤트. 이미지는 기다리지 않는다. 사용자 화면과는 직접 관계가 없다.

DCL의 위치는 고정이 아니다. 서버가 완성된 HTML을 보내는 페이지는 브라우저가 파싱하면서 그리기 시작하므로 FCP가 DCL보다 먼저 올 수 있다. 반대로 <div id="root"></div>만 담긴 SPA 셸은 파싱이 순식간에 끝나 DCL이 먼저 오고, 그 뒤 JS가 렌더해야 FCP가 온다. 그래서 SPA에서 "DCL 0.3초"는 사용자에게 아무 의미가 없다. 출처: MDN — DOMContentLoaded.

§3 · 왜 셋만 Core인가 — 판별 기준 두 개

일곱 중 셋만 Core Web Vitals다. 구글이 임의로 고른 게 아니라 두 조건을 다 만족하는 것만 남긴 결과다.

지표① 사용자가 체감하는 결과인가② 실사용자 브라우저(field)에서 잴 수 있나판정
LCP예 — 주요 콘텐츠가 보인 순간예Core
INP예 — 누른 뒤 화면이 바뀐 순간예 (field에서만)Core
CLS예 — 밀림을 겪은 정도예Core
TTFB부분 — LCP의 앞 구간일 뿐예보조 · LCP 진단용
FCP부분 — "무엇이든" 보인 것, 주요 콘텐츠 아님예보조 · LCP 진단용
TBT간접 — 먹통 가능성의 총량아니오 — lab 로드 시퀀스 전제보조 · INP의 lab 대리
DCL아니오 — 파서 상태예지표가 아님 · 디버깅 기준선

구글 원문이 이 표를 그대로 뒷받침한다. TTFB와 FCP는 "로딩 경험의 중요한 측면이며 LCP 문제를 진단하는 데 유용"하고, TBT는 "INP에 영향을 줄 수 있는 상호작용 문제를 잡아내는 lab 지표지만, field에서 측정할 수 없기 때문에 Core Web Vitals에 포함되지 않는다." (web.dev — Web Vitals)

INP를 lab에서 못 재는 이유가 곧 TBT가 존재하는 이유다. INP는 "사용자가 실제로 누른 순간"의 반응이다. 실험실은 사용자가 언제 무엇을 누를지 모른다. 그래서 대신 "로드 중 main thread가 얼마나 막혀 있었나"(TBT)를 재고, 그게 낮으면 INP도 낮을 가능성이 높다고 본다. 대리 지표라는 말은 정확히 이 뜻이다 — 같은 것을 다른 환경에서 어림잡는 것. (web.dev — Lab and field data differences)

§4 · DCL은 왜 목록에 끼어 있나

"보조 성능 지표"로 TTFB·FCP·TBT와 함께 DCL을 묶어 왔다면, 하나는 종류가 다르다. 여섯은 화면 또는 입력에 관한 값이고, DCL은 문서(document) 상태에 관한 이벤트다. MDN의 정의는 이렇다 — "HTML 문서가 완전히 파싱되고 모든 defer 스크립트가 다운로드·실행되었을 때 발생한다. 이미지, 서브프레임, async 스크립트의 로드 완료는 기다리지 않는다."

그래도 알아야 하는 이유는 두 가지다.

  • DevTools에서 매번 보인다. Network 패널의 파란 세로선이 DCL, 빨간 선이 load다. 리포트를 읽을 때 "이 선이 뭐지"에 답해야 한다.
  • DCL과 FCP의 간격이 진단 정보다. DCL이 빨리 왔는데 FCP가 한참 뒤면, HTML은 다 읽었지만 JS가 화면을 만들기까지 걸린 시간이다. 전형적인 CSR SPA 증상이고, SSR로 옮기면 그 간격이 줄어드는 게 눈에 보인다.

같은 이유로 load 이벤트도 지표가 아니다. MDN: "load는 완전히 로드된 페이지를 감지할 때만 써야 한다. DOMContentLoaded가 더 적절한 자리에 load를 쓰는 것은 흔한 실수다." 둘 다 Navigation Timing의 타임스탬프로 읽는다 — 지도 §7 스니펫.

§5 · 숫자 — 임계값과 75퍼센타일

표에 적힌 2.5초·200ms·0.1은 사이트의 어느 값에 적용하는가. 평균이 아니다. 모바일·데스크톱 각각 75퍼센타일이다. 백엔드의 p99 SLO와 논리가 같고 분위수만 다르다.

구글이 75를 고른 이유는 두 문장으로 적혀 있다 — "75퍼센타일을 쓰면 방문 4회 중 3회가 목표 수준 이상의 경험을 했음을 안다. 또한 75퍼센타일 값은 이상치의 영향을 덜 받는다." p99를 쓰면 느린 기기·느린 망 몇 명이 전체 판정을 뒤집고, 평균을 쓰면 그 몇 명이 값을 끌어올린다. (web.dev — Defining the Core Web Vitals thresholds)

임계값 자체도 근거가 있다. 외울 필요는 없고, "왜 2.5초냐"에 답할 수 있으면 된다.

  • LCP 2.5s — Miller·Card의 인지 연구: 사용자의 주의가 유지되는 한계가 "약 0.3~3초". 2.5는 그 안이면서 당시 모바일 사이트 42%가 달성 가능했다.
  • INP 200ms — Michotte의 인과 지각 연구: "약 100ms까지"는 화면 변화를 내 행동의 결과로 느낀다. 200은 그것과 달성 가능성(56%)의 절충.
  • CLS 0.1 — 선행 연구가 없어 실제 페이지를 보며 정했다. "0.1 이하는 눈에 띄지만 과도하게 방해하지 않았다."

§6 · Lab과 Field — 같은 이름, 다른 숫자

리포트를 처음 열면 혼란스러운 지점이 여기다. PageSpeed Insights 한 화면에 같은 지표가 두 번 나온다. 위쪽은 field(CrUX — 실제 크롬 사용자 28일 데이터, p75), 아래쪽은 lab(Lighthouse — 지금 이 순간 정해진 기기·네트워크로 한 번 돌린 값).

그리고 Lighthouse의 Performance 점수는 다섯 지표의 가중 합이다 — FCP 10% · Speed Index 10% · LCP 25% · TBT 30% · CLS 25%. INP·TTFB·DCL은 점수에 없다. (Lighthouse — Performance scoring)

따라서 "Lighthouse 95점"은 "Core Web Vitals 통과"가 아니다. INP가 점수에 없으니, TBT를 통과한 사이트가 실사용자 INP에서 poor일 수 있다. 프론트 결과물을 리뷰할 때 Lighthouse 점수만 들고 오면 첫 질문은 정해져 있다 — "field INP는 얼마인가요?"

§7 · 백엔드 개발자의 칸

일곱 지표 중 서버가 직접 움직일 수 있는 것은 TTFB다. 그런데 TTFB는 Core가 아니다. 그러면 서버는 Core Web Vitals와 무관한가? 아니다 — TTFB는 LCP 안에 들어 있다.

구글이 제시한 2.5초 LCP의 이상적 배분이다 (web.dev — Optimize LCP).

TTFB
~40% · ≈1.0s
load delay
<10%
resource load
~40% · ≈1.0s
render delay
<10%

왼쪽부터: 서버가 HTML 첫 바이트를 주기까지 → 브라우저가 LCP 리소스(보통 이미지)를 발견하기까지의 공백 → 그 리소스를 받는 시간 → 받고도 그리지 못한 공백. 구글의 원칙: "LCP 시간의 대부분은 HTML 문서와 LCP 리소스를 내려받는 데 쓰여야 한다. 둘 중 무엇도 로딩되지 않는 시간은 전부 개선 기회다."

그러니 백엔드의 예산은 약 1초다. 그 1초 안에 리다이렉트(HTTP→HTTPS 한 번이면 왕복 하나가 사라진다), TLS 핸드셰이크, DB 쿼리, SSR 렌더, 캐시 미스가 전부 들어간다. web.dev의 TTFB 문서는 이걸 백엔드의 책임으로 명시하고 경고 하나를 덧붙인다 — "캐싱은 훌륭하지만 느린 백엔드를 가려서 긴 TTFB의 진단을 어렵게 만들 수 있다." (web.dev — Optimize TTFB)

리뷰에서 바로 쓰는 첫 질문. 나쁜 LCP 하나를 봤을 때 — "TTFB가 얼마죠? 0.8초 넘으면 제 쪽(서버)이고, 안 넘으면 이미지 발견·렌더 쪽이니 프론트 쪽입니다." 책임 칸을 먼저 나누는 이 한 문장이 성능 회의를 취향 싸움에서 구해 낸다. 다른 증상들의 첫 질문은 지도 §6 진단표에 있다.

§9 · 다음

지도가 생겼으니 이제 축을 하나씩 판다. 다음 레슨은 로딩 축 — TTFB → FCP → LCP를 4구간으로 쪼개고, "LCP 리소스를 늦게 발견한다"가 코드에서 어떤 모습인지(lazy-load된 히어로 이미지, CSS 배경이미지, JS 뒤에 숨은 <img>)를 본다. 그 다음이 반응 축(INP 3구간 · long task · TBT 계산), 그 다음이 CLS 산식, 마지막에 실제 PSI 리포트 하나를 같이 읽는다.

먼저 읽을 1차 출처 (짧고, 이 레슨의 원본이다):

  • web.dev — Web Vitals — Core 3종·75퍼센타일·보조 지표 관계·도구 매트릭스가 한 페이지에. 이 레슨에서 딱 하나만 읽는다면 이것.
  • web.dev — Defining the Core Web Vitals metrics thresholds — "왜 2.5초, 왜 75퍼센타일"의 연구 근거. 면접에서 임계값을 말할 때 이 페이지가 배경이다.
  • web.dev — Lab and field data differences — §6의 원본. INP를 lab에서 못 재는 이유가 여기 있다.

연결된 자료: 레퍼런스 0022 — Web Vitals 지도 (§2 지표 표 · §6 증상→지표→책임 칸 진단표 · §7 측정 스니펫). 75퍼센타일의 논리는 레슨 0037의 응답 측정(p99)과 같은 자리에 있다.
