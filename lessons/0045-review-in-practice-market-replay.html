실전 리뷰 — 배운 어휘로 실제 문서 읽기

여덟 레슨이 끝난 뒤 남는 유일한 질문은 이것이다 — 이 어휘가 실제로 도구가 되는가. 그래서 마켓 리플레이(S15P21A605)의 백엔드 설계 문서를 질문 카드로 읽고, 0044 §2의 네 산출물 — 비위험 · 위험 · 민감점 · 절충점 — 으로 정리했다.

먼저 정직하게. 이 문서들은 좋다. ADR 네 편은 문맥·대안 비교·기각 사유· 감수하는 것까지 갖췄고, CONTEXT.md는 사실상 보편 언어 사전이다. 그래서 이 리뷰의 절반은 이미 맞는 결정에 이름을 붙이는 일이다. 지적 목록만 있는 리뷰는 방어를 부르고, 무엇보다 좋은 결정에 이름이 없으면 나중에 누가 바꾸려 할 때 지킬 수 없다.

§0 · 읽은 범위

backend/docs/architecture/overview.md · backend/docs/CONTEXT.md · backend/docs/decisions-later.md · backend/docs/adr/0001~0004 · docs/projects/market-replay-api/{ord,acc,ipo}.md의 관련 절. 읽지 않은 것: 기능명세서, ERD, 나머지 API 문서 15편, 실제 코드. 따라서 아래 발견은 문서에 근거한 것이고, 코드에 이미 반영돼 있다면 그 자체가 답이다.

§1 · 비위험 — 이미 맞는 결정들 NONRISK

N1. CONTEXT.md는 보편 언어 사전이다 — 0041 §2

Account (계좌): 한 User 가 한 시즌에서 갖는 자산 전체 (…) 로그인 계정의 뜻으로 쓰지 않는다 (그쪽은 User · OAuth Account). — backend/docs/CONTEXT.md

Fowler가 BoundedContext에서 지목한 다의어 문제 — 같은 단어가 집단마다 다른 뜻을 갖는 것 — 를 회피어(Avoid) 목록까지 붙여서 정면으로 닫았다. "Tick" 항목이 "Candle·캔들·봉 — 고가·저가·시가를 쓰지 않는 단일 가격 모델과 정면으로 충돌한다"고 적은 것은 용어가 데이터 모델의 제약을 실어 나른다는 걸 알고 쓴 문장이다.

이름 붙이기: 이건 경계 컨텍스트의 보편 언어이고, 나중에 서비스를 나눌 일이 생기면 이 사전이 그대로 경계 후보 목록이 된다. 지금 당장 쓰는 문서가 아니라 미래의 자산이다.

N2. IPO 청약이 자연 멱등이다 — 0042 §2

단수 리소스라 POST가 멱등이 된다. 두 번 눌러도 증거금이 두 번 잠기지 않고 같은 청약을 반환한다. 컬렉션이었다면 중복 방지를 위한 상태 검사가 별도로 필요했다. — docs/projects/market-replay-api/ipo.md

멱등 키도 중복 제거 저장소도 없이 자원 모델만으로 멱등을 만들었다. 0042 §2가 "자연 멱등을 먼저 설계하고, 안 되는 것에만 중복 제거 기법을 더하라"고 한 것의 정확한 실행이다. DELETE가 청약하지 않은 공모에도 204를 주는 것도 같은 원리다.

N3. lastAckedTickSeq를 max()로 갱신한다 — 0042 §2

max()인 이유: 재시도나 지연으로 낡은 값이 도착해도 뒤로 가지 않는다. 같은 값을 여러 번 보내도 결과가 같다. — docs/projects/market-replay-api/acc.md

0042 §2에서 경고한 것 — "절대 상태로 바꾸면 순서 문제가 생긴다" — 을 max()가 통째로 막는다. 멱등이면서 순서에도 무관하다. 이건 Azure가 말한 교환 가능한 갱신(commutative update)이고, 분산 시스템에서 가장 안전한 형태의 쓰기다.

게다가 CONTEXT.md가 "lastSeenAt·마지막 접속을 쓰지 않는다 — 연결 기반 신호는 자동 재연결과 백그라운드 탭에서 전부 깨진다"고 이유까지 적어 뒀다. 워터마크를 시각이 아니라 순번으로 잡은 것 자체가 결정이다.

N4. ADR에 "감수하는 것"이 실제로 적혀 있다 — 0044 §4

0044 §4에서 "Consequences가 장점뿐이면 트레이드오프를 계산하지 않은 것"이라고 했다. ADR-0003은 감수하는 것을 여덟 줄 적었다 — 더미 ID 토큰, UserRepository 직접 참조, "유일한 격리 누출점"까지 스스로 이름 붙였다. ADR-0001은 "Redis 장애 시 전원 로그아웃"을 영향에 그대로 남겼다.

리뷰어로서 할 말: 이 칸이 채워져 있으면 그 결정은 논쟁할 필요가 없다. 대가를 알고 낸 결정이기 때문이다. 논쟁해야 하는 건 이 칸이 빈 결정이다.

N5. fail-closed가 기본값이다 — 0038 §3 보안 전술

인증 우회 기본값 fail-closed: 프로파일(미지정 시 켜짐) vs 프로퍼티(미지정 시 꺼짐). — ADR-0003

보안 전술 목록의 "기본 설정 변경"과 "노출 제한"을 동시에 만족한다. 게다가 "빈 미생성이 경로 차단보다 안전"은 인가 설정 실수라는 결함 자체를 예방하는 선택이다 — 감지·복구가 아니라 예방 칸이다.

N6. 리소스를 화면이 아니라 생명주기로 잘랐다 — 0041 §1

생명주기가 반대다. 미체결은 수정·취소되고 폐장에 소멸한다. 체결은 영구 불변이며 복기·시즌 리포트·MDD·승률의 원천이다. — ord.md, orders와 executions를 나눈 이유

0041 §1의 "잘못된 경계 기준 세 가지"(화면·테이블·계층)를 전부 피했다. 필드가 겹치지 않고, 생명주기가 반대고, 조회 패턴이 다르다는 세 근거는 그대로 경계가 맞는지 검사하는 질문이다.

§2 · 위험 RISK

R1. 품질 속성 시나리오가 하나도 없다 — 0037 §3

읽은 문서 전체에서 숫자로 된 응답 측정을 하나도 못 찾았다. 가용성 목표도, 응답 시간 목표도, 동시 접속 규모도 없다. ADR-0004는 이걸 정직하게 인정한다:

clientOutboundChannel 스레드풀·버퍼는 기본값이다. 부하 데이터 없이 정하면 추측이다. — ADR-0004, 결과

태도는 맞다. 문제는 부하 데이터를 언제 얻을지다. decisions-later.md에서 "부하 테스트 시나리오 파일"은 P3이고, 미룬 이유는 "부하를 걸 대상 도메인 API가 아직 없어 지금 쓰면 곧 버린다"다. 그런데 지금은 ord·acc·ipo API 계약이 다 나와 있다.

"추측하지 않겠다"가 "영원히 정하지 않는다"로 굳는 경로가 여기다. 숫자가 없으면 적합성 함수도 못 만들고, 발표 당일에 "이 정도면 되는 건가"를 판정할 기준도 없다.

제안: 시나리오 세 개만 6부로 쓴다. 30분이면 된다. ① 심사 중 동시 접속 N명에서 POST /orders p99 · ② 한 틱에서 메시지 19종이 전 접속자에게 나가는 데 걸리는 시간 · ③ Redis가 죽었을 때 무엇이 어떻게 되는지. 셋 다 이미 아는 값으로 채울 수 있다 — N은 심사 인원, 틱 간격은 31~36초.

R2. 선언된 스타일이 강제되지 않는다 — 그리고 첫 균열이 이미 기록돼 있다 — 0039 §4 · 0044 §3

overview.md는 계층형의 제약을 명확히 선언한다.

단방향 흐름: Controller → Service → Repository → Entity · global → domain 역참조 금지 · 도메인 간 협력: 엔티티 직접 참조 지양, Service 호출로 협력. — backend/docs/architecture/overview.md

그런데 이걸 검사하는 장치가 문서 어디에도 없다. 그리고 ADR-0003이 첫 균열을 스스로 기록했다:

UserRepository 직접 참조: 테스트 지원 서비스에서 (…) 저장소 직접 호출 (의도적 Service 우회, 기능 제거 시 함께 제거). — ADR-0003, 감수하는 것

문서화된 예외 하나는 문제가 아니다. 문제는 두 번째다 — 검사가 없으면 두 번째 우회는 ADR에 적히지 않는다. 그리고 "지양"은 강제가 아니다. 0039의 문장 그대로: 제약을 자동으로 강제하지 않는 스타일은 스타일이 아니라 희망이다.

제안: 아키텍처 테스트 세 줄이면 시작된다 — ① global이 domain을 참조하면 실패 ② controller가 repository를 직접 참조하면 실패 ③ 도메인 패키지 간 순환 의존이 있으면 실패. 난도가 낮고 효과가 즉시라 가장 먼저 할 일 후보다(§4).

R3. POST /orders가 멱등하지 않다 — 0042 §2·§3

이 프로젝트는 IPO 청약을 일부러 멱등하게 설계했다(N2). 그리고 그 문서가 바로 옆에 이렇게 적었다 — "컬렉션이었다면 중복 방지를 위한 상태 검사가 별도로 필요했다."

POST /api/v1/orders가 정확히 그 컬렉션이다. 그리고 ord.md의 검증 표(기획서 6.5)에는 중복 방지 항목이 없다 — 수량·지정가·phase·잔고·수량·휴장·UPCOMING까지 일곱 줄인데 중복이 없다.

중복이 생기는 경로결과
사용자가 버튼을 두 번 누른다시장가 매수 2회 — 즉시 전량 체결이므로 되돌릴 수 없다
응답이 늦어 클라이언트가 재시도한다같은 주문 2건. 사용자는 왜 그런지 모른다
모바일에서 연결이 끊긴 채 성공했다재전송 → 2회 체결

"모의투자라 돈이 아니잖아"가 반론이 되지 않는다. 이 게임에서 잔고가 곧 점수다. 중복 매수는 순위를 바꾸고, 사용자는 "내가 두 번 눌렀나?"라고만 생각하고 신고하지 않는다 — 감지되지 않는 결함이다.

제안 두 가지. ⓐ 클라이언트 생성 멱등 키를 헤더로 받고 (Stripe 방식) 키 컬럼에 유니크 제약 — 가장 확실하지만 프론트 계약이 바뀐다. ⓑ 짧은 시간 창 안의 동일 조건 주문을 409로 거부 — 계약 변경이 없지만 정당한 연속 주문도 막을 수 있다. 어느 쪽이든 지금 정하는 게 낫다 — 체결이 붙은 뒤에는 되돌리는 코드가 필요해진다.

R4. 감지 전술이 비어 있다 — 0038 §2·§3

복구와 예방은 있다 — fail-closed 플래그, 세션 즉시 무효화, 구독 검증 인터셉터, 재연결 백오프. 감지는 없다. 특히 두 곳이 조용히 실패한다.

어디조용히 실패하는 방식필요한 감지
clientOutboundChannel 기본값 버퍼가 넘치면 메시지가 버려진다. 사용자는 "가끔 틱이 안 온다"만 겪고, 서버는 정상이다 드롭 카운터 · 전송 지연 지표. 틱은 절대시각 스케줄이라 "예정 − 실제"가 그대로 지표가 된다
orders.lockedAmount ↔ accounts.lockedKrw 같은 사실을 두 곳에 적는다(ord.md 열린 질문 1이 "저장"으로 표기). 어긋나도 아무도 모른다 정합성 검사 — 미체결 예약 합계와 계좌 잠금액이 같은지 주기 대조

두 번째가 특히 0042 §6 ③과 같은 형태다 — 보상·복구 체계에 감지가 없으면 어긋난 상태가 조용히 남는다. 그리고 이 게임에서 잠금액이 어긋나면 사용자가 "왜 주문이 안 되지"를 겪고 원인은 안 나온다.

§3 · 민감점과 절충점 SENSITIVITY / TRADEOFF

T1. messageBrokerTaskScheduler 공유 — 진짜 절충점 — 0044 §2

TaskScheduler가 둘이 되면 나중에 붙는 @Scheduled의 스케줄러 선택이 모호해진다. 역으로, 이 빈이 있으면 Boot는 taskScheduler를 만들지 않으므로 게임 시계의 @Scheduled가 이 스케줄러 풀을 함께 쓴다 — 부하 데이터가 생기면 그 시점에 분리를 판단한다. — ADR-0004, 결과

ADR이 이미 정확히 짚었다. 이름을 붙이면 이건 교과서적 절충점이다 — 하나의 결정이 두 품질에 반대 방향으로 작용한다.

축빈 하나(현재)빈 둘로 분리
변경 용이성모호함 없음. @Scheduled가 어디로 갈지 명확스케줄러 선택을 매번 명시해야 함
격리성 / 시간 정확도브로커 전송이 밀리면 틱 스케줄이 함께 밀린다틱 시계가 브로커 부하와 무관해짐

여기 하나가 비어 있다 — 분리 판단의 트리거. "부하 데이터가 생기면"은 조건이 아니라 희망이다. 그런데 이 프로젝트에는 트리거로 쓸 수 있는 지표가 이미 설계상 존재한다 — 틱을 절대시각으로 스케줄하므로 "예정 시각 − 실제 발행 시각"이 그대로 관측된다 (0036).

제안: ADR-0004에 한 줄 추가 — "틱 지연이 N ms를 넘는 일이 관측되면 스케줄러를 분리한다." 숫자를 넣는 순간 이 미결이 결정이 된다.

민감점무엇에 민감한가상태
clientOutboundChannel 스레드풀·버퍼 실시간 전달의 신뢰성 — 넘치면 메시지 유실 기본값 + 관측 없음 (R1·R4와 같은 뿌리)
세션 유휴 만료 1일 Redis 메모리 ↔ 탈취 세션의 생존 기간 decisions-later에 "절대 만료" 항목으로 미정
STOMP 하트비트 10초 ↔ nginx proxy_read_timeout 연결 유지 — 타임아웃이 하트비트보다 짧으면 주기적으로 끊긴다 이미 스스로 찾아 decisions-later에 적어 뒀다. 민감점 식별의 모범 사례

세 번째 줄이 이 리뷰에서 가장 인상적인 항목이다. "기본값(60s)으로도 동작하지만 명시하지 않으면 나중에 값을 줄인 사람이 연결이 주기적으로 끊기는 이유를 찾지 못한다" — 민감점의 정의를 그대로 쓴 문장이고, 어휘를 몰라도 개념은 이미 쓰고 있었다는 뜻이다.

§4 · 무엇부터 하나 — 두 축으로

0044 §1의 방식대로 발견을 (비즈니스 중요도, 기술 난도) 두 축에 놓는다. 중요도가 높은 것 중 난도가 낮은 것이 먼저다.

§5 · 이 실험에서 확인된 것

가설결과
어휘가 없던 발견을 만들어낸다 그렇다. R3(주문 멱등성)와 T1(스케줄러 절충점)은 문서를 그냥 읽어서는 안 나온다. R3는 "IPO는 멱등인데 주문은?"이라는 대조 질문에서 나왔고, T1은 ADR이 이미 서술한 것에 이름을 붙이자 결론(트리거 부재)이 따라 나왔다.
어휘가 좋은 결정을 방어하게 해 준다 그렇다. N1~N6은 전부 "왜 이게 좋은가"에 일반명사로 답할 수 있게 됐다. "이거 잘했네요"와 "이건 자연 멱등이라 중복 제거 저장소가 필요 없습니다"는 다른 문장이다.
어휘가 지적 목록이 되지 않는다 주의가 필요하다. 이 문서에서 비위험을 먼저 쓴 것은 의도적이다. 네 산출물 중 비위험을 빼면 어떤 리뷰든 공격으로 읽힌다.
문서가 어휘를 모르고도 개념은 쓰고 있었다 여러 곳에서. nginx 타임아웃 항목은 민감점의 정의를 그대로 썼고, IPO 단수 리소스는 자연 멱등이며, max()는 교환 가능한 갱신이다. 어휘의 값은 없던 걸 만드는 게 아니라, 흩어진 판단을 같은 이름으로 묶어 재사용하게 하는 것이다.

가장 중요한 발견은 R3의 발견 방식이다. 나는 주문 문서를 먼저 읽고 "멱등성이 없네"라고 판단한 게 아니다. IPO 문서가 스스로 쓴 문장("컬렉션이었다면 중복 방지가 별도로 필요했다")을 읽고, 그 조건이 성립하는 다른 엔드포인트를 찾은 것이다. 같은 팀이 한 곳에서 내린 좋은 판단을 다른 곳에 적용했는지 확인하는 것 — 이게 어휘를 가진 리뷰어가 할 수 있는 가장 값싼 고품질 리뷰다.
