브로커만 갈아끼우기: SimpleBroker → RabbitMQ Relay

0031 §9에서 "서버가 2대가 되는 순간 SimpleBroker는 무너진다"고 했다. 이 레슨은 그 다음 장면이다 — 무엇이 바뀌고, 무엇이 놀랄 만큼 안 바뀌는지. 가는 길에 세 채널도 한 번 더 정리한다.

1. 세 채널, 다시 한 번

0032 §3에서 채널이 네트워크가 아니라 JVM 안의 큐 + 스레드 풀 + 수신자 목록이라는 걸 봤다. 셋을 방향으로 다시 세워보면 이렇다.

채널방향누가 넣나누가 꺼내나
clientInboundChannel클라이언트 → 서버 내부 StompSubProtocolHandler
(소켓에서 읽은 CONNECT/SUBSCRIBE/SEND)		 어노테이션 핸들러 · 브로커 · UserDestination 핸들러
brokerChannel서버 코드 → 브로커 내 애플리케이션 코드
(SimpMessagingTemplate, @SendTo 반환값)		 브로커 (하나뿐)
clientOutboundChannel서버 내부 → 클라이언트 브로커 (복제된 메시지들) StompSubProtocolHandler
(MESSAGE/CONNECTED로 인코딩해 소켓에 씀)

세 채널의 성격 차이는 어디에 인터셉터를 걸어야 하는가를 정할 때 그대로 드러난다.

하고 싶은 일거는 곳왜 거기인가
토큰 검증 · CONNECT 시 인증clientInboundChannel 클라이언트가 보낸 것을 서버가 처리하기 전에 잡는 유일한 지점
SUBSCRIBE 권한 검사clientInboundChannel 브로커가 레지스트리에 등록하기 전에 막아야 한다
발행 메시지 로깅 · 감사brokerChannel 서버가 발행하는 것만 골라 볼 수 있다
나가는 메시지 통계 · 마스킹clientOutboundChannel 소켓에 쓰이기 직전의 마지막 지점

2. 라우팅은 브로커가 하는 일이 아니다

흔한 오해 하나 — "브로커가 메시지를 보고 컨트롤러로 보내준다"가 아니다. 브로커는 @MessageMapping이 존재하는지조차 모른다.

clientInboundChannel 끝에는 서로 독립적인 구독자들이 서 있고, 각자 "이 목적지가 내 담당인가"를 판단한다. 갈림길을 만드는 if문이 어딘가에 있는 게 아니라, 구독자들이 각자 자기 접두사만 집어가는 구조다.

목적지집어가는 일꾼HTTP로 치면
/app/...SimpAnnotationMethodMessageHandler
→ 내 @MessageMapping 메서드 호출		 DispatcherServlet이 컨트롤러를 찾아 부르는 역할
/topic/..., /queue/...브로커
→ 구독 등록 / 발행		 대응물 없음 (HTTP엔 구독 개념이 없다)
/user/...UserDestinationMessageHandler
→ 재작성 후 브로커로		 대응물 없음

그래서 순서가 이렇다 — 어노테이션 핸들러가 먼저 일하고, 브로커는 그 뒤에 일한다. 컨트롤러가 convertAndSend를 호출해 brokerChannel에 뭔가 넣어야 비로소 브로커가 움직인다. 컨트롤러가 void면 브로커는 아무 일도 하지 않는다 (0033 §6).

3. 브로커를 갈아끼워도 안 바뀌는 것

바뀌는 코드는 설정 한 줄이다.

@Override
public void configureMessageBroker(MessageBrokerRegistry registry) {
    registry.setApplicationDestinationPrefixes("/app");       // 그대로
    registry.setUserDestinationPrefix("/user");               // 그대로

    // registry.enableSimpleBroker("/topic", "/queue");     ← 이 줄을
    registry.enableStompBrokerRelay("/topic", "/queue")      // ← 이 줄로
            .setRelayHost("rabbitmq.internal")
            .setRelayPort(61613)                              // RabbitMQ STOMP 플러그인 포트
            .setSystemLogin("app").setSystemPasscode("...")    // 서버 발행용
            .setClientLogin("ws").setClientPasscode("...");   // 클라이언트 중계용
}

컨트롤러도, SimpMessagingTemplate 호출부도, 틱 스케줄러도 안 바뀐다. 셋 다 brokerChannel에 메시지를 넣을 뿐이고, 그 채널에서 누가 꺼내 가는지는 모르기 때문이다. 이것이 0032 §6에서 본 spring-messaging 추상화가 실제로 값을 하는 순간이다.

4. 릴레이가 실제로 하는 일 — TCP 연결 모델

"브로커로 넘긴다"는 말은 편리하지만 실제 동작을 가린다. 릴레이는 RabbitMQ에 대해 스스로 STOMP 클라이언트가 된다. 그리고 연결을 이렇게 연다.

연결 종류몇 개용도
클라이언트 연결 WebSocket 세션 1개당 1개 클라이언트가 보낸 CONNECT마다 브로커로 독립 TCP 연결을 열고, 그 클라이언트의 모든 메시지를 그 연결로만 주고받는다.
"system" 연결 서버당 1개 (공유) 서버 코드가 발행하는 메시지 전용 — 세션 ID가 없는 메시지들. 보내기 전용이라 수신은 못 한다.

모의투자에서 이게 진짜 문제가 되는 지점. 동시 접속 500명이면 RabbitMQ 쪽에 TCP 연결이 500개 + 1개 열린다. SimpleBroker에서는 존재하지 않던 자원이다. 브로커의 연결 수 한도, 파일 디스크립터, 메모리를 미리 확인해야 한다.

setSystemLogin과 setClientLogin을 나눠 둔 이유도 여기 있다 — 브로커 쪽에서 "서버가 발행하는 것"과 "클라이언트가 중계하는 것"에 다른 권한을 걸 수 있다. 클라이언트 계정에는 발행 권한을 빼고 구독만 허용하는 식으로.

5. 그래서 실제로 무엇이 바뀌는가

항목SimpleBrokerStompBrokerRelay + RabbitMQ
구독 장부 위치앱 서버의 JVM 힙RabbitMQ 안
앱 서버 여러 대불가 — A서버 발행이 B서버 구독자에게 안 감 가능 — 모두 같은 브로커를 보므로 자동으로 해결
앱 재배포전 사용자 구독 소멸브로커는 살아 있음 (단 세션은 끊기니 재연결·재구독은 필요)
/queue의 의미/topic과 똑같이 동작 — 이름만 관례 진짜 큐 — point-to-point, 지속성 설정 가능
메시지 저장안 함. 구독 전 발행분은 영영 못 봄큐라면 보관 가능
ACK/RECEIPT/트랜잭션제한적STOMP 전 기능 지원
추가 인프라없음RabbitMQ 서버 + STOMP 플러그인 + reactor-netty 의존성
새로운 실패 모드앱이 죽으면 끝 (단순) 브로커가 죽거나 네트워크가 끊기면 전달 실패 — 앱은 살아 있는데 메시지만 안 감
/user 목적지그대로 동작 동작하지만, 여러 서버에서는 userDestinationBroadcast 설정이 추가로 필요

6. 모의투자에 대입하면 — 언제, 그리고 그다음에 뭘 다시 생각하나

지금은 갈아탈 이유가 없다. 서버 1대에 SimpleBroker면 충분하고, 그게 정답이다.

갈아탈 신호는 셋 중 하나다.

신호왜 SimpleBroker로는 안 되나
앱 서버를 2대 이상으로 늘린다장부가 JVM마다 따로라 구조적으로 불가능
체결·주문에 전달 보장이 필요해진다SimpleBroker는 ack/receipt가 제한적이고 저장을 안 한다
브로커를 다른 서비스와 공유해야 한다SimpleBroker는 이 애플리케이션 안에서만 존재한다

갈아탄 뒤 다시 생각해야 하는 것 — 설정 한 줄로 끝나지 않는 부분이다.

  • 틱 스케줄러를 어느 서버가 돌리나. 앱 서버 2대가 각자 스케줄러를 돌리면 같은 틱이 두 번 발행된다. 리더 선출을 하든 스케줄러를 별도 프로세스로 빼든 발행자는 하나여야 한다. 브로커를 바꾼다고 이게 해결되지 않는다.
  • 가상 시계도 공유해야 한다. 공용 시계 모델의 전제가 "서버가 하나의 장을 돌린다"였으니, 서버가 여러 대면 시계 자체를 어디에 둘지 정해야 한다.
  • TCP 연결 수. §4의 "세션당 1개"가 브로커 용량 계획의 핵심 변수가 된다.
  • 브로커 장애가 새 실패 모드다. 앱은 멀쩡한데 시세만 안 오는 상황을 감지하고 알릴 방법이 필요하다.

정리하면 — 브로커 교체는 "메시지 전달"만 해결한다. 분산 환경의 나머지 문제(중복 발행, 공유 상태, 장애 감지)는 그대로 남는다. 설정 한 줄이 바뀌는 것에 비해 운영해야 할 것은 훨씬 많이 늘어난다는 점이 "지금은 SimpleBroker가 정답"인 진짜 이유다.
