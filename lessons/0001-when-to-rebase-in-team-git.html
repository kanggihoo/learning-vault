협업 Git에서 rebase를 써도 되는 순간

이번 lesson의 목표는 하나다. rebase가 안전한지 그래프만 보고 판단하기.

1. rebase는 해시를 바꾼다

Git 공식 책은 rebase를 “한 브랜치의 변경을 다른 브랜치 위에 다시 적용하는 것”으로 설명한다. 그래서 결과 파일 내용은 같을 수 있지만 커밋 객체는 새로 만들어지고 해시가 바뀐다. Pro Git: Rebasing

처음 상태

A1b2c3d -- B2c3d4e -- C3d4e5f  main
              \
               D4e5f6a -- E5f6a7b  feature/login

명령
git switch feature/login
git rebase main

결과
A1b2c3d -- B2c3d4e -- C3d4e5f  main
                          \
                           F6a7b8c -- G7b8c9d  feature/login

D4e5f6a, E5f6a7b는 사라진 것이 아니라 feature/login이 더 이상 가리키지 않는다.
같은 변경이지만 새 커밋 F6a7b8c, G7b8c9d가 생겼다.

따라서 rebase의 위험은 “파일이 망가진다”보다 “팀원이 알고 있던 커밋 이름이 바뀐다”에 가깝다.

2. 안전한 경우: 내 브랜치, 내 커밋

아직 push하지 않았거나, 원격에 push했더라도 사실상 나 혼자 쓰는 PR 브랜치라면 rebase는 좋다. main의 최신 변경 위에 내 작업을 얹어서 PR 이력을 읽기 쉽게 만들 수 있다.

origin/main이 앞으로 감

A1b2c3d -- B2c3d4e -- C3d4e5f -- H8c9d0e  origin/main
              \
               D4e5f6a -- E5f6a7b  feature/login

내 작업 브랜치 정리
git fetch origin
git switch feature/login
git rebase origin/main

결과
A1b2c3d -- B2c3d4e -- C3d4e5f -- H8c9d0e  origin/main
                                     \
                                      I9d0e1f -- J0e1f2a  feature/login

이미 원격에 올린 내 PR 브랜치라면 push가 거절될 수 있다. 이때는 단순 --force보다 --force-with-lease가 낫다. 공식 git-push 문서 기준으로 이 옵션은 내가 알고 있는 원격 상태와 다를 때 덮어쓰지 않도록 보호한다.

git push --force-with-lease origin feature/login

3. 위험한 경우: 공개된 커밋

다른 사람이 이미 pull 해서 그 위에 작업했을 수 있는 커밋은 rebase하지 않는다. Git 공식 책도 “저장소 밖에 존재하고 다른 사람이 기반으로 삼았을 수 있는 커밋을 rebase하지 말라”고 경고한다.

원격 공유 브랜치

A1b2c3d -- B2c3d4e -- C3d4e5f -- D4e5f6a  origin/shared
                                     \
                                      E5f6a7b -- F6a7b8c  teammate/work

내가 shared를 rebase 후 force push

A1b2c3d -- B2c3d4e -- C3d4e5f -- X1x2x3x -- Y2y3y4y  origin/shared
                                     \
                                      E5f6a7b -- F6a7b8c  teammate/work

문제: 팀원의 E5f6a7b는 옛 D4e5f6a를 부모로 기억한다.
이제 같은 변경이 D4e5f6a와 X1x2x3x처럼 다른 해시로 중복될 수 있다.

팀원이 같이 쓰는 브랜치라면 merge commit이 조금 생겨도 보통 그게 낫다. 복잡한 그래프보다 공유 이력을 망가뜨리는 비용이 더 크다.

4. 실무 판단표

rebase 추천

내 로컬 커밋 정리, 개인 PR 브랜치 최신화, merge 전 commit squash.

merge 추천

main, develop, release처럼 보호되는 공유 브랜치 통합. 여러 명이 같은 feature 브랜치에서 작업할 때.

팀 규칙 우선

GitHub의 “Squash and merge”, “Rebase and merge”, “Create a merge commit” 중 무엇을 쓰는지는 팀의 추적 전략에 맞춘다.
