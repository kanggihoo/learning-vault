브라우저에서 HTTPS 요청이 서버까지 가는 계층 흐름

목표: https://api.example.com/users를 입력했을 때, 브라우저가 HTTP를 HTTPS로 “바꿔서” 보내는 게 아니라 HTTPS scheme 때문에 처음부터 TLS 연결 위에 HTTP 메시지를 올린다는 점을 잡는다.

1. 정답 그림

URLhttps://api.example.com/users
↓ scheme이 https라서 보안 연결 선택
DNSapi.example.com -> IP 주소 찾기
↓
TCP서버 IP의 443 포트로 연결
↓
TLShandshake: 인증서 검증 + session key 생성
↓
HTTPGET /users 요청을 TLS 안에 넣어 전송
↓
ServerTLS record 복호화 -> HTTP 요청 처리 -> 응답 암호화

핵심: HTTP 메시지는 있다. 하지만 네트워크에는 평문 HTTP가 아니라 암호화된 TLS record가 흐른다.

2. OSI 7계층으로 보면

먼저 구분해야 한다. 실제 송신 흐름과 논리 통신 그림은 다르다. 실제로 브라우저가 보낼 때는 위에서 아래로 내려가고, 서버가 받을 때는 아래에서 위로 올라간다. 

실제 송신 흐름:
  브라우저 application
  -> HTTP 메시지 생성
  -> TLS가 HTTP 메시지를 암호화
  -> TCP segment
  -> IP packet
  -> link/physical 전송

실제 수신 흐름:
  link/physical 수신
  -> IP
  -> TCP
  -> TLS가 복호화
  -> HTTP 메시지 복원
  -> 서버 application 처리

반대로 “L7끼리 통신한다”는 말은 논리 모델이다. 브라우저의 HTTP 계층과 서버의 HTTP 계층이 같은 HTTP 규칙으로 대화한다는 뜻이지, 데이터가 물리적으로 L7에서 L7로 순간이동한다는 뜻은 아니다. 

논리 view:
  Browser HTTP  <---------------->  Server HTTP
  Browser TLS   <---------------->  Server TLS
  Browser TCP   <---------------->  Server TCP

실제 byte 흐름:
  Browser L7 -> ... -> L1 -> network -> L1 -> ... -> Server L7

3. TLS는 몇 계층인가?

TLS는 OSI 7계층에 딱 하나로 예쁘게 들어맞지 않는다. 실무 멘탈 모델은 “TCP 위, HTTP 아래”가 가장 덜 헷갈린다. 이름은 Transport Layer Security지만 TCP 자체는 아니므로 순수 L4도 아니다. HTTP 같은 application protocol도 아니므로 순수 L7도 아니다. 

실무 stack:
  HTTP       application protocol
  TLS        HTTP를 암호화하는 보안 layer
  TCP        transport
  IP         network
  Ethernet   link/physical

OSI식으로 굳이 말하면:
  TLS는 L5 session / L6 presentation 성격이 강함
  또는 application과 transport 사이 보안 계층으로 봄

https://api.example.com/users는 L7 정보가 맞다. 하지만 “이미 L7이라서 TLS로 다시 내려간다”가 아니라, 브라우저 application이 URL scheme을 보고 “HTTP 메시지를 TLS layer에 맡겨서 보내라”를 결정하는 것이다.

4. http와 https의 갈림길

https://api.example.com/users
  -> 브라우저가 처음부터 443/TLS 선택
  -> TLS handshake
  -> 암호화된 HTTP 요청 전송

http://api.example.com/users
  -> 브라우저가 80/plain HTTP 선택
  -> 서버가 301/308 Location: https://... 줄 수 있음
  -> 브라우저가 새 HTTPS 요청 시작

HSTS 적용된 사이트
  -> 브라우저가 http:// 요청을 보내기 전에 https://로 내부 승격
  -> 평문 첫 요청 위험 감소

5. handshake는 매 요청마다?

매 HTTP 요청마다 handshake를 새로 하지 않는다. 브라우저는 같은 origin에 대한 연결을 재사용한다. HTTP/1.1은 persistent connection을 쓰고, HTTP/2는 한 TLS 연결 위에서 여러 stream을 multiplex한다. 

처음:
  TCP 연결
  TLS handshake
  GET /me

같은 연결 재사용:
  GET /orders
  POST /cart
  GET /notifications

연결 종료 후 나중:
  새 연결 필요
  TLS handshake 다시 필요
  단, TLS session resumption이면 더 빠름

WebSocket처럼 앱이 계속 양방향 메시지를 흘리는 구조는 아니다. 다만 밑의 TCP/TLS 연결은 일정 시간 살아 있고 여러 HTTP 요청이 재사용할 수 있다.

6. 대칭키 문제는 어떻게 푸나?

맞다. 대칭키 암호화의 큰 문제는 “같은 키를 어떻게 둘만 알게 하느냐”다. TLS는 이 문제를 key exchange로 푼다. 

낡은 단순 비유:
  서버 공개키로 대칭키를 암호화해서 전달
  -> 서버 개인키로 복호화
  -> 둘이 같은 대칭키 사용

현대 TLS 1.3에 가까운 그림:
  브라우저와 서버가 ephemeral Diffie-Hellman 재료 교환
  -> 네트워크에는 비밀키 자체가 흐르지 않음
  -> 양쪽만 같은 session key 계산
  -> session key로 HTTP data 암호화

그래서 “비대칭키로 대칭키를 교환한다”는 말은 큰 방향은 맞지만, 현대 TLS 1.3에서는 보통 대칭키를 직접 보내는 게 아니라 key exchange 재료로 같은 키를 계산한다.

7. Session key는 정확히 무엇인가?

여기서 session key는 로그인 세션 ID나 서버 session 객체가 아니다. TLS 연결 하나에서 브라우저와 서버가 HTTP 데이터를 암호화/복호화할 때 쓰는 임시 대칭키를 뜻한다. 

session key의 뜻:
  이 TLS 연결에서만 쓰는 임시 암호화 키
  브라우저와 서버만 계산 가능
  HTTP request/response를 빠르게 암호화/복호화
  연결이 끝나면 버려짐

session key가 아닌 것:
  로그인 session id 아님
  JSESSIONID 같은 쿠키 아님
  JWT 아님
  서버 DB에 저장하는 사용자 세션 아님

TLS 1.3에서는 더 정확히 여러 traffic key가 만들어진다. 예를 들면 client가 서버로 보내는 데이터용 키와 서버가 client로 보내는 데이터용 키가 나뉜다. 수업에서는 이 묶음을 쉽게 session key라고 부른다. 

쉽게 말하면:
  handshake 결과물 = session key 계열
  client -> server HTTP 데이터 = client write traffic key로 보호
  server -> client HTTP 데이터 = server write traffic key로 보호

왜 "session"인가?
  특정 TLS 연결/세션 동안만 유효하기 때문

모양은 사람이 외우는 문자열이라기보다 랜덤 bytes다. 디버깅 도구나 key log 파일에서는 16진수 문자열처럼 보일 수 있지만, 실제 의미는 암호 알고리즘에 들어가는 byte 배열이다. 

사람 눈에 보이게 표현하면:
  7f 4a 91 0c 2b ...
  또는
  7f4a910c2b...

중요:
  비밀번호처럼 사람이 정하는 문자열 아님
  HTTP body에 들어가는 값 아님
  네트워크에 그대로 보내는 값 아님
  handshake 결과로 양쪽이 계산한 비밀 bytes

8. 인증서는 신뢰 보증서인가?

거의 맞다. 더 정확히는 인증서는 “이 공개키가 이 도메인의 서버에 속한다”는 CA 서명 보증서다. 

브라우저 질문:
  이 key exchange 상대가 진짜 api.example.com인가?

인증서 답:
  api.example.com의 공개키/신원 정보를 CA가 서명함

브라우저 검증:
  도메인명 맞음
  CA chain 신뢰 가능
  기간 유효
  서버가 해당 private key 소유 증명

결과:
  잘못된 중간자와 session key를 만들 위험 감소

9. 한 줄 멘탈 모델

https://는 “HTTP를 나중에 HTTPS로 바꿔라”가 아니라 “처음부터 TLS 보안 연결을 만들고 그 안에 HTTP를 넣어라”라는 지시다. OSI로 보면 브라우저에서 L7 HTTP 데이터가 TLS를 거쳐 아래 계층으로 내려가고, 서버에서는 TLS 복호화 후 다시 L7 HTTP로 올라온다.
