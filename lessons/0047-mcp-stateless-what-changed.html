MCP 2026-07-28 · 1/2 · 레슨 0047 · 용어집·변경 지도(레퍼런스 0023)의 §1–§2를 판다

세션이 사라졌다 — 무상태 MCP

2026-07-28 판의 헤드라인은 한 문장이다. "MCP는 이제 무상태(stateless) 프로토콜이다." 서버가 "이 클라이언트가 누구고 무엇을 지원하는지"를 기억하던 구조에서, 매 요청이 자기소개서를 들고 오는 구조로 바뀌었다. 이 레슨은 그 전환을 이전·이후 시퀀스로 나란히 놓고, 왜 그렇게 했는지, 그리고 "서버가 사용자에게 뭘 물어야 할 때"라는 가장 어려운 케이스를 어떻게 해결했는지(MRTR)를 다룬다.

이 레슨 하나로 얻는 것. ① 옛 흐름(initialize + 세션 ID)과 새 흐름(_meta 매 요청)을 그림으로 그릴 수 있다. ② "왜 무상태인가"를 로드밸런서 한 장으로 설명할 수 있다. ③ MRTR을 "서류 미비 → 보완 후 재접수"로 설명하고 requestState가 왜 서명돼야 하는지 안다. 점진적 도구 로딩은 다음 레슨이다 — 그건 이 층의 이야기가 아니기 때문이다.

§0 · 이 레슨에서 쓰는 용어 여섯 개

Host / Client / Server
AI 앱 / 서버당 하나씩 만드는 연결 담당자 / 도구를 제공하는 프로그램. 서버는 위치가 아니라 역할이다.
Capability
"나는 tools를 제공한다", "나는 elicitation을 받을 수 있다" 같은 지원 기능 선언.
Session (세션)
연결이 앞선 대화를 기억하는 것. HTTP에선 Mcp-Session-Id 헤더로 구현했었다. 이번 판에서 제거.
Stateless (무상태)
요청을 처리할 정보가 그 요청 안에 전부 있다. 서버는 이전 요청을 참조하면 안 된다.
_meta
모든 요청에 붙는 메타데이터 가방. 이번 판에서 버전과 capability를 여기에 매번 싣는다.
MRTR
Multi Round-Trip Requests. 서버가 추가 입력이 필요하면 "요청"을 보내는 대신 "미비 서류 목록"을 답으로 돌려주는 패턴.

전체 용어는 레퍼런스 0023 §1.

§1 · 이전 — 세션이 있던 세계 (2025-11-25)

옛 판에서 클라이언트는 첫 요청으로 반드시 initialize를 보내야 했다. "나는 이 버전을 말하고, 이런 기능을 받을 수 있다." 서버가 자기 capability로 답하고, 클라이언트가 notifications/initialized를 보내면 그때부터 정상 운영. HTTP에서는 서버가 Mcp-Session-Id를 발급하고 클라이언트가 이후 모든 요청에 그 헤더를 붙였다.

백엔드 개발자라면 이 그림의 문제가 바로 보인다. 서버 인스턴스가 3대라면 세션 abc를 3대가 공유해야 한다. Redis에 넣든, sticky session으로 같은 인스턴스에만 보내든. 그리고 서버가 클라이언트에게 무언가를 물어야 할 때는 스트림을 열어 둔 채 기다려야 하니, 연결이 끊기면 그 질문도 사라진다.

§2 · 이후 — 자기소개서를 매번 들고 오는 세계 (2026-07-28)

새 판은 initialize도, notifications/initialized도, Mcp-Session-Id도 없다. 대신 모든 요청의 _meta에 두 가지가 필수로 들어간다 — io.modelcontextprotocol/protocolVersion(내가 말하는 판)과 io.modelcontextprotocol/clientCapabilities(내가 받을 수 있는 기능). 권장으로 clientInfo. 스펙 원문:

"서버는 같은 연결 위의 이전 요청에 의존해 문맥(capability, 프로토콜 버전, 클라이언트 신원)을 세우면 안 된다. 모든 요청이 이 메타데이터를 _meta 필드에 제공한다." — Base Protocol §Statelessness

실제 요청 하나를 보면 "자기소개서"가 어디에 있는지 분명해진다 (Streamable HTTP, 스펙 예제):

POST /mcp HTTP/1.1
MCP-Protocol-Version: 2026-07-28
Mcp-Method: tools/call        ← 게이트웨이가 본문을 안 열고도 라우팅
Mcp-Name: get_weather

{ "jsonrpc": "2.0", "id": 1, "method": "tools/call",
  "params": {
    "name": "get_weather", "arguments": { "location": "Seattle, WA" },
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",   ← 필수
      "io.modelcontextprotocol/clientCapabilities": {},          ← 필수
      "io.modelcontextprotocol/clientInfo": { "name": "ExampleClient", "version": "1.0.0" }
    } } }

§3 · 왜 — 로드밸런서 한 장

릴리스 블로그의 표현은 이렇다. "개발자들이 가장 많이 요청한 기능 중 하나 … MCP 서버의 신뢰성과 확장성." 그리고 결과: "어떤 요청이든 공유 저장소 없이 평범한 라운드로빈 로드밸런서 뒤의 아무 인스턴스에 떨어져도 된다."

그럼 "장바구니에 담기 → 결제"처럼 호출 사이에 상태가 필요한 도구는? 스펙의 답은 단순하다. 프로토콜이 아니라 도구 인자로 핸들을 주고받아라. create_basket이 basket_id: "bsk_a1b2c3"를 돌려주고, add_item이 그 id를 인자로 받는다. 모델이 id를 들고 다닌다. 서버는 그 키로 저장소를 조회한다. 핸들은 불투명하게, 유효기간을 설명에 적고, 인증된 서버라면 매 호출 권한을 다시 검사한다. (Tools §Stateful Tools)

§4 · 가장 어려운 케이스 — 서버가 사용자에게 물어야 할 때 (MRTR)

무상태의 진짜 시험대는 여기다. 도구를 실행하다가 "GitHub 계정이 뭐죠?"를 사용자에게 물어야 한다면? 옛 판은 서버가 열어 둔 스트림으로 elicitation/create라는 요청을 보냈다. 그건 상태다. 새 판은 서버가 요청을 시작하는 일 자체를 없앴다. 대신 이렇게 한다.

규칙 몇 개가 이 패턴을 안전하게 만든다. 백엔드 개발자에게 익숙한 것들이다.

  • requestState는 공격자 입력이다. 클라이언트를 거쳐 되돌아오므로 서버는 이걸 "믿으면" 안 된다. 권한·자원 접근·비즈니스 로직에 영향을 주면 HMAC 또는 AEAD로 무결성 보호, 검증 실패는 거절. 서명된 쿠키·JWT와 같은 논리.
  • 재전송(replay) 방지: 봉인 안에 인증 주체·짧은 만료(TTL)·원래 요청의 식별자(메서드 + 인자 다이제스트)를 넣고 수신 때 대조. 단 이것만으로 "1회성"은 보장되지 않으니 그게 필요하면 서버가 별도로 강제.
  • 재시도는 새 JSON-RPC id여야 한다. 독립된 요청이기 때문.
  • 클라이언트가 선언하지 않은 기능(예: elicitation 미지원)을 inputRequests에 넣으면 안 된다. 그래서 clientCapabilities가 매 요청 필수다.
  • 서버는 클라이언트가 재접수한다고 가정하면 안 된다. 안 올 수도 있다. 그래도 서버는 잃을 게 없다 — 기억한 게 없으니까.
  • MRTR을 쓸 수 있는 요청은 tools/call · resources/read · prompts/get 세 개뿐.

Sampling과 Roots는 이번 판에서 폐기(Deprecated)됐다. MRTR로 실어 보낼 수는 있지만 새 구현은 만들지 말라는 뜻이다. "서버가 클라이언트의 LLM을 빌려 쓴다"(Sampling)는 이제 "서버가 LLM API를 직접 부른다"로, "클라이언트가 작업 디렉토리를 알려 준다"(Roots)는 "도구 인자로 경로를 넘긴다"로. 남은 클라이언트 기능은 Elicitation 하나다. 12개월 이상 유지되니 급하진 않다 — 지도 §4.

§5 · 서버→클라이언트 알림은 그럼 어떻게?

"도구 목록이 바뀌었다"처럼 서버가 먼저 말해야 하는 것도 있다. 옛 판은 HTTP GET으로 독립 스트림을 열었다. 새 판은 그것도 요청/응답 모양으로 바꿨다 — 클라이언트가 subscriptions/listen 요청을 보내고, 그 응답이 닫히지 않는 SSE 스트림이 된다. 원하는 알림 종류를 필터로 고르고(toolsListChanged: true), 서버는 첫 메시지로 acknowledged를 보낸 뒤 알림마다 subscriptionId를 붙인다. 상태는 그 요청에 귀속되고 연결에 귀속되지 않는다. 끊기면 다시 subscriptions/listen을 보내면 된다.

진행률(notifications/progress)처럼 특정 요청에 딸린 알림은 이 스트림이 아니라 그 요청의 응답 스트림으로 흐른다. 두 통로를 헷갈리지 말 것. 출처: Subscriptions.

§6 · 옛 서버·옛 클라이언트와는 어떻게 만나나

ClientServer결과
새(modern)새동작. server/discover는 선택.
새옛(legacy)실패. 옛 서버는 initialize 없는 요청을 어떻게 다룰지 정해져 있지 않다. stdio에선 server/discover를 먼저 보내 확실히 실패시키는 게 권고.
양쪽(dual-era)옛동작. 새 방식으로 먼저 시도 → 알아볼 수 있는 새 에러가 아니면 initialize로 폴백.
옛새실패. 옛 클라이언트는 앞으로 갈 방법이 없다. 새 서버는 initialize 거절 에러에 지원 버전을 적어 주는 게 예의.

핵심 판별 규칙: "알아볼 수 있는 새 판 에러"(예: -32022)가 오면 새 서버다 — 버전만 맞춰 재시도하고 폴백하지 않는다. 그 외 아무 에러나 침묵이면 옛 서버. 새 판만 지원하는 서버는 옛 트래픽에 GET/DELETE → 405, Mcp-Session-Id → 무시, Last-Event-ID → 무시. 출처: Versioning §Compatibility Matrix.
