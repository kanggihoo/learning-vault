쿠버네티스 전체 구조: Docker에서 K8s로

목표: 쿠버네티스 클러스터의 전체 지도를 머릿속에 그리고, 자주 나오는 용어(Pod, Node, Deployment, Service, kubelet, etcd…)가 그 지도의 어디에 있는 무엇인지 말할 수 있게 된다. 이미 아는 Docker를 출발점으로 삼는다.

0. 출발점 — Docker는 되는데, 왜 쿠버네티스가 필요한가

Docker로 컨테이너 하나 띄우는 건 이미 할 수 있다. 문제는 그게 여러 대의 서버에서, 계속 살아있어야 할 때 생긴다. 

Docker만 있을 때 직접 해야 하는 일:

  "컨테이너가 죽었다"        → 누가 감지하고 누가 다시 띄우나?
  "서버 3대에 나눠 띄우자"    → 어느 서버에 여유가 있는지 누가 판단하나?
  "트래픽 늘었다, 10개로"     → 10번 docker run? 그리고 어디에?
  "새 버전 배포한다"          → 무중단으로 하나씩 교체를 누가 순서대로 하나?
  "컨테이너 IP가 계속 바뀐다" → 앞단에서 어느 IP로 요청을 보내나?

→ 이걸 사람이 아니라 시스템이 자동으로 하게 만든 것이 쿠버네티스.

이 레슨에서 가장 중요한 한 문장: 쿠버네티스는 "내가 원하는 상태(desired state)를 선언하면, 시스템이 현재 상태를 거기에 계속 맞추는" 구조다. 명령이 아니라 선언이다. "컨테이너를 띄워라"가 아니라 "항상 3개가 떠 있어야 한다"고 적어두면, 누가 죽든 시스템이 알아서 3개를 유지한다.

1. 클러스터 전체 지도 — 이 그림 하나가 이 레슨의 전부다

쿠버네티스 클러스터는 크게 두 덩어리다. Control Plane(두뇌: 무엇을 할지 결정)과 Node(손발: 실제로 컨테이너를 실행). 아래 그림을 먼저 눈에 익히고, 이후 섹션에서 각 상자를 하나씩 연다.

이 그림에서 딱 두 가지만 먼저 가져가자.
① Control Plane = 결정, Node = 실행. 두 덩어리다.
② 모든 대화는 kube-apiserver를 통과한다. scheduler도, kubelet도, 나(kubectl)도. apiserver는 클러스터의 유일한 정문이다.

2. Docker 개념 → 쿠버네티스 개념 대응표

이미 아는 것에 붙이면 훨씬 빨리 붙는다. 왼쪽은 알고 있는 것, 오른쪽이 새로 배울 것이다.

Docker에서쿠버네티스에서달라지는 핵심
docker run으로 띄운 컨테이너 Pod 안의 컨테이너 K8s는 컨테이너를 직접 다루지 않는다. 항상 Pod라는 껍데기로 감싼다.
컨테이너를 실행하는 서버 1대 Node 여러 대가 모여 하나의 Cluster. 나는 이제 "어느 서버"를 신경 쓰지 않는다.
docker-compose.yml 매니페스트 YAML (kubectl apply -f) compose는 "실행 명령"에 가깝고, K8s YAML은 "유지되어야 할 상태"의 선언이다.
--restart=always Deployment (ReplicaSet) 재시작만이 아니라 개수 유지 + 무중단 버전 교체 + 롤백까지 한다.
docker run --scale / 수동 여러 번 replicas: 3 몇 개인지만 적으면 어느 Node에 배치할지는 scheduler가 정한다.
compose의 서비스 이름으로 통신 Service (ClusterIP) Pod IP는 계속 바뀐다. Service가 고정된 이름·IP를 제공한다.
docker ps, docker logs kubectl get pods, kubectl logs 대상이 한 서버가 아니라 클러스터 전체다.
이미지 (nginx:1.25) 이미지 (그대로) 바뀌지 않는다. K8s도 결국 같은 컨테이너 이미지를 실행한다.

가장 자주 넘어지는 지점: "Pod = 컨테이너"라고 외우면 안 된다. Pod는 컨테이너 한 개 이상을 담는 상자이고, 상자 안 컨테이너들은 IP 하나와 저장소를 공유한다. 실무에선 대부분 Pod 하나에 컨테이너 하나지만, "왜 굳이 껍데기를 씌웠나"의 답은 다음 섹션에 있다.

3. Pod — 쿠버네티스가 다루는 가장 작은 단위

공식 문서의 정의는 이렇다:

"저장소와 네트워크 리소스를 공유하는 하나 이상의 컨테이너 그룹이자, 그 컨테이너들을 어떻게 실행할지에 대한 명세. Pod의 내용물은 항상 같은 곳에 배치되고 함께 스케줄된다." — Kubernetes Docs: Pods 
Pod 하나 = "논리적인 서버 한 대"라고 생각하면 정확하다.

┌─ Pod (IP: 10.1.2.3) ────────────────┐
│  컨테이너 A (app)   :8080           │
│  컨테이너 B (로그 수집)              │
│                                      │
│  → 둘은 localhost 로 서로 통신 가능   │  ← IP·포트 공간 공유
│  → 같은 볼륨을 함께 마운트 가능        │  ← 저장소 공유
│  → 항상 같은 Node에 함께 뜬다      │  ← 함께 스케줄
└──────────────────────────────────────┘

왜 껍데기가 필요한가? 어떤 프로세스들은 "붙어 있어야만" 의미가 있다. 앱 컨테이너와 그 앱의 로그를 긁어가는 컨테이너는 같은 디스크·같은 네트워크를 봐야 한다. Docker에서 이걸 하려면 네트워크·볼륨을 수동으로 엮어야 했지만, K8s는 Pod라는 단위 자체로 이 묶음을 표현한다.

Pod는 일회용이다(ephemeral). 죽으면 고쳐지지 않는다. 버려지고, 새 IP를 가진 새 Pod가 생긴다. 이 성질이 뒤에 나올 두 개념의 존재 이유가 된다: 개수를 유지하는 Deployment, 그리고 바뀌는 IP를 가려주는 Service.

4. Control Plane 4형제 — 각자 무슨 일을 하는가

① kube-apiserver

"쿠버네티스 API를 노출하는 컨트롤 플레인 컴포넌트."
클러스터의 유일한 정문. kubectl도, scheduler도, kubelet도 전부 여기로만 말한다. etcd에 직접 쓰는 것도 오직 apiserver뿐.
기억법: 모든 화살표가 모이는 곳.

② etcd

"모든 클러스터 데이터를 담는, 일관성 있고 고가용성인 key-value 저장소."
클러스터의 유일한 진실. "Pod 3개가 있어야 한다"는 희망도, "지금 2개 떠 있다"는 현실도 전부 여기 적힌다.
기억법: 여기가 날아가면 클러스터의 기억이 사라진다.

③ kube-scheduler

"Node가 배정되지 않은 새 Pod를 감시하다가, 실행될 Node를 골라주는 컴포넌트."
하는 일은 딱 하나: 배치 결정. CPU/메모리 여유, 제약 조건을 보고 고른다. 직접 실행하지는 않는다. "이 Pod는 Node 2로" 라고 적기만 한다.
기억법: 정하는 사람, 만드는 사람 아님.

④ kube-controller-manager

"컨트롤러 프로세스들을 실행하는 컴포넌트."
희망 상태 ≠ 현재 상태이면 같아질 때까지 계속 조정하는 무한 루프들의 모음. Node 컨트롤러, Job 컨트롤러 등 여러 개가 한 바이너리에 들어있다.
기억법: 쿠버네티스의 "자동 복구"는 전부 여기서 나온다.

cloud-controller-manager는 다섯 번째지만 조건부다. AWS·GCP 같은 클라우드에서 돌 때만 있고, 클라우드 쪽 로드밸런서·라우팅을 연결해준다. 노트북의 로컬 클러스터(minikube 등)에는 없다. 지금은 "클라우드 붙일 때 나오는 것"으로만 알아두면 충분하다. — Kubernetes Docs: Cluster Architecture

5. Node 3형제 — 실제로 컨테이너를 띄우는 쪽

① kubelet

"클러스터의 각 Node에서 실행되는 에이전트. Pod 안의 컨테이너들이 실행 중인지 보장한다."
Node에 파견된 대리인. apiserver를 지켜보다 "내 Node에 배정된 Pod"를 발견하면, 런타임에게 컨테이너를 띄우라고 시키고 상태를 다시 보고한다.

② kube-proxy

"각 Node에서 실행되는 네트워크 프록시. Service 개념의 일부를 구현한다."
Service로 온 요청이 실제 Pod에 도달하도록 Node의 네트워크 규칙을 관리한다. 6장의 Service를 실제로 동작하게 만드는 손.

③ 컨테이너 런타임

컨테이너의 실행과 생명주기를 실제로 관리하는 소프트웨어. containerd, CRI-O 등.
Docker로 이미 아는 그 부분이다. 이미지를 받아 컨테이너로 띄우는 최하단 계층.

자주 나오는 오해: "쿠버네티스가 Docker를 대체했다"가 아니다. 쿠버네티스는 컨테이너 런타임 위에서 오케스트레이션(배치·유지·연결)을 하는 계층이고, 맨 아래에서 컨테이너를 실제로 돌리는 일은 여전히 런타임(containerd 등)이 한다. 이미지 만드는 법(Dockerfile)은 그대로 쓴다.

6. Deployment와 Service — 실무에서 가장 많이 쓰는 두 개

Deployment: "몇 개가, 어떤 버전으로 떠 있어야 하는가"

공식 정의: "Pod와 ReplicaSet에 대한 선언적 업데이트를 제공한다. Deployment에 희망 상태를 기술하면, Deployment 컨트롤러가 실제 상태를 그 희망 상태로 통제된 속도로 바꾼다." (Deployment 문서) 

Deployment  ─ 내가 쓴다. "nginx:1.25를 3개 유지해줘"
     │
     ↓ 만든다
ReplicaSet  ─ 자동 생성. "이 버전의 Pod 개수를 정확히 3개로 유지"
     │
     ↓ 만든다
  Pod  Pod  Pod   ─ 실제로 도는 것

내가 손대는 건 Deployment 하나. ReplicaSet은 직접 만지지 않는다.
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  replicas: 3                 # ← "3개가 항상 떠 있어야 한다" (희망 상태)
  selector:
    matchLabels:
      app: my-app             # ← 이 라벨을 가진 Pod가 내 담당
  template:                   # ← 이 아래가 "Pod를 어떻게 만들지"의 틀
    metadata:
      labels:
        app: my-app           # ← 위 selector와 반드시 맞아야 한다
    spec:
      containers:
      - name: my-app
        image: nginx:1.25     # ← 여기만 바꾸면 무중단 롤링 업데이트
        ports:
        - containerPort: 80

롤링 업데이트가 공짜로 따라온다. image만 새 버전으로 바꿔 apply하면, Deployment가 새 ReplicaSet을 만들어 천천히 늘리고, 옛 것을 천천히 줄인다. 그래서 무중단이다. 잘못됐으면 kubectl rollout undo로 되돌린다. 이게 --restart=always와 결정적으로 다른 점이다.

Service: "계속 바뀌는 Pod IP를 어떻게 부르는가"

Pod는 죽고 살아나며 매번 IP가 바뀐다. 프론트엔드가 백엔드 Pod IP를 하드코딩하면 다음 재시작에 바로 깨진다. 공식 문서가 던지는 질문 그대로다: "프론트엔드는 어느 IP로 접속해야 하는지를 어떻게 알아내고 계속 추적하는가?" 

Service 없이:
  frontend → 10.1.2.3:8080 에 직접 요청
    → 그 Pod 죽음 → 새 Pod는 10.1.9.7 → frontend는 깨진 IP를 계속 호출 ✗

Service 있을 때:
  frontend → "my-backend" 라는 고정된 이름으로 요청
    → Service가 라벨(app: my-backend)이 붙은 살아있는 Pod들을 항상 추적
    → 그중 하나로 자동 분배 (로드밸런싱)
    → Pod가 몇 번 죽고 살아나든 frontend 코드는 그대로 ✓
apiVersion: v1
kind: Service
metadata:
  name: my-backend
spec:
  selector:
    app: my-app        # ← 이 라벨이 붙은 Pod들에게 요청을 보낸다
  ports:
    - port: 80         # ← Service가 여는 포트
      targetPort: 8080 # ← Pod 안 컨테이너의 실제 포트

라벨(label)과 셀렉터(selector)가 쿠버네티스를 엮는 접착제다. Service는 Pod를 IP나 이름으로 지목하지 않는다. "app: my-app 라벨이 붙은 것 전부"라고 조건만 건다. 그래서 Pod가 새로 생기든 없어지든 자동으로 목록이 갱신된다. Deployment가 Pod를 관리하는 방식도 똑같이 라벨이다.

Service 타입 세 가지 — "누가 접근할 수 있는가"의 차이

ClusterIP (기본값)

클러스터 내부에서만 접근 가능한 IP를 부여.
백엔드 ↔ DB처럼 내부 통신용. 외부에는 안 열린다.
대부분의 Service가 이것.

NodePort

모든 Node의 IP에 고정 포트(30000–32767)를 연다.
<NodeIP>:<NodePort>로 외부 접근.
개발·테스트용. 운영에는 잘 안 쓴다.

LoadBalancer

클라우드의 외부 로드밸런서를 붙여 고정 외부 IP를 받는다.
운영 환경에서 외부 트래픽을 받는 표준 방법.
클라우드 제공자가 있어야 동작.

7. 전체 흐름 — kubectl apply 한 번에 무슨 일이 벌어지나

지금까지의 모든 조각이 한 줄기로 이어지는 장면이다. 이 흐름을 말로 설명할 수 있으면 이 레슨의 목표는 달성이다. 

내가: kubectl apply -f my-app.yaml   (replicas: 3)

1. kubectl → kube-apiserver
   "Deployment my-app, 3개 원함" 이라는 희망 상태를 제출

2. apiserver → etcd
   희망 상태를 저장. 이 시점엔 아직 아무것도 안 떠 있다.

3. controller-manager (apiserver를 watch 중)
   "Deployment가 3개 원하는데 현재 0개네" → ReplicaSet 생성
   → ReplicaSet 컨트롤러: "3개 원하는데 0개" → Pod 3개 생성 요청
   → 이때 Pod들은 아직 Node가 안 정해진 상태

4. kube-scheduler (apiserver를 watch 중)
   "Node 미배정 Pod 3개 발견" → 자원 여유를 보고 배치 결정
   → "Pod-1은 Node1, Pod-2는 Node2, Pod-3은 Node1"이라고 apiserver에 기록
   → scheduler는 여기까지. 실행은 안 한다.

5. kubelet (각 Node에서 apiserver를 watch 중)
   Node1의 kubelet: "내 Node에 Pod-1, Pod-3이 배정됐네"
   → 컨테이너 런타임(containerd)에게 실행 지시
   → 이미지 pull → 컨테이너 시작
   → "떴다"고 apiserver에 상태 보고 → etcd에 현재 상태 기록

6. 이제 희망(3개) == 현재(3개). 컨트롤러는 조용해진다.

── 그런데 Pod 하나가 죽는다면? ──

7. kubelet이 감지 → apiserver에 보고 → etcd의 현재 상태가 2개로 바뀜
8. ReplicaSet 컨트롤러: "3개 원하는데 2개네" → 새 Pod 생성
9. scheduler가 Node 배정 → kubelet이 실행 → 다시 3개

→ 아무도 나에게 묻지 않았고, 내가 아무것도 안 했다.
   이것이 쿠버네티스의 reconciliation loop(조정 루프)다.

이 구조가 왜 이렇게 됐는가: 각 컴포넌트는 서로를 모른다. scheduler는 kubelet의 존재를 모르고, kubelet은 controller-manager를 모른다. 전부 apiserver라는 게시판만 보고 "내가 할 일이 올라왔나?"를 확인할 뿐이다. 그래서 컴포넌트 하나가 잠시 죽어도 나머지가 계속 돌고, 살아나면 게시판을 다시 읽고 따라잡는다. 느슨한 결합(loose coupling)이 이 설계의 핵심이다.

8. 자주 나오는 용어 — 한 줄 정리

용어어디에한 줄 설명
Cluster전체Control Plane + Node들을 묶은 전체 단위. "쿠버네티스 한 채".
Node실행컨테이너가 실제로 도는 서버 1대(물리/VM). Worker Node라고도 함.
Pod실행배포 가능한 가장 작은 단위. IP·저장소를 공유하는 컨테이너 1개 이상의 묶음.
kube-apiserver두뇌클러스터의 유일한 정문. 모든 통신이 여기를 거친다.
etcd두뇌희망 상태와 현재 상태를 모두 담는 유일한 key-value 저장소.
kube-scheduler두뇌Node 미배정 Pod에게 어느 Node에서 돌지만 정해준다. 실행은 안 함.
controller-manager두뇌희망≠현재이면 같아질 때까지 조정하는 컨트롤러 루프들의 집합.
kubelet실행각 Node의 에이전트. Pod 안 컨테이너가 실행 중임을 보장하고 상태를 보고.
kube-proxy실행각 Node의 네트워크 규칙 관리. Service를 실제로 동작하게 한다.
컨테이너 런타임실행containerd/CRI-O. 이미지를 받아 컨테이너를 실제로 띄우는 최하단.
Deployment선언"이 버전 Pod 몇 개 유지"를 선언. 롤링 업데이트·롤백 담당.
ReplicaSet선언Deployment가 자동 생성. 개수 유지만 담당. 직접 만지지 않음.
Service연결바뀌는 Pod IP를 고정된 이름·IP로 가려주고 로드밸런싱.
Label / Selector연결라벨은 리소스에 붙이는 꼬리표, 셀렉터는 "이 꼬리표인 것 전부"라는 조건. K8s의 접착제.
Namespace구획한 클러스터를 논리적으로 나누는 칸막이(dev/prod 등). 이름 충돌 방지.
Manifest선언희망 상태를 적은 YAML 파일. kubectl apply -f로 제출.
Desired state개념"이렇게 되어 있어야 한다"고 내가 선언한 상태. 쿠버네티스 전체를 관통하는 핵심.
Reconciliation개념현재 상태를 희망 상태에 계속 맞추는 무한 루프. 자동 복구의 정체.

10. 다음에 직접 해볼 것 (선택)

구조는 한 번 직접 띄워보면 훨씬 단단해진다. Docker Desktop을 쓰고 있다면 설정에서 Kubernetes를 켜는 것만으로 로컬 클러스터가 생긴다. 

kubectl get nodes                    # 내 클러스터의 Node 목록
kubectl create deployment web --image=nginx --replicas=3
kubectl get pods -o wide             # 어느 Node에 배치됐는지 확인 (scheduler의 결정)
kubectl delete pod <pod-이름>         # 하나 지워보기
kubectl get pods                     # ← 잠시 뒤 다시 3개가 된다 (reconciliation!)

마지막 두 줄이 이 레슨의 핵심을 눈으로 확인시켜준다. Pod를 지웠는데 다시 생긴다 — 아무도 명령하지 않았는데.
