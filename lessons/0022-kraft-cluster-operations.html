KRaft 클러스터 운영: Controller를 늘리고 줄이고 진단하기

0018 레슨에서 KRaft가 무엇인지(ZooKeeper를 없애고 Kafka 내부 Controller Quorum이 Raft로 metadata를 관리하는 방식)와 왜 그렇게 바뀌었는지를 배웠다. 이 레슨은 그 지식을 전제로, 실제로 Controller를 몇 대 둘지, 어떻게 늘리고 줄이는지, 문제가 생기면 무엇으로 들여다보는지 — 운영 단계의 감각을 잡는다. 0018을 안 읽었다면 먼저 읽고 오는 걸 추천한다.

0. 이 레슨에서 다루는 것 / 다루지 않는 것

Kafka 4.1 기준 KRaft 운영 문서는 CLI 옵션과 설정 키가 아주 많다. 여기서는 실무 도입을 준비하는 단계에서 감각으로 갖고 있어야 할 것만 추린다. 정확한 flag 이름과 명령어 전체 목록은 필요한 시점에 공식 문서를 체크리스트로 펼쳐보면 된다 — 지금 다 외울 필요는 없다.

1. Process Role — 이 서버는 Broker인가, Controller인가, 둘 다인가

KRaft mode의 모든 Kafka 서버는 process.roles 설정으로 자기 역할을 선언한다. 0018 레슨에서 본 "Broker는 data만, Controller는 metadata만"이라는 역할 분리가 바로 이 설정 하나로 결정된다.

설정값역할실무 적합도
process.roles=brokerdata 요청만 처리운영 환경 표준
process.roles=controllermetadata 요청만 처리, quorum 참여운영 환경 표준
process.roles=broker,controller한 프로세스가 둘 다 ("combined")개발용으로만. Controller만 따로 rolling·scale 못 함

Combined mode는 노트북에서 Kafka를 하나 띄워 테스트할 때는 편하지만, 운영 환경에서는 피해야 한다 — Controller가 Broker와 같은 프로세스에 묶여서 격리되지 않기 때문이다 (예: Broker 쪽 부하가 튀면 metadata 처리까지 함께 영향받는다).

2. Controller Quorum — 왜 항상 홀수인가

Controller로 뽑힌 서버들은 0018 레슨에서 본 Raft 합의에 함께 참여하는 Quorum을 이룬다. 그중 하나만 Active(진짜 일하는 놈)이고, 나머지는 Standby로 로그만 따라 복제한다.

Controller 1대가 죽어도 나머지 과반수(majority)가 살아있으면 클러스터는 멈추지 않는다. 그래서 "견뎌야 하는 동시 장애 수 N"과 "필요한 Controller 대수"의 관계는 2N + 1이다 — 딱 N+1이 아니라 과반수 투표가 항상 가능해야 하므로 여유분까지 포함해 이 공식이 나온다.

Controller 대수견딜 수 있는 동시 장애
3대1대 장애까지 정상 동작
5대2대 장애까지 정상 동작

그래서 실무 기본값은 3대다. 5대는 더 큰 장애 내성을 주지만, 매 metadata 변경마다 더 많은 노드의 합의를 기다려야 해서 그만큼의 비용(디스크 5GB, 메모리 5GB 정도가 Controller 하나의 일반적인 목표치)을 추가로 감수하는 것이다.

3. Static Quorum vs Dynamic Quorum — Controller 구성을 바꿀 때 뭐가 달라지나

Kafka 4.1부터 Controller 구성 방식이 두 가지로 나뉜다. 핵심 차이는 "Controller를 하나 추가/제거하려면 무엇을 건드려야 하는가"다.

방식Controller 목록을 아는 법Controller 추가/제거 시
Static Quorum (예전 방식) controller.quorum.voters에 모든 Controller의 id·host·port를 고정 목록으로 명시 클러스터의 모든 노드 설정 파일을 고쳐야 하고, 사실상 전체 재구성·재시작이 필요
Dynamic Quorum (KIP-853, 4.1+ 권장) controller.quorum.bootstrap.servers로 "일단 여기 물어봐" 정도만 지정 전용 CLI 명령 한 번으로 살아있는 채로 추가/제거 가능

지금 신규로 클러스터를 만든다면 Dynamic Quorum이 사실상 기본 선택지다 — 나중에 Controller를 늘리거나 교체해야 할 때 클러스터 전체를 건드리지 않아도 되기 때문이다. 어떤 방식으로 떠 있는지는 아래처럼 확인한다. 

$ bin/kafka-features.sh --bootstrap-controller localhost:9093 describe
Feature: kraft.version  ...  FinalizedVersionLevel: 1  ...
                                                  └─ 0이면 Static, 1 이상이면 Dynamic

4. Controller 추가·제거 — 대략적인 흐름

정확한 명령어 옵션은 버전마다 조금씩 다르므로, 여기서는 "무슨 순서로 진행되는가"라는 흐름만 잡는다.

Controller 추가

  1. 새 노드를 storage 도구로 포맷해서 준비시킨다.
  2. 새 Controller 프로세스를 시작한다 — 아직 quorum의 정식 멤버는 아니다.
  3. Active Controller의 metadata를 따라잡을 때까지(catch up) replication 진행 상황을 지켜본다.
  4. 충분히 따라잡으면 add-controller 명령으로 quorum에 정식 합류시킨다.

Controller 제거

  1. 프로세스를 끄기 전에 remove-controller 명령으로 먼저 quorum에서 뺀다.
  2. 그 다음에 프로세스를 종료한다.

순서가 중요하다 — 먼저 죽이고 나중에 빼려 하면, 그 사이 남은 Controller들이 "과반수가 몇 대인지" 잘못 계산하는 위험한 순간이 생길 수 있다.

5. Debugging 도구 3종 — 뭘 볼 때 뭘 쓰나

도구용도
kafka-metadata-quorum.sh지금 누가 Leader Controller인지, 각 Controller가 얼마나 뒤처졌는지(lag) 등 quorum의 현재 상태를 확인
kafka-dump-log.shmetadata log 파일이나 snapshot을 열어서 실제로 어떤 변경 기록이 쌓였는지 직접 들여다봄
kafka-metadata-shell.shsnapshot을 마치 파일시스템처럼 ls·cat으로 탐색하며 특정 topic·partition의 현재 상태를 확인

셋 다 "지금 뭐가 문제인지 알 수 없을 때 순서대로 좁혀가며 보는" 도구다: 먼저 quorum tool로 "누가 Leader고 얼마나 뒤처졌는지" 큰 그림을 보고 → 이상하면 dump-log나 shell로 실제 기록된 내용을 파고든다.

6. 배포 시 기억할 것 2가지

  • Controller도 장애를 견뎌야 하는 대상이다 — "메타데이터만 다루니까 덜 중요하겠지"라고 생각하면 안 된다. Controller 전체가 죽으면 클러스터 전체가 새 Leader 선출도, 신규 Topic 생성도 못 하는 상태가 된다.
  • 홀수 개(3 또는 5)로 구성한다 — 위 2절에서 본 2N+1 공식을 그대로 따른다.

7. 심화 학습 — 여기서는 짧게만 짚는다

ZooKeeper → KRaft migration 절차(bridge release를 거쳐 단계적으로 전환하는 방법)는 이미 ZooKeeper 기반 클러스터를 운영 중일 때만 필요한 내용이다. 지금은 신규 도입을 준비하는 단계이므로 처음부터 KRaft로 시작하면 되고, 이 절차는 필요해지는 시점에 공식 migration 가이드를 바로 펼쳐보면 된다. kafka-features.sh로 KRaft feature version을 올리는 세부 절차도 같은 이유로 여기서는 생략한다.
