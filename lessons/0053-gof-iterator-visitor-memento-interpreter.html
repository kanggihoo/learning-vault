Iterator · Visitor · Memento · Interpreter

행위 패턴의 나머지 넷이다. 앞 묶음처럼 서로 닮아서 헷갈리는 쌍이 아니라, 각각 따로 떨어진 질문에 답한다: 순회(Iterator), 연산 분리(Visitor), 상태 저장·복원(Memento), 문법 해석(Interpreter). 그래서 이번엔 "이 키워드가 나오면 이것"으로 빨리 알아보는 연습이 중심이다.

§0 · 워밍업 — 지난 묶음 4문제

신호 요약. 구조: 자기와 같은 타입의 리스트를 들고 재귀하면 Composite / 여러 서브시스템 앞의 새 창구는 Facade / 기능·구현 두 계층 분리는 Bridge / 공유로 아끼면 Flyweight.

R1. class Folder implements Node { List<Node> children; int size(){ sum of children.size() } }

R2. 나무 1만 그루가 모델·텍스처 객체 하나를 공유하고 위치만 따로 가진다.

R3. 구독자 목록을 들고 있다가 값이 바뀌면 전원의 onChange()를 호출한다.

R4. 래퍼가 원본과 같은 인터페이스이고, 권한이 없으면 원본을 호출하지 않고 예외를 던진다.

§2 · Iterator (반복자) — 속을 숨기고 순서대로 꺼낸다

한 문장. 리스트든 트리든 해시든, 내부가 어떻게 생겼는지 몰라도 요소를 하나씩 순서대로 꺼낼 수 있게 공통 방법(hasNext()로 남았는지 묻고 next()로 꺼내기)을 주는 패턴이다. 별칭 Cursor.

비유. TV 리모컨의 채널 다음/이전 버튼. 방송국이 채널을 어떻게 보관하든 누르면 다음 채널이 나온다. 비유가 맞지 않는 곳: 채널 버튼은 끝에서 처음으로 돌아가지만, Iterator는 끝에 닿으면 hasNext()가 false가 되어 멈춘다.

interface Iterator<T> { boolean hasNext(); T next(); }
Iterator<String> it = list.iterator();      // 리스트 내부 구조를 몰라도 된다
while (it.hasNext()) System.out.println(it.next());

Java의 java.util.Iterator가 그대로 이 패턴이다 (Javadoc: "An iterator over a collection", hasNext()/next()). for-each 문도 내부에서 이터레이터를 쓴다. 출처: Refactoring.Guru: Iterator.

§3 · Visitor (방문자) — 연산을 밖으로 뺀다

한 문장. 요소 클래스(Circle, Square 등)를 고치지 않고 새 연산(넓이 계산, 출력 등)을 추가하려고, 연산을 요소 밖의 별도 클래스(Visitor)로 빼는 패턴이다.

구조. 요소는 accept(visitor) 메서드 하나만 갖고, 그 안에서 visitor.visit(this)를 부른다. Visitor 인터페이스에는 요소 타입마다 visit() 오버로드(이름은 같고 인자 타입이 다른 메서드)가 있다. 새 연산이 필요하면 Visitor 클래스만 하나 더 만들면 된다.

왜 accept를 한 번 거치나: 더블 디스패치. Java는 오버로드된 메서드를 컴파일할 때의 변수 타입으로 고른다. 예를 들어 Shape s = new Circle(); 처럼 변수 타입이 Shape이면, visitor.visit(s)는 visit(Circle)이 아니라 visit(Shape)을 찾는데, 그런 메서드가 없어 컴파일이 안 된다. 그래서 두 번에 나눠 부른다.

  1. s.accept(visitor)를 부른다. 실행 중에 s가 실제로 Circle이므로 Circle.accept가 실행된다(1번째 선택: 요소 타입).
  2. Circle.accept 안에서 visitor.visit(this)를 부른다. 이 코드 안에서 this는 컴파일 때부터 Circle이므로 visit(Circle)이 선택된다(2번째 선택: Visitor 메서드).

이 두 번의 선택을 "더블 디스패치(이중 호출 선택)"라고 부른다.

비유. 집(데이터)은 그대로인데 검침원, 배달원, 수리공(연산)이 번갈아 방문해 각자 일을 한다. 집은 "들어오세요"(accept)만 안다. 비유가 맞지 않는 곳: 현실의 방문자는 집 종류를 눈으로 보고 행동하지만, 코드의 Visitor는 visit(Circle), visit(Square)처럼 요소 종류별 메서드를 미리 전부 갖고 있어야 한다.

interface Shape { void accept(ShapeVisitor v); }
class Circle implements Shape { public void accept(ShapeVisitor v) { v.visit(this); } }
class Square implements Shape { public void accept(ShapeVisitor v) { v.visit(this); } }

interface ShapeVisitor { void visit(Circle c); void visit(Square s); }
class AreaVisitor implements ShapeVisitor {          // 새 연산 = 새 클래스
    public void visit(Circle c) { /* 원 넓이 */ }
    public void visit(Square s) { /* 사각형 넓이 */ }
}
shape.accept(new AreaVisitor());                     // 요소가 알아서 맞는 visit을 호출

JDK 예: FileVisitor를 Files.walkFileTree에 넘기면 파일 트리의 각 항목에서 visitFile, preVisitDirectory 같은 메서드가 호출된다. 출처: Refactoring.Guru: Visitor.

알아볼 표지. 요소 클래스마다 accept(Visitor v) { v.visit(this); }가 똑같이 들어 있고, Visitor 인터페이스에 요소 타입별 visit() 오버로드가 있다. 이 모양이면 거의 Visitor다.

가장 흔한 오해. "Visitor를 쓰면 확장이 쉬워진다." 한쪽만 그렇다. 새 연산을 추가하기는 쉽다(Visitor 클래스 추가). 하지만 새 요소 클래스를 추가하면 Visitor 인터페이스에 visit(NewShape)를 넣어야 하고, 기존 Visitor 구현체를 전부 고쳐야 한다. 요소 종류가 자주 바뀌는 구조에는 맞지 않는다.

§4 · Memento (메멘토) — 캡슐화를 지키며 저장·복원

한 문장. 객체가 자기 상태를 스냅샷(Memento) 객체로 꺼내 두었다가, 나중에 그 스냅샷으로 되돌아가게 하는 패턴이다. 별칭 Token.

핵심 조건. 객체의 private 필드를 getter/setter로 열지 않고 저장하고 복원해야 한다(필드를 밖에 숨기는 것을 캡슐화라 한다). 그래서 스냅샷을 만드는 것도, 읽어서 복원하는 것도 상태의 주인 객체(Editor)만 한다. 스냅샷을 쌓아 두는 쪽(Caretaker)은 스택에 보관만 하고 내용은 열어 보지 못한다.

비유. 게임 세이브 파일. 게임이 자기 상태를 파일로 만들어 주고, 불러오면 그때로 돌아간다. 세이브 파일을 관리하는 메뉴는 파일 안을 모른다. 비유가 맞지 않는 곳: 세이브 파일은 디스크에 오래 남지만, 코드의 Memento는 보통 메모리에 쌓이는 객체라서 많이 쌓으면 메모리를 쓴다.

class Editor {
    private String text;
    Snapshot save() { return new Snapshot(text); }          // 상태를 포장
    void restore(Snapshot s) { this.text = s.text; }        // 상태 복원
    static class Snapshot {                                  // 밖에서는 내용을 못 연다
        private final String text;
        private Snapshot(String t) { this.text = t; }
    }
}
Deque<Editor.Snapshot> undoStack = new ArrayDeque<>();     // Caretaker가 보관만 한다

Command와 함께 undo를 구현할 때 짝으로 쓴다 — Command가 동작하기 직전에 Memento로 상태를 저장한다 (Refactoring.Guru: Memento).

§5 · Interpreter (인터프리터) — 문법을 클래스로

한 문장. 간단한 언어(수식, 검색 조건 등)의 문법 규칙 하나하나를 클래스로 만들고, 문장 하나를 그 객체들의 트리로 표현해서 interpret()를 불러 계산하는 패턴이다.

구조. 클래스는 두 종류다. 끝(terminal)은 숫자처럼 더 쪼개지지 않는 규칙이고, 가지(nonterminal)는 더하기처럼 다른 규칙 객체를 품는 규칙이다. 가지의 interpret()는 자식들의 interpret()를 재귀로 불러 결과를 합친다. 이 모양은 Composite와 같다(차이는 §6).

비유. 수식 계산기. "(1 + 2) * 3"을 Mul(Add(Num 1, Num 2), Num 3)이라는 객체 트리로 만들고 루트에서 interpret()를 부르면 (1+2)=3, 3×3=9가 나온다.

"클래스 패턴"이라는 분류와 코드가 어긋나 보이는 이유. GoF 원전의 분류표는 Interpreter를 클래스 패턴 4개(Factory Method, Adapter, Interpreter, Template Method)에 넣는다. 그런데 아래 코드는 상속이 아니라 객체를 필드로 들고 있어서 "클래스 패턴 = 상속" 설명(레슨 0049 §3)과 맞지 않아 보인다. 분류표가 왜 그렇게 되어 있는지는 이 레슨에서 확인하지 못했다. 시험에서는 4개 이름을 외워 두는 것으로 처리한다.

interface Expr { int interpret(); }
class Num implements Expr { int n; public int interpret() { return n; } }            // 끝
class Add implements Expr {                                                          // 가지
    Expr l, r;
    public int interpret() { return l.interpret() + r.interpret(); }
}
// (1 + 2) → new Add(new Num(1), new Num(2)).interpret()  == 3

한계: 이 패턴은 문자열을 파싱하지는 않는다(트리가 이미 만들어졌다고 가정). 문법이 복잡하면 파서가 더 적합하다 (SourceMaking — Interpreter). Refactoring.Guru 카탈로그에는 이 패턴이 없다.

쌍구분 질문
Visitor vs IteratorIterator는 꺼내는 순서를 정하고, Visitor는 꺼낸 요소에 무슨 일을 할지를 정한다. 둘을 함께 쓰기도 한다
