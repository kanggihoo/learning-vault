Consumer Group 설정: 그룹 안에서 어떻게 행동할지 정하기

목표: Apache Kafka Documentation: Group Configs와 Consumer Configs 원문에서, 초보자가 실제로 판단해야 하는 설정 몇 개만 뽑아 "왜 이 값을 이렇게 정하는가"를 이해한다. Consumer Group 자체의 동작은 0016 레슨과 0019 레슨에서 이미 배웠다고 가정하고, 이 레슨은 그 동작을 "어떤 설정 값이 실제로 조종하는지"에 집중한다.

0. 큰 그림 — 브로커의 한계값 안에서 Client가 값을 고른다

이 레슨은 서로 다른 두 위치에 있는 설정을 함께 다룬다. 이 구분은 0026 레슨에서 본 "브로커 기본값 vs 토픽별 override" 패턴과 완전히 같은 모양이다 — 여기서는 대상이 "토픽"이 아니라 "Consumer Group"으로 바뀐 것뿐이다.

구성 위치파일역할
Group Configs브로커(서버) 설정"Consumer Group이 요청할 수 있는 값의 허용 범위"를 브로커가 미리 정해둔다 — 일종의 가드레일
Consumer ConfigsClient(컨슈머 앱) 설정그 가드레일 안에서 각 컨슈머 애플리케이션이 실제로 고르는 값

Client가 가드레일을 벗어난 값을 요청하면 브로커가 거부한다. 예: 브로커가 group.min.session.timeout.ms=6000으로 정해뒀는데 컨슈머가 session.timeout.ms=3000을 요청하면 연결이 거부된다.

1. 브로커의 가드레일 — Group Configs

137줄짜리 짧은 문서라 다룰 값도 적다. 핵심은 세션 타임아웃(장애로 인식하기까지 걸리는 시간)의 허용 범위를 브로커가 강제한다는 것 하나다.

설정기본값의미
group.min.session.timeout.ms6000 (6초)Consumer가 요청할 수 있는 세션 타임아웃의 최소값 — 너무 짧게 잡으면 하트비트 폭주로 클러스터에 부담
group.max.session.timeout.ms1800000 (30분)최대값 — 너무 길게 잡으면 죽은 컨슈머를 알아채는 데 30분씩 걸릴 수 있음
consumer.session.timeout.ms / consumer.heartbeat.interval.ms45초 / 5초신규 Consumer Group Protocol(group.protocol=consumer)에서는 세션 타임아웃·하트비트 간격을 브로커가 이 값으로 강제한다 — 옛 방식(classic)처럼 클라이언트가 직접 정하지 못함
share.*, streams.* 접두사 설정들-Share Group(0019 §7)과 Kafka Streams 그룹에도 같은 패턴(간격·타임아웃 브로커 강제)이 각각 존재 — 지금은 이름만 알아두면 충분

기억할 것은 하나: "이 그룹이 얼마나 빨리 장애를 알아챌지"는 컨슈머 코드가 아니라 브로커가 최종 결정권을 갖는다는 것. 새 Consumer Group Protocol로 갈수록 이 결정권이 브로커 쪽으로 더 넘어가는 추세다(뒤에서 다시 설명).

2. 그룹 멤버십과 장애 감지 — 이 컨슈머가 살아있다고 어떻게 알리나

하트비트 3형제: session.timeout.ms / heartbeat.interval.ms / max.poll.interval.ms

설정기본값역할
session.timeout.ms45초이 시간 안에 하트비트가 안 오면 브로커가 "죽었다"고 판단 → rebalance 시작
heartbeat.interval.ms3초얼마나 자주 하트비트를 보낼지 — 보통 session.timeout의 1/3 이하로
max.poll.interval.ms5분poll()을 이 시간 안에 다시 호출 안 하면 "메시지 처리 로직이 멈췄다"고 보고 그룹에서 내보냄 — 하트비트는 별개 스레드라 살아있어도 이건 별도로 체크됨

흔한 실수: 메시지 하나 처리에 오래 걸리는 로직(예: 무거운 API 호출)을 넣었다가 max.poll.interval.ms를 넘겨서 멀쩡한 컨슈머가 그룹에서 쫓겨나는 경우가 잦다. "왜 계속 rebalance가 일어나지?"의 원인 1순위.

group.instance.id — Static Membership을 켜는 스위치

0019 레슨 §4에서 배운 Static Membership은 바로 이 설정 하나로 켜진다. 값을 주면 재시작해도 같은 멤버로 인식되어 session.timeout.ms 안에만 돌아오면 rebalance 없이 파티션을 이어받는다. 실수로 두 인스턴스에 같은 값을 주면 FencedInstanceIdException으로 나중에 붙은 쪽이 튕겨나간다(0019에서 이미 본 그대로).

group.protocol — classic vs consumer, 그리고 위 타임아웃들이 무효화되는 경우

group.protocol=consumer(신규 프로토콜, 0025 레슨에서 미리 본 그 개선된 rebalance 프로토콜)로 설정하면, 위 표의 session.timeout.ms·heartbeat.interval.ms client 설정은 더 이상 적용되지 않는다 — 대신 브로커 설정 group.consumer.session.timeout.ms가 그 역할을 대신한다. "분명 설정했는데 왜 안 먹지?"의 흔한 원인이니, 어느 프로토콜을 쓰는지부터 확인해야 한다.

3. 어디서부터 읽을지, 언제 커밋할지

auto.offset.reset — 저장된 위치가 없거나 사라졌을 때

값동작
latest (기본값)지금 이 순간부터 새로 들어오는 메시지만 읽음 — 과거 데이터는 건너뜀
earliest남아있는 가장 오래된 메시지부터 전부 읽음
none이전 offset을 못 찾으면 그냥 예외를 던짐(자동으로 아무거나 선택하지 않음)

새 컨슈머 그룹을 처음 붙일 때 이 값이 latest이면, 지금까지 쌓인 데이터를 몽땅 건너뛰고 시작한다 — "데이터가 안 보이는데요?"라는 질문의 흔한 원인 1순위다.

enable.auto.commit + auto.commit.interval.ms — 자동 저장이 만드는 전달 보장

0019 레슨 §5에서 배운 "읽기→처리→저장 순서가 전달 보장을 정한다"는 원칙이 여기 그대로 적용된다. 기본값 enable.auto.commit=true + auto.commit.interval.ms=5000은 백그라운드에서 5초마다 자동으로 offset을 저장하는데, 이건 정확히 "처리 완료 여부와 상관없이 시간이 되면 저장"하는 방식이라 메시지 유실 가능성이 있는 조합이다. 정확한 at-least-once를 원한다면 enable.auto.commit=false로 끄고 처리가 끝난 뒤 직접 커밋해야 한다.

isolation.level — 트랜잭션 메시지를 볼지 말지

read_committed로 설정하면 0019 레슨 §6에서 배운 트랜잭션 커밋 마커를 활용해 커밋되지 않은(취소된) 트랜잭션 메시지를 건너뛴다. 기본값은 read_uncommitted라서, 트랜잭션을 쓰는 Producer와 짝을 맞추려면 Consumer 쪽에서 이 값을 명시적으로 바꿔줘야 한다.

4. 가져오기(Fetch) 튜닝 — 지연 시간 vs 처리량

이 트레이드오프는 0028 레슨에서 볼 Producer의 batch.size/linger.ms와 정확히 같은 모양이다 — "조금 기다렸다가 크게 가져올까, 아니면 바로바로 가져올까."

설정기본값효과
fetch.min.bytes1이만큼 쌓일 때까지 브로커가 응답을 미룸 — 크게 잡으면 처리량↑ 지연↑
fetch.max.wait.ms500msfetch.min.bytes가 안 채워져도 이 시간이 지나면 그냥 응답 — 무한 대기 방지
max.poll.records500한 번의 poll()이 애플리케이션에 넘겨주는 최대 레코드 수 — 처리 로직이 느리면 줄여서 max.poll.interval.ms 초과를 방지
max.partition.fetch.bytes1MB파티션 하나당 한 번에 가져올 최대 크기

5. Share Consumer 전용 설정

0019 레슨 §7에서 본 Share Group(파티션을 여러 Consumer가 나눠 갖는 대안 모델)에는 전용 설정이 따로 있다. 딱 두 가지만 기억하면 된다.

  • share.record.lock.duration.ms (기본 30초) — "이 메시지 지금 내가 처리 중이니 건드리지 마"라는 점유 잠금이 유지되는 시간. 0019에서 말한 "acquisition lock"이 바로 이 설정으로 조절된다.
  • share.delivery.count.limit (기본 5) — 같은 메시지를 최대 몇 번까지 재전달 시도할지. 이 횟수를 넘기면 포기하고 다음으로 넘어간다.

ssl.*/sasl.* 계열의 보안 설정은 Producer·Admin Client와 완전히 공통이다 — 0028 레슨과 0030 레슨에서 한 번만 짚고, 여기서는 반복하지 않는다.
