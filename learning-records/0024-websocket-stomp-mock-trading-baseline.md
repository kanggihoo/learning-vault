# 모의투자 WebSocket/STOMP 학습 시작 — 2026-09-01

사용자가 모의투자 도메인에서 "여러 사용자가 ws로 연결되고, 각자 다른 종목 정보를 받고, 틱 발생 시
서버가 전달하고, 구독을 취소하는" 전체 flow를 코드 없이 내부 동작 수준으로 이해하고 싶다고 요청했다.

## 확정한 전제 (이게 설계를 갈랐다)
세션 시작 시 두 가지를 물어 확정했다.

1. **재생 시계 = 전 사용자 공용.** 서버가 하나의 가상 장(場)을 돌리고, 09:30:01 틱은 그 종목을
   구독한 모두에게 같은 값으로 간다. → 틱은 `/topic/ticks/{code}` 공용 목적지로 가고, 브로커가
   1:N 복제를 담당한다. 만약 **사용자별 개인 시계**였다면 같은 종목이라도 사용자마다 값이 달라져
   `/user/queue/...` + 사용자별 재생 커서가 필요했을 것이고, 레슨 전체 구조가 달라졌을 것이다.
   이 갈림길을 먼저 물은 것이 이번 세션에서 가장 중요한 판단이었다.
2. **목적 = 개념 이해 우선 + 실제 프로젝트 설계에도 사용.** 그래서 내부 동작 설명을 본문으로 하되,
   §9에 "이 설계가 깨지는 지점 5가지"를 실무 판단용으로 붙였다.

## 레슨 구성의 핵심 프레임
사용자의 질문 표현("각 사용자마다 다른 정보")에 **개념적 오해가 하나 숨어 있다**고 판단했다.
그래서 레슨 §0을 그 오해를 깨는 데 썼다: "사용자마다 다른 정보"는 사실 세 층위가 섞인 말이다.

- ① 공용 값 (005930 틱) — 값이 같다 → `/topic`
- ② 구독 조합 차이 (A는 2종목, B는 1종목) — **값은 같고 구독 목록만 다르다** → 여전히 `/topic`
- ③ 진짜 개인 값 (내 체결·잔고) — 값 자체가 다르다 → `/user/queue`

가장 흔한 실수는 ②를 ③처럼 구현해서, 브로커가 공짜로 해주는 fan-out을 서버 코드가 손으로 다시
짜게 되는 것. 여기서 **"개인화는 발행 시점이 아니라 구독 시점에 일어난다"**는 한 문장을 레슨의
중심 명제로 세웠다.

## 그 밖에 강조한 것
- 구독 레지스트리를 "JVM 힙 안의 맵"으로 눈에 보이게 덤프 형태로 그렸다. 이 표가 곧 답이라는 것.
- 세션 ≠ 사람 (탭 3개 = 세션 3개) → `/user` 목적지가 존재하는 이유로 연결.
- `SimpleBrokerMessageHandler`가 `clientInboundChannel`과 `brokerChannel`을 **둘 다** 구독한다는 점.
  구독 등록과 메시지 발행이 서로 다른 입구로 들어온다는 사실이 배관 이해의 열쇠다.
- 과거 데이터 재생이라 **구독 직후 스냅샷 공백**이 실시간보다 훨씬 심각하다는 점(다음 틱까지
  가상시간으로 몇 분일 수 있음)과, 스냅샷/스트림 경계의 구멍·중복은 시퀀스 번호로만 풀린다는 점.
