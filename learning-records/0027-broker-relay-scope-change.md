# 브로커 교체를 미션 범위로 편입 — 2026-09-01

[[0024-websocket-stomp-mock-trading-baseline|초기 미션]]에서 외부 브로커 릴레이는
"언제 필요해지는가 수준까지만"으로 out of scope에 넣어뒀다. 사용자가 직접
"RabbitMQ를 쓰면 clientInbound/OutboundChannel은 그대로 있고 브로커만 바뀌는 구조냐"고
물어와서 0034를 만들고 미션 제약을 수정했다. (여전히 실제 구축·운영은 제외)

## 사용자가 가져온 자료의 검증 결과
핵심 주장("채널 3개는 그대로, 브로커 부품만 교체")은 **맞다.** 다만 두 군데를 고쳤다.

1. **`/queue`에 대한 오해** — 자료는 "`/queue`로 시작하면 RabbitMQ 등 외부 브로커로 직행
   (1:1 메시지, 큐 보관)"이라고 했는데, `/queue`는 *설정된 브로커가 무엇이든* 그리로 간다.
   그리고 **SimpleBroker에서는 `/queue`가 `/topic`과 동작이 완전히 같다** — 이름만 관례다.
   "큐라서 1:1이고 저장된다"는 건 외부 브로커로 바꿨을 때의 이야기. 0033 §4와 0034 §5에 명시.
2. **연결 모델** — 자료에는 없던 내용. javadoc으로 확인한 결과
   `StompBrokerRelayMessageHandler`는 **CONNECT마다 독립 TCP 연결**을 열고, 별도로
   **서버 발행 전용 "system" 연결 1개**(수신 불가, 공유)를 유지한다.
   동시접속 500명 = RabbitMQ에 TCP 501개. SimpleBroker엔 없던 용량 변수라 0034 §4의 핵심으로 삼았다.

## 이 레슨의 진짜 payoff
"설정 한 줄 바꾸면 끝"이 아니라는 것. **브로커 교체는 '메시지 전달'만 해결한다.**
0034 §6에 남는 문제들을 정리했다:
- **틱 스케줄러 중복 발행** — 앱 서버 2대가 각자 스케줄러를 돌리면 같은 틱이 두 번 나간다.
  발행자는 하나여야 하고, 브로커를 바꾼다고 해결되지 않는다. (이게 Q5 정답)
- **가상 시계 공유** — 공용 시계 모델의 전제가 "서버가 하나의 장을 돌린다"였다.
- 브로커 장애라는 **새 실패 모드** — 앱은 멀쩡한데 시세만 안 오는 상황.

즉 0031에서 세운 "공용 시계 / 서버 1대" 전제가 여기서 되돌아와 발목을 잡는다는 걸 보여줬다.
결론은 "지금은 SimpleBroker가 정답"이지만, **왜 정답인지가 처음보다 훨씬 구체적**이 됐다.

## 부수적으로 정리한 것
사용자가 "컨트롤러한테 전달하는 건 누가 하냐, 이게 브로커 역할이냐"고 물었다 — 아니다.
`SimpAnnotationMethodMessageHandler`가 하고, HTTP의 `DispatcherServlet`에 대응한다.
브로커는 `@MessageMapping`의 존재조차 모르고 컨트롤러가 `brokerChannel`에 뭘 넣어야 움직인다.
0033 §4 뒤에 경고 박스로, 0034 §2에 독립 절로 넣었다.
