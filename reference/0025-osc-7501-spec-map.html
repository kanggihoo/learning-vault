OSC 7501 스펙 지도

스펙 한 장을 절별로 압축한 것. 레슨은 이 지도의 절을 하나씩 파고, 찾아볼 때는 여기를 연다.

§1 · 시퀀스의 모양 (레슨 0055)

OSC 7501 ; pairs ST        report (보고)
OSC 7501 ; ? ST            feature detection (지원 질의)

OSC = ESC ]  (0x1B 0x5D)
ST  = ESC \  (0x1B 0x5C)  또는  BEL (0x07)

모르는 OSC는 터미널이 반드시 무시한다(MUST). 그래서 질의 없이 보내도 된다.

§2 · 본문 문법 (report-syntax, 예정)

pairs := pair (":" pair)*
pair  := key "=" value
key   := [a-z]+
value := [A-Za-z0-9_.,+/=-]*
상황결과
잘못된 pair (= 없음, 빈 key, 허용 밖 byte)그 pair만 skip, 나머지는 처리
모르는 key무시 (확장 방식)
key가 반복됨마지막 값이 이김
한도 초과 / base64 디코딩 실패 / 디코딩 결과에 제어문자보고 전체 폐기. 아무것도 적용되지 않음

자유 텍스트(msg, title)는 UTF-8의 표준 base64, padding 선택. 디코딩 결과에 제어문자(U+0000–001F, 007F, 0080–009F. 줄바꿈·탭 포함) 금지. 한 줄 값이다.

§3 · state (states-model, 예정)

state뜻수명

working실행 중. progress 가능교체·삭제·프로세스 종료·다음 shell prompt
done한 단위 작업 끝, 사용자가 아직 못 봄교체·삭제될 때까지. 종료·prompt 뒤에도 남음
blocked사용자가 뭔가 해야 진행 가능. kind, msg. progress 가능working과 같음
error실패하고 멈춤done과 같음
clearstate가 아니라 삭제 명령. id 지정 시 그 record와 하위 전부, id 없으면 이 터미널의 모든 record-

사용자가 중단·취소하면 idle을 보고한다. 끝나자마자 종료하는 프로그램은 종료 직전에 done/error를 보고하는 것이 좋다(SHOULD).

§4 · key (states-model, record-replace)

key값비고
stateidle|working|done|blocked|error|clear필수. 없거나 모르는 값이면 보고 전체 무시
id슬래시 경로, 예 build/test없으면 root record. 문법 위반이면 무시(root로 폴백하지 않음)
kindpermission|question|authblocked일 때만. permission=승인, question=답 입력, auth=로그인·토큰
progress정수 0~100working·blocked일 때만. 없으면 "진행률 미정"
app[A-Za-z0-9_.+-]{1,32}프로그램 식별자(예: cargo). 라벨 아님. 없으면 가장 가까운 조상 record의 app을 물려받음
titlebase64 UTF-8record의 짧은 라벨. root의 라벨은 보통 window title
msgbase64 UTF-8한 줄 설명. 터미널이 줄여도 되고 의미를 읽으면 안 됨

§5 · record 모델 (record-replace, lifetime)

  • 터미널은 id당 record 하나를 가진다. 보고는 해당 id의 record를 통째로 교체한다. 빠진 key는 사라진다. 그래서 app·title도 매 보고에 다시 넣는다.
  • /는 부모-자식 관계다: build/test는 build의 자식. clear와 app 상속에만 쓰이고, 그룹핑에는 써도 된다(MAY). 부모 record가 없어도 된다.
  • root와 자식 record는 동시에 존재한다. 예: root는 idle인데 worker 하나는 blocked.
  • record는 화면이 아니라 터미널에 속한다. primary/alternate screen 전환은 영향 없음. RIS(full reset)는 전부 삭제, DECSTR(soft reset)은 삭제하지 않음.
  • heartbeat 없음. 다시 보내야 유지되는 방식을 요구하면 안 된다. 프로세스 종료나 새 shell prompt(OSC 133 A)에서 working·blocked는 반드시 삭제, idle은 삭제해도 됨, done·error는 살아남는다.

§6 · 지원 감지·보안·한도 (이름과 위치만)

  • 감지: OSC 7501 ; ? ST 직후 CSI c(DA)를 보낸다. DA 응답이 먼저 오면 미지원. 지원 터미널은 ?:states=…:kinds=…로 답한다.
  • 보안: 보고 내용은 전부 untrusted 입력. 제어문자 거부, markup 금지, bidi 같은 방향 제어·보이지 않는 문자는 터미널 밖에서 보일 때 무력화(SHOULD). 터미널이 되돌려 쓰는 것은 감지 응답뿐.
  • 한도: 전체 4096 bytes(합법 최대 약 3300), key 16, msg 인코딩 2732/디코딩 2048, title 256/192, app 32, id 128(세그먼트 32, 깊이 8), record 256개(최소 64개 지원. 초과 시 가장 오래 갱신 안 된 것 삭제).

§7 · 다른 시퀀스와의 관계 (why-7501, 예정)

시퀀스스펙이 말하는 한계
OSC 9;4 (progress)busy·퍼센트·error만. 사용자 대기 여부, 요청 내용, 메시지, 식별 정보가 없다. iTerm2 알림과 번호 9를 공유해 출력이 깨진 사례가 있다.
OSC 9, 99, 777 (알림)일회성 사건이라 "지금 무엇이 참인지"가 남지 않는다. 사용자를 방해한다는 뜻을 내포한다.
OSC 133 (shell integration)shell이 보내므로 명령이 실행 중인지·종료 코드만 안다. 프로그램이 무엇을 하는지, 막혔는지는 모른다.
OSC 0, 2 (window title)구조 없는 문자열 하나. 글리프·스피너로 상태를 흉내 내지만 기계가 읽기에 신뢰할 수 없다.
OSC 21337 (iTerm2), 9999 (Orca)같은 아이디어의 앞선 시도. 표현(색·표시)을 기술하거나 JSON 파싱이 필요해 목표가 다르다고 스펙 저자는 본다.

§8 · 스펙의 예 (base64는 디코딩해 병기)

ESC ] 7501 ; state=working:app=brew:msg=SW5zdGFsbGluZyB1cGRhdGVz ESC \                      # Installing updates
ESC ] 7501 ; state=blocked:kind=auth:app=brew:msg=UGFzc3dvcmQgcmVxdWlyZWQgdG8gaW5zdGFsbCB1cGRhdGVz ESC \  # Password required to install updates
ESC ] 7501 ; state=working:app=brew:msg=SW5zdGFsbGluZyB1cGRhdGVz ESC \                      # Installing updates
ESC ] 7501 ; state=done:app=brew:msg=VXBncmFkZWQgMTIgcGFja2FnZXM= ESC \                     # Upgraded 12 packages

매 보고가 app=brew를 반복하는 이유는 §5의 "통째 교체" 때문이다. 마지막 done은 다음 shell prompt 뒤에도 남는다.

검증 노트

사용처 표(어느 도구가 emit·consume하는지)는 이 지도에 넣지 않았다. 아직 원문 대조 전이다. ecosystem-map 레슨에서 추적 사이트·이슈 원문으로 확인한 뒤 채운다. 스펙 문서(Rex)에는 저자가 적혀 있지 않다. 다만 추적 사이트(areweosc7501yet.com)는 rev 0.1(2026-09-28)의 출처를 github.com/mitchellh 계정의 gist(spec.md, secret gist, 마지막 수정 2026-09-30)로 적고 있고, 이 gist가 존재하는 것은 확인했다. 그 계정이 Mitchell Hashimoto 본인인지, Rex 문서가 이 초안에서 이어진 것인지는 미확인이다.
