§0 · 30초 요약

과거 80개월(2020.01~2026.08)의 실제 시세를 3일 시즌으로 재생하는 모의투자 게임. 수백 명이 같은 가상 시각을 공유한다 — 서버가 하나의 장(場)을 돌린다.

재생 페이스게임 1개월 = 실제 720초(12분) 고정. 틱 간격은 31~36초 유동. 하루 약 27개월
가격 모델단일 가격 — 일봉 종가만. 시가·고가·저가·거래량을 게임 전체에서 쓰지 않는다. 차트는 선 그래프
시드1억 원. 1주 단위 정수 거래. 공매도·레버리지·부분 체결 없음
통화원화·달러 두 지갑. 수동 환전. 나스닥·코인은 달러 결제, 국내는 원화
인증소셜 로그인 전용(Google·Kakao). 세션 방식, JWT 없음. Redis 인덱스 세션
실시간STOMP over WebSocket. destination 4개. 서버→클라이언트 단방향(`SEND` 프레임 없음)
핵심 설계 원칙"모르는 채로 겪기" — 미래 데이터는 서버에만 존재하고 응답 계층이 게임 시각으로 잘라 낸다
스택Spring Boot 4.1.1 · Java 21 · PostgreSQL + Flyway · Redis · JPA · springdoc-openapi

§1 · 하루 — 타임라인과 phase

phase실제 시각거래채팅리더보드가능한 것
BRIEFING11:00~11:05✗송·수신열람열람, 채팅
TRADING11:05~16:40✓송·수신열람전 기능 — 시장가·예약·환전·청약·채팅
SETTLING16:40~17:00✗송·수신열람열람, 채팅
REVIEW_ONLY17:00~익일 11:00✗읽기만열람계좌·차트·랭킹·복기·뉴스 열람

feeFree와 leaderboardBlackout은 phase가 아니라 플래그다. 둘 다 거래가 계속되므로 phase로 쪼개면 "거래 가능한 phase가 3개"가 되어 모든 게이팅 표기가 복잡해진다.

일시정지는 없다. 12분 그리드가 IPO 8건·폐장·정산 시각을 전부 고정하므로 멈추면 그 전부가 흔들린다. 장애 대응은 세션 조기 종료 — 계약상 TRADING → SETTLING 조기 전환 하나이고 새 엔드포인트도 새 phase도 만들지 않는다.

⚠ 발견 — 종목.md의 시각이 이 표와 다르고, 그리드 검산에 실패한다. 종목.md는 카카오게임즈 공시 12:05 · 등장 12:25로 적었는데, 12:25는 11:05로부터 80분이라 12분의 배수가 아니다(6.67개월). 8건 전부가 같은 방식으로 어긋나며 일관되게 약 16~24분 이르다.

기능명세서 IPO 편성표가 맞고 종목.md가 낡은 값으로 보인다 — 전자만 720초 그리드를 만족하고, 공시가 "상장 2개월 전"이라는 기획서 8장 규칙도 전자에서만 성립한다 (종목.md 값으로는 3개월 전이 된다). 구현 전에 종목.md를 갱신하거나 "편성 시각의 정본은 기능명세서"임을 명시해야 한다.

이 모순은 0036의 그리드 검산을 적용해서 찾았다. 개념이 실제로 쓰인 첫 사례다.

IPO 규칙: 시즌당 8건 · 무작위 추첨(전원 동일 확률) · 1인 1청약(종목당) · 청약 단위 고정(국내 1,000만 원 = 시드의 10%, 나스닥은 상당 달러) · 증거금 100% 즉시 잠금 · 당첨 예정 인원 = round(청약자 × 30%) 최소 1명 · 배정 수량 = floor(증거금 ÷ 공모가) · 낙첨 증거금은 추첨 즉시 전액 반환.

수익률 정의 — 두 곳에서 따로 계산하면 안 되는 값들

총 평가액   = krwCash + usdCash × 당일환율 + 보유자산 원화평가액
누적 수익률 = (총평가액 − 시작잔고) ÷ 시작잔고 × 100     // rank SEASON과 같은 값이어야 한다
일간 수익률 = (총평가액 − 당일개장평가액) ÷ 당일개장평가액 × 100  // rank DAILY와 같은 값
등락률      = (close − prevClose) ÷ prevClose × 100      // 휴장일은 null (0.00이 아니다)
평단가      = totalCost ÷ quantity                       // 파생. 저장하지 않는다
소급 인덱스 = 1억 × (합류시점 지수 ÷ 시즌시작 지수)        // 기준 지수는 QQQ 대리값 제안

같은 값을 두 곳에서 계산하면 화면이 어긋난다. 계좌의 cumulativeReturn과 리더보드 SEASON의 returnRate는 같은 값이어야 하고(기획서 11.1.2 명시), dailyReturn도 마찬가지다. 공통 모듈로 뽑는 것이 계약이 아니라 정합성 요구다.
