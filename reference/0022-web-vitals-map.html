Web Vitals 지도

일곱 이름 — TTFB · FCP · DCL · LCP · TBT · INP · CLS — 은 서버 로그가 아니라 사용자의 눈과 손을 기준으로 페이지 하나의 삶을 잘라 놓은 것이다. 이 문서는 그 일곱이 타임라인 어디에 있고, 왜 셋만 "Core"이고, 어느 도구가 어느 것을 재는지를 한 장에 모은다. 레슨은 이 지도의 한 축씩을 판다.

§0 · 30초 요약

  • Core Web Vitals 3종은 사용자의 세 질문에 답한다 — 보이나? LCP(2.5s) · 반응하나? INP(200ms) · 흔들리나? CLS(0.1). 셋 다 실제 사용자 브라우저(field)에서 측정되고, 기준은 75퍼센타일이다.
  • 보조 지표는 Core를 진단하는 용도다. TTFB·FCP는 LCP의 앞부분이고, TBT는 lab에서 INP를 대신 짚는 대리 지표다. 구글 원문: TTFB·FCP는 "LCP 문제를 진단하는 데 유용", TBT는 "field에서 측정 불가라 Core가 아님".
  • DCL(DOMContentLoaded)은 Web Vitals가 아니다. 화면이 아니라 HTML 파서 상태를 알리는 브라우저 이벤트다. 개발자 타이밍이지 사용자 체감 지표가 아니다.
  • Lighthouse 점수 ≠ Core Web Vitals 통과. Lighthouse는 lab이라 INP를 못 재고(TBT로 대체), 점수 가중치에 INP·TTFB·DCL이 없다. 실제 판정은 CrUX(field, 28일, p75)로 한다.
  • 백엔드의 칸은 TTFB다. 2.5초 LCP 예산에서 TTFB는 약 40%(≈1.0s). DB 쿼리·SSR·리다이렉트·TLS가 전부 여기에 들어간다.

§5 · 임계값의 근거 — 왜 75퍼센타일, 왜 2.5초

결정근거 (web.dev 원문 요지)
75퍼센타일"방문 4회 중 3회가 목표 수준 이상의 경험을 했음을 안다. 또한 75퍼센타일은 이상치 영향을 덜 받는다." — 평균은 소수의 극단값에 끌려가고, p99는 달성 불가능한 목표가 된다. 백엔드의 p99 SLO와 같은 논리, 다른 분위수.
모바일·데스크톱 같은 기준기기별로 기준을 나누지 않되 측정은 분리한다. "대부분 사이트에서 모바일이 트래픽의 다수"라 모바일이 사실상 병목.
달성 가능성"good" 기준은 상위 10% 이상의 origin이 이미 달성하고, 잘 최적화된 사이트가 꾸준히 달성할 수 있어야 한다.
LCP 2.5sMiller·Card의 인지 연구 — 사용자의 주의 유지 한계 "약 0.3초~3초". 2.5s는 그 범위 안이고 당시 모바일 origin의 42%가 달성.
INP 200msMichotte의 인과 지각 연구 — "약 100ms까지의 지연"은 내 행동의 결과로 느낀다. 200ms는 그것과 달성 가능성(모바일 56%)의 절충.
CLS 0.1선행 연구가 없어 실제 페이지를 평가 — "0.1 이하는 눈에 띄지만 과도하게 방해하지 않았다." 서드파티 임베드 때문에 달성이 어려운 점을 감안.

§6 · 증상 → 지표 → 책임 칸 진단표

사용자가 말하는 증상먼저 볼 지표그 다음 볼 것책임 칸이 갈리는 질문
"흰 화면이 한참 떠 있다"TTFB → FCPTTFB가 0.8s 넘는가?넘으면 서버·인프라 몫(쿼리·SSR·리다이렉트·TLS·CDN). 안 넘으면 렌더 차단 CSS/JS → 프론트 몫.
"글은 나왔는데 큰 이미지가 늦다"LCPFCP~LCP 간격, LCP 4구간load delay가 크면 이미지가 늦게 발견됨(lazy-load·JS 뒤에 숨음) → 프론트. TTFB가 크면 서버.
"버튼 눌렀는데 한참 멈춘다" (로드 직후)TBT (lab)long task 목록, 스크립트 평가 시간거의 항상 프론트 JS 몫. 단, 로드 직후 API 응답을 동기적으로 기다리는 구조면 서버 응답도 연루.
"버튼 눌렀는데 한참 멈춘다" (사용 중)INP (field)3구간 중 어디가 긴가input delay → 다른 long task · processing → 핸들러 · presentation → 큰 DOM/레이아웃. 전부 프론트. fetch 대기 시간은 INP에 안 들어간다 — 다음 프레임만 그리면 끝.
"읽는 중에 내용이 밀려서 잘못 눌렀다"CLS이동 원인 요소, 세션 윈도우이미지·광고·폰트에 크기 예약이 없음 → 프론트. 서버가 늦게 도착하는 데이터로 목록 위에 배너를 끼워 넣는 구조면 설계 문제.
"Lighthouse는 90인데 Search Console이 빨갛다"CrUX INPlab에 INP가 없음을 확인lab-field 차이 자체가 답. 실사용자 기기·상호작용에서만 드러남. TBT는 통과했어도 INP는 별개.

§7 · 측정 스니펫

브라우저 콘솔에 붙여 넣으면 현재 페이지에서 바로 값이 나온다. 정식 수집은 web-vitals 라이브러리를 쓴다(엣지 케이스 처리).

// TTFB · DCL — Navigation Timing (단위 ms, 내비게이션 시작 기준)
const nav = performance.getEntriesByType('navigation')[0];
console.log('TTFB', nav.responseStart, 'DCL', nav.domContentLoadedEventStart, 'load', nav.loadEventEnd);

// FCP — Paint Timing
new PerformanceObserver(list => {
  for (const e of list.getEntriesByName('first-contentful-paint')) console.log('FCP', e.startTime);
}).observe({ type: 'paint', buffered: true });

// LCP — 후보가 여러 번 갱신되고, 사용자가 상호작용하면 멈춘다
new PerformanceObserver(list => {
  for (const e of list.getEntries()) console.log('LCP candidate', e.startTime, e.element);
}).observe({ type: 'largest-contentful-paint', buffered: true });

// CLS — hadRecentInput=false 인 것만 누적 (세션 윈도우 계산은 web-vitals가 해 준다)
new PerformanceObserver(list => {
  for (const e of list.getEntries()) if (!e.hadRecentInput) console.log('shift', e.value);
}).observe({ type: 'layout-shift', buffered: true });

// INP · 전체 — 공식 라이브러리
import { onLCP, onINP, onCLS, onTTFB, onFCP } from 'web-vitals';
onINP(console.log); onLCP(console.log); onCLS(console.log);
