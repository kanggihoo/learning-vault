§0 · 30초 요약 — 하나의 파이프라인

아키텍처는 "구조를 고르는 일"이 아니라 "무엇이 구조를 강제하는지 찾아 거기에 답하는 일"이다. 그래서 순서가 있다. 스타일부터 고르면 (예: "일단 MSA로 가죠") 이 파이프라인을 거꾸로 탄 것이고, 그게 대부분의 나쁜 설계가 생기는 방식이다.

§1 · Architecture Driver — 설계를 강제하는 5종

Architecture driver = 아키텍처 설계에 실질적 영향을 주는 요구·제약의 총칭. "설계자가 마음대로 정할 수 없고, 정해지면 구조가 따라 결정되는 것"이 driver다. Cervantes & Kazman은 이를 다섯 범주로 나눈다.

범주무엇인가예놓치면 생기는 일
설계 목적
Design purpose		 왜 지금 설계하는가. 제안서용 개략 설계인지, 기술 검증 프로토타입인지, 실제 구축용인지. "수주 전 공수 산정용" vs "3년 운영할 시스템 구축용" 깊이를 잘못 잡는다. 제안서에 서비스 분해도를, 실제 구축에 개략도를 그린다.
품질 속성
Quality attributes		 측정·검증 가능한 시스템 속성. 구조를 가장 크게 형성한다. 반드시 시나리오로 표현한다(§2). "피크 시 p99 응답 300ms 이하", "단일 노드 장애 시 30초 내 복구" 구조를 정당화할 근거가 사라진다. "왜 큐를 뒀나"에 답을 못 한다.
주요 기능
Primary functionality		 비즈니스에 결정적이거나 기술 난도가 높은 기능. 전체 유스케이스의 약 10%. 주문 체결, 결제 승인 — 회원 정보 수정은 여기 들어가지 않는다. 모든 기능을 동등하게 다루다 구조가 평평해지고 정작 어려운 곳을 늦게 만난다.
아키텍처 관심사
Architectural concerns		 요구사항 문서에 안 적히지만 반드시 결정해야 하는 것. 구조·코드 조직·배포, 그리고 횡단 관심사. 예외 처리 방식, 로깅·추적, 인증, 캐싱, 설정 관리, 개발 환경 분리 각 팀이 제각기 정해서 시스템이 조각난다. AI에게 맡기면 특히 여기가 무작위가 된다.
제약
Constraints		 설계자가 통제할 수 없는 결정. 기술 지정, 법·규제, 기존 시스템 연동, 팀 역량, 마감. "사내 표준이 Spring Boot", "개인정보 국외 이전 불가", "발표까지 6주", "팀 5명 전원 Java만" "좋은 설계"를 만들었는데 못 쓴다. 제약은 좁혀진 공간에서 최선(satisfice)을 찾게 한다.

면접에서 쓰는 문장. "이 시스템의 아키텍처 driver는 ○○였습니다"로 시작하면 구조 설명이 취향 발표가 아니라 근거 있는 결정으로 들린다. 자세히는 레슨 0037.

§2 · Quality Attribute — 어휘와 시나리오

2.1 시나리오 6부 — 형용사를 문장으로

"빨라야 한다"는 driver가 아니다. 검증할 수 없기 때문이다. 품질 속성은 여섯 조각으로 써야 측정·검증 가능해진다.

조각의미예 (모의투자 주문)
자극원 Source자극을 만든 주체로그인한 사용자
자극 Stimulus응답이 필요한 사건·조건매수 주문을 제출한다
대상 Artifact자극을 받는 시스템 부분주문 처리 서비스
환경 Environment자극이 발생하는 상황동시 접속 500명의 피크 시간
응답 Response그 결과 일어나는 활동주문이 접수되고 접수 확인이 반환된다
응답 측정 Response measure응답을 평가할 지표 — 숫자p99 300ms 이내, 유실 0건

출처의 표준 예시: "사용자가 <C> 버튼을 누르면 게임은 500ms 이내에 시점 모드를 전환한다" — 자극원=사용자 / 자극=<C> 입력 / 대상=시스템 전체 / 환경=정상 운영 / 응답=모드 전환 / 응답 측정=<500ms.

2.2 ISO/IEC 25010:2023 — 공용 어휘 9종

품질 속성 이름을 팀마다 다르게 부르면 논의가 안 된다. 국제 표준 어휘가 ISO/IEC 25010이고, 2023년 개정에서 항목이 8개 → 9개로 바뀌었다.

2.3 실무 용어 ↔ 표준 어휘 대응

현업에서 쓰는 말이 표준의 어디에 붙는지 알면, 뭉뚱그린 요구를 쪼갤 수 있다.

현업 용어ISO 25010에서의 자리주의
가용성 Availability신뢰성 > 가용성SLA의 99.9%는 여기. 복구성과 다른 지표다.
복원력 Resilience신뢰성 > 결함 허용성 + 복구성표준 용어가 아니다. 두 개가 합쳐진 말이라 항상 쪼개서 물어야 한다.
확장성 Scalability유연성 > 확장성성능과 다르다. "느리다"와 "더 못 늘린다"는 다른 문제.
지연시간 Latency성능 효율성 > 시간 반응성평균이 아니라 p95·p99로 적는다.
처리량 Throughput성능 효율성 > 수용력지연시간과 동시에 최적화되지 않는다.
관측 가능성 ObservabilityISO 25010에 없다Well-Architected의 운영 우수성(Operational Excellence) 쪽 어휘.
비용 CostISO 25010에 없다제품 품질이 아니라 제약·비즈니스 목표. Well-Architected의 비용 최적화 필러.

클라우드 쪽에서는 ISO 대신 Well-Architected 필러를 쓴다 — Azure 기준 신뢰성 · 보안 · 비용 최적화 · 운영 우수성 · 성능 효율성. 같은 것을 다른 축으로 자른 것이다.

§3 · Tactic — 품질별 전술 카탈로그

전술(tactic) = 하나의 품질 속성 응답에 직접 영향을 주는 설계 결정 하나. 구조를 만들지 않고, 이름도 동사구다("결함을 감지한다", "수요를 제어한다"). 아래는 Cervantes & Kazman의 분류다. 표를 위에서 아래로 읽으며 "우리는 이 칸이 비어 있나?"를 묻는 체크리스트로 쓴다.

§4 · Style — 전체 골격 비교

스타일 = 어떤 종류의 요소가 등장할 수 있고 그들 사이에 어떤 관계가 허용되는지에 대한 제약. 제약이 선택지를 좁히기 때문에 바람직한 속성이 "저절로" 나온다. 예: 마이크로서비스의 제약("서비스는 하나의 책임", "데이터는 사유")을 지키면 독립 배포와 장애 격리가 따라온다. 제약을 어기면서 이름만 쓰면 이점은 안 오고 비용만 온다.

스타일구조 제약잘 사는 품질희생하는 품질언제 고르나
계층형
Layered / N-tier		 수평 계층으로 나누고, 아래 계층만 호출한다 변경 용이성(계층 내) · 학습 용이성 · 테스트 용이성 성능(계층 통과 비용) · 배포 민첩성 전통적 업무 도메인, 변경 빈도 낮음. 기본값으로 시작하기 좋다.
클라이언트-서버 요청자와 제공자가 분리, 서버가 공유 자원을 보유 중앙 통제 · 보안 · 확장성(서버 측) 서버가 단일 실패 지점이 되기 쉬움 거의 모든 웹 시스템의 밑바탕. 단독으로 고르기보다 전제에 가깝다.
파이프-필터
Pipes and Filters		 필터는 상태를 공유하지 않고 스트림을 변환, 파이프로만 연결 재사용성 · 조합성 · 병렬 처리 대화형 응답 · 전역 오류 처리 · 상태 필요한 작업 ETL, 미디어 변환, 로그 처리. Kafka Streams·Spring Batch가 이 모양.
마이크로커널
Microkernel / Plug-in		 최소 코어 + 플러그인. 코어는 플러그인을 모른다 확장성(기능) · 배포 용이성 · 격리 플러그인 계약 설계가 어렵고, 전역 최적화가 힘듦 IDE, 브라우저 확장, 규칙 엔진, 결제 수단이 계속 늘어나는 시스템.
이벤트 기반
Event-Driven		 생산자와 소비자가 서로를 모르고 브로커를 통해서만 만난다 확장성 · 장애 격리 · 실시간 반응성 · 확장 용이성 전달 보장 · 순서 · 최종 일관성 · 디버깅 난이도 IoT, 실시간·스트리밍, 한 사건에 반응할 곳이 계속 늘어나는 시스템.

스타일을 실제로 고르고 거절하는 법은 레슨 0039 — 제약이 이점을 만든다는 원리, 분산 모놀리스 진단표, 마이크로서비스 프리미엄 체크리스트.

이름이 겹치는 문제: Mark Richards 계열은 이들을 "아키텍처 스타일", Microsoft는 "architecture styles", 옛 문헌·시험은 "아키텍처 패턴"이라 부른다. 같은 것을 가리킨다. §6에서 구분 기준을 정리한다.

§5 · Pattern — 문제별 패턴 카탈로그

패턴은 "반복되는 문제 → 검증된 국소 해법 + 그 대가"의 묶음이다. 고르는 순서는 기술이 아니라 문제다. 아래는 문제별로 묶은 것이고, 각 패턴이 어떤 품질 속성을 겨냥하는지 함께 적었다.

이미 배운 것과의 연결: Outbox · Competing Consumers · Pub/Sub.

§7 · 트레이드오프 — 공짜 품질은 없다

모든 전술·패턴·스타일은 어떤 품질을 올리면서 다른 품질을 내린다. 설계 리뷰의 실질은 "좋은가"가 아니라 "무엇을 내주고 무엇을 얻었나"를 말하게 만드는 것이다.

§8 · 설계·평가 프로세스

ADD — Attribute-Driven Design (설계하는 법)

"품질 속성 요구를 근거로 아키텍처를 설계하는 단계적 방법." 핵심은 재귀다. 시스템 전체를 한 번에 설계하지 않고, 요소 하나를 골라 분해하고, 그 안에서 같은 루프를 다시 돈다.

  1. 입력이 충분한지 확인한다 (기능 요구 · 품질 속성 시나리오 · 제약).
  2. 분해할 요소를 하나 고른다.
  3. 그 요소의 후보 driver를 식별하고 우선순위를 매긴다.
  4. driver에 답하는 설계 개념을 고른다 (전술 · 패턴 · 스타일 · 기성 컴포넌트).
  5. 요소를 만들고 책임을 배정한다.
  6. 요소 간 인터페이스를 정의한다.
  7. 요구를 검증하고, 남은 요구를 하위 요소의 제약으로 바꾼다. → 2번으로.

7번이 이 방법의 핵심 장치다. 상위에서 못 다 푼 품질 요구가 하위 요소의 제약이 되어 내려간다.

유틸리티 트리 (무엇부터 볼지 정하는 법)

루트에 "효용", 그 아래 품질 속성, 그 아래 세부 관심사, 잎에 시나리오를 달고 각 시나리오에 (비즈니스 중요도, 기술 난도) 두 축으로 H/M/L을 매긴다. (H, H)인 잎이 설계·평가에서 먼저 다룰 것이다. 실무에서 요구사항 우선순위를 정할 때 그대로 쓸 수 있다.

§8·§9 전체를 실제로 쓰는 법은 레슨 0044 — 유틸리티 트리로 우선순위, 평가 4산출물, 적합성 함수, ADR 실물 예시, 그리고 전체 아크 진단 표.

ATAM — Architecture Tradeoff Analysis Method (평가하는 법)

평가팀 · 결정권자(아키텍트·PM) · 이해관계자 대표가 모여, 시나리오를 뽑아 우선순위를 매기고, 상위 시나리오에 대해 아키텍트가 "이 구조가 이 시나리오를 어떻게 만족시키는지" 설명한다. 산출물은 위험 · 비위험 · 민감점 · 절충점 네 가지다.

혼자서도 쓸 수 있는 축소판. AI가 설계안을 내놓으면 이렇게 묻는다 — ① 이 설계가 겨냥한 품질 속성 시나리오를 6부로 적어줘 ② 그 시나리오를 만족시키는 경로를 구조 위에서 짚어줘 ③ 이 결정의 절충점은 무엇이고 무엇을 내줬어? 세 질문이 ATAM의 뼈대다.

적합성 함수 Fitness Function (계속 지키는 법)

품질 속성을 자동으로 계속 검증하는 테스트로 바꾼 것. "계층 규칙을 어긴 import가 있으면 빌드 실패", "p99가 300ms를 넘으면 배포 중단", "순환 의존이 생기면 CI 실패". 시나리오의 응답 측정이 있어야 쓸 수 있다 — §2가 여기서 회수된다.

  • 안티패턴 — 저부하에선 멀쩡하다가 부하가 오르면 무너지는 설계. 패턴 카탈로그와 짝을 이루는 목록이 따로 있다.
