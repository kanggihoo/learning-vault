STOMP + SimpleBroker 치트시트

Spring 내장 SimpleBroker · 서버 1대 기준. 레슨: 0031 — 모의투자 틱 스트리밍 · 0032 — STOMP와 Spring 메시징의 어휘

0. 어휘 — 헷갈리면 여기부터

용어정체 (한 줄)
WebSocket양방향 바이트 통로. 메시지의 뜻은 하나도 안 정해준다.
STOMP그 통로로 주고받을 텍스트 프레임 규격. 명령어 + 헤더 + 빈 줄 + 본문 + NULL.
Message<T>getHeaders() + getPayload(). 봉투. 프레임을 파싱한 자바 객체.
MessageChannel네트워크 아님. JVM 안의 큐 + 스레드 풀 + 수신자 목록. send()는 큐에 넣고 즉시 리턴.
MessageHandlerhandleMessage(Message) 하나짜리 인터페이스. 채널에 등록해두면 불리는 콜백.
SimpleBrokerMessageHandler구독 명부(DefaultSubscriptionRegistry)를 필드로 든 상태 있는 핸들러.
StompSubProtocolHandler프레임 텍스트 ⇄ Message 번역 + 실제 소켓 쓰기를 담당하는 유일한 곳.
브로커가 오래 보관하는 것은 구독 목록뿐이다. 메시지는 복제되어 outbound 채널로 넘어가면 끝 — 저장하지 않는다. 그래서 구독 전에 발행된 것은 영원히 못 본다. (Kafka와의 결정적 차이)
서버가 덧붙이는 헤더 2개. simpSessionId와 simpUser는 프레임에 없다. 서버가 "어느 소켓으로 들어왔는지" 알기에 붙인다. 브로커가 누구에게 보낼지 아는 근거가 정확히 이 헤더다.

1. 목적지 접두사 — 어떤 글자로 시작하느냐가 전부

접두사담당 핸들러의미모의투자 예
/appSimpAnnotationMethodMessageHandler 서버 코드가 처리. 브로커를 거치지 않는다./app/order 주문 전송
/topicSimpleBrokerMessageHandler 1:N. 구독자 전원에게 같은 값./topic/ticks/005930
/queueSimpleBrokerMessageHandler SimpleBroker에서는 /topic과 동작이 같다. 관례상 개인용 이름 공간. /queue/execution-s1 (직접 쓰지 않음)
/userUserDestinationMessageHandler 브로커가 모르는 가상 접두사. 세션별 주소로 재작성된다. /user/queue/execution
설정 규칙 3가지. ① 브로커 접두사에 /queue가 있어야 /user 재작성 결과가 배달된다. ② /user는 브로커 접두사에 넣으면 안 된다 — 브로커가 삼켜 재작성 기회를 잃는다. ③ /app과 브로커 접두사는 겹치면 안 된다.

2. 목적지 고르는 판단 기준

질문 하나만 던진다 — "이 값이 다른 사람에게도 똑같은가?"
예 → /topic/... · 브로커가 복제한다. 서버 코드는 1번만 발행.
아니오 → /user/queue/... · 값 자체가 그 사람 것이다.

"사용자마다 보는 종목이 다르다"는 아니오가 아니다. 값은 같고 구독 목록만 다른 것이므로 답은 여전히 /topic이다.
데이터목적지근거
종목 틱 / 호가 / 체결가/topic/ticks/{code}공용 시계라 전원 동일
가상 시계 상태 (개장·마감·배속)/topic/clock전원 동일
지수 · 랭킹 · 공지/topic/index, /topic/notice전원 동일
내 주문 접수 / 체결/user/queue/execution값이 그 사람 것
내 잔고 / 평가손익/user/queue/portfolio값이 그 사람 것
내 요청에 대한 에러/user/queue/errors (broadcast=false)보낸 세션에게만

3. 프레임 레퍼런스 (STOMP 1.2)

클라이언트 → 서버

CONNECT accept-version:1.2 필수 host:trade.example.com 필수 heart-beat:10000,10000 보낼주기,받을주기(ms)
SUBSCRIBE id:sub-0 필수 · 연결 내 유일 destination:/topic/... 필수 ack:auto 기본값
UNSUBSCRIBE id:sub-0 필수 · destination 없음!
SEND destination:/app/order 필수 content-type:application/json {"code":"005930","qty":10}
DISCONNECT receipt:bye 선택 · RECEIPT 후 닫기

서버 → 클라이언트

CONNECTED version:1.2 필수 session:s1 선택 heart-beat:10000,10000 협상 결과 = 양쪽 MAX
MESSAGE destination:/topic/... 필수 message-id:s1-42 필수 subscription:sub-0 필수 · 라우팅 키 content-type:application/json {"code":"005930","price":68400}
ERROR message:... 보낸 뒤 연결을 닫는다
RECEIPT receipt-id:bye

ack 모드

auto기본. 보내면 전달된 것으로 간주. 시세는 이것.
client누적 ACK. 앞의 것까지 한 번에 확인.
client-individual메시지 하나씩 개별 ACK.

4. 서버 내부 배관

채널방향구독하는 핸들러
clientInboundChannel클라이언트 → 서버 SimpAnnotationMethodMessageHandler, UserDestinationMessageHandler, SimpleBrokerMessageHandler
brokerChannel서버 코드 → 브로커SimpleBrokerMessageHandler
clientOutboundChannel서버 → 클라이언트StompSubProtocolHandler

셋 다 ExecutorSubscribableChannel — 스레드 풀 위의 비동기 큐다. convertAndSend는 즉시 리턴하고, 실제 전송은 워커 스레드가 한다.

구독 레지스트리에 저장되는 것

DefaultSubscriptionRegistry (JVM 힙. 영속성 없음.) 목적지 문자열 ─→ { 세션ID ─→ [구독ID, ...] } "/topic/ticks/005930" ─┬─ s1 ─ ["sub-0"] └─ s2 ─ ["sub-3"] "/queue/execution-s1" ─── s1 ─ ["sub-2"] 매칭: AntPathMatcher (/topic/ticks/* 같은 와일드카드 구독 가능) 캐시 한도 기본 1024

6. 발송 API 대조표

수단어디로 가나브로커 경유
convertAndSend("/topic/x", p)/topic/x 구독자 전원예
convertAndSendToUser("userA", "/queue/x", p)userA의 모든 세션예 (재작성 후)
@SendTo("/topic/x")/topic/x 구독자 전원예
@SendToUser(..., broadcast=false)요청을 보낸 그 세션만예 (재작성 후)

7. 모듈 경계 — 어느 클래스가 어디 사는가

spring-boot-starter-websocket → spring-boot-starter-web + spring-websocket + spring-messaging

클래스패키지모듈
Message · MessageChannel · MessageHandlerorg.springframework.messagingspring-messaging
SimpleBrokerMessageHandler · DefaultSubscriptionRegistry…messaging.simp.brokerspring-messaging
SimpMessagingTemplate · SimpMessageHeaderAccessor…messaging.simpspring-messaging
StompDecoder · StompEncoder · StompCommand…messaging.simp.stompspring-messaging
StompSubProtocolHandler · WebSocketAnnotationMethodMessageHandlerorg.springframework.web.socket.messagingspring-websocket (어댑터)
STOMP 파싱도 spring-messaging의 것이다. spring-websocket이 가진 것은 어댑터 — 소켓에서 읽은 바이트를 StompDecoder에 넘기고 결과를 채널에 태우는 연결 담당. 그래서 브로커를 RabbitMQ 릴레이로 바꿔도 컨트롤러 코드가 안 바뀐다.

8. 세션 쿠키 인증 (JWT 아님)

단계일어나는 일
핸드셰이크 GET진짜 HTTP 요청 → 서블릿/Security 필터 체인 통과 → JSESSIONID로 HttpSession 복원 → Authentication 확정
WebSocket 세션 생성request.getUserPrincipal()이 WebSocket 세션에 영구 부착
이후 모든 프레임simpUser 헤더로 따라다닌다. 재인증 없음.
사용처@MessageMapping(… Principal p), /user/queue/… 라우팅
쿠키 방식에서 반드시 챙길 두 가지.
① Origin 화이트리스트 — WebSocket 핸드셰이크는 동일 출처 정책이 막아주지 않는다. 악성 사이트에서 연 연결에도 브라우저가 쿠키를 붙여 보낸다(CSWSH). CSRF 토큰은 여기서 무력하다.
② 세션 만료 ≠ 소켓 종료 — HttpSession이 만료되어도 이미 열린 WebSocket은 계속 산다. 장시간 연결에서는 이 간극을 처리해야 한다.
