Redis Streams 내부 구조 시각화

레슨 0014의 보조 자료. Spring이 작업을 밀어 넣고 → Worker가 가져가 실제로 일을 하고 → 결과가 다시 Spring으로 돌아오는 왕복 전체를 먼저 보고, 그 다음 Stream과 Consumer Group의 내부를 열어본다.

특히 헷갈리기 쉬운 네 지점을 따로 다룬다 — 결과를 어떻게 돌려주나(XACK로는 안 된다) · "Redis가 깨운다"는 게 정확히 무슨 뜻인가 · Producer는 Consumer Group을 지정하지 않는다 · 그룹은 어디에 저장되나(Redis는 key-value인데?)

1. 용어부터 — Consumer가 worker인가?

Consumer와 Worker는 서로 다른 층위의 말이다. 실무에서 1:1로 맞춰 쓰기 때문에 섞어 부르지만, 정확히는 이렇다.

용어누구의 개념정확한 뜻
Consumer Redis의 개념 XREADGROUP GROUP ai-workers ai-worker-1 에서 넘긴 이름 문자열. Redis가 아는 건 이 이름뿐이다. 그 뒤에 프로세스가 있는지, 살아 있는지조차 모른다.
Worker 내 애플리케이션의 개념 실제로 돌아가는 프로세스. LLM을 호출하고 DB에 쓰는 주체. Redis에는 이런 개념이 아예 없다.

그래서 "Consumer Group 안에 worker가 있다"는 말은 느슨한 표현이다. 정확히는 "Consumer Group 안에 consumer 이름이 등록돼 있고, 그 이름을 내 worker 프로세스가 하나씩 쓰고 있다". 이 구분이 중요한 이유: worker 프로세스가 죽어도 consumer 이름과 그 PEL은 Redis에 그대로 남는다. 그래서 회수(XAUTOCLAIM)가 가능한 것이다. 이 문서에서는 편의상 worker라고 부르되, Redis 쪽 그림에서는 consumer로 표기한다.

2. 전체 왕복 — 발행부터 결과가 돌아오기까지

Spring이 XADD로 밀어 넣는 것까지는 봤다. 그 다음 누가 실제로 일을 하고, 그 결과가 어떻게 Spring에게 돌아오는지가 아래 그림이다. 화살표 방향에 주목 — Redis는 아무것도 밀어주지 않는다. 양쪽 모두 자기가 물어본다.

왜 화살표가 위로 향하나

Redis Streams에는 서버 푸시가 없다. Redis는 연결된 클라이언트를 찾아가 메시지를 밀어주지 않는다. worker가 XREADGROUP을 호출해야만 그때 응답한다. "요청(위) → 응답(아래)" 두 화살표가 정확한 그림이다.

Stream이 두 개인 이유

jobs:ai는 할 일, events:ai-result는 끝난 일. 방향이 반대이므로 같은 Stream을 쓰면 worker가 자기가 만든 결과를 다시 집어가는 사고가 난다. 요청/응답은 항상 채널을 나눈다.

job 42, job 43 … 은 무엇인가

Stream에 쌓인 엔트리 하나 = 작업 요청 한 건이다. "이력서 42번을 AI로 분석해줘" 같은 실제 요청이 JSON으로 들어 있다. 7절에서 엔트리 하나를 열어본다.

왜 굳이 결과도 Stream으로

worker가 Spring API를 직접 호출해도 되지만, 그러면 Spring이 죽어 있을 때 결과가 날아간다. Stream에 넣으면 Spring이 되살아난 뒤 이어서 소비한다. 발행 때와 같은 이유다.

3. 결과는 어떻게 돌려주나 — XACK로는 못 보낸다

"작업이 끝났으면 XACK로 결과를 돌려주면 되지 않나?" — 불가능하다. XACK에는 데이터를 담을 자리가 아예 없다. 

XACK jobs:ai ai-workers 1765432100123-0
     ───────  ──────────  ────────────────
     스트림    그룹         메시지 ID          ← payload를 넣을 인자가 없다

→ 반환값: (integer) 1        "PEL에서 1개 지웠다"는 숫자일 뿐

XACK는 Redis와의 정산이지 Spring에게 보내는 메시지가 아니다. 결과 전달은 완전히 별개의 XADD로 이뤄진다 — 2절 그림의 ④번이 그것이다. 

result = call_llm(job)                       # 실제 작업

r.xadd("events:ai-result", {...})            # ④ 결과 발행  ← Spring에게 전달
r.xack("jobs:ai", "ai-workers", msg_id)      # ⑤ 완료 확정  ← Redis와 정산

# 순서 중요: XADD 먼저, XACK 나중.
# 반대로 하면 XACK 직후 죽었을 때
#   → 작업은 "완료"로 확정됐는데 결과는 어디에도 없는 상태가 된다.

결과가 클 때 — Stream에 큰 데이터를 넣으면 안 되는 이유

메모리

Redis는 인메모리다. 디스크가 아니다. 8MB 결과 × 1,000건 = 8GB RAM이 그대로 물린다. 게다가 XACK해도 엔트리는 Stream에 남으므로 트리밍 전까지 계속 차지한다.

블로킹 (더 위험)

Redis는 싱글 스레드다. 8MB 값 하나를 읽고 쓰는 동안 다른 모든 클라이언트의 명령이 전부 멈춘다. 전혀 무관한 서비스의 GET 하나까지 밀린다.

실무 기준선: 엔트리 하나 수 KB 이하. 넘어갈 것 같으면 아래 Claim Check로 간다.

Claim Check 패턴 — 데이터 대신 보관증을 보낸다

여기서 dual-write 문제가 다시 나온다. DB 저장은 성공했는데 XADD 직전에 worker가 죽으면? → 레슨 0013의 Outbox가 그대로 적용되는 자리다. 다만 이 방향은 "결과 전달이 늦어질 뿐 유실은 아니다" — XACK를 안 한 채 남겨두면 XAUTOCLAIM이 회수해 재처리하기 때문이다. 그래서 재처리해도 안전하도록 멱등하게 짜는 게 전제다.

4. pull의 주기는? — 주기가 없다 (BLOCK)

"worker가 당겨간다"고 하면 "몇 초마다 폴링하나?"가 자연스러운 질문인데, Redis Streams는 폴링하지 않는다. BLOCK 옵션 때문이다.

XREADGROUP ... BLOCK 5000 ... 를 호출하면 worker는 그 자리에서 잠든다 (CPU 0%, 네트워크 0). 메시지가 도착하는 순간 Redis가 잠든 클라이언트를 깨워 즉시 응답한다. 그래서 "주기"라는 개념이 없고, 발행-수신 지연은 사실상 0이다.

"Redis가 깨운다"는 게 정확히 무슨 뜻인가

여기서 모순처럼 보이는 지점이 있다. "Redis는 worker가 누군지 모른다"고 했는데 "Redis가 잠든 worker를 깨운다"고도 했다. 둘 다 맞다 — Redis가 아는 건 consumer의 신원이 아니라 지금 답을 기다리고 있는 소켓이기 때문이다.

Redis는 요청-응답 프로토콜이다. 클라이언트가 보낸 요청에 답만 할 수 있고, 아무 때나 먼저 말을 걸 수는 없다. BLOCK은 이 제약 안에서 만들어진 장치다 — 응답을 즉시 주지 않고 미뤄두는 것이 전부다.

주소록이 필요 없는 이유

push 구조라면 "worker-1 = 192.168.0.5" 같은 주소록을 영구 저장하고 죽은 항목을 정리해야 한다.
pull 구조에서는 요청이 도착하는 순간 소켓이 손에 쥐어진다. 저장할 필요가 없는 게 아니라, 저장할 대상이 생기지 않는다.

consumer 이름은 매번 통보받는다

XREADGROUP GROUP ai-workers ai-worker-1 …
이름이 매 요청마다 실려 온다. Redis가 "이 소켓이 누구인지"를 기억할 이유가 없다. 그 이름은 오직 PEL에 소유자를 적을 때만 쓰인다.

누구부터 깨우나

먼저 대기하기 시작한 커넥션부터 순서대로 서비스된다. 다만 이건 구현 세부사항이지 보장된 계약이 아니다. "공평하게 나눠진다"에 의존하는 설계를 하면 안 된다.

커넥션이 끊기면

대기목록에서 그 소켓만 빠진다. consumer 이름과 PEL은 그대로 남는다. 둘은 저장 위치가 다르기 때문이다 — 소켓은 휘발성 런타임 상태, PEL은 Stream 안의 영속 데이터. 그래서 프로세스가 죽어도 회수가 가능하다.

worker의 실제 루프

while not shutting_down:
    # ① 최대 5초 잠들어 대기. 메시지 오면 즉시 깨어남
    msgs = r.xreadgroup("ai-workers", "ai-worker-1", {"jobs:ai": ">"},
                        count=1, block=5000)

    if not msgs:              # ② 5초 타임아웃 — 할 일 없음
        maybe_run_autoclaim() # 이 틈에 죽은 worker 것 회수 시도
        continue              # 다시 ①로

    for id, fields in msgs:
        try:
            do_the_actual_work(fields)          # ③ 진짜 작업 (LLM 호출 등)
            r.xack("jobs:ai", "ai-workers", id) # ④ 성공했을 때만 XACK
        except Exception:
            pass  # XACK 안 함 → PEL에 남음 → 나중에 XAUTOCLAIM이 회수

count=1인 것에 주목. LLM 호출처럼 오래 걸리는 작업은 한 번에 하나씩 가져와야 다른 worker가 놀지 않는다. 반대로 짧은 작업(알림 발송 등)은 count를 키워 왕복 비용을 아낀다.

5. Consumer Group은 여러 개일 수 있다 — 두 개의 축

여기서 헷갈리기 쉬운 게 "나눠 갖기"와 "다 받기"가 서로 다른 축이라는 점이다. 같은 Stream에 그룹을 여러 개 붙이면 의미가 완전히 달라진다.

"모든 Consumer Group이 데이터를 다 읽어가면, 작업이 중복되는 것 아닌가?"
아주 자연스러운 의문이고, 모든 그룹이 같은 데이터를 다 읽어가는 것은 사실이다. 다만 이건 같은 일을 3번 하는 것이 아니라 하나의 사건을 가지고 서로 전혀 다른 일 3가지를 동시에 처리하는 것(Fan-out)이다. "메시지가 3번 배달됐다"와 "같은 작업이 3번 실행됐다"는 다른 이야기다.

실무 예시 — 쇼핑몰 [결제 완료] 이벤트 하나가 만드는 세 가지 일

사용자가 결제를 마치면 orders-stream에 메시지가 딱 하나 찍힌다. 그런데 그 뒤에 일어나야 할 일은 하나가 아니다.

굳이 왜 그룹을 나누나 — 한 worker가 다 하면 안 되나

"결제 저장 + 카카오톡 발송 + 통계 반영"을 한 worker가 순서대로 다 처리하게 만들 수도 있다. 그러면 이런 일이 생긴다. 

def handle(msg):
    save_payment(msg)        # ①
    send_kakao(msg)          # ② ← 카카오 API 장애로 여기서 예외
    update_ranking(msg)      # ③ ← 실행조차 안 됨

→ XACK 안 됨 → 메시지 재전달 → ①이 또 실행됨 (결제 중복 기록 위험)
→ 카카오 장애 하나가 결제·통계까지 끌고 들어간다

① 장애 격리

카카오톡 시스템이 뻗어도 Group B만 멈춘다. Group A의 결제 정산과 Group C의 통계는 아무 영향 없이 100% 정상 동작한다.
PEL도 그룹마다 따로라, B가 쌓아둔 미처리 메시지가 A의 회수 로직을 건드리지 않는다.

② 확장이 무해하다

"결제 완료되면 쿠폰 1,000원 지급도 해줘" 요구가 들어오면 — 기존 결제·알림 코드를 한 줄도 건드리지 않고 Group D (쿠폰 지급)를 만들어 같은 Stream에 붙이면 끝이다. Producer(결제 서버)도 수정 대상이 아니다.

③ 재시도 단위가 정확해진다

합쳐놓으면 카카오 발송이 실패했을 때 결제 저장까지 재실행된다. 나눠놓으면 실패한 그룹만 재시도하므로, 각 작업이 자기 실패에만 책임진다. 멱등성 부담도 그만큼 줄어든다.

④ 스케일 단위가 달라진다

통계는 가볍고 알림은 외부 API 대기가 길다. 합쳐놓으면 가장 느린 것에 전체가 묶인다. 나눠놓으면 Group B만 worker를 5대로 늘리는 식의 조정이 가능하다.

다만 그룹을 무한정 늘리면 생기는 비용: ① 그룹마다 PEL을 따로 들고 있으므로 메모리가 그룹 수만큼 늘어난다. ② MAXLEN 트리밍은 느린 그룹을 기다려주지 않는다 — 한 그룹이 크게 밀려 있으면 아직 못 읽은 엔트리가 잘려나갈 수 있다. 그룹을 나눌 땐 XINFO GROUPS로 가장 뒤처진 그룹의 lag을 같이 봐야 한다.

두 축 정리

그룹 안의 worker들끼리   →  메시지를 1/N로 나눠 가진다   (중복 방지 · 일 분담)
그룹 과 그룹 사이       →  메시지를 똑같이 다 가져간다  (서로 다른 목적 · Fan-out)
무엇을 늘리나결과이럴 때 쓴다
같은 그룹 안에 consumer 추가 메시지를 나눠 가짐
(작업 분배)		 "AI 분석이 밀린다" → ai-workers 그룹에 ai-worker-4 투입. 총 처리량이 늘어난다.
Consumer Group 추가 각 그룹이 전부 받음
(팬아웃 / 브로드캐스트)		 "결과를 DB에도 저장하고 알림도 보내야 한다" → 용도별로 그룹을 나눈다. 서로 영향 없음.
Stream 추가 아예 다른 파이프라인 "AI 작업과 알림 작업이 서로를 막는다" → jobs:ai / jobs:notification으로 분리.

Producer는 Consumer Group을 지정하지 않는다 — 지정할 수도 없다. XADD jobs:ai * jobId 42 에는 그룹을 적을 자리가 없다. Spring은 어떤 그룹이 존재하는지조차 모르고, 알 필요도 없다.

  • 그룹이 0개여도 XADD는 성공한다 (아무도 안 읽을 뿐)
  • 나중에 그룹을 새로 만들어 붙여도 된다 — Producer 코드는 그대로
  • 그룹이 5개면 5개 전부가 그 메시지를 받는다

그룹은 소비하는 쪽이 스스로 갖다 붙이는 것이고, 발행하는 쪽과 협상하지 않는다. Producer를 건드리지 않고 소비자를 추가할 수 있는 게 이 구조의 핵심 목적이다. 그래서 발행 측과 소비 측을 잇는 유일한 접점은 "jobs:ai"라는 문자열 하나다 — 양쪽 코드에 각각 하드코딩된, 서로 같기로 한 약속. 

# Spring 쪽 — 스트림 이름 하나만 안다
XADD "jobs:ai" * jobId 42 type ANALYZE

# Worker 쪽 — 세 개를 자기가 정해서 넘긴다
STREAM   = "jobs:ai"                   # 어디서 읽을지  — 내 코드에 하드코딩
GROUP    = "ai-workers"                # 어느 그룹으로  — 내 코드에 하드코딩
CONSUMER = os.environ["POD_NAME"]      # 내 이름       — 내가 정함

r.xgroup_create(STREAM, GROUP, id="$", mkstream=True)   # 그룹도 내가 만든다
r.xreadgroup(GROUP, CONSUMER, {STREAM: ">"}, block=5000)

→ 세 값이 전부 worker 쪽에서 온다. Redis가 알려주는 건 하나도 없다.

Redis는 중매쟁이가 아니라 게시판이다. 게시판은 글쓴이도 읽는 사람도 모른다. 다만 "3번 게시판"이라는 이름이 있어서, 3번에 붙이면 3번을 보러 온 사람이 볼 뿐이다. "연결"이라는 게 애초에 존재하지 않는다.

6. 그룹은 어디에 저장되나 — Redis는 key-value 아니었나

Redis가 key-value인 건 맞다. 다만 value가 단순 문자열만은 아니다 — string / list / hash / set / zset / stream 중 하나다. 그리고 Consumer Group은 별도의 key가 아니라 stream value 안에 들어 있다.

직접 확인하는 명령

TYPE jobs:ai                        → "stream"      (string이 아니다)
KEYS *                              → 1) "jobs:ai"   ← 그룹은 여기 안 보인다

XINFO STREAM jobs:ai                → 엔트리 수, 마지막 ID, groups 개수
XINFO GROUPS jobs:ai                → 그룹 목록 + 각 커서 / pending 수
XINFO CONSUMERS jobs:ai ai-workers  → 그룹 안 consumer 목록 + idle / pending

이 구조가 실무에서 갖는 의미

DEL 한 번이면 전부 증발

DEL jobs:ai 는 메시지만 지우는 게 아니라 그룹 · PEL · 커서까지 통째로 날린다. 미처리 작업이 PEL에 있었다면 회수할 근거 자체가 사라져 영구 유실이다. worker는 다음 호출에서 NOGROUP 에러를 받는다. 같은 이유로 Stream 키에 EXPIRE를 거는 것도 위험하다.

MAXLEN 트리밍은 안전하다

트리밍은 entries만 건드린다. 그룹과 PEL은 그대로 남는다. 그래서 큐로 쓸 때 정리 수단은 DEL이 아니라 MAXLEN이다.
단, 아직 pending인 엔트리가 잘려나가면 PEL엔 ID가 있는데 본문이 없는 상태가 된다. MAXLEN은 넉넉히 잡는다.

Cluster에서 분산되지 않는다

스트림과 그 그룹들은 한 key 안에 있으므로 항상 같은 노드에 산다. 스트림 하나가 노드 하나의 처리량 상한을 넘으면 key를 손으로 나누는 것 외에 방법이 없다 (jobs:ai:0, jobs:ai:1 …). Kafka가 partition으로 자동 해결하는 지점이다.

PEL은 영속, 소켓은 휘발

consumer 이름과 PEL은 이 value 안의 영속 데이터다. 반면 "지금 blocked인 소켓" 목록은 메모리상의 런타임 상태일 뿐 여기 저장되지 않는다. 프로세스가 죽어도 PEL이 남아 회수가 가능한 이유가 이 분리다.

7. Stream 한 줄(Entry)의 내부 — job 42는 실제로 무엇인가

Stream은 읽어도 줄어들지 않는다. XACK는 PEL에서만 지우지 Stream에서는 안 지운다. 그래서 XADD jobs:ai MAXLEN ~ 10000 * 처럼 길이를 잘라주지 않으면 메모리가 계속 늘어난다. Redis Streams를 큐로 쓸 때 가장 자주 놓치는 운영 항목이다.

8. Consumer Group이 들고 있는 상태는 딱 두 가지

① last-delivered-id (커서 1개)

"이 그룹은 여기까지 배달했다"는 표시 하나. XREADGROUP ... > 는 이 커서 다음 엔트리를 주고 커서를 밀어 올린다. 그룹당 1개이므로 consumer가 몇이든 같은 엔트리를 두 번 배달하지 않는다.

② PEL (배달 장부)

배달했지만 아직 XACK 안 된 엔트리 목록. 엔트리마다 소유 consumer · 마지막 배달 시각 · delivery count를 들고 있다. XAUTOCLAIM은 오직 이 장부만 보고 회수를 결정한다.

PEL을 표로 펼치면

Entry ID소유 consumeridle (ms)delivery count해석
…123-0ai-worker-13,0001정상 처리 중. 건드리면 안 됨
…456-0ai-worker-271,0001min-idle-time 60s 초과 → 회수 대상
…789-0ai-worker-392,00055번 재시도 실패 → DLQ 후보

XPENDING jobs:ai ai-workers - + 10 이 실제로 보여주는 게 정확히 이 표다. 운영 중 "뭐가 안 끝나고 있나"를 볼 때 이 네 컬럼만 읽으면 된다.

9. 엔트리 하나의 일생 — PEL이 변하는 순간들

10. worker 개수 = 서버 개수인가? — 아니다

1절에서 봤듯 Redis가 인식하는 consumer는 이름뿐이다. 그 이름을 쓰는 게 별도 서버인지, 같은 서버의 다른 프로세스인지, 같은 프로세스의 다른 스레드인지 Redis는 구분하지 못하고 관심도 없다. 조건은 하나 — 이름이 서로 다를 것.

그럼 worker 몇 개를 어디에 띄우나 — 병목이 어디냐로 갈린다

I/O 바운드 (외부 LLM API 호출)

대부분의 시간이 응답 대기다. CPU는 놀고 있다. → 서버 1대에 worker 여러 개(또는 asyncio 태스크 여러 개)를 붙여도 된다. 이 경우 worker 수 >> 서버 수가 정상이다. 실제 상한은 서버가 아니라 API rate limit이 정한다.

CPU/GPU 바운드 (로컬 모델 추론)

worker 하나가 코어/GPU를 다 쓴다. 같은 서버에 2개 띄우면 서로 느려지기만 한다. → worker 수 ≒ GPU 수로 맞추고, 늘리려면 서버를 늘려야 한다. 여기서만 "worker 수 = 서버 수"에 가까워진다.

실무 기본값

k8s Deployment의 replicas = worker 수, 파드 1개에 프로세스 1개. consumer 이름은 파드명(POD_NAME)을 그대로 쓴다. 단순하고, 스케일이 kubectl scale 한 줄이 되고, 이름 충돌도 없다.

절대 하면 안 되는 것

여러 프로세스가 같은 consumer 이름을 쓰는 것. PEL 소유권이 뒤섞여 A가 처리 중인 메시지를 B가 0으로 읽어가 중복 실행이 난다. 이름은 반드시 인스턴스마다 고유해야 한다.

worker를 늘려도 처리량이 안 늘 때: 병목이 Redis가 아니라 뒤쪽(LLM API rate limit, DB 커넥션 풀, GPU)에 있는 경우가 대부분이다. worker를 늘리면 PEL만 두꺼워지고 idle time이 길어져 엉뚱하게 XAUTOCLAIM이 정상 작업을 회수하기 시작한다. 늘리기 전에 XPENDING부터 본다.

11. 한 장 요약

저장 구조 — 전부 key 하나 안에 들어 있다

  key "jobs:ai"  →  value (TYPE: stream)
      ├ entries                      append-only 로그. 읽어도 안 줄어듦. MAXLEN으로 잘라야 함
      │   └ 1765…-0 + 필드들         "job 42" 상자 하나 = 작업 요청 1건
      └ groups                       별도 key가 아님! DEL jobs:ai 하면 같이 증발
          └ "ai-workers"
              ├ last-delivered-id    커서 1개 → 그룹 안에서 중복 배달 방지
              ├ PEL                  배달 장부: 엔트리별 (소유자, idle, delivery count)
              └ consumers            "ai-worker-1" 등 이름 목록 (연결 정보는 없음)

  Worker 프로세스                     Redis 밖. Redis는 이 존재를 모름.
                                      consumer 이름은 매 요청에 실려 오므로 기억할 필요가 없다

두 개의 축 — 이걸 섞으면 "중복 아니냐?"는 오해가 생긴다
  그룹 안의 worker끼리  →  1/N로 나눠 가짐      (같은 일을 나눠서 처리)
  그룹과 그룹 사이      →  똑같이 다 가져감     (서로 다른 일을 각자 처리 = Fan-out)
  ※ 메시지가 3번 배달됐다 ≠ 같은 작업이 3번 실행됐다
  ※ 비용: 그룹마다 PEL을 따로 들고 있고, MAXLEN 트리밍은 느린 그룹을 기다려주지 않는다

방향 — XADD 하나만 밀고 나머지는 전부 pull
  Spring  --XADD-->        jobs:ai                            (유일하게 미는 동작)
  Worker  --XREADGROUP-->  jobs:ai          --응답-->  Worker  (worker가 먼저 물어봄)
  Worker  --XADD-->        events:ai-result
  Spring  --XREADGROUP-->  events:ai-result --응답-->  Spring  (spring이 먼저 물어봄)

  ※ Producer는 Consumer Group을 지정하지 않는다. 양쪽을 잇는 건 "jobs:ai" 문자열 약속뿐.

"Redis가 깨운다"의 정체
  worker가 미리 걸어둔 XREADGROUP의 응답을 미뤄뒀다가, 데이터가 생기면 그 소켓에 write.
  Redis는 요청-응답만 가능 → 보류 중인 요청이 없는(=처리 중인) worker에겐 말을 걸 수 없다.
  그래서 바쁜 worker는 후보에조차 안 오른다 = 부하 분산이 공짜로 되는 이유.
  BLOCK 5000은 폴링 주기가 아니라 "최대 대기 시간". 메시지 오면 즉시 반환, 지연 ≈ 0.

결과 돌려주기
  XACK로는 불가능 (payload 인자가 없음). 별도 XADD로 결과 스트림에 발행.
  순서: XADD(결과) 먼저 → XACK 나중.
  결과가 크면 Claim Check — 본문은 DB/S3, Stream엔 jobId만. 엔트리는 수 KB 이하 유지.
  (Redis는 인메모리 + 싱글스레드 → 큰 값 하나가 전체를 멈춘다)

명령어가 건드리는 곳
  XADD        → entries에 추가             (PEL 무관)
  XREADGROUP >→ 커서 전진 + PEL에 등록
  XREADGROUP 0→ 내 PEL 조회 (커서 무관)
  XACK        → PEL에서만 제거             (entries는 그대로)
  XAUTOCLAIM  → PEL의 소유자 변경 + deliv +1
  XPENDING    → PEL 읽기 전용 조회
  XINFO       → 위 저장 구조를 눈으로 확인
  DEL         → ⚠ entries + groups + PEL 전부 삭제
